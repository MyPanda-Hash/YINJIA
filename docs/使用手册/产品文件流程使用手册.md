## 一、这套流程是干什么的

MES 里"研发管理 → 产品文件"这一组面板，负责**产品技术文件的编制与变更**。核心是四份**受控文件**（合称"四个受控文件"）：

| 受控文件 | 面板名（菜单里的叶子项） | 面板编码 |
|---|---|---|
| 成型工艺清单（含成型配方页） | 成型工艺清单 | `RD_MOLD_PROC` |
| 组装工艺清单（含组装BOM页） | 组装工艺清单 | `RD_ASM_PROC` |
| 规格书 | 规格书 | `RD_SPEC_DOC` |
| 出货检验计划表 | 出货检验计划表 | `RD_INSP_PLAN` |

流程分成两条主线：

1. **新产品从零到归档**：先建产品信息表（`RD_PROD_INFO`）→ 两级审批 → 归档 → 由二级审核人**分发责任人** → 四个受控文件各自填写、送审、归档 → 在"产品文件列表"核对四文件开发状态。
2. **产品变更走单**：产品变更申请单（`RD_CHANGE`）关联产品编号、勾选本次要变的受控文件、各部门按本部门栏填意见 → （可选）会签 → 冯总审批 → **生效即自动生成下一版草稿** → 各文件责任人修改后重走受控审核 → 归档，变更闭环完成。

这套机制的关键约束（都是系统强制，不是建议）：

- **保存 = 送审**：普通用户点 `保存` 会**自动进审批中**；管理员点 `保存` 是**直接归档**。想存一半不送审，用 `保存为草稿`。
- **四文件编辑门禁**：未分发责任人之前，四个受控文件谁都不能编；分发之后，只有**该文件的责任人 ∪ 管理员**能编，界面上其余人打开就是整张只读。
- **两级审批只针对产品信息表**：其余面板（含四个受控文件和变更单）是单节点审批，冯总一次审批通过即归档/生效。

## 四、流程一：新产品文件从零到归档

> 每一步都写清了"用哪个账号 → 打开哪个菜单 → 点什么 → 状态变成什么"。菜单路径统一是
> **研发管理 → 产品文件 → 对应面板**。

### 步骤 1：建「产品信息表」（产品开发部）

1. 用 `cp` 登录 → 打开 **研发管理 → 产品文件 → 产品信息表**。
2. 点侧栏 `新增` → 系统立刻给出一张空白草稿（单据编号自动生成），落在当前页内联填写。
3. 填产品编号、产品名称、产品类别、客户项目名称、产品负责人、产品形态等，点侧栏 `保存`。
4. 结果：普通用户点 `保存` = **自动提交审批**，单据状态变成 **审批中**。
   - 管理员点 `保存` 是"保存即归档"，**不走审批**，请勿用 `admin` 做这一步。
   - 只想存一半：点 `保存为草稿`（不触发送审，也不做必填校验）。

### 步骤 2：冯总一级审批，必须选取二级审核人

1. 用 `admin` 登录 → 打开同一张产品信息表单据。
2. 点侧栏 `审批通过` → 弹窗里除审批意见外，**必须选取"二级审批人"**（候选 = 全部启用账号；演示建议选 `glm53`）。
3. 结果：状态变成 **待二级审批**（不归档）；纸面「审核人（二级审批人）」自动写回被选人的姓名；被选人收到"待二级审批"消息。
4. 一级审批通过前可以先点 `审批情况` 查看本单全部审批留痕（提交、一级通过、二级通过逐条在列）。

### 步骤 3：二级审核人审批通过 → 已归档

1. 用 **被选定的二级审核人**（演示为 `glm53`）登录 → 打开该产品信息表。
2. 点侧栏 `审批通过`（二级节点由被选人本人 ∪ 管理员处理）→ 结果：单据 **已归档**。
3. 任一级点 `审批驳回` 都会**一律回草稿**（意见必填），不退回上一级，并通知制单人。

### 步骤 4：归档后由二级审核人「分发责任人」

1. 用 `glm53`（或 `admin`）打开**已归档**的产品信息表。
2. 点侧栏 `分发责任人`（已分发过的单据此按钮显示为 `改责任人`，可随时改人）。
3. 弹窗里**四个受控文件各选一个责任人**（默认带出产品负责人，可逐个改），例如：成型工艺清单 → `cp`、规格书 → `cp`、组装工艺清单 → `glm53`、出货检验计划表 → `glm53`。
4. 结果：四个责任人各收到一条待办消息；这四个人成为**四文件编辑门禁**的唯一判据。

> 按钮在两种情况下是灰的：单据还不是"已归档"，或当前账号既不是二级审核人也不是管理员。
> 另有一个同名容易混淆的按钮 `规格书分发` —— 那是"单张规格书"级别的分配，与本步骤的
> "产品 × 文件"责任人不是一回事。

### 步骤 5：各责任人各自填写四个文件 → 送审 → 归档

四个受控文件**并行、无先后依赖**，每个文件的实际操作人**必须是它自己的责任人**：

| 文件 | 演示责任人 | 打开面板 | 关键字段 |
|---|---|---|---|
| 成型工艺清单 | `cp` | 研发管理 → 产品文件 → 成型工艺清单 | 产品编号（关联键）、页签"成型工艺清单 / 成型配方 / 修订记录" |
| 规格书 | `cp` | 研发管理 → 产品文件 → 规格书 | 规格书种类的页签、产品信息封面、检验项目及标准页 |
| 组装工艺清单 | `glm53` | 研发管理 → 产品文件 → 组装工艺清单 | 产品编号、页签"组装BOM表 / 关键工序控制清单 / 修订记录" |
| 出货检验计划表 | `glm53` | 研发管理 → 产品文件 → 出货检验计划表 | 产品编号、必测项与型式检验两套表区 |

每个文件的流程一样：

1. 责任人登录 → 打开对应面板 → `新增`（或用现有草稿）→ 填内容（产品编号必须填对，**它是关联产品的唯一键**）。
2. 点 `保存` → 普通用户 **自动进审批中**；`admin` 点 `保存` 则直接归档。
3. `admin` 打开该文件 → `审批通过` → 单据 **已归档**。四个文件逐个走完，该产品的四份受控文件就齐了。
4. 非责任人打开别人的文件时：整张纸**只读**，侧栏显示 `本文件责任人：X（只读）`；产品还没分发责任人时显示 `尚未分发责任人：请先在产品信息表点「分发责任人」`。

### 步骤 6：用「产品文件列表」核对开发状态矩阵

1. 打开 **研发管理 → 产品文件 → 产品文件列表**（`RD_PROD_DOCLIST`）。
2. 这是**只读的派生视图**（没有"新增"入口，也不需要归档）：一张"产品 × 四文件"的开发状态矩阵，每格取值 = `未开发` / `开发中` / `开发审核中` / `开发完毕`（判据分别是：无单据 / 有草稿 / 审批中 / 已归档）。
3. 四个文件全部"开发完毕"时，该行的"是否受控"为"是"，并给出受控日期；该视图的数据源与产品信息表侧栏的"产品开发"是同一份。

## 五、流程二：产品变更申请单（`RD_CHANGE`）

演示数据里 `DEMO-CHG-001` 已经是一张**草稿**，可以从下面的第 2 步直接开始；如果自己新建，从第 1 步开始。

### 步骤 1：发起人新建变更单（如产品开发部）

1. 用发起人账号（演示 `cp`）登录 → 打开 **研发管理 → 产品文件 → 产品变更申请单** → 点 `新增`。
   - 新建后系统会**自动铺好 7 个部门评审行**（开发部/成型工艺科/组装车间/销售部/品质部/计划组/仓管部），不需要手工加行，也不提供增删行。
2. 填表：
   - **产品编号**（必填，按参照控件从产品信息表里选；产品名称随之带出）；
   - **变更文件**：勾选本次要变的受控文件（可多选：成型工艺清单 / 组装工艺清单 / 规格书 / 出货检验计划表）；
   - **变更事由**、**验证数据**（多行文本，写清楚改什么、为什么改、有什么试验数据支撑）；
   - **性质**（变更/新增）、**申请部门**、**相关变更**；
   - **四、库存产品处理方式**：原料 / 半成品 / 成品三行，各填数量与处理方式（继续使用 / 返工 / 报废 / 降级 / 待定）；
   - **需会签**：本次范围大就选"是"，并在**会签人**里填会签人账号（多人用逗号分隔，如 `glm53,demo_pinzhi`）；范围小选"否"，后续直接提交审批。
3. 点 `保存为草稿` 落库（也可以直接 `保存`，但发起人自己点保存不会自动送审，变更单走的是会签/审批按钮）。

### 步骤 2：各部门用自己的账号填本部门那一行

1. 每个部门人员**用自己的账号**登录 → 打开这张变更单 → 在"三、部门评审意见"表里找到**本部门那一行**，在 `变更/新增申请内容`（数据键是"变更后内容"）里写意见 → 点 `保存为草稿`。
2. **非本部门的行是灰的、改不动**；服务端也会把越权写入的值还原（界面先说清楚，后端再强制一次）。
3. **签字和日期由系统自动盖章**：只有"变更后内容"真的填成了非空文本，系统才把签字盖成操作人姓名、日期盖成当天。界面上这两格只读。

### 步骤 3：提交会签 → 会签人各自签

1. 发起人（`cp`，或 `admin`）确认各部门行填好后，点侧栏 `提交会签` → 状态变成 **会签中**；每个会签人各收到一条待签。
   - 提交会签的前提：`需会签 = 是`、已填会签人账号、**发起人不能是会签人**（编制与会签分离）。
   - **会签中不可保存正文**，要改先撤回。
2. 会签人（演示 `glm53`、`demo_pinzhi`）各自登录 → 打开该单 → 点 `会签通过`；有异议时点 `会签驳回`（**驳回意见必填**）。
3. 规则：
   - **一票驳回即回草稿**，其余还在等签的签名自动作废；
   - 发起人可点 `撤回会签` 回到草稿重发（撤回不打扰会签人）；
   - **全部会签通过 → 自动转「审批中」** 交冯总，不需要发起人再点一次。
4. `需会签 = 否` 的单，发起人直接点 `提交审批` 即可。

### 步骤 4：冯总审批通过 → 已生效

1. 用 `admin` 登录 → 打开该单 → 点 `审批通过`（可填审批意见）→ 单据状态变成 **已生效**（终态）。
2. 点 `审批驳回` 则回草稿，并按部门行的签字人通知发起人与已填写部门，提醒重填。

### 步骤 5：生效时系统自动做的事

点下"审批通过"的同一时刻，系统会：

1. 按 **变更文件** 勾选项，为**每个勾选的文件建一张「下一版草稿」**：
   - 该产品已有版本 → **整单复制**（头字段 + 全部明细行）；
   - 该产品还没有该文件 → 建一张只带产品标识的空白草稿；
   - 新草稿都写 **变更来源单号** = 本变更单号（列表可见；纸张上不打印）；
   - 新草稿是**草稿**状态，等待责任人按正常流程编辑 → 保存 → 重走受控审核。
2. **通知该文件的责任人**（`rd_dev_task` 里登记的那个人；没登记责任人时兜底通知管理员），消息带新草稿单号；
3. 在审批留痕里记一条"已生成下一版草稿：成型工艺清单 SD-xxxx；规格书 SD-yyyy"，方便日后追溯。

### 步骤 6：责任人改下一版草稿 → 归档，闭环完成

1. 责任人（演示：成型工艺清单与规格书都是 `cp`）登录 → 打开对应面板 → 找到那张带"变更来源单号"的新草稿 → 按变更单要求修改内容 → 点 `保存`。
2. 普通用户保存 → **自动进审批中**（即"重走受控审核"）。
3. `admin` 打开新版 → `审批通过` → **已归档**。
4. 版本链核对：**旧版仍归档在册、不被改写**，新版是独立单据，两张都能在列表里查到（旧版没有"变更来源单号"，新版有）。

## 六、状态说明表

| 状态 | 含义 | 谁能推进它 / 怎么推进 |
|---|---|---|
| `草稿` | 新建或驳回后的可编辑状态。产品变更申请单在草稿态可被各部门填行；驳回也一律回这里 | 有编辑权的人直接改；普通用户点 `保存` 会转 `审批中`；变更单走 `提交会签` 或 `提交审批` |
| `审批中` | 已提交，等审批人处理（一级节点） | 审批人点 `审批通过` → 归档面板归档 / `已审核`；变更单 → `已生效`。点 `审批驳回` → 回 `草稿` |
| `待二级审批` | **仅产品信息表**：一级已通过并选定了二级审核人，等二级签核 | 被选定的二级审核人本人 ∪ 管理员点 `审批通过` → `已归档`；驳回 → 回 `草稿`。此状态下单据不可保存 |
| `会签中` | **仅产品变更申请单**：提交会签后存在待签签名 | 会签人 `会签通过`（全部通过自动转 `审批中`）/ `会签驳回`（回 `草稿`）；发起人 `撤回会签`（回 `草稿`）。此状态下不可保存正文 |
| `已生效` | **仅产品变更申请单**：审批通过即生效，**终态** | 系统自动生成下一版草稿并通知责任人；**本单不可再改** |
| `已归档` | 文书面板的终点：审批通过（或管理员保存）后归档，四文件以此判定"开发完毕" | 要改先走 `申请修改` 闭环：申请修改中 → 管理员审批通过 → 修改中 → `提交审批` → 通过 → 再归档 |
| `已作废` | 单据被作废（软删，业务行仍保留作审计线索） | 作废后不占文档编号；作废单据在列表里仍可查 |

补充：**归档会落审核人**（2026-09-12 起的口径：首次归档即写审核人，再做「申请修改」闭环时保留首审人），
所以归档单纸面「审核人」栏是有名字的、列表也带「已审批」角标。要确认"这张纸归档了没有"，看 `单据状态` 是不是 `已归档`。
（本行 2026-09-21 与 `ButtonService.markArchived` 核对后修正过：旧文档写的"归档不写审核人、归档单无角标"已被推翻。）

## 七、常见问题（FAQ）

**Q1：为什么我不能改这个文件？**
四个受控文件有**编辑门禁**：未分发责任人之前谁都不能编；分发之后**只放该文件的责任人 ∪ 管理员**。
非责任人打开时整张纸只读，侧栏会写明 `本文件责任人：X（只读）`；还没分发时会写 `尚未分发责任人：请先在产品信息表点「分发责任人」`。
服务端在**保存 / 申请修改 / 删除**三个入口都强制同一套判定，所以"界面上能改、保存被拒"的情况不会出现。另有两处放宽：单据**产品编号为空**的历史单不拦；规格书另放"该单已分配的责任人 / 产品总负责人"。

**Q2：为什么"变更后内容"填完保存后没生效？**
本系统里**空字符串等于"不改动"**（保存时空串会被归一化丢弃）。所以：
- 填写时请把内容写成非空文本，保存后签字/日期才会盖上去；
- 想把某格**清空**做不到——只能改写内容，或者请管理员处理；
- 同一行内容没变化时，签字与日期也不会被刷新（这是设计：避免管理员改表头时把各部门的签字刷成自己）。

**Q3：规格书的「编号」为什么是产品编号？**
规格书面板用「编号」这一格**关联产品**（查询、编辑门禁、变更单复制都按它匹配），填产品编号（如 `DEMO-A-001`），**不要**把它当单据号去改。单据号是系统自己生成的流水号（`DEMO-SD-001` 这种），不用人工填。

**Q4：变更单已经生效了还能改吗？**
不能。`已生效` 是终态，保存会被拒（提示"已生效单据不可保存，如需再次变更请另开一张变更申请单"）。要再变，**另开一张变更单**，重新走"各部门填写 → 会签 → 审批 → 生效 → 下一版草稿"。

**Q5：会签人不填会怎样？**
勾了 `需会签 = 是` 但没提交会签（或会签没全部通过）时，点 `提交审批` 会被拒：**"本单勾选了「需会签」，请先提交会签并等全部会签通过后再提交审批"**。
提交会签时若会签人为空，提示"请先填写会签人（账号）"；会签人账号不存在或已停用也会被拒。

**Q6：表单里的字、按钮是英文（或别的语言）？**
顶栏右侧有语言下拉，可按 **`Alt + L`** 快速循环切换，切换**即时生效、不用刷新页面**，并按账号记忆。
注意：**切换的只是界面文案**——面板/字段的"中文数据键"、单据编号、客户名称等业务数据永远保持原文，这是准确性要求，不是没翻译。

**Q7：单据卡住了（提交了申请但没人审批，改也改不了）？**
文书归档面板提供出口按钮：`撤回删除申请`（回到真实状态，通常是已归档）、`撤回修改申请`。这两个动作允许**申请发起人本人**或**该面板审批人**执行。

## 八、演示数据的清理方式

`tools/` 下有两个清理脚本，用途完全不同，**不要用错**：

| 脚本 | 做什么 | 什么时候用 |
|---|---|---|
| `tools/migrate-testdata-cleanup.sql` | **按特征精确圈定**的清理：①名称里命中探针特征（`PROBE%` / `探针%` / `T-PF%` / `probe` / `TEST-%` / `测试产品%` 等）的单；②点过"新增/保存为草稿"留下的空壳单；③孤儿状态行/留痕/消息/附件/流转/修改记录；④孤儿分工行（`rd_dev_task` 里产品已不存在）；⑤探针账号（`probe_%`）。**`DEMO-` 开头的演示数据与 `demo_` 演示账号一律保留** | 有真实数据的库上做日常清理；可反复执行（幂等）。清完仍然"一登录就有单可跑" |
| `tools/migrate-golive-cleanup.sql` | **正式上线前的清空**：按表把业务单据（出入库/品质/生产/研发全族）整表 DELETE，并清状态行、日志、号池归零等；只保留基础档案与元数据、金蝶同步的真实订单、期初库存 | **全量部署/正式上线前**用，且**必须先做保险备份**。服务器库不要直接执行；执行完演示数据也没了，需要重新灌 `seed-demo-prodfile.sql` |

两个脚本的破坏性都要注意：执行前先备份数据库。演示数据本身可随时用 `tools/seed-demo-prodfile.sql` **反复重灌**（脚本先按 `DEMO-` 前缀删上一次的数据再插，幂等）。
