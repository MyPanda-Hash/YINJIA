# 工单排产 · 日排产「分配完整性 + 产能可见」方案（2026-10-31）

> 状态：**已实现（前端构建 + 后端 JDK25 编译通过）**，待现场看效果。
> 起由：用户 2026-10-31 逐轮讨论敲定（`/grill-me`）。核心诉求原话：
> 「现在的产线产量是没有做限制的，就是填写了一个数值在这里……但是这样实现又过于死板」
> 「其实可以不用顺延啥的，就是给他看下而已，不需要管实际的生产排线处理，我们现在就是再说如何完成这个日期数量的分配」
> 「（产能）就是当前不影响我们的实际排产量」「工单的开工日和完工日是作为查询存在，而不是作为实际的排产处理」。

## 1. 结论（设计树最终态）

| # | 问题 | 结论 |
|---|---|---|
| 1 | 产能限制卡什么 | **不做录入闸门**。允许同线同日多单并行；产能只作为「线×日」的显示与提示 |
| 2 | 产能值从哪来 | `bs_prod_line.日产能`（产线档案面板已可改，零新增 DDL） |
| 3 | 数量口径 | **工序口径直接比，不换算**（换算率已把成品折成支/块，同一条线上同一把尺） |
| 4 | 超限怎么办 | **不堵死录入**：超了照填照存，只把列头标红 + 顶部汇总一行 |
| 5 | 日历 | 每天都有产能（不做工作日/节假日/停机表；以后要加再挂「线×日期」覆盖表，结构不挡路） |
| 6 | 记账 | **实时算、不落表**；三处显示（列头 / 顶部 / 左侧树） |
| 7 | 存量/历史 | **不回改历史**；今天及以后照常实时算并标色 |
| 8 | 顺延 | **不做**（系统不改人的计划） |
| 9 | 自动均摊 | 保持 2026-10-30 的删除状态，**不恢复** |
| 10 | 分配 | 人工逐格填；系统只提示「未分配量」（允许只排一部分，不逼一次排完） |
| 11 | 开工/完工/交期 | **只做查询与显示**：不排序、不均摊、不卡日期列窗口、不拦任何东西 |
| 12 | 优先级字段 | 不做（排产链无排序需求；真要"谁先占产能"再加急单/排序号，语义照搬 `wo_progress`） |

## 2. 现役实现（改动前）

- **日期列**：`WorkOrderDayPlanService.buildDates` 按数据生成（日计划 ∪ 已审报工 ∪ 各道计划开工~完工区间；过去日期只有当天有报工才出列；上限 160 列）。窗口**不读** `plang.cp_date`。
- **格子**：`WorkOrderBoard.vue` 日期列，`row.日计划[d]` + `保存日排产` → `POST /px/scheduleBoard/dayPlan/save`。
- **保存唯一闸门**：同一工单行同工序 `Σ计划 ≤ 排产数量 × 该道换算率`，超了整笔回滚（`WorkOrderDayPlanService.save`）。**没有**「线×日产能」概念。
- **产能**：`bs_prod_line.日产能/小时产能` 两个标量；列注明「负荷>日产能 提示超载，**只提示不拦截**」；铺底 8 条线 `日产能=0`，即 **0 = 不判超载**。
- **两笔「负荷」并存（本次未合并，见 §7）**：
  - 理论负荷：`ScheduleBoardService.lineLoads` / 视图 `v_line_load` —— 把 `plang.pl_sl`（**成品口径**）按 [开工日→交期] 均摊到每天（今天起 14 天），消费方是快速排产/批量排产弹窗的产线下拉标签；
  - 真实日排产：`wo_day_plan`（**工序口径**）—— 排产员在日期格里填的那笔账。
- **行顺序**：原 `ORDER BY pc.cp_date, pc.pl_no, pc.pl_xc`（按**计划完工日期**排）⇒ 交期在偷偷决定"从上到下的优先度"，与「交期只做查询与显示」冲突。

## 3. 本次实现

### 3.1 后端

**`WorkOrderDayPlanService`**
- `data()` 新增两项（仅「工单排产页」按产线调用时返回；生产工单页按行 id 调用不受影响）：
  - `产线产能`：`bs_prod_line.日产能`（0/空 = 未配）；查询 `dayCapacity(line)`；
  - `每日已排`：`{日期: 该线当天 Σ计划数量}`，只保留窗口内日期；查询 `dailyLinePlan(line, dates)`。
    - **按 `plang.scx`（当前归属）汇总**，不读 `wo_day_plan.生产线`：调拨只改 `plang/plang_pc/wo_process_line`，日计划行上记的线是写入那天的旧线 ⇒ 按旧列汇总会把调走的活算回原线。
  - 行上新增 `工序计划量` = `round(排产数量 × 该道换算率)`，与 `save()` 的守卫**同一公式**；换算率取 `bs_route.换算率`（空按 1）。
  - 行集 `RowRef` 增加 `route`（工艺路线编码）；产线模式下一次批量补齐 `routesByIds`（不在循环里 N+1 查）。

**`ScheduleBoardService`**
- `scheduled()` 行顺序：`ORDER BY pc.cp_date, ...` → **`ORDER BY pc.pl_no, pc.pl_xc`**（交期退出排序）。
- `stats()` 新增 `今日超载线数` / `今日超额合计`（全部启用线，今天 `已排 > 日产能` 的条数与合计超额）。
- `linesSummary()` 每条线新增 `日产能` / `今日已排` / `今日余量`（未配产能时 `今日余量 = null`）。
- 新增私有 `dayPlanLoads(workshop)`：各启用线的当日日排产负荷（已排/产能/余量/超载），实时查、不落表；`stats` 与 `linesSummary` 共用同一份口径，不各算各的。
- **未改动** `lineLoads` / `v_line_load`（§7 的两笔账问题，留待单独拍板）。

### 3.2 前端

**`WorkOrderBoard.vue`（工单排产）**
- 日期列头改为两行：`MM-DD` + 该线当天 `已排/日产能`；超产能整列头**标红**（不弹窗、不改数、不禁填）；未配产能写「未配产能」，不判超载。
- 新增列「未分配量」＝ `工序计划量 − 计划合计`，取不到工序计划量显示 `-`；>0 显示橙色提示（允许只排一部分）。
- 顶部汇总行新增「今日超载 N 条线，合计超 M」（>0 高亮）。
- 左侧产线树每条线追加「今日已排/日产能」，超了标红；未配产能显示「未配产能」。
- 数据来源：`loadDayPlan` 读 `data['产线产能']` / `data['每日已排']`；行上带 `工序计划量`。

**`business/dayPlan.js`（纯函数 + 单测）**
- `isOverCapacity(planned, capacity)`：产能 ≤ 0 视为未配、不判超载；**只用于显示**。
- `unplannedQty(opCap, plannedTotal)`：工序计划量 ≤ 0 返回 `null`（界面显示 `-`）。

**多语言**：新增文案已进 `i18n/locales/en.js` 的 `biz`（至少 en；其余语言走 `tt()` 缺失补齐/机翻管线）。

## 4. 验收标准

1. 工单排产页选中任意线：日期列头显示 `已排/日产能`；把某天格子里数字填到 > 日产能 → **仍能保存成功**，列头变红，顶部出现「今日超载 1 条线，合计超 X」。
2. 把该线 `bs_prod_line.日产能` 清 0 → 列头显示「未配产能」，**不再标红/不判超载**。
3. 某行 `Σ日计划 < 工序计划量` → 「未分配量」显示差额（橙色）；补满后归 0；判不出工序计划量的老数据显示 `-`。
4. 交期/开工日期改动后：行顺序仍按 工单号+工单行号（**不再随计划完工日期跳动**），日期列窗口不受交期影响。
5. 同一条线上多张工单同一天都有日计划 → 列头「已排」为合计，超过日产能只标红，**不阻止任何一行录入**。
6. 切到英文界面：上述新增文案显示英文（`en` 包已补）。

## 5. 明确不做（后续要做得重新拍板）

- ❌ 顺延（把超出的量自动挪到后面日期）——系统不改人的计划；
- ❌ 自动均摊 / 一键铺排（2026-10-30 已删，保持删除状态）；
- ❌ 硬拦：超日产能禁止保存、禁止继续填；
- ❌ 超载留痕/原因/日志表（用户口径「不需要记录，给提示就行」）；
- ❌ 工作日历/节假日/停机表（现状每天满产能；要加时按「线×日期」覆盖表，不新建产能主数据）；
- ❌ 优先级/急单/排序号字段（当前不参与计算）。

## 7. 遗留 / 需要单独拍板

1. **两笔「负荷」仍未合并**：`lineLoads`/`v_line_load`（`pl_sl` 成品口径按 [开工→交期] 均摊，14 天窗口）与本次新增的 `wo_day_plan` 实时账（工序口径）不是同一笔账。快速排产弹窗的下拉标签仍显示前者。合并口径（谁作废、谁改读日排产）需单独决策。
2. **产能值仍可能大面积未配**：`bs_prod_line.日产能` 铺底为 0（=不判超载），要先在产线档案补齐，阈值才"活"。
3. **`停用` 列类型隐患**：`bs_prod_line.停用` 物理是 `nvarchar(1)`，现役 SQL 用 `ISNULL(停用,0)=0` 做数值比较；新写的查询沿用了同一写法（与现役一致，实测能跑），但若该列出现 `Y/N` 值会隐式转换失败，建议单独迁移统一。
