# 工单部分量转序（按完成量流转）—— 现状核查与方案评估（2026-11-03）

> 状态：**待拍板，未实现**。本文只有核查与设计，不含任何代码/库变更。
>
> 用户口径（原话）：
> 「当前排产的工单转单是实现的，我现在是要工单需要完成的数量（系统为工序需求量）全排完那一个工单，
> 才会进入到下一个工序，但是实际生产会存在我今天只报工报了这个工单一部分，也就是只生产完了这一部分，
> 然后这一部分需要进入到下一个工序内进行处理，且这一部分也会存在未完成进入下一部分的情况。」
>
> 结论先行：现状确实是「**整道全量做完才转下一道**」，但**报工数据面其实早就允许部分报工**
> （"不跳序"只要求前道有**任意一条**已审报工）。真正卡死"部分量往下走"的只有 4 处：
> **台账状态机、`当前工序` 单值显示、自动派线判据、报工封顶判据**。
> 建议改成「**按量流转**」：把每道工序的「可加工量 = 上一道已审完工量折算」定为一等公民，
> 台账按量推进（计划 → 在制 → 完工），报工按可加工量封顶，界面按工序展示进度与在制。
> P1 **不新增业务表**（只加视图 + 索引），P2 再解决车间级并行派工可见性，P3 可选批次级流转留痕。

## 1. 现状核查（全部为代码/实库事实）

### 1.1 现在的转序规则

| 环节 | 现役规则 | 取证位置 |
|---|---|---|
| 转序判据 | 该道「已审报工量 ≥ 该道计划量」才算达标；计划量 = 本行排产数量 × **该道自己的**换算率 | `ProcessTaskService.java:1291`（`d + 0.0001 >= plan`） |
| 推进方式 | 逐道扫台账，**遇到第一道未达标就停**；该道置「已落实」、按计划线切 `plang.scx`/`plang_pc.scx`，写 `wo_transfer_log` | `ProcessTaskService.java:1283-1352` |
| 触发点 | ①报工单审核/审批钩子 ②**每次打开看板** `advanceSatisfied` ③外部/手机端报工吸收（每分钟） | `ButtonService.java:2382`；`ScheduleBoardController.java:155`；`ExternalReportAbsorbService.java:275` |
| 台账状态 | `计划 → 已落实`，**单向**；代码从不写「已完工」，也从不回退 | `ProcessTaskService.java:1295,:1344`（全库无回退语句） |
| 「当前工序」 | 台账里**最后一道「已落实」**；缺台账回落本行 `plang.当前工序` | `ProcessTaskService.java:580-591`、`ScheduleBoardService.java:870-879` |
| 报工不跳序 | 前道**只要有任意一条已审报工**就能报后道（**不要求做满**） | `WoReportService.java:301-323` |
| 报工封顶 | 本行该道 计划量 × 1.01（按已审累计） | `WoReportService.java:363-401` |
| 完工判定 | 末道已审报工 ≥ 末道计划量 → `plang.完工状态=生产完工` | `ProcessTaskService.syncOneRowState:1567-1582` |
| 结案 | `入库 ≥ 排产` + 组装成品检验已审（与报工无关） | `ProcessTaskService.java:1648-1679`、`PlangClose.java` |

**一句话**：报工是唯一的推进键，而推进键的阈值是「全量」。

### 1.2 卡点只有 4 处（不是全链路推倒重来）

1. **台账没有"量"**：`wo_process_line` 只有 `计划数量`，没有 已完成 / 已流入 / 已转出 / 在制 ——
   无法表达"这道工序现在可以做多少"。
2. **「当前工序」是单值**：一行工单只能在一个工序、一条线；`plang.scx` 单值，
   工单排产看板按 `pc.scx = 选中线` 过滤（`ScheduleBoardService.java:964`），
   后道一旦并行就"看不见"。
3. **自动派线以全量达成为前提**：前道没做满 ⇒ 后道台账永远「计划」、线永远不切。
4. **报工封顶按全量计划**：后道能报满全量，也能报 0，与"流入了多少"无关。

另有两个**已在存量数据里存在的口径问题**，改按量流转前必须先收口（否则会被放大）：

- `syncOneRowState:1571` 用 `qty < plan` 判"没做满"，其中 `qty` 是**工序口径**、`plan` 是**成品口径**
  （排产数量）—— 换算率 ≠ 1 的路线会**误判为已做满**（例：切炭率 3，计划 6000，实做 3000 就被当成达标）。
- 台账 `计划数量` 与 `pl_sl × 换算率` **实测 9 行不一致**（历史重算遗留）。

### 1.3 实库实证（正式账套 HSDZ_MES，2026-11-03）

| 指标 | 值 | 说明 |
|---|---|---|
| `plang` / `plang_pc` | 479 / 435 | 工单行 / 排产镜像 |
| `wo_process_line` | 155（有效 125） | 工序台账 |
| `scjl` | 1289（已审 1286） | 报工 |
| **违反"后道完工 ≤ 前道完工"的工单行** | **0** | 现有数据天然满足流转约束，改造**不会产生历史冲突** |
| 台账 `计划数量 ≠ pl_sl×率` | 9 行 | 需一次性对账 |
| 「后道有报工、前道未做满」 | 0 行 | 现状门槛确实在拦，没有"偷跑"数据 |

**典型样本 `GD-2026-11-0008` 行 2180**（就是本次要解决的场景）：

```
排产 5000（需求 5000，路线 GY-CB-STD 成型→切炭→组装，换算率全 = 1）
成型：已审报工 2000（两笔 1000）  台账「已落实」，实际线 2号车间
切炭：0                          台账「计划」，计划线 切炭2(自动)
组装：0                          台账「计划」，计划线 装箱1(老厂)
plang.当前工序 = 成型 / 完工状态 = 在制 / scx = 2号车间
```
⇒ 物理上这 2000 件半成品今天就该进切炭；系统里切炭线**看不到这 2000**，也**没有"可加工 2000"这个概念**。

## 2. 业务场景拆解（要支持的 4 种）

| # | 场景 | 例子 |
|---|---|---|
| C1 | 部分完工流入下道 | 成型 2000/5000 → 切炭可加工 2000 |
| C2 | 下道再部分完工继续往下 | 切炭做 1200 → 组装可加工 1200；切炭在制 800 |
| C3 | 多道并行 | 成型继续做剩余 3000，切炭同时做已流入的 2000 |
| C4 | 回退 | 报工弃审/作废 → 下游可加工量随之减少 |

**本次明确不做**（要做得单独拍板）：
- ❌ 物理暂存（做完了但先不下转，搁在中间仓）—— 系统默认"做完即流转"；
- ❌ 报废/不良扣减流转量 —— `scjl` 现役只有 `sl` 一个数量列（`bf_qty/bl_qty/loss` 是参考库遗留列，全库为 0），
  不良在检验单侧；
- ❌ 跨工序返工/回流。

## 3. 方案对比

| | **A 派生按量流转（推荐）** | B 流转台账 `wo_process_flow` | C 自动拆行（切单扩展） |
|---|---|---|---|
| 核心 | 不落流水：每道「可加工量」由**报工数据实时派生** | 新建流转流水表，每次转出记一行 | 部分完工后自动把这一部分拆成子工单行，到下一道继续 |
| 新增表 | **0**（仅视图 + 索引） | 1 张主表 + 迁移 | 0 表，但工单行数暴涨 |
| 账一致性 | **天然自洽**（报工是唯一真源，弃审自动回滚） | 双账本，需保证流水与报工对得上 | 父子账需保证数量守恒（切单已有的痛点） |
| 批次留痕 | 无（只能看到数量与时间） | **有**（每批转出多少、谁转的、何时） | 有（子单即批次） |
| 手工干预（暂存/挑选/报废） | 不支持 | **支持** | 不适用 |
| 改动面 | 后端 5-6 处 + 1 视图 + 前端 3 页 | 再加表/服务/页面/弃审对称 | 切单服务大改 + 看板/日计划/结案全受影响 |
| 工作量（估） | **P1 约 4-6 人天** | 8-12 人天 | 8-12 人天（且业务账变复杂） |

**推荐 A**。理由：①现有数据已验证满足按量约束（0 冲突），派生式不会产生对不上的账；
②用户当前诉求是"让这部分往下走 + 看得见"，不是"精确到批次的流转卡"；
③B 的价值（批次/人工调整）真实存在，但可以在 A 之上后补（P3），不需要一开始就付双账本的成本；
④C 会把"工单行"语义拆碎（现在的唯一键是 工单号+工单行号，报表、结案、检验、领料全按它算），不划算。

## 4. 推荐方案 A —— 详细设计

### 4.1 口径（沿用现行"两把尺子"，只补一个"流的量"）

设某工单行 `pl_sl` = 排产数量（成品口径），第 i 道工序换算率 `rate(i)`（`bs_route`，空/0 按 1）：

| 量 | 公式 | 口径 |
|---|---|---|
| 已审完工 `done(i)` | `Σ scjl.sl`（该行该道、`wgzt='Y'`、未作废） | 工序口径 |
| 已审完工折成品 `doneBase(i)` | `done(i) / rate(i)` | 成品口径 |
| **可加工量** `availBase(i)` | i = 首道：`pl_sl`；否则：`doneBase(i-1)` | 成品口径 |
| **可加工量(工序)** `avail(i)` | `availBase(i) × rate(i)` | 工序口径 |
| **在制量** `wip(i)` | `avail(i) − done(i)` | 工序口径 |
| 工序计划量 `planQty(i)` | 台账 `计划数量` 优先，缺失回落 `pl_sl × rate(i)`（与现状同一套兜底） | 工序口径 |
| 完成进度 | `doneBase(i) / pl_sl` | 成品口径 |

> 换算率带来"单位不同"的问题在这里被消掉了：**先把各道折回成品口径再比**，不与工序口径相减
> （2026-10-07 定死的"两把尺子"口径，见 `docs/plans/2026-10-07-预排全程线与转序-方案评估.md §2.4.2`）。

### 4.2 台账状态机（`wo_process_line.状态`）

| 状态 | 条件 | 现在怎么写 | 改造后 |
|---|---|---|---|
| `计划` | `avail(i) ≤ 0`（前道还没流出量） | 已写 | 同 |
| `已落实`（= 在制可做） | `avail(i) > 0` 且 `doneBase(i) < pl_sl` | 已写（但要全量达标才进） | **首次有流入量就写**，并补 `实际生产线`、`落实时间` |
| `已完工` | `doneBase(i) ≥ pl_sl − ε` | **代码从不写**（状态值在注释里，无写入） | 新写 |
| 回退 | 弃审/作废后按量重算 | **从不回退** | 允许回退（见 4.7） |

多道并行时，**「当前工序」不再是单值**，但为兼容现有页面（调拨、日计划、打印、负荷），保留一个兼容单值：

> **当前工序（兼容）= 第一道「已完成折成品 < 排产数量」且「已落实」的工序**；
> 全部做完则取末道。`plang.scx` 同步取该道的实际生产线。

新增 **在制工序集合 = 所有「已落实且未完工」的道**，用于列表 / 追溯 / 在制看板。

### 4.3 推进算法（替换 `applyNextProcess`，幂等）

```
applyNextProcess(pid = 工单号, rowId = 工单行id):
  ops = 该行工艺路线（bs_route 按加工顺序，同名去重，与 ensureLedger 同口径）
  prevDoneBase = null
  for i, op in ops:
     rate   = rateOf(op)                        // 空/0 → 1
     done   = approvedQty(rowId, op)            // WoInspGate.reportedQty（现役三级锚）
     doneBase = done / rate
     availBase = (i == 0) ? pl_sl : prevDoneBase
     ledger = 台账(rowId, op)
     if ledger 不存在: 沿用现有懒预排兜底，跳过推进
     // ① 状态推进（set 语义，可重复执行，不会重复累加）
     新状态 = availBase <= 0 ? 计划
            : doneBase >= pl_sl - ε ? 已完工
            : 已落实
     if 新状态 != 计划 && ledger.实际生产线 为空:
         ledger.实际生产线 = ledger.计划生产线        // 计划线空 ⇒ 只提示「请人工派线」，不瞎切
         ledger.落实时间   = i == 0 ? now : (上一道 max(scjl.wgsj) ?: now)
         if 实际生产线 != plang.scx: 写 wo_transfer_log(原因='部分转序', 数量=本次流入折工序口径)
     update ledger.状态 = 新状态                     // 允许回退，见 4.7
     prevDoneBase = doneBase
  // ② 工单行兼容列
  当前工序 = 第一道 已落实且未完工（全完 ⇒ 末道）
  plang.当前工序 = 当前工序
  plang.当前工序完工量 = done(当前工序)              // 工序口径（修现行口径 bug）
  plang.scx = 当前工序的实际生产线
  plang.完工状态 = doneBase(末道) >= pl_sl ? 生产完工 : (任一道 done>0 ? 在制 : 未开工)
```

要点：
- **一次性把整行推到"该到哪到哪"**（现在一次只推一道），幂等；
- 台账状态用 **set（按数据重算）** 而不是累加，天然幂等，并发重复调用不会重复计数；
- 轨迹只在**真的换线**时写，原因区分「转序自动派线」（全量达标）与「部分转序」（部分流入）。

### 4.4 报工闸门（`WoReportService.validateRow`）

| 校验 | 现在 | 改造后 |
|---|---|---|
| 不跳序 | 前道有任意已审报工 | 改成 `availBase(i-1) > 0`（**按量**，口径更硬） |
| 封顶 | `已报 + 本次 ≤ pl_sl × rate × 1.01` | `已报 + 本次 ≤ avail(i) × 1.01`（首道 avail = pl_sl×rate，与现状一致） |
| 已报累计 | 只算已审 | 建议 **已审 + 待审**（防止待审堆积过账时超量）—— 见拍板 Q2 |
| 外部直写/PDA | 吸收时**不校验**封顶 | 保留不拦，但落库后按新视图标红「超流入」 |

### 4.5 产线与 `plang.scx`（单值兼容）

- 每道实际线只落 `wo_process_line.实际生产线`（**P1 不新增字段**，已有列够用）；
- `plang.scx` = 当前工序（最前未完工道）的实际线 ⇒ 调拨、负荷、日计划、打印**旧语义不变**；
- **P1 的局限**：切炭线在"工单排产看板"（按 `pc.scx` 过滤）里仍看不到这张单 —— 这是 P2 要解决的；
- **P2 方案**：工单排产页新增「工序在制」页签（或把看板行按工序展开）：
  行 = 工单行 × 在制工序，列 = 可加工量 / 已完工 / 在制量 / 计划线 / 实际线 / 上道完工 / 最后报工时间，
  按 车间 / 产线 / 工序 筛选。数据全来自 4.9 的视图，不再各写一套 SQL。

### 4.6 界面改动

**P1（主管视角能看懂，能录进去）**

- 工单追溯弹窗「工序步骤」块：加 `可加工量 / 已完工 / 在制` 三列（现状只有 完工/计划/待审）。

**P2（车间视角能派工）**
- 工序在制看板（见 4.5）；日计划按工序（`wo_day_plan` 本来就有 `工序` 列，天然支持）；

### 4.7 弃审 / 作废 / 撤销（现状缺陷，必须一并补）

- **弃审**：重算该行 → 台账状态可回退、`plang` 当前工序/完工状态重算；
  **若弃审后"下游已审报工 > 新的可加工量"（负在制）⇒ 拒绝弃审**，提示「后道已报 X，请先处理」。
- **作废**：现状 `voidDoc` 不跑任何报工钩子（`scjl.wgzt` 仍 `Y`，完工量不减）——
  本次在作废后补一次同样的重算（否则部分流转的账会漂）。
- **撤销排产**：现状"有报工即不可撤"保留；若确需回退，先弃审/作废报工。

### 4.8 下游口径（保持不变，但要确认）

| 项 | 现状 | 本次 |
|---|---|---|
| 首件检验 / 制程检验 / 组装成品检验 自动出单 | 该道累计已审 ≥ 该道**计划量**才出草稿 | **不变**（全量达标才出单）；若要"首批产出即出首件"另议（拍板 Q5） |
| 生产完工 | 末道 ≥ 末道计划量 | 不变（按 4.3 修口径） |
| 结案 | 入库 ≥ 排产 + 组装成品检验已审 | 不变 |
| 切单上限 | `pl_sl − max(已入库, 各道已完工报工折成品)` | 核对取 **max** 而非累加；流转后仍成立 |
| 日计划 | 可自由填，超量只标红 | 不变；P1 加"可加工量"提示，**不硬拦** |

## 6. 验收标准（用 `GD-2026-11-0008` 行2180 现场验）

1. 现状：成型已报 2000/5000。改造后：切炭台账变「已落实」、实际线 = `切炭2(自动)`；
   切炭报工上限 = 2000；报 2001 被拒；成型继续报 1000 不受影响。
2. 切炭报 1200 后：组装台账变「已落实」、可加工 1200；切炭在制 = 800。
3. 弃审切炭 1200：组装可加工回落 0、台账回「计划」；若组装已报 500，则弃审被拒并提示。
4. 多行互不影响：只推进被报工的那一行（唯一键 工单号+工单行id）。
5. 换算率 ≠ 1 的路线（如 `GD-2026-10-0228` 切炭率 3）：成型报 2000 → 切炭可加工 6000、台账计划 6000。
6. 列表/追溯/报工页显示 计划/已做/在制；「当前工序」= 最前未完工道。
7. 历史全量重算后：`后道完工折成品 > 前道完工折成品` 的行数 = **0**。
8. 性能：工单排产看板加载（25 工单/125 台账）不超过 1s；派生查询走新索引。
9. 两账套迁移执行 0 失败；`DbNormAudit` 不新增 FAIL。

## 7. 风险

1. **口径 bug 被放大**：`syncOneRowState` 成品/工序口径错配、9 行台账偏差、6+ 处完工量 SQL 锚点不一致
   （`WoInspGate` 三级锚 vs 看板两级锚）—— 必须先做 P0，否则"该转没转 / 不该转已转"。
2. **弃审/作废现状不回退**：部分流转后每次反复都会让账更漂 ⇒ 本次必须补回退与"负在制"拒绝。
3. **三个触发源 + 无锁/无唯一键**：报工审核、每次看板加载、每分钟吸收都在推进；
   新算法虽然是 set 语义幂等，仍建议给 `wo_process_line` 加 `(工单行id, 工序)` 唯一约束或行锁，
   避免重复写 `wo_transfer_log`、重复切 `scx`。
4. **单值 `plang.scx` 与多道并行的表达冲突**：P1 只能"兼容"（当前工序 = 最前未完工道），
   车间的真实并行可见性必须 P2 解决 —— 若用户要一步到位，需把 P2 并入本期（见拍板 Q1）。
5. **检验门禁仍按全量**：部分流转不触发首件/制程/成品检验出单（与现状一致，不影响流转，但业务上可能想改）。
6. **换算率取整尾差**：各道折成品再乘回，四舍五入会在道间累积（切单已有同类尾差）——
   统一 `decimal(18,4)`，只在显示层取整，封顶给 1% 容差。
7. **外部直写无法预校验**：手机端/参考库直写 `scjl` 不受封顶约束（现状如此），
   只能落库后标红「超流入」；是否拦截见拍板 Q7。
