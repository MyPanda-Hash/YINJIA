## 0. 需求与一句话结论

**需求原文**（2026-10-16 用户）：
> 「当前首件检验单、制程检验单、组装成品检验单都需要实现当前完成了进行，**成型完成后的生产工单才能生成**这个首件检验单，
> 当前实现的所有生产工单都能生成检验单据，修改当前的实现逻辑，先去 GitHub 查询这类实现方式，再进行编写实现方案。」

**结论（一句话）**：把「能不能开单」从「不看工序」改成「**该工单行的成型工序已完成**」，判据收敛到**一个深模块**
`WoInspGate`（唯一取数 + 唯一话术），门禁落在 **4 个后端接入点**（2 个手工开单 + 2 个自动出单钩子），
前端只做体验（置灰 + 写明原因），并在**同一份判据**上补一处现役缺陷（§3.4）。
现役工作区**已落地这一版的骨架**（可编译），缺口是**强度开关 / 强制放行 / 判据统一 / 单测**四件（§5）。

```
判据（口径 1，默认）  : 该工单行的「成型」工序存在已审核报工（完工量 > 0）
落点（D2 深模块）     : WoInspGate.check / checkPage —— 四处入口共用，禁止各写一份

兜底（C4）            : 无工艺路线/路线无成型 ⇒ 免门禁；无任何已审核报工 ⇒ 存量放行（可切严格）
开关（C3，待补）      : yj_panel.config 的 inspGate = off | warn | block
```

### 1.2 三条被反复印证的「实做模式」

1. **「建单」与「卡流转」是两个独立的闸**。ERPNext/InvenTree 建单从不看前道，卡的是「完成/入库」那一步；carbon 干脆把检验做成路线里的一道工序，让统一的依赖状态机去管先后。把两件事耦合，就会出现「上游没报工 ⇒ 检验单一辈子开不出来」。
2. **门禁强度必须是可配置的，而不是写死的**。ERPNext 用 `Stop / Warn` 两个选项、InvenTree 用 `PREVENT_BUILD_COMPLETION_…` 开关、畅捷通用「系统参数」——三家独立做出同一个设计：**默认宽松、可收紧**。
3. **必检与否挂在「工序/物料」上，而不是挂在全局**。ERPNext 是 `BOM.inspection_required` × `Work Order Operation.quality_inspection_required`，InvenTree 是 `PartTestTemplate.required`，金蝶是「工序资料里勾首件检 + 选控制方式」。

### 1.3 必须说清的一件事：**开源里没有「工序完成→才允许建检验单」这条因果链**

调研遍查 carbon / ERPNext / InvenTree / OpenMes / GC-MES / iMES-Factory 与金蝶、畅捷通文档，
**没有一家是「后向门禁」（先判工序完成、再放行建单）**：
carbon 是「打开检验工序时懒创建」、ERPNext/InvenTree 是「完工/入库时**反向**要检验单」，商业 ERP 是「报工审核后**自动**出单」。

⇒ **这说明两件事**（也是本方案的立足点）：

1. 用户要的这条规则**必须自研**，没有可直接照搬的现成实现 —— 但可以**借用它们的形态**：
   「判据取报工记录」（carbon 的 `jobOperation.status`、商业 ERP 的报工单）、
   「强度可配」（ERPNext Stop/Warn）、「自动出单 + 手工补单双通道」（金蝶下推补生成）。
2. **三张单的时点不可能统一**，必须各按自己那道工序定（§3.1）：
   首件检验的现场语义是「**脱模后立马首件检验**」（用户口径 C-95），若把闸定成「整批成型做完」，
   首件就永远晚于现场实际动作 —— 这正是 §3.2 分档的由来。

### 2.2 本项目其实早就有「同源判据」的前向门禁（这一点很关键）

- **报工不跳序**（`WoReportService` :171-217）：报工的工序必须在**本行**工艺路线内，且路线上排在它之前的工序
  必须**已有已审核报工**，否则拒绝（「前道工序「成型」尚未报工，不能跳到「组装」」）。
- **结案前向门禁**（`ProcessTaskService.syncCloseState` :1222）：结案要求「组装成品检验单已审核 + 入库达标」。
- **工序进度**（`ProcessTaskService.detail` :355-380 / `reportedQty` :998）：按 `scjl` 已审核报工统计标准五道工序的完工量。

⇒ **本项目不是「引入门禁的新范式」，而是把现有的三处同源判据接到开单口上**。
也正因为判据同源，**必须共用一份实现** —— 否则「报工能报」与「单能开」会出现两套口径。

## 3. 判据：「成型完成」到底怎么算

### 3.1 口径（`WoInspGate.CALIBER`，唯一开关）

| 口径 | 定义 | 今日命中 | 现场语义 | 评价 |
|---|---|---|---|---|
| **`REPORTED`（默认，已落地）** | 该行「成型」有**已审核报工**（完工量 > 0） | **1/424** | 「首批已成型/已脱模」——与 C-95「脱模后立马首件检验」一致 | ✅ 推荐，也是流程图「质检数据随报工产生」的直接读法 |
| `DONE` | 成型**达标**（已审完工量 ≥ 该道计划量 = 本行 `pl_sl` × `bs_route.换算率`） | **0/424**（该行 161 < 500） | 「整批成型做完」 | ⚠ 会把首件推到整批之后，与 C-95 冲突；且今日会封死全库 |

> 行业依据（§1）：ERPNext/InvenTree 都允许「宽松/严格」两档并存；**首件常常只有 1 件**，用「产出 vs 计划」判前道必然判早判错
> （OpenMes 的 `floor(produced/N)` 是「每 N 件抽检」语义，不适用于判前道）。

### 3.2 三张单是否同一时点？（建议 E1，已落地）

| 单据 | 建议时点 | 理由 |
|---|---|---|
| 首件检验单 | **成型有已审报工** | 成型那道工序的质检数据（`QC_MOLD_INSP` 已下架，由本单承接）；脱模后立即检 |
| 制程检验单 | **成型有已审报工**（同口径） | 流程图品质泳道没画它，它是按《生产相关品质检验.xlsx》第 3 步人工开单；门槛与首件同 |
| 组装成品检验单 | **出单时必然已过成型** | 组装报工本身就要过「不跳序」；加闸只为堵手机端/外部直写 |

> 若后续要按金蝶范式做**串联**（首件已审 → 才允许制程 / 制程已审 → 才允许组装成品），属于 **E2**，会改变现场作业顺序，需另立变更。

### 3.3 取数：必须**三级锚定**（否则判不出来）

`scjl` 锚回工单行的三条链路，**依次**尝试（`WoInspGate.attributeKey`）：

1. **`scjl.[工单行号]`**（审核时写定，最可靠）；
2. **`scjl.gd_id → plang_pc.plang_id`** —— **仅当该 `plang` 行确实存在**；
   实测 `plang_pc` 两行全悬空（575→1127、576→1128），若不做「存在性」校验，这条会**把报工挂到不存在的行**上；
3. **`批次号`**（**非空才比**，防 `''=''` 恒真 —— 同 `ProcessTaskService.syncCloseState` :1242 的既有教训）。

计划量：`pl_sl × bs_route.换算率`（路线无「成型」行 ⇒ 免门禁；换算率空/≤0 按 1）。

### 3.4 🔴 必须一并修：现役 `reportedQty` 只有两级锚定，与门禁**当场对不上**

**实证**（`AnchorGapProbe`，今日）：

```
plang_pc: id=575→plang_id=1127（plang 里没有 1127）、id=576→1128
plang  : GD-2026-10-0007 行1 → id=10, 批次 20261014
scjl   : gd_id=575, [工单行号]=1, gxdm=成型, wgzt=Y, sl=161
① 现役 reportedQty（ProcessTaskService:998，锚 pc.plang_id 或 "gd_id=0 且同批次"）
      → 成型完工量 = 0.0      ← ❌ 161 件报工被吞掉
② WoInspGate.check（三级锚定）            → 成型完工量 = 161.0
③ 仅 [工单行号]=1 锚定                     → 161.0
```

原因：`gd_id=575 ≠ 0` ⇒ 批次兜底分支（只在 `gd_id=0` 时启用）**不生效**；而 `pc.plang_id=1127` 指向不存在的行
⇒ 两级锚定在这条数据上**两个分支都落空**。

**后果**：同一条成型报工，**工序进度/转序**段（`ProcessTaskService`）判为「成型未报」，**门禁**段判为「已完成」——
两处屏幕对同一事实给出相反答案。这不是门禁引入的 bug，但**门禁一旦上线就会被现场第一时间发现**。

**处置（P1，建议随本期一起做）**：把三级锚定下沉为**唯一取数口**（`WoInspGate.reportedQty(jdbc, 工单号, 行id, 工序)`），
`ProcessTaskService.reportedQty`(:998) 与 `detail`(:370) 改为调用它；`WoReportService` 不跳序那段（:197-217）同步改。
改动量小（3 处调用点），收益是「报工能不能报」「单能不能开」「进度显示多少」三处**永远同源**。

## 4. 门禁强度与兜底

### 4.1 现役行为（已落地）

- **硬拦截**（C1）：`fromWoLine` 返回 **422** + 中文话术；前端置灰 + tooltip（体验层，可绕过但后端兜住）。

- **存量兜底**（C4②）：该行**没有任何已审核报工** ⇒ 放行，行上标 `存量放行`。
- 自动出单钩子：**闸不过只跳过出单**，绝不阻断报工审核本身（§1.2 模式 1）。

### 4.2 🔴 今日风险量化：**423/424 行走存量兜底 ⇒ 门禁当日等于不生效**

```
424 行 → 可开单 1 / 拦截 0 / 免门禁 0 / 存量放行 423
```

也就是说：**按现役实现，用户今天仍然能给 423 行开检验单**（只是行上标了「存量放行」）。
这不是实现错误，而是「存量兜底」必然的结果 —— 本地库是 10-16 从金蝶 CSV 重导的**测试数据面**，压根没有报工历史。

> **对照组（重要，别误判成"门禁没做"）**：同一探针在 `HSDZ_MES_TEST` 上给出 **拦截 4 / 存量放行 29 / 可开单 1**（30 行）。

> ⇒ 门禁是否「看得见」，取决于**数据面**（有没有报工），不取决于代码。
> 验收「拦截路径」请**用测试账套**做（§7），别在正式库上找不存在的样例。

**因此本方案必须把选择权显式交给用户**，不能默认替他决定：

| 取舍 | 效果 | 代价 |
|---|---|---|
| **A. 保留存量兜底（现役）** | 今天仍能开单（标「存量放行」）；等报工数据长起来后门禁自然生效 | **现在看起来「没改」** —— 与用户「所有工单都能生成，要改掉」的诉求在观感上冲突 |
| **B. 关掉存量兜底（严格）** | 真正实现「只有成型完成的工单才能开单」：今天 423 行立刻不可开 | 现场/演示**一张单也开不出**（除非先去报工）；需与现场确认 |

**推荐**：做成**开关**（C3，§5.1），默认 `block + 兜底开`，把「切严格」变成一次配置动作而不是一次发版。

## 5b. 强度开关怎么改（给运维/实施看）

改档位**只需要一条 UPDATE**，不必发版（`WoInspGate` 有 30s 缓存，改完最多半分钟生效）：

```sql
-- 三张检验单面板任一写即可生效,优先级固定 首件 > 制程 > 组装(见 WoInspGate.GATE_PANELS)
UPDATE yj_panel SET config = N'{"inspGate":"warn","inspGateLegacy":"pass"}' WHERE panel_code = N'QC_FIRST_INSP';
-- inspGate       : off(不做门禁) | warn(放行+预警+留痕) | block(拦截,默认)
-- inspGateLegacy : pass(存量行放行,默认) | block(存量行也拦 —— 真正实现"只有成型完成的工单才能开单")
```

> ⚠ **两个账套要分别改**（工厂切换走不同库；本方案的门禁配置是账套级的元数据）。
> ⚠ 三张面板**同时**写了 `inspGate` 时按上面的优先级取值 → 想全局改，改「首件」那张最稳。
> ⚠ 本机实测：**只在首件面板上改档位是有效的**（曾因 `ORDER BY panel_code` 让组装面板的老值抢先而"改了没用"，
> 已修成显式 `CASE WHEN` 定序 —— 这类"改了没生效"必须留日志，`WoInspGate` 读配置失败会 `log.warn` 而不是静默回退）。

## 6. 边界与例外

1. **未绑工艺路线 / 路线无「成型」** ⇒ 免门禁（今日 0 行；`GY-2026-10-0004` 那条怪路线（成型→下料）也不受影响，因为含成型）。
2. **存量单不动**：只约束新单（用户已定口径）。
3. **弃审回退**：报工弃审后成型量回退 ⇒ 已有检验单**不自动作废**；首件/组装两张「随报工弃审级联作废」的既有链路保持不变（`woInspUnauditCascade` :3262，调用点 `ButtonService` :1778 的 `WO_REPORT` 弃审分支）。
4. **手机端/外部直写 `scjl`**（`ExternalReportAbsorbService`）：不生成任何检验单 ⇒ 门禁天然不被它绕过，但也意味着**手机端报工不会自动出检验单**；是否补上属 F2 二期。
5. **多行工单**：一律按「工单号 + 工单行号」判，不看整单（与 2026-10-15 行级口径一致）。
6. **生产线为空（今日 424/424）**：判据不得依赖产线；要判「在成型线上完成」得先把排产补起来。
7. **无路线工单的连带问题**：`快速排产 → 工序路线排线` 会拒绝「未绑定路线」，现场只能人工挑线 —— 这是**数据面问题**，不是门禁能解决的（门禁已按「豁免 + 标注」处理）。

## 附录 B：现役 `WoInspGate` 的成型完工量取数（三级锚定，已落地）

```sql
-- 单行判定:该工单行的「成型已审核完工量」
--   rows = SELECT p.id AS 行id, p.pl_no AS 工单号, p.pl_xc AS 工单行号,
--                 ISNULL(p.[批次号],N'') AS 批次号, ISNULL(p.[工艺路线],N'') AS 工艺路线,
--                 ISNULL(p.pl_sl,0) AS 排产数量
--          FROM dbo.plang p WHERE p.pl_no=? AND p.pl_xc=? AND ISNULL(p.asp_cancel,'N')<>'Y'
SELECT ISNULL(SUM(ISNULL(s.sl,0)),0) AS 成型完工量
  FROM dbo.scjl s LEFT JOIN dbo.plang_pc pc ON pc.id = s.gd_id
 WHERE s.gldh = @工单号 AND s.gxdm = N'成型'
   AND ISNULL(s.wgzt,'N') = 'Y' AND ISNULL(s.asp_cancel,'N') <> 'Y'
   AND (
        (@行id > 0 AND EXISTS (SELECT 1 FROM dbo.plang p WHERE p.id = @行id)
                   AND pc.plang_id = @行id)                    -- ① 有效 plang_id 锚定(悬空必须落空)
     OR (@行号 > 0 AND ISNULL(s.[工单行号],0) = @行号)          -- ② 工单行号(审核时写定)
     OR (ISNULL(s.gd_id,0) = 0 AND @批次号 <> N''              -- ③ 批次兜底(空批次不比)
         AND ISNULL(s.[批次号],N'') = @批次号)
   );
```
