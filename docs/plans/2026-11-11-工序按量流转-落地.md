# 工单工序「按量流转」落地记录（2026-11-11）

> 前情：`docs/plans/2026-11-03-工单部分量转序-按量流转-方案评估.md`（方案 A，状态「待拍板未实现」）。
> 2026-11-11 用户拍板口径，本文记录**实际落地的范围、代码位置、验收方式与遗留**。

## 一、用户口径（原话）

> 「是我当前第一个工序有500个计划完成量，那么当前我就应该有200个报工完成的数量后，
> 第二个工序就能报工对应的200来源于上一道工序完成的报工数」

即：工序之间按**上一道已审完工量**往下流。不许「前道没做满 ⇒ 后道一个都报不了」，
也不许「后道按自己的计划量报满，跟前道实际做了多少无关」。

## 二、口径（唯一实现 = `ProcessFlow`）

| 量 | 公式 | 口径 |
|---|---|---|
| `done(i)` | 该工单行该道**已审**报工量（`scjl`，`wgzt='Y'`，未作废） | 工序口径 |
| `rate(i)` | `bs_route.换算率`（空/≤0 按 1） | — |
| `doneBase(i)` | `done(i) / rate(i)` | 成品口径 |
| `availBase(i)` | 首道 `pl_sl`；否则 `doneBase(i-1)` | 成品口径 |
| `avail(i)` | `availBase(i) × rate(i)` | 工序口径 = **本道可加工量** |
| `planQty(i)` | 台账 `计划数量` 优先，缺失回落 `pl_sl × rate(i)` | 工序口径 |
| `wip(i)` | `avail(i) − done(i)`，不足 0 记 0 | 工序口径 = 在制量 |
| **可报上限** | `min(planQty, avail) × 1.01` | 工序口径（1% = 沿用既有超产容差） |

用户例子对得上：工序1 计划 500、已审报工 200 ⇒ `avail(2) = 200` ⇒ 工序2 可报 200（报 300 被拒）。

## 三、改了什么（逐处）

| # | 位置 | 改动 |
|---|---|---|
| 1 | **新增** `backend/.../service/ProcessFlow.java` | 按量口径的唯一实现（`steps / indexOf / stepOf / currentOp / assertNoNegativeWip`），与 `PlangDone`/`PlangClose`/`WoInspGate` 同一种「口径类」做法 |
| 2 | `WoReportService.validateRow` | ① 不跳序：由「前道有**任意一笔**已审报工」改为**按量**（前道 `availBase>0` 才放行）；② 封顶：由「本道计划量 ×1.01」改为 **`min(计划量, 可加工量) ×1.01`**，报错文案带「本道可加工量 / 来自上一道已审完工折成品」 |
| 3 | `ProcessTaskService.applyNextProcess` | 重写成**按量推进**：无流入=`计划`、有流入未做满=`已落实`、折成品做满=`已完工`；**允许回退**（弃审/作废后量被收回）；「实际生产线/落实时间」按道补；换线轨迹区分「转序自动派线（整道做满）」与「**部分转序（部分流入）**」；工单行状态列（当前工序/当前工序完工量/完工状态/完工时间/`scx`）由它**唯一**写入 |
| 4 | `ProcessTaskService.syncOneRowState` | 退化为调用 `applyNextProcess`（此前一处两套算法，且成品/工序口径错配会把"没做满"误判成"做满"） |
| 5 | `ProcessTaskService.applyReport` | 报工审核/弃审都跑按量重算；**弃审前先挡「负在制」**（后道已审 > 新可加工量 ⇒ 拒绝并提示先处理下游） |
| 6 | `ProcessTaskService.advanceSatisfied` | 看板加载的触发条件由「这一道做够了」改为「这一行有已审报工量」⇒ 部分完工当场把后道置「已落实」 |
| 7 | `ScheduleBoardService` / `WorkOrderListController` | 「当前工序」由**最后一道已落实**改为**最前一道已落实**（= 最前未完工道，多道在制时取最前），与 `ProcessFlow.currentOp` 同口径 |
| 8 | `WorkReportController.context` | 工序台账每道新增 `可加工量 / 在制量 / 剩余可报 / 上道已完`（供报工页显示"还能报多少"） |
| 9 | `MobileReport.vue` + 10 个 `locales/*.js` | 手机端每道工序显示「可报 X（可加工量 Y）」；数量默认值改为**剩余可报**；超量/无流入给出可读提示；5 条新文案 10 语言齐备 |
| 10 | **新增** `tools/migrate-wo-process-line-qty-20261111.sql`（已登记 `tools/db-migrations.txt`） | 存量台账「状态 / 实际生产线 / 落实时间」按按量口径**一次性对账重算**（幂等、零 DDL、末尾自检不一致即报错）。正式库实测改 56 行：计划→已完工 34、已落实→已完工 20、计划→已落实 2 |

**数据库：零 DDL**（不新增表/视图/列；`wo_process_line.状态` 已有列即可表达 `计划/已落实/已完工`）。
唯一一次库操作是上面的**数据对账**（只写 `wo_process_line` 三列），两个账套都已执行（`DbSync`：正式/测试各「执行 1、失败 0」）。
之后无需再跑：运行时每次报工/看板加载都会按同一口径重算（幂等）。

## 四、验收方式（复跑用）

1. **单元级**：见 `tools/archive/_wo-qty-flow-20261111/check-flow.sql`（只读：全库扫「后道已审折成品 > 前道已审折成品」的行，应为 0）。
2. **接口级**：`GET /px/workReport/context?woNo=<工单号>` 看 `工序台账[].可加工量/剩余可报`。
3. **界面级**（ego 浏览器）：手机端「工序报工」页 —— 工序1 报 200 后，工序2 卡片显示「可报 200」，
   填 300 提交被拒（提示「超出本道可报量:200」），填 200 通过。

## 五、遗留 / 下一期（P2）

- **车间可见性**：工单排产看板按 `pc.scx`（单值）过滤，`plang.scx` 跟「当前工序」走 ⇒
  **后道车间在自己的产线看板上仍看不到"等我的那批"**（方案文档 §4.5 的 P1 已知局限）。
  要在后道线看板上看见，需要 P2「工序在制看板」（行 = 工单行 × 在制工序）。
- **多道并行的单值兼容**：`plang.当前工序/scx` 仍是单值（取最前未完工道），调拨/日计划/打印沿用旧语义。
- **超产容差**：后道可报上限保留了 1% 容差（与首道/历史口径一致），所以「前道流 200」时后道可到 202。
  若现场要求**严格等于**流入量，把 `ProcessFlow.OVER` 改成 1.0 即可（一处生效）。
