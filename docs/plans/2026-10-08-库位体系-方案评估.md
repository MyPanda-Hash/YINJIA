# 库位体系 方案评估（仓库库位信息表 → 系统建模）

**输入：** `仓库库位信息表.xlsx`（业务 2026-09-28 提供，Sheet1 平面布局图 + Sheet2 库位编码总册）

**结论（先看这四句）：**

1. 当前库位 = **一张表 `bs_wh_loc` + 通用档案引擎**（`mode='archive'`），
   **没有任何库位专属后端代码**（只有 `PanelConfigService` 两处二维码标签注入）。
   它是**「平面自由文本 + 二维码标签」**模型 —— 能建档、能打标签，但**表达不了 Excel 的层次结构**，
   也**与库存链路零引用**（录了库位不影响账）。
2. Excel 实际是**约 1,100+ 个库位**的编码总册（含区间简写、排列继承、22 处截断待补），
   而库里只有 **5 行试录数据**（`da5x` / `d2` / `s` / `e` / `d`）。**这不是"补数据"能解决的，是模型要换代。**
3. **必须修正我上一版的判断**：层次化**不需要新增任何机制、更不需要第二张表** ——
   引擎早已支持**自参照**（`data_type='参照'` + `ref_panel=自己`），
   `DEPT` 部门树 / `FIN_ACC` 会计科目 / `FIN_EXP` 费用类别 / `REGION` 地区 **4 处先例**，
   且 `bs_dept` 就是**一张表装完整棵树**。库位照抄即可。**唯一做不到的是"级联筛选"**（引擎无此契约）。
4. 建议：**库位档案层次化（一期，仍是一张表）→ 单据挂参照（二期）→ 库位库存/扫码作业（三期，待定）**，
   **不推翻**现有 WHLOC 面板与二维码能力；**一期不新增表、不碰 `kucun`/`inh`/`outh`**。

## 一、Excel 里到底是什么

它不是"一张库位档案表"（不是"一行一个库位、列是字段"），而是**仓库规划资料**，两张 Sheet 语义完全不同：

### Sheet1 —— 平面布局图（老厂区）

| 项 | 内容 |
|---|---|
| 结构 | 一张俯视平面图：数字 `1..24` 成对排布（每格 = 一个货架列的 `1#位/2#位`），共 114 个数字格、唯一值 24 |
| 混入的空间元素 | `办公室` `洗手间` `过道` `货梯` `叉车` `客梯` `柱子` |
| 区域 | 包材区、辅料区、碳粉区1/2、成品区、呆滞区、不良品、胶粉区、设备区 |
| 价值 | **物理坐标**（哪排挨着哪个过道/货梯）+ 区域划分。做"库位地图""拣货路径"才用得上 |

### Sheet2 —— 库位编码总册（老厂区 + 新厂区 D仓）

**这才是权威的编码清单。** 编码规则可以从表头注释直接读出来：

```
B1-01-1/2  =  B仓1区 - 01排 - 1#位/2#位
└┬┘ └┬┘ └┬┘
 │   │   └─ 位号（一排货架的第几格/第几层）
 │   └───── 排号（货架列）
 └───────── 仓区码（仓 + 区）
```

老厂区（R4–R29）实测可解析：

| 列 | 区域 | 库位 | 列 | 区域 | 库位 |
|---|---|---|---|---|---|
| A–D | 成品仓（B仓）B1/B2/B3/B4 | 54 / 32 / 47 / 44 | J | 纸箱区 | 24 |
| E–F | 成品仓（C仓）C1 / C2 | 24 / 48 | K | 端盖区 | 25 |
| G | 炭粉区仓位 | 36 | I | **货架区（AH5–AH15）** | **截断待补** |
| H | 胶粉区仓位 | 12 | M/N/O | **无纺布区 / 网套区 / 标签区（AH1–AH4、AH17/18）** | **截断待补** |

**小计 346 条 + 22 处截断待补。**

新厂区 D仓（R31–R48）：

| 列 | 区域 | 库位 | 列 | 区域 | 库位 |
|---|---|---|---|---|---|
| A–C,E | 成品仓 D1 / D2 / D3 / D8 | 32 / 12 / 12 / 16 | K | 端盖区 | 12 |
| G–H | 炭粉区 | 72 / 216 | L | PP棉区 | 12 |
| I | 胶粉区 | 180 | M | 折叠棉 | 24 |
| J | 纸箱区 | 21 | N | 网套&布区 | 12 |

**小计 641 条 + 2 条排列继承规则（D4–D7、D9–D11，按模板复制约 +96）。**

> **规模实测：≥ 987 条可解析，实际约 1,100+**（区间去重低估 + 22 处截断待补）。
> 对照库里现状：**5 行试录数据**。

### 四类"非逐行"写法 —— 这是设计的钥匙

| 写法 | 实例 | 含义 | 系统必须支持 |
|---|---|---|---|
| 一格多库位 | `B1-01-1/2` | 一个货架排有 2 个位 | 批量拆解 |
| 顺序号区间 | `1-36` `1-24` `1-14` `1-7` `1-12` | 某区下连续编号 | **按规则生成，不可能手录** |
| 排列继承 | `D2-D7库位排列一样` | D4–D7 复制 D2/D3 的排布 | 模板复制 |
| 原文截断 | `AH5-1/2/3-1...` | 表里没写完 | **必须业务补全（22 处）** |

**另发现 3 处疑似笔误**，需业务确认：`B-1-18-1/2/3`（R23，应为 `B1-18-…`）、`41-20-1/2/3`（R29，应为 `A1-20-…`）、`4H16-1/2/3-1...`（R29，应为 `AH16-…`）。

## 二·补、当前库位实现全貌（**只有一个表**，跑在通用档案引擎上）

> 2026-10-08 补测。这是"如何处理"的事实基础：**库位没有专属代码，它就是约 40 个 `mode='archive'` 档案面板中的一个。**

### 补.1 分层落点

| 层 | 落点 | 内容 |
|---|---|---|
| **表** | `bs_wh_loc` | **唯一一张表**（12 业务/审计列 + 20 备用列，5 行试录） |
| **元数据** | `yj_panel` | `WHLOC / 库位 / category=基础档案 / mode=archive / line_table=bs_wh_loc / pk_col=id / detail_key=locations / page_size=50` |
| **元数据** | `yj_field` | 6 行：仓库(参照 WH.仓库名称) · 仓库编码 · 库位编码 · 库位地址 · 停用 · 备注 |
| **元数据** | `yj_role_panel` | 全角色 `view,query` |
| **元数据** | `yj_translation` | 面板译名 ×9 语言 + 字段译名 ×9 语言 |
| **后端** | `PanelConfigService` 第 107–110 / 194–203 行 | 注入 `qrLabel` + `qrLabelKey=库位编码` + `qrLabelScopeKey=仓库` + `qrLabelKind=whloc`。**除这 2 处外零专属代码** |
| **前端** | `menus.js:389` | 基础数据 → 库位（紧跟「仓库」） |
| **前端** | `PanelxList.vue:3753-3789 / 6386-6406` | 通用档案列表 + 二维码标签勾选分支 |
| **前端** | `print-formats.js:366-410` | `locationCardQrText` 三段码 + `printLocationCards` 75×100mm |

**CRUD 全部走通用引擎**，没有为库位写任何 Service：
- 查询：`QueryService.queryArchive` — **全量返回**，上限 `ARCH_LOAD_CAP = 50_000` 行
- 保存：`ButtonService.saveArchive` — 全量 upsert，**缺席行 = 已删除**（另有"带筛选保存"误删护栏，2026-10-03 商品面板踩过 3873 行）

### 补.2 引擎能力实测（决定"能怎么实现"）

| 能力 | 支持 | 证据 |
|---|---|---|
| 档案面板 = **扁平全量网格**（无表头字段） | ✅ | `buildArchiveConfig`：`place` 对 archive **强制 detail**；`dataSchema` 仅"备注" |
| 行数规模 | ✅ 50,000 | `QueryService.ARCH_LOAD_CAP` —— 1,100 库位仅占 2% |
| **参照字段（含自参照）** | ✅ **4 处先例** | `DEPT.上级部门→DEPT` · `FIN_ACC.上级科目→FIN_ACC` · `FIN_EXP.上级类别→FIN_EXP` · `REGION.上级地区→REGION`，全部 `data_type='参照'`、`ref_panel=自己` |
| 同表层次冗余列先例 | ✅ | `bs_dept`：`上级部门` + `上级编码` + `上级id` + `级次` + `长编码` + `部门全称` + `是否叶子节点` 全在**一张表**里 |
| 参照双模（≤20 下拉 / >20 弹窗带搜索） | ✅ | `REF_DROPDOWN_THRESHOLD = 20`（`PanelxList.vue:2108`） |
| 参照**静态**过滤 `ref_filter` | ✅ | `parseRefFilter` 只解析常量 `k=v`（如 `单据状态=已归档`） |
| 参照**级联**（按另一字段的值动态过滤） | ❌ **不支持** | `ref_filter` 无 `$字段` 占位语法；引擎无此契约 |
| 树形网格 / treeGrid | ❌ **引擎无** | 全库仅 2 处树 UI，都是**定制页**：`OrgAdmin.vue`（`el-tree-select` 部门）、`ShareFileCenter.vue`（`el-tree` 分类） |
| `WHLOC` 被其它字段参照 | ❌ **零引用** | `SELECT … FROM yj_field WHERE ref_panel='WHLOC'` → **空**（库位是一座孤岛） |

### 补.3 由此得出的三条硬约束

1. **层次 = 单表自参照，不是新表。** `DEPT` 已经在做同一件事（部门树 + 上级部门参照 + 级次/长编码冗余列），
   **零代码改动**即可照抄到 WHLOC。**我原方案里"需要新增结构"的判断是错的 —— 机制早就有了。**
2. **级联筛选做不到。** 想"选完仓库，库区下拉只剩该仓的"必须改引擎（`ref_filter` 加动态变量）或写定制页，
   **不在"单表"范围内**。→ 层次列应做成**普通列**（数据本来就是批量生成的），只把 `上级库位`/`仓库` 做成参照。
3. **第二张表只在"库位级库存"时才需要。** 不做库存维度 = 永远一张表。

## 三、诊断：现在这套撑不住在哪

| # | 问题 | 证据 / 后果 |
|---|---|---|
| 1 | **仓库用名称关联** | `bs_wh_loc.仓库` 存仓库名称 + 冗余 `仓库编码` 两列。`库存表清单.md` 坑 6 记过 `bs_wh` 重名导致按名称 join 翻倍；改仓库名即断链。**应只存 `仓库编码`** |
| 2 | **库位编码只承诺"仓内唯一"** | 为此前端做了 `qrScopeKey` 复合行键（`仓库\u0001库位编码`）、二维码三段来绕开重码。**全局唯一能一次性消掉这三处补丁** |
| 3 | **`库位地址` 是自由文本且进了二维码** | 二维码 = `仓库编码@库位地址@库位编码`。改个描述 → 已打印的码内容就"漂"了。地址与编码语义重叠 |
| 4 | **无层次列** | 厂区/仓/库区/排/位全丢。不能按"哪个区的所有库位"筛选、聚合、批量生成 —— **Excel 的层次信息 100% 浪费** |
| 5 | **无 `库位类型` / `存储类别`** | 炭粉区、胶粉区、PP棉区、网套区是**用途约束**（这些位只能放这类料）。表达不了 → 扫码上架无法校验"这料能不能放这" |
| 6 | **无状态 / 容量** | 做不了空位推荐、占用率、满位预警、盘点 |
| 7 | **与库存链路零引用** | `kucun`/`inh`/`outh` 无库位维度 → **录了库位不影响任何账** |
| 8 | **与单据 20 处 `仓位*` 字段不通** | 那些字段 `ref_panel=null`（无参照）、`hidden=1`（不显示）、实测零数据 → 库位档案建了，**单据上根本选不到** |
| 9 | **术语两套并存** | 新的是「库位」（`bs_wh_loc`、WHLOC 面板、`bs_wh.库位`），老的是「仓位」（20 处字段）。同一概念两个词 |
| 10 | **WH 面板的 `库位` 单值字段语义打架** | `migrate-wh-location.sql` 自述"不做仓位管理体系"，一个仓库一个"库位"字符串；与"一个仓库多库位档案"直接冲突。**应废弃或降级为「默认库位」** |
| 11 | **数据规模差 200 倍** | 应建 ~1,100 条，实有 5 条试录 |

## 四、建议方案

### 决策 1｜做多重？（决定整个方案的重量）

| 档 | 含义 | 代价 |
|---|---|---|
| **A 档·档案化** | 库位 = 主数据 + 标签 + 单据上一个下拉。**库存仍按仓库记账** | 低。不动 `kucun`/流水/报表 |
| **B 档·库存化** | 库存按库位记账，单据必选库位，扫码上架/拣货/盘点 | 高。动 `kucun` 主键、`inh`/`outh` 列、移动加权成本分区、启动自检、4 张报表 |

**建议：A 档一期落地 + 结构上为 B 档预留。**

理由：20 处 `仓位*` 字段零数据说明业务**从没按库位管过**；`库存表清单.md` §2 已逐条登记"为什么 `kucun` 分区不能轻易加维度"（批号进分区键会让 51% 的分区只出不进、成本恒 0）。
**一次到位冲 B 档 = 拿成本核算的准确性去赌一个还没被业务验证的流程。**

### 决策 2｜术语统一为「库位」

物理列名**不建议批量改名**（牵动面板字段、参照、报表、审计、`采购链四单字段与基线文档`）。做法：

- ✅ 把 20 处 `仓位*` 字段在 `yj_field` 里 **`label` 正名为「库位」**、**`ref_panel='WHLOC'` / `ref_field='库位编码'`**、按需放开 `hidden=0`
- ✅ `bs_wh.启用仓位管理` **正名为「启用库位管理」**，保留为"哪些仓库走库位管理"的阀门
- ✅ 老物理列名登记进 `tools/db-legacy-whitelist.txt` **冻结**，新代码不再新增 `仓位` 字样

### 决策 3｜库位表结构：层次化 —— **仍然只用这一张表**（自参照 + 冗余层次列）

Excel 编码本身就是 4–5 层树（`厂区 > 仓/区 > 排 > 位[/层]`）。

**关键修正（见 §二·补）：层次不需要任何新机制。** `DEPT` 部门树早就在单表里做完了同一件事：

```sql
-- 现成的先例（tools/migrate-base-fields.sql:168-170）——库位照抄这一行即可，零代码改动
INSERT INTO yj_field (panel_code, col_name, label, data_type, place, seq, width, editable, required, hidden, visible,
                      ref_panel, ref_field, display_field)
VALUES ('DEPT', N'上级部门', N'上级部门', N'参照', N'detail', 50,140,1,0,0,1,
        N'DEPT', N'部门编码', N'部门名称');
```

`bs_dept` 也是**一张表**装完整棵树：`上级部门` + `上级编码` + `上级id` + `级次` + `长编码` + `部门全称` + `是否叶子节点`。

**目标结构（`bs_wh_loc` 加列，仍是同一张表）：**

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | bigint | 主键（保留） |
| `库位编码` | nvarchar(60) | **全局唯一**（唯一索引）。规则化生成，二维码内容、扫码反查键 |
| `库位名称` | nvarchar(120) | 现场叫法（如"成品B仓1区01排1位"） |
| **`上级库位`** | nvarchar(60) | **参照 WHLOC.库位编码，display=库位名称** ← 照抄 `DEPT.上级部门`，树就成立了 |
| `上级库位id` / `上级编码` | bigint / nvarchar(60) | 与 `bs_dept` 同款冗余（供同步/追溯；`上级库位` 为人工/参照列） |
| `级次` / `长编码` / `是否叶子节点` | nvarchar / bit | 与 `bs_dept` 同款（`长编码` 让子树查询免递归） |
| `厂区` / `仓库编码` / `库区` / `排号` / `位号` / `层号` | nvarchar | **冗余层次列**（普通列，非参照 —— 引擎不支持级联） |
| `库位类型` | nvarchar(30) | 货架位/地面堆垛/纸箱区/端盖区/PP棉/折叠棉/网套/标签/炭粉/胶粉/不良品/呆滞/设备/柱 |
| `存储类别` | nvarchar(200) | 允许存放的物料大类（多值）；上架校验用 |
| `是否可拣货` / `停用` | bit | 默认 1 |
| `库位地址` | nvarchar(200) | **保留但降级为"人工补充说明"，不再进二维码** |
| `备注` / `状态` / `asp_*` / `备用1-20` | — | 保留 |
| `仓库` | nvarchar(200) | **保留做兼容**（存量/参照展示），新逻辑改用 `仓库编码` |

**关键四点：**
1. **仓库编码唯一承载仓库关系** —— 去掉按名称 join 的隐患（`bs_wh` 重名即翻倍）
2. **库位编码全局唯一** —— 消掉前端 `qrScopeKey` 复合行键、二维码三段两处补丁
3. **层次列冗余落库** —— 支持"按仓/区/排筛选""按规则批量生成"
4. **`上级库位` 走参照** —— 树形关系成立，且**完全复用引擎既有能力，不新增表、不改后端**

> ⚠ **级联选择做不到**：想"选完仓库，库区只剩该仓的"需要改引擎（`ref_filter` 加动态变量）或写定制页。
> 因此 `厂区/仓库/库区/排/位` 这几列做成**普通列/下拉**（数据本就是批量生成的），只 `上级库位` 与 `仓库` 做参照。

### 决策 4｜数据靠"批量生成"，不靠手录

1,100 条不可能手敲。建议提供 **「库位批量生成」** 入口：

```
选择：仓库 + 厂区 + 库区 + 排号区间 + 位号集合 + 层数 + 库位类型 + 存储类别
  ↓ 预览（列出将生成的编码，冲突高亮）
  ↓ 生成（幂等：已存在则跳过或提示）
```

迁移脚本里也**按规则生成**（`WHILE` 循环拼编码），比 1,100 行手写 INSERT 可靠得多。
生成时**同时写 `上级库位`**（如 `B1-01-1` 的上级 = 排节点 `B1-01`，或直接挂库区 `B1`）——层次是生成的副产品，不是手工维护的负担。

### 决策 5｜二维码改单段（兼容旧码）

```
现在：仓库编码@库位地址@库位编码     ← 地址是自由文本，会漂
建议：库位编码                        ← 全局唯一，扫码直接命中
兼容：解析时按 @ 切分，取最后一段 → 新旧码都能读
```

### 决策 6｜库位库存 —— **挂起，暂不做第二张表**（待业务确认）

`bs_wh_loc_stock` 是**第二张表**。既然当前实现只有一张表，**这一块不并入一期**，先明确它是否真的需要：

| 选项 | 内容 | 代价 |
|---|---|---|
| **⑥-a 不做**（默认） | 库位只做档案 + 标签 + 单据选择，**库存仍按仓库记账** | 一期零风险，永远一张表 |
| ⑥-b 新增库位库存表 | `bs_wh_loc_stock(库位编码,物料编码,批号,数量)`，与 `kucun.yl` 对账 | +1 张表；需出入库单据联动 |
| ⑥-c 下沉到 `kucun`/`inh`/`outh` | 库位进结存主键与流水 | **高风险**：动移动加权成本分区、启动自检、4 张报表 |

**建议：先按 ⑥-a 交付一期，看业务是否真的按库位要数 —— 20 处 `仓位*` 字段零数据说明它从没被验证过。**
真要上，走 ⑥-b（加表不改账），**不要**直接做 ⑥-c。

## 八、我的一句话建议

**先把"库位是什么"这件事定下来（层次 + 唯一码 + 类型），再谈"库位管什么"。**
现在这套的根问题是**它把库位当成了一段可打印的字符串**，而不是仓库里的一个**有位置、有归属、有用途约束的坐标**。
Excel 已经把坐标体系画好了 —— 我们要做的是把它**照抄成结构**，而不是继续往 `库位地址` 这个自由文本框里塞。

**而且好消息是：这个"结构"不用买新的。** 系统里 `DEPT` 部门树已经在做一模一样的事
（单表 + 自参照 + 级次/长编码冗余列），**照抄那一行 `yj_field`，库位树就成了**。
真正缺的不是机制，是**把 Excel 的编码规则翻译成数据**（仓映射、编码规则、22 处截断）。
