## 一、流转机制(先弄清"数据应该怎么过去")

| 路径 | 触发 | 落库方式 | 是否受映射表保护 |
|---|---|---|---|
| **A. 推式/选单(分批生单)** | 采购订单「生成送料暂收单」、暂收单「生成来料检验单」/「生成采购入库单」、检验单选单 | `PanelConfigService.buildSelectConfig` 产出的 `headerMap`/`detailMap`,由 `PushGenerateHandler` 按标签写入 | ✅ 有同名 + 同义词兜底 |
| **B. 审核自动生单** | 检验单审核 → 采购入库单 / 暂收退料单(`ButtonService.inspAutoPurchaseIn` / `inspAutoReturn`) | **手写「中文标签」清单** → 标签经 `labelsToCols()` 转列,`retainAll(tableCols())` **对不上的标签静默丢弃** | ❌ 手写路径**不走**同义词表 |
| **C. 保存镜像(raw SQL)** | 暂收单保存 → 同步到已存在的检验单(`ButtonService.syncInspFromSlRecv`) | 手写 `UPDATE ... SET d.列 = s.列`(**按列名**) | ❌ 按列名硬写 |

要点:**同义词表只保护 A 路径**;B/C 手写路径必须自己把"目标列名/标签"写对,写错就是静默丢失。
另:**暂收单审核不会**自动生成检验单(`audit()` 只挂了 QC_INSP 两个钩子),只有推式按钮 + 保存镜像两条路。

链路口径(2026-09-22 用户口径):**所有采购订单都必须先生单到送料暂收单**,采购订单的
「生成采购入库单」免检直达出口已整体下线(按钮 + 选单来源两处同时改);去向改由送料暂收单人工分流 ——
「生成来料检验单」(走品检)或「生成采购入库单」(判为免检直达)。落地链路:

```
采购订单 ──生成送料暂收单(分批)──▶ 送料暂收单 ──┬─生成来料检验单──▶ 来料检验单 ─审核─▶ 采购入库单 + 暂收退回单
                                              └─生成采购入库单────────────────────▶ 采购入库单(是否来料检验=否)
```

映射表的两个硬上限(`PanelConfigService.java:1080`、`:1102`):
**表头 7 条**(含「来源单号」1 条)、**明细 14 条**,按来源字段 seq 先到先得,超出的**直接 break**(静默丢弃)。

`单价`、`采购订单行号 → 源单行号`、`批次号`;表头 `单据日期`、`供应商`、`采购订单号`。

### 2.3 已修:规格命名(用户点名的那个)

- **根因**:全链 5 张明细表里只有 `sl_recv_detail` 把"规格"列命名为 **`型号`**,其余都叫 **`规格型号`**;
  暂收→检验的镜像 SQL 按**列名**写 `d.型号 = s.型号` → 值落进 `qc_insp_detail.型号`(界面**不显示**的列)
  → 实测 **检验行 规格型号 0/40、退料行 0/10、入库行 81/149**。
- **附带发现(严重)**:该镜像 SQL 引用的 `sl_recv_detail.型号` 在本次改动前**已不存在**(改名遗留),
  所以"检验单还是草稿时保存暂收单"会直接抛 `Invalid column name '型号'`,而检验单已审核时又被门槛提前 `continue` 静默跳过
  —— 这正是第 1 条(0/22)的直接原因。
- **修法**(`tools/migrate-spec-unify.sql` + `ButtonService` 三处):
  ① `sp_rename sl_recv_detail.型号 → 规格型号`(带守卫)+ 列中文注明;
  ② `yj_field` 的 QC_RECV 明细字段 `型号 → 规格型号`(列名与标签同改);
  ③ 存量回填(只填空值):检验行 ← 暂收行、入库行/退料行 ← 检验行,走 `form_flow_link` 精确对齐 + 同物料兜底;
  ④ 代码:镜像改 `d.规格型号 = s.规格型号`;检验→入库/退料 取值改 `ISNULL(NULLIF(规格型号,N''),型号)` 兼容存量行。
- **实测**:检验行 **40/40**、退料行 **10/10**、入库行 **105/149** 有值;链路逐行比对 **0 处不一致**;
  暂收单界面列头显示「规格型号」。后端已重建重启,`_verify-spec-unify.mjs` 全 PASS。

## 三、成因分类(回答"是命名不同还是新增字段")

| 成因 | 含义 | 典型字段 |
|---|---|---|
| **A. 命名不统一** | 同一概念在不同单据叫不同名字,靠同义词兜;手写路径不兜 | `规格型号`/`型号`(**已修**)、`日期`/`单据日期`、`单位`/`计量单位`、`采购订单行号`/`源单行号` |
| **B. 目标面板缺字段登记** | 目标表**有列**,但目标面板没登记 `yj_field` → 映射表"看不见"这个落点 | `PURCHASE_IN`:外部单据号/来源单据/来源单号;**`QC_INSP` 头**:供应商代码/业务员/部门/部门名称;`QC_RECV`:仓库 |
| **C. 目标表缺列** | 新增字段没落到下游表 | 暂收侧:数量2/计量单位2/税率%/含税单价/含税金额/预计到货日期/现存量/折扣%;入库/退料侧:送检数量/损耗/损耗率/生产日期/部门名称/入库单号 |
| **D. 生单代码没写/写错标签** | 列也在、字段也登记了,手写清单里就是没写(或写了目标不存在的标签) | 入库行 `是否来料检验`、`仓库`;退回行 `单位`、`不良原因`、`剩余数量`;退回头 `单据日期`(写了「日期」) |
| **E. 机制上限** | 头 7 / 明细 14 条**硬截断**,超出静默丢弃 | 暂收→检验:明细同名循环在 `部门` 处截断 → `日期`、`部门名称` 落榜 |

## 四、待修清单(按建议优先级)

**P0(影响面最大、都在本链上)**

1. **退回头「单据日期」全空(9/9)** —— `ButtonService` 写的是标签「日期」,`QC_RETURN` 的字段叫「单据日期」→ 一行代码。
2. **`PURCHASE_IN` 登记「外部单据号/来源单据/来源单号」** —— 列早就有、代码也 `put` 了,只是面板没登记 → 全库 86 张入库单 0 值;
   它同时让映射同义词 `单号 → 外部单据号` 恒失效,**转 ERP 的源单关联 `src_bill_no` 因此没有依据**。
3. **`QC_INSP` 头登记「供应商代码/业务员/部门/部门名称」+ 放开镜像门槛** —— 现在唯一写入者是"仅草稿期"的镜像,
   实测 0/22;它同时卡死下游 `采购入库单.供应商编码`(0/13)。

**P1**

4. 入库行 `是否来料检验`(有列有字段,生单没写)、`仓库`(需先给 `qc_insp_detail.仓库代码` 登记字段)。
5. 退回行 `单位`(选单映射本可覆盖,手写路径漏了)、`不良原因`/`剩余数量`(缺来源,需产品口径确认)。
6. `QC_RECV` 明细 `仓库`(表有列,面板无字段)。

**P2(机制改善)**

7. 头 7 / 明细 14 的**硬截断**改为按需裁剪(或至少在被截断时记日志),避免"字段增删改变被挤掉对象"的隐形坑。
8. 清理形同虚设的同义词:`QC_RECV|QC_INSP` 的 `日期→日期`(目标没有该标签)。
9. 统一"单位"命名(采购订单侧 `单位` vs 其余 `计量单位`)——目前靠同义词接通,不影响数据,但登记口径应统一。

**待产品确认(不建议直接加列)**

- 暂收侧的金额/税额/含税系列、检验侧的损耗/损耗率/生产日期、入库/退料侧的部门名称/入库单号:
  属于"下游业务是否真需要"的问题,需业务拍板后再补列(补列成本 = 建列 + 字段 + 译名 + 生单映射)。
