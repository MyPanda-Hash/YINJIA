> 范围:**送料暂收单 SL_RECV / 来料检验单 QC_INSP / 暂收退回单 QC_RETURN** 三张单的字段,
> 对照参照库备份 `HSDZ_MES_backup_2026_08_28_230001_6527824.bak` 补充;
> 并归并同名的空面板(删 QC_RECV、SL 面板改用 QC 命名)。
> 状态:**分析稿(2026-09-20),待拍板后实施**。
> 起因:三单的字段曾是「简化草稿 → 按 legacy 重建 → 多轮补丁」的叠加产物,
> 与参照库现网单据的字段集从未做完整对账,存在「参照库有、我们没有」的通用字段。

## 一、结论(先给答案)

1. **能补,但不是照搬。** 参照库是同款 legacy MES 在**光缆厂**的现网库
   (字节扫描:含「光缆」960 处、「护套」178 处,而「银嘉/铝棒/烧结/炭棒」0 处),
   字段里混着大量线缆行业特有项(护套颜色/纱型/外径/膜厚/测点/紧包编号…),这些不能进银嘉。
2. **参照库里与三单对应的现网单据是**:
   | 我们的单 | 参照库对应物 | 字段量 |
   |---|---|---|
   | 送料暂收单 SL_RECV | **来料入库单**(表 `inh`)头 + 来料入库单明细 | 头 18 / 行 52 |
   | 来料检验单 QC_INSP | **品检明细**(`pjjl`)/ 品检数据 / 扫码全检 | 31 / 33 / 32 |
   | 暂收退回单 QC_RETURN | **没有独立退回单**;退款语义挂在来料入库单行的「退料数量/报废数量」+ 菜单「生产退料」 | — |
3. **可补的通用字段约 30 项**(详见 §三),其中采购链口径的 9 项(P0)建议优先补;
   包装/物流 9 项(P1)看银嘉是否需要;其余为行业特有,不搬。
4. 面板侧按你的口径归并:**删掉 0 行的 QC_RECV 面板**,SL 面板改用 **QC 命名**(§四)。

## 二、取证方式与可信度(必读)

**为什么不能直接查参照库**:参照库只有 `.bak`(45MB,`D:\little_mes\数据库\` 原件,
仓库副本在 `参照数据库（不上传仓库）/`);本机 `yinjia` 账号**无 sysadmin/dbcreator**(实测
`IS_SRVROLEMEMBER('sysadmin')=0`),不能 `RESTORE`,也不能给自己授权;本机另有
`HSDZ_MES_inspect`(2026-09-14 10:22 建)但 `yinjia` 无库内映射,登录被拒。

**本次取证做法**(只读文件、不碰任何库):
- `tools/_bak-scan.cjs`:按 UTF-16LE 扫 .bak 字节,提取含中文的字符串 → `tools/_bak-strings.txt`
  (128,299 条;4MB,生成物,不入库)
- `tools/_bak-parse.cjs`:把元数据行 `0<面板><面板>00<字段><表码>` 拆成「面板 → 字段」清单
  → `tools/_bak-panels.md`(930 个面板/元数据块)。例:
  `0来料入库单明细0发货数量inh`、`0品检明细0检验编号pjjl`

**可信度边界**(实施前请知悉):
- 字段**存在性可靠**——串来自元数据行原文,非推测;
- **不可知**的:物理列名、类型、长度、顺序、是否必填/隐藏、下拉字典;
- 检出的是**全库面板并集**,个别字段可能实际属于相邻档案面板(如 `测点/膜厚/镀种`
  实属「客户物料编码」档案,不是来料入库单行字段);
- 因此本文清单按「**建议补**」给,**不是**直接可执行的 DDL。要落到列级精度,需按 §六 还原一次 .bak。

### 3.4 先回答:参照库里有「送料暂收单 dh」和「来料检验单」吗?

**都没有。** 逐项核实(全部基于 .bak 字节扫描的元数据行):

| 你问的 | 参照库实际情况 | 证据 |
|---|---|---|
| 送料暂收单 | **不存在**。全库字符串里「暂收」0 命中、「送料」0 命中 | `grep -c 暂收` = 0;`grep -c 送料` = 0 |
| 表 `dh` | 存在,但 `dh` 是**委外工单**的表码,不是暂收单 | `0委外工单00产品编码dh`、`0委外工单00领料单号dh`、`0委外工单00入库数量dh`、`0委外工单00委外日期dh`(共 10 个字段挂在 `dh`) |
| 来料检验单 | **没有这个名**。入厂检验是菜单「**进料检验**」(T+ 体系叫法),数据落在**品检系**面板:品检明细 / 品检数据 / 扫码全检(表码均 `pjjl`),过程巡检另用 `xjjl` | `0品检明细0检验编号pjjl`、`0扫码全检…检验结论pjjl`、`0过程巡检…检验员xjjl` |

> **⚠ 需要更正的历史注释**:`tools/migrate-qc-3docs-rebuild.sql` 抬头写「暂收入库单(legacy **dh**)/检验单(legacy **jyd**)」——
> 这两处表名归属在参照库里**对不上**:`dh` 是委外工单,`jyd` 0 命中。
> **不改那个脚本**(改动会变哈希 → DbSync 重跑,而它开头的 `DELETE FROM yj_field WHERE panel_code IN (...)` 会清掉后续脚本补的字段),
> 仅在此更正记录:当年重建时的字段来源应是**来料入库单系(inh)+ 品检系(pjjl)**,不是 dh/jyd。

### 3.5 追问:「来料入库单和送料暂收单是一致的吗?还有什么别的表也可能是吗?」

**不一致。** 参照库的 `inh` 不是「来料入库单专用表」,而是**通用入库宽表**(实测 **44 个面板共用**),
「来料入库单」只是它的一个面板视图:

| 表码 | 共用面板数 | 同族面板(节选) |
|---|---|---|
| `inh` 通用**入库**宽表 | 44 | 来料入库单(明细)、采购入库明细、产品入库明细、其他入库明细、委外入库(明细)、出入库明细_入库、订单追踪_来料/外入/产品、应付账款 … |
| `outh` 通用**出库**宽表 | 57 | 销货出库单明细、生产领料明细、委外领料明细、超额领料明细、其他出库明细、订单追踪_领料/委外/销货、应收账款 … |
| `pjjl` **品检**记录 | 10 | 品检明细、品检数据、扫码全检、品质追溯_品检 |
| `xjjl` **巡检**记录 | 6 | 过程巡检、巡检明细 |
| `dh` | 1 | 委外工单(不是暂收单,见 §3.4) |

由此得到三条结论:

1. **语义不同**:参照库「来料入库单」是**入库单**(审核即计入库存);我们的「送料暂收单」是**暂收**
   (物料到厂暂存,检验合格才转采购入库)。两者是**流程前后两段**,不是同一张单。
2. **字段同源**:因为同族入库单共用 `inh` 的同一套列,「来料入库单」的列集 ≈ 采购入库/其他入库/委外入库的列集,
   所以我们行上 15 个字段能一一对上(§附-2),缺的 10 个也出自同族 —— **换别的入库面板看,列集不会更多**。
3. **没有别的表能提供额外字段**:检验侧同理(`pjjl` 三个面板列集基本重合,并集已并入 §附-3);
   退回侧 `outh` 族里**没有**退货/退料面板(面板名含「退」= 0 命中),参照库把退料表达为入库行上的
   「退料数量/报废数量」+ 菜单「生产退料」(制程领料退回,不是采购退回)。
   → 三单的字段补充来源到此为止,不存在「还有一张没看的表」。

## 六、如何还原 .bak 做列级终校(需管理员)

```powershell
# ① 先看逻辑文件名(两条 MOVE 的目标名要与之匹配)
sqlcmd -S 127.0.0.1,1433 -E -Q "RESTORE FILELISTONLY FROM DISK='D:\little_mes\数据库\HSDZ_MES_backup_2026_08_28_230001_6527824.bak'"
# ② 还原为独立库(不要覆盖 HSDZ_MES)
sqlcmd -S 127.0.0.1,1433 -E -Q "RESTORE DATABASE HSDZ_MES_REF FROM DISK='D:\little_mes\数据库\HSDZ_MES_backup_2026_08_28_230001_6527824.bak' WITH MOVE 'HSDZ_MES' TO 'D:\SQL\HSDZ_MES_REF.mdf', MOVE 'HSDZ_MES_log' TO 'D:\SQL\HSDZ_MES_REF_log.ldf', RECOVERY"
# ③ 授权给应用账号(只读即可)
sqlcmd -S 127.0.0.1,1433 -E -Q "USE HSDZ_MES_REF; CREATE USER yinjia FOR LOGIN yinjia; ALTER ROLE db_datareader ADD MEMBER yinjia"
```

还原后即可用 `sys.columns` + `MS_Description` 把本清单逐列**定名/定型/定序**,
并可顺带核对参照库的 `yj_field` 等元数据行是否被字节扫描误并。
