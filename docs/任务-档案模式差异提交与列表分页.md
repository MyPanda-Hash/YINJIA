# 任务单：档案模式改为「差异提交」+ 列表分页（解决 INV 商品档案一次请求 4 MB）

> 本任务单可整份转交其他 agent 执行。**结论先行**：`INV`（商品档案）是 `archive` 模式，
> 因保存语义为「缺席行=已删除」而必须**全量返回** 3838 行 = **4,020,278 B**；
> 空闲 786 ms，机器有并行负载时实测 28~36 s，是当前唯一还没修的真实热点。
> 先改保存契约为差异提交，列表才可安全分页。

## 二、目标（可量化）

1. **保存契约改为差异提交**：前端只回传**变更行**（新增/修改）+ **显式删除集**；
   后端据此 upsert / 删除，**不再**把"未回传的行"当作已删除。
2. **列表可安全分页**：`INV` 列表请求返回 ≤ 1 页（默认 50 行/页）且响应 **< 500 KB**、
   **< 1 s**；翻页/搜索/条件过滤走库侧（`OFFSET/FETCH` + `WHERE`），不再受 `ARCH_LOAD_CAP` 影响。
3. **语义零回退**（硬要求，逐条自证）：
   - 全量新增：一次性导入 N 行（N > 1 页）→ 全部入库；
   - 修改：只改 1 行 → 仅该行变化，其它行**逐列比对无差异**；
   - 删除：勾选删除 1 行 → 仅该行消失，**其它行不受影响**（这正是旧实现靠"全量返回"防的坑）；
   - 边界：一个分批保存（先存第 1 页改动，再存第 2 页改动）→ 两次结果与一次全量保存一致；
   - 「同值护栏」仍需在"提交行数 > 阈值"时生效（阈值语义改为**本次提交行数**）。
4. **不改口径**：不动 `bs_inv` 列、不动 `asp_cancel` 软删语义（删除仍走现有软删/归档规则）。
5. `archive` 模式是**通用机制**，其它档案面板（若存在）必须同步受益或明确不受影响 —— 落地前先列出
   `SELECT panel_code,name,line_table FROM yj_panel WHERE mode='archive'` 的全部使用者并在报告里注明。

## 三、设计（建议，可优化但要写清偏离理由）

- **后端**：`saveArchive` 的入参增加差异字段（建议 `detail.<tabKey>` 只含变更行，另加
  `deletedIds: []` 与 `mode:'diff'`）；为兼容旧调用，保留 `mode:'full'` 分支（旧全量语义），
  但前端默认走 `diff`。差异提交时按 `id` 做 upsert；`deletedIds` 逐条按现有删除规则处理
  （软删 `asp_cancel` 或物理删，沿用 `saveArchive` 现有规则，不要新造语义）。
- **前端**：档案虚拟单渲染改为**按页取数 + 本地改动集**（`changed` Map<id,row> + `newRows` + `deletedIds` Set）；
  保存只发这三样；保存后按当前页重新取数并清空改动集。
- **查询**：`queryArchive` 增加分页分支（保留 `mode/参数` 兼容），`totalSize` 走 `COUNT(*)`。

## 七、施工进度与设计修正（2026-09-22，第一步已落地）

### 7.1 已完成：后端「差异提交」能力（向后兼容，未改任何现有行为）

`ButtonService`：

- `save()`：解析 `body.diffSave`（布尔）与 `detail.deletedIds`（数组），透传给 `saveArchive`；
  **未带 `diffSave` 的旧调用仍是「整表 upsert，缺席行=已删除」原语义**（Excel 导入、其它调用方零影响）。
- `saveArchive(def, items, user, diffSave, deletedIds)`：
  - `diffSave=true` → 只按 `deletedIds` 软删（新增私有方法 `softDeleteArchiveRows`，空集不动、幂等），
    **未回传的行一律保留**；数据量护栏改为按「本次提交行数」判定（整表提交仍按库里存活行数判定，护栏语义不丢）。
  - 修改记录（`yj_archive_change_log`）在差异提交下把「未回传但存活」的行并入 keep 集，
    否则会把整表未改动行误判成「删除」。
- `mvn -DskipTests compile` 通过（exit=0）。

### 7.2 ⚠ 施工中发现的设计修正：档案列表不能"直接换成服务端分页"

`PanelxList.vue` §3152 的注释写得很清楚：档案大表**前端本来就是内存分页**
（"数据全量驻留内存（保存语义'缺席行=已删除'不变），DOM 只渲染当前页"），
而且 `blockRows()` 里**列过滤 `applyColFilters`、高级筛选 `applyAdvFilters`、视图排序 `sortViewRows`
全部在前端基于全量行计算**（§3145-3150），`QR 标签勾选`（§3161-3193）也跨页自管。

因此 §二.2「列表直接分页」会连带改变这些行为（前端过滤/排序只能看到当前页、总数不再准确）。
**修正后的两步走**（每步独立可验证、独立提交）：

- **第 2 步（下一步）**：前端保存改发差异（`diffSave:true` + 变更行 + `deletedIds`），
  取数仍全量。行为与今天完全一致，只是把保存契约切换到差异提交 —— 为第 3 步扫清语义风险。
  变更集口径：载入时做基线深拷贝，保存时按行 JSON 比对得出"修改行"，新增行单列，网格删除动作进 `deletedIds`；
  服务端返回新 `id` 后必须刷新基线（否则第二次保存会把同一行当"新增"重复插入）。
- **第 3 步**：档案取数改服务端分页，同时把列过滤/高级筛选/排序迁到服务端（或明确降级为"仅当前页过滤"并写进 UI 提示），
  总数改由 `COUNT(*)` 下发；QR 勾选集改为按 id 记录、允许跨页累积。

> 第 2 步完成前，本次后端改动对线上无任何行为影响（`diffSave` 无人发送即原路径）。

### 7.3 用户口径修正（2026-09-22）：**以 ERP 为主，本地只做获取，不存在并发**

用户明确：需要"下拉"的 ERP 单据都在**金蝶 ERP 侧维护**，MES 本地只负责**获取（下拉）**，
**实际数据以 ERP 为准**；两侧不并发编辑。据此修正前面的判断：

1. **不做并发防护**：§7.2 与讨论中"打开页面期间 ERP 插/改行"的场景不成立（无并发），
   不需要版本号/时间戳校验，也不需要"保存前提示该行已被 ERP 更新"。
2. **ERP 行不是"要保护的本地数据"，而是"ERP 的镜像"**：本地对 ERP 来源行
   （`bs_inv.数据来源` ∈ {ERP导入, 金蝶同步}）的编辑是**临时的**——下一次下拉即被 ERP 覆盖。
   故不因"怕丢 ERP 行"而保留全量语义。
3. **差异提交仍然必须做**，理由是它自己的两条：
   - 它是**分页取数的前提**（不做它，分页保存一次就会误删未加载的行）；
   - 保存请求体从 4 MB 降到 KB 级（今天保存也在传 3838 行）。
4. **待定产品问题（决定第 3 步的设计）**：ERP 来源行在 MES 列表里**是否允许编辑**？
   - 若**不允许**（推荐，"以 ERP 为主"的直译）→ ERP 行在列表/表单中只读，本地只新增/维护"本地建档"行；
     第 3 步的服务端分页风险降到最低（不存在"跨页未加载的可编辑行"），甚至可直接关掉 ERP 行的编辑入口。
   - 若**允许** → 第 3 步必须把列过滤/排序迁到服务端（§7.2），否则跨页编辑会静默丢失。
5. **顺带的既有隐患（与本次无关）**：本地新增行可能与 ERP 同步进来的同一存货编码重复，
   建议加"新增行按业务键（`存货编码`）查重"守卫。
