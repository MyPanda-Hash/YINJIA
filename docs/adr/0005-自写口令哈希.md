# ADR-0005: 登录口令哈希改为仓库自写实现(PBKDF2-HMAC-SHA256, yj1)

- 状态：已接受（2026-09-22）
- 决策人：仓库所有者（拍板替换 BCrypt；方案二选一确认为「加盐+多轮迭代、SHA-256 内核也手写、不调 JDK MessageDigest」）
- 取代：《小程序对接-口令与账号.md》(2026-09-21)「保持 BCrypt」的建议——该建议在当时的约束下是对的，本 ADR 记录约束变了。

## 背景

用户口令存 `yj_user.password_hash`（nvarchar(400)），原实现为
`new BCryptPasswordEncoder()`（spring-security-crypto，`MesApplication.java`）。
2026-09-21 的调研文档（《密码哈希口径-BCrypt.md》《小程序对接-口令与账号.md》）
结论是"不必换、不建议换"：BCrypt 是行业基线，且实测证明把库里的值换成简单哈希后
正确口令也登不进去（编码器只认 BCrypt 格式）。

## 决策

**不再用任何现成密码学封装（JDK 的 MessageDigest/Mac/SecretKeyFactory、Spring 的 BCrypt 均不用），
由仓库自写口令哈希**，动机：算法细节留在本仓库可审、可移植（其它语言要复现时，
本仓库代码就是唯一权威规格，不必再依赖某语言的某个库实现）。

新方案（`backend/src/main/java/com/yinjia/mes/config/`）：

- `Sha256.java`：手写 SHA-256（FIPS 180-4）、HMAC-SHA256（RFC 2104）、
  PBKDF2-HMAC-SHA256（RFC 8018）、hex 编解码、常量时间比较。
- `YjPasswordEncoder.java`：存储格式 `yj1$<迭代50000>$<盐16B的hex32>$<派生32B的hex64>`（107 字符）；
  每次换随机盐（盐的随机源用 `SecureRandom`——随机源不是"加密函数"，自写伪随机等于白加盐）；
  迭代 50000 次 ≈ **49ms/次**，对齐原 BCrypt cost=10 的登录体感（50.3ms）。

**过渡（不可省）**：`matches()` 同时认存量 BCrypt（`$2a$/$2b$/$2y$`）；BCrypt 不可逆、
拿不到明文，故借"用户带着明文登录"这一次机会在 `AuthController` 里把哈希重写成 yj1
（`upgradeEncoding` 判定，失败只记日志、绝不影响登录）。库里 10 个存量账号因此不会被锁死。

## 验证（全部实测，证据在仓库）

1. `tools/verify/YjHashVerify.java`（生成 `docs/development/密码哈希-自写方案自测报告.md`）：
   SHA-256 对 NIST 向量 ×5、HMAC 对 RFC 4231 ×3、PBKDF2 对标准向量 ×6、编码器行为 ×28，
   **42/42 通过**；期望值另用 Python 标准库独立复算交叉验证。
2. 端到端（8091 临时实例 + 两个一次性测试账号，admin 与 8090 未动）：
   - Python 按同规格生成的 yj1$ 哈希 → Java 服务端**登录成功**（规格跨语言一致）；
   - 存量 BCrypt 账号登录成功且**库里自动升级为 yj1$**，升级后再登录走新路径；
   - 错误口令 / 不存在账号 → 409。测试账号已删、残留 0。

## 后果与代价（诚实口径）

- **抗 CPU 暴力与 BCrypt 相当**：单线程全枚举 6 位纯数字 13.3h（BCrypt cost10 为 14.0h）。
- **抗 GPU/ASIC 明显弱于 BCrypt**：bcrypt 的 4KB 随机访存天然抗并行，SHA-256 没有；
  GPU 爆破差距可达 2~3 个数量级。⇒ **口令长度/复杂度这道门不能省**（弱口令照破）。
- 自写密码学是行业公认反模式，本决策是所有者的明确取舍：换来的是**规格自包含、
  跨语言零依赖可复现**（Python 端到端已证）。SHA-256/HMAC/PBKDF2 均有公开标准与测试向量，
  实现正确性不靠"信自己"，靠对向量逐位比对——这条防线必须随实现保留。
- 换算法/调参：格式带版本号，加 `yj2$…` 即可平滑演进；`upgradeEncoding` 已支持
  "新格式但参数旧"时提示升级。
- 已知遗留（本 ADR 范围外，另行处理）：顶栏「修改密码」是前端假实现
  （`TopBar.vue:359` 写死 123456、不落库），后端本就没有改密接口。

## 被放弃的替代方案

- **保持 BCrypt**（2026-09-21 文档的建议）：抗 GPU 更强、久经考验；但依赖库实现、
  跨语言复现要移植 bcrypt（C→WASM 等，成本高且易错）。所有者不接受。
- 只自写"组合逻辑"、SHA-256 仍调 `MessageDigest`：代码更短；但不满足"不引用现成封装函数"的要求。
- 无盐单轮 MD5/SHA-256：直接否决——1 秒级可爆破且同口令同哈希，预计算表可用。
