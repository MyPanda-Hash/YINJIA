## 1. 字段能力契约(逐字段必查的 9 个维度)

**这是本方案的核心增量。** 每个新增/改动字段都必须在这 9 个维度上有明确取值,否则视为设计未完成(AGENTS.md:只插字段不配能力 = 任务未完成)。

### 1.1 契约真源(实测自 `PanelConfigService` + 既有面板)

| 维度 | 承载列 | 语义 | 引擎行为 |
|---|---|---|---|
| **1 数据类型** | `yj_field.data_type` + `dict_sql` | `文本` / `日期` / `小数` / `下拉框` / `标准库` / `参照` | 见 §1.2 分派规则 |
| **2 可编辑** | `editable` | `0` ⇒ `buildMeta` 下发 `readonly` | 新增弹窗/单据签名格/列表内联编辑**三处只读** |
| **3 必填** | `required` | `1` ⇒ `isRequired` / `isNotNull` | 保存时服务端校验 `requiredColsCache` |
| **4 唯一** | (无列) | 仅 `文档编号` 走 `checkDocNoUnique` | 同面板内唯一,排除作废单(业务表 `asp_cancel='Y'` + 状态表 `canceled='Y'` 两侧都排) |
| **5 参照** | `ref_panel` / `ref_field` / `display_field` | `参照` 类型三键 | `refLabelOf()` 把 ref_field **列名→label** 下发;`display_field` 决定下拉显示列 |
| **6 参照过滤** | (硬编码) | 仅 `RD_APPROVAL` 命中 | `PanelConfigService:504` 给 `filter={单据状态:已归档}`(草稿/审批中项目编号未定稿) |
| **7 显隐** | `hidden` + `visible` | 见 §1.3 两套语义 | 编辑表格按 `hidden` 过滤;表单按 `visible` 过滤 |
| **8 归档闭环** | 面板级 | `DOC_ARCHIVE_PANELS` 登记 | 保存即归档 + 申请修改/撤回修改闭环 + 角色动作集 |
| **9 多语言** | `yj_translation(scope='field')` | 按 **label** 为键 | 改 label 必须同步改/加译名,否则英文界面显中文 |

### 1.2 数据类型分派规则(`PanelConfigService:491-505` / `1238-1248`)

```java
if ("下拉框".equals(f.dataType()) && f.dictSql() != null) {
    m.put("options", dictOptions(f.dictSql()));          // dict_sql = 可执行 SELECT
} else if ("标准库".equals(f.dataType()) && f.dictSql() != null) {
    m.put("options", stdLibOptions(f.dictSql()));         // dict_sql = 库编码(不是 SQL!)
    m.put("stdLib", f.dictSql());                        // 前端据此显示「标准库维护」按钮
}
if ("参照".equals(f.dataType())) {
    m.put("refPanel", f.refPanel());
    m.put("refField", refLabelOf(f.refPanel(), f.refField()));      // 列名 → label
    m.put("displayField", refLabelOf(f.refPanel(), f.displayField()));
    if ("RD_APPROVAL".equals(f.refPanel())) m.put("filter", Map.of("单据状态", "已归档"));
}
```

> ⚠ **陷阱**:`标准库` 类型的 `dict_sql` 存的是**库编码**(如 `lab.device`),不是 SQL。误写成 SQL 会导致 `stdLibOptions()` 查 `WHERE lib_code='<整条SQL>'` 返回空 ⇒ 下拉空白且**无报错**。

### 1.3 `hidden` / `visible` 两套语义(实测分布:`0|1` 2950 行 / `1|0` 790 行 / `1|1` 45 行)

| 组合 | 语义 | 引擎行为 | 用法 |
|---|---|---|---|
| `hidden=0, visible=1` | 正常字段 | 列表 + 表单都出现 | 绝大多数 |
| `hidden=1, visible=0` | **纯内部字段** | 编辑表格不出现,表单也不出现 | 主键 id、`表区` 物理分块键、审计列 |
| `hidden=1, visible=1` | **表单可见但列表隐藏** | 列表/编辑表格隐藏,表单仍渲染 | 需在表单里填、但不该占列表列宽的字段(`文档编号` 一族 45 行全是这个组合) |

> ⚠ **RD_PROGRESS 的 `文档编号` 现在是 `hidden=1, visible=1`(第 3 类)** —— 它能在表单里填、只是列表不显示。若本次要求它"显示在标题右侧",改 `hidden=0` 即可;**不要动 `visible`**。

### 1.4 标准库字段的完整能力(新增字段若选 `标准库` 类型,自动获得)

| 能力 | 实现 | 维护入口 |
|---|---|---|
| 下拉选项来自库 | `stdLibOptions(libCode)` 查 `yj_std_lib WHERE lib_code=? AND enabled=1 AND asp_cancel<>'Y' ORDER BY seq,id` | — |
| 新增条目 | `POST /stdlib/add {lib,item,content}` | 字段旁「标准库维护」按钮 |
| 编辑条目 | `POST /stdlib/update {id,content}`(只改 content,记 `asp_user2/asp_time2`) | `StdLibManager.vue` 行内编辑 |
| 停用(软删) | `POST /stdlib/remove {id}` ⇒ `enabled=0` | 同上;灰显划线、可恢复 |
| 恢复启用 | `POST /stdlib/enable {id}` | 同上 |
| 彻底删除 | `POST /stdlib/destroy {id}`(物理删,确认弹窗) | 同上 |
| **不污染已录入数据** | 单据列存**内容文本**、不存条目 id | 改库只影响以后的勾选候选 |

> **硬约束**:`StdLibController.add/update` 拒绝 `content.length() > 4000`。库条目设计必须满足此上限(§7.1 已实测)。

### 2.1.0 ⚠ 修正:RD_PROD_INFO 三分类字段的真实映射(推翻第一版分析)

实测现有字典后,**第一版方案的分析有误**,真实情况是:

| 现有字段 | 现有 dict_sql 取值 | 实际语义 | 与设计的关系 |
|---|---|---|---|
| `产品类别` | 阻垢 / 除铅 / 除余氯 / VOC / 抑菌 / 矿化 / 碱性(7 项) | **产品功能** | = 设计的 **`产品功能类别`**(设计示例 `除余氯/VOC/重金属` 同类) |
| `产品分类` | 重点产品 / KPC产品 / 其他(3 项) | **管控等级** | = 设计的 **`产品管控等级`**(设计 `C9` 同值) |
| `产品类型` | 成品 / 半成品 / 裸棒(3 项) | 形态 | 与设计的 `产品形态`(包布/套网/打端盖/套PP棉)语义重叠但取值不同 |
| `产品形态` | 包布 / 套网 / 打端盖 / 套PP棉 | 形态 | = 设计的 `产品形态` ✅ |

**结论:设计没有引入新的分类维度,而是把两个既有字段改了名,并给 `产品类别` 换了一套更细的字典。**

处置(**只加列、不改已有列语义、不丢历史值**):

```sql
-- ① 新增 产品功能类别,历史值从 产品类别 搬来(同义)
IF COL_LENGTH('rd_prod_info_head', N'产品功能类别') IS NULL
  ALTER TABLE rd_prod_info_head ADD [产品功能类别] nvarchar(200) NULL;
UPDATE rd_prod_info_head SET [产品功能类别] = [产品类别]
  WHERE [产品功能类别] IS NULL AND [产品类别] IS NOT NULL AND [产品类别] <> N'';

-- ② 新增 产品管控等级,历史值从 产品分类 搬来(同义)
IF COL_LENGTH('rd_prod_info_head', N'产品管控等级') IS NULL
  ALTER TABLE rd_prod_info_head ADD [产品管控等级] nvarchar(50) NULL;
UPDATE rd_prod_info_head SET [产品管控等级] = [产品分类]
  WHERE [产品管控等级] IS NULL AND [产品分类] IS NOT NULL AND [产品分类] <> N'';

-- ③ 产品类别 换字典为设计 20 项(历史值已搬到 产品功能类别,不丢)
UPDATE yj_field SET data_type=N'下拉框', dict_sql=N'SELECT v FROM (VALUES …20 项… ) AS t(v)'
WHERE panel_code='RD_PROD_INFO' AND col_name=N'产品类别';

-- ④ 旧列 产品分类 / 产品类型 保留为历史列(不进纸面,visible 保持 1 以便表单仍可见? → 见下)
```

### 2.3 必填(维度 3)的取舍

**本次新增字段一律 `required=0`**,理由:

| 字段 | 设计语气 | 取值 | 理由 |
|---|---|---|---|
| RD_SAMPLE_NO.`样品编号` | 编号规则生成,应唯一 | **1** | 无编号的样品卡不可追溯;面板内唯一 |
| RD_INSP_PLAN.`序号` | 设计表头列 | 0 | 加行自动补,不需要人工必填 |
| 其余新字段 | 设计未标注必填 | 0 | 设计原文没有 `*` 标记;追加必填会**卡住历史单据的再保存** |

> ⚠ **为什么"一律不加必填"是要点**:文书面板是"保存即归档"一族,历史单据被修改申请/弃审后会**再次保存**。给新列加 `required=1` 而历史单据该列为空 ⇒ 老单一保存就被必填校验拦住(即 `migrate-fix-ghost-required.sql` 修过的"幽灵必填"同类事故)。**新列只对将来的数据有意义,不该约束历史单据。**

### 2.4 唯一性(维度 4)的落点

| 字段 | 唯一? | 怎么实现 |
|---|---|---|
| RD_PROGRESS / RD_PROD_DOCLIST / RD_SAMPLE_NO / RD_ASM_PROC / RD_SPEC_DOC 的 `文档编号` | 文档编号一族已由 `checkDocNoUnique` 覆盖 | 无需新代码,面板进 `DOC_ARCHIVE_PANELS` 即生效 |
| **RD_SAMPLE_NO.`样品编号`** | **面板内唯一** | 需新增:复用 `checkDocNoUnique` 的形态,改判 `rd_sample_no_detail.样品编号` 在**同面板单据内**不重复(注意:它不在头表,不能直接用现成方法) |

```java
// ButtonService 新增(形态照 checkDocNoUnique,但判目标是明细列)
/** 样品编号在同一面板内不重复(作废单据不计) */
private void checkSampleNoUnique(String panelCode, String docNo, Map<String,Object> head, List<Map<String,Object>> items) {
    if (!"RD_SAMPLE_NO".equals(panelCode)) return;
    for (Map<String,Object> it : items) {
        String no = str(it.get("样品编号"));
        if (no.isBlank()) continue;
        Integer dup = jdbc.queryForObject(
            "SELECT COUNT(*) FROM rd_sample_no_detail d JOIN rd_sample_no_head h ON h.[单据编号]=d.[单据编号] "
          + "WHERE d.[样品编号]=? AND d.[单据编号]<>? AND ISNULL(h.asp_cancel,'N')<>'Y'", Integer.class, no, docNo);
        if (dup != null && dup > 0) throw new IllegalArgumentException("样品编号不允许重复：" + no);
    }
}
```

**不会因内容变宽**,于是 `nowrap` 的文字直接溢出压到值格上。
**修法**:不再手算像素 —— 两列改由浏览器按内容定宽(`table-layout:auto` + 单元格 `nowrap`)。
同一份 `cover.fields` 所有行的标签列自然等宽,值列左边界仍逐行对齐。

**⚠ 顺带踩到一个更隐蔽的坑(整块文字不渲染)**:两表"同宽对齐"最初用
`.rsp-cover-block { width: max-content }` + 内部签字表 `width:100%` 实现 ——
**父宽取自子宽、子宽又取自父宽 = 循环依赖**,实测会把整块布局塌成空:
**表格边框都在、文字全部不渲染**。正解是两层分工:
外层只做居中(`left:50% + translateX(-50%)`),内层 `display:inline-block` 由内容撑开,
签字表 `width:100%` 跟随内层 ⇒ 两表同宽且左右边界对齐。

**本轮其它调整(用户口径):**
- **去掉右上角「编号」**(设计 [D5] 那一格)。行内的「编 号」仍保留,单据编号不丢失。
- 标题与大标题改为**画布水平居中**(旧值 `left: 367.5px` 取自另一张 708 宽的 PNG 画布,
  在 767 宽画布上并不居中)。
- 标签列文字**居中**(设计 B 列即居中)。

**验证方式已升级(不再只靠目视)**:
- 用 `vision_html_screenshot` + `vision_ocr` 出图并**逐字转录**核对:
  最初发现"表格内文字整块不见"就是靠它(OCR 只回出标题、回不出表格内容);
  修好后 9 行 + 签字栏全部回出。

#### 6.4.4 公司名与大标题压字(2026-09-18 第四轮,用户报「产品规格书压到公司名」)

**症状**:大标题「产品规格书」压住公司名「惠州市银嘉环保科技有限公司」末尾。
**根因**:两者**都渲染在 `top:25 / 高 33` 的同一条带**里。而
公司名 13 字 × 20.7 = 占 x44..313,居中标题 5 字 × 47.3 = 占 x268..499 ⇒
**水平重叠 45px**;竖向又同带 ⇒ 直接压字。
**修法**:照设计把封面竖向拆成 **4 个首尾相接的分区**,各占一带:

| 分区 | y 区间 | 来源 |
|---|---|---|
| ① 公司名 | 25..58 | 设计 B5(33px) |
| ② 大标题 | 58..106 | 设计 B6 带 |
| ③ 字段表 | 106..520 | 设计 B7..B15(9 行 × 46) |
| ④ 签字栏 | 605..671 | 设计 B17/B18(2 行 × 33) |

**⚠ 这个坑连踩两次,两次都是"凭感觉给高度"**:
1. 第一次:公司名与标题同带 ⇒ 标题压公司名(用户报的就是这次);
2. 第二次:把标题下移后**手填 60px 高** ⇒ 标题带 52..112 又同时压住公司名(底 58)
   与字段表(顶 106),各溢出 6px。
⇒ 正解是**把 4 段当分区算、首尾相接**:标题带高 = `106 − 58 = 48` **由分区反推,不手填**。
标题带高 48 ≥ 字号 47.3,刚好装下。

**防回归**:探针新增「4 个分区两两不重叠 + 相邻两区相接不留空档 + 带高 ≥ 字号」的断言
(见 `_probe-spec-cover.cjs`),并连同水平越界一起校验 —— 这类"手填高度"的错误以后走不动。
**实测确认**(像素量文字墨迹行):
公司名 y27..38 / 标题 y77..96,中间**38px 空档**;标题 → 表格 9px;表格行间 4px,均不重叠。

## 12. 配方计算器(已定:落地)

### 12.1 设计源与定位

来源:`20267月22日-最新烧结配方模板-1.xlsx` sheet **`信息录入-配方计算器`**。

**定位:它不是一张纸,是一台计算器。** 输入 = 产品基础信息 + 配方(物料/设计比例/水分);输出 = 工艺管控清单(页 1)要用的**灌料三值**与 **实际水分**,加配方单的折算结果。

**落点:作为「成型工艺清单」(RD_MOLD_PROC)的第 3 个页签**,与页 1(工艺清单)/页 2(配方)并列 —— 复用既有 `pages[]` 机制,`pages[2].headMode` 用 `report`,`staticTitle='配方计算器'`。

### 12.2 ⚠ 必须实现的公式(逐格实测自设计文件,不是推断)

```js
// 输入(设计 A1:K3 · 用户填)
产品编号 产品名称 外径C2 内径D2 长度E2 生产车间 一切几G2 折算比H2   // H2 设计值 0.65
模具尺寸      = VLOOKUP(C2, 烧结尺寸表 C→E)      // C4
中心杆尺寸    = VLOOKUP(D2, 烧结尺寸表 D→G)      // D4
管控密度下限E4 管控密度上限F4 产品管控类型G2 炭棒外观要求

// 水分(A6:F16 · 物料三组)
粉料 5 行:   物料名C7..C11 | 设计比例&添加量D7..D11 | 水分含量E = VLOOKUP(物料名, 物料清单 C→D)
             含水分材料数量F7 = 1(设计常量)
胶粉 2 行:   设计比例 D12 D13
折算物料 3 行: 设计比例 D14 D15 D16
D7 = 1 - D8 - D9 - D10 - D11 - D12 - D13        // 粉料首行吃剩余比例

// 派生 · 水分
物料平均水分J2 = SUMPRODUCT(E46:E50, E7:E11) / SUM(E46:E55)
混合料水分参考K2 = SUMPRODUCT(H46:H50, E7:E11) / SUM(H46:H55)

// 派生 · 尺寸(用设计给定的三个长度)
成型长度标准B35 = E2*G2 + (10 + G2*3)            // G2=一切几
成型长度下限B34 = B35 - 2.5
成型长度上限B36 = B35 + 2.5
各体积 D34/D35/D36 = (外径² - 内径²)/4000 * 3.14 * 对应长度

// 派生 · 重量与灌料(湿/干)
F44 炭棒干重量标准未折算 = D35 * ((E4+F4)/2)      // 体积 × 管控密度均值
H44 折算炭粉量          = (C53+C54+C55) * H2     // 折算物料量 × 折算比
B37 炭棒重量下限干 = D36*E4 - H44 + SUM(D53:D55)
B38 炭棒重量标准干 = D35*((E4+F4)/2) - H44 + SUM(D53:D55)
B39 炭棒重量上限干 = D34*F4 - H44 + SUM(D53:D55)
D37 灌料下限湿 = B37 / (1 - J2)
D38 灌料标准湿 = B38 / (1 - J2)
D39 灌料上限湿 = B39 / (1 - J2)
B40 = B37*99.5%    B42 = B39*100.5%    B41 = (B40+B42)/2
B43 实际水分 = 1 - (B41 / D38)

// 配方单明细(C46:I56 · 三组统一到"未折算物料前各种类物料重量")
C46 = F44 * SUM(D7:D11)          // 粉料总重
C51 = D12*F44                    C52 = D13*F44        // 胶粉
C53 = D14*G2                     C54 = D15*G2         C55 = D16*G2   // 折算物料
D46..D55 = C46..C55
// 行 46-50(粉料):E=比例 F=添加量 H=含水分添加量 I=占比
E46 = 1 - E47 - E48 - E49 - E50 - E51 - E52 - E53 - E54 - E55
E47..E50 = D8..D11
F* = E* * D56                    // D56 = SUM(D46:D55)
H* = F* / (1 - 对应水分含量)
I* = H* / H56                    // H56 = SUM(H46:H55)
// 行 51-55(胶粉/折算物料):H = F(不减水分)
```

> ⚠ **原表在空白状态下大量返回 `#DIV/0!`**(J2、K2、D37~D39、E46、F46、H46、I46…)。实现时必须**分母为零则显示空**而不是 `#DIV/0!` —— 与既有 `IFERROR(...)` 语义一致,也让空草稿可读。

## 13. 参照"只列已归档"过滤(已定:要过滤)

### 13.1 现状与机制选择

`PanelConfigService:504` 的过滤是**硬编码单面板**:

```java
if ("RD_APPROVAL".equals(f.refPanel())) m.put("filter", Map.of("单据状态", "已归档"));
```

`yj_field` **没有 filter 列**(实测列清单确认)。三个候选机制:

| 方案 | 做法 | 评价 |
|---|---|---|
| A 硬编码加分支 | `if (refPanel in Set.of(...))` | 又变成清单硬编码,新面板要改 Java —— 与技术债清单第 1 条同类问题 |
| B `yj_panel.config` JSON | 加 `refFilter` 键 | 面板级,不够细(同面板不同字段可能要不同过滤) |
| **C `yj_field.ref_filter` 新列** ← **采用** | 加列存过滤条件 | 与既有字段级 `filter` 语义一致;数据驱动;一句话 UPDATE 即可扩展 |

### 13.2 迁移与代码

```sql
-- tools/migrate-ref-filter.sql
IF COL_LENGTH('yj_field', 'ref_filter') IS NULL
  ALTER TABLE yj_field ADD ref_filter nvarchar(200) NULL;

-- 既有 RD_APPROVAL 口径搬进新列(与硬编码等价,行为不变)
UPDATE yj_field SET ref_filter = N'单据状态=已归档'
WHERE ref_panel = N'RD_APPROVAL' AND ref_filter IS NULL;

-- 本次新增参照一律按"只列已归档"
UPDATE yj_field SET ref_filter = N'单据状态=已归档'
WHERE ref_panel IN (N'RD_PROD_INFO', N'RD_PROGRESS') AND ref_filter IS NULL;
```

```java
// PanelConfigService.buildMeta / fieldSpec 两处(491-505 与 1238-1248)统一替换硬编码
if ("参照".equals(f.dataType())) {
    m.put("refPanel", f.refPanel());
    m.put("refField", refLabelOf(f.refPanel(), f.refField()));
    m.put("displayField", refLabelOf(f.refPanel(), f.displayField()));
    Map<String, Object> filter = parseRefFilter(f.refFilter());   // "单据状态=已归档" → {单据状态:已归档}
    if (!filter.isEmpty()) m.put("filter", filter);
}
```

> **兼容性**:`ref_filter` 为 NULL ⇒ 行为与改造前**逐字等价**(无 filter)。所以这次改动是**纯增量**,不动任何既有面板的表现。
> `parseRefFilter` 支持多条件(逗号分隔 `k=v,k2=v2`),比硬编码的 Map 更通用,但当前只需单条件。

### 13.3 ⚠ 实施期实测修正:必须白名单,且有 3 个例外

**修正 1:不能用 `WHERE ref_panel IN ('RD_PROD_INFO','RD_PROGRESS')`(第一版就是,错的)。**
实测发现那会把**既有**参照字段一起改掉,后果是功能回退:

| `RD_MOLD_PROC.产品编号` | 成型工艺清单只能选已归档产品 |
| `RD_ASM_PROC.产品编号` | 组装工艺清单同上 |
| `RD_ASM_BOM.产品编号` | 组装BOM表同上 |
| `RD_INSP_PLAN.产品编号` | 出货检验计划表同上 |
| `RD_SPEC_DOC.编号` | **规格书选不到在研产品** —— 规格书恰恰是产品开发中编写的,整条产品文件流程被堵死 |

⇒ 改为**白名单**,只碰本次新增的 4 个跨面字段(`RD_ASM_PROC.客户项目名称` / `RD_ASM_PROC.产品功能类别` / `RD_INSP_PLAN.产品功能类别` / `RD_SPEC_DOC.客户项目名称`)。

| 字段 | 为什么不能过滤 |
|---|---|
| `RD_PROD_DOCLIST.产品编号` | 本表跟踪的就是**开发中**的产品,过滤掉未归档等于没数据 |

> 这三条例外是**实现时验证出来的**,不是设计时想到的 —— 已在 `migrate-ref-filter.sql` 里显式清空并注明,兼作误改回滚。

## 14. 样品编号规则(已定:走口径 a —— 确定性规则)

### 14.1 ⚠ 关键发现:不需要序号计数器

把口径 (a) 推到底,得到一个比预期更简单也更强的结论:

```
样品编号 = 客户项目代号XX  +  项目编号(原样,含末段)
         = XX + "-" + <基号> + "-" + <序号>

即:样品编号 = 客户代号 与 项目编号 的**直接拼接**(中间只隔项目编号自带的连字符)
```

**逐样例校验结果(设计自身 38 个样例):**

| 校验项 | 结果 |
|---|---|
| `样品编号 == 前缀XX + 项目编号`(直接拼接) | **38 / 38 成立** |
| `项目编号` 恒为 `<基号>-<数字>` 形态 | **38 / 38 符合** |
| 前缀 `XX` 恒为纯字母(不含连字符) | **38 / 38 符合**(含 3 字母的 `FLN`) |
| `项目编号` 全表唯一 | **38 个唯一 / 38 行 ⇒ 无重复** |
| `(客户代号, 样品编号)` 重复 | **无** |
| `(客户代号, 项目编号)` 重复 | **无** |

**所以设计表尾那三段 `XX` / `XXX` / `01` 就是:**

| 段 | 设计标注 | 实际含义 | 例(`FL201-1`) |
|---|---|---|---|
| `XX` | 客户项目代号 | 客户代号 | `FL`(飞利浦) |
| `XXX` | 项目编号 | 项目编号的**基号** | `201` |
| `01` | 编号序号 | 项目编号的**末段** | `1` |

> **推论(重要)**:`XXX` + `01` 合起来 = 项目编号本身。也就是说 **`01` 不是样品计数器,而是项目编号自带的分支序号**,它在设计表里本来就存在(`F 列 = 201-1` / `201-2`)。
>
> 因此:**样品编号是 `(客户代号, 项目编号)` 的确定性函数 —— 不需要任何计数器、不需要查历史最大序号、不需要新端点。** 原方案里的"组内下一个序号"逻辑与"`GET /px/nextSampleNo` 端点"**全部作废**。

### 14.2 生成规则(最终)

```js
/**
 * 样品编号生成(唯一真源,纯函数 —— 可单测)
 * 口径:样品编号 = 客户项目代号 + 项目编号(原样拼接)
 *   例:FL   + 201-1  =>  FL201-1
 *       FL   + 201-2  =>  FL201-2
 *       FLN  + 407-1  =>  FLN407-1
 * 依据:设计自身 38 个样例 38/38 成立
 */
export function makeSampleNo(customerCode, projectNo) {
  const xx = String(customerCode || '').trim()
  const pno = String(projectNo || '').trim()
  if (!xx || !pno) return ''
  if (!/^[A-Za-z]+$/.test(xx)) throw new Error('客户项目代号必须是纯字母(不含连字符/数字/空格)')
  if (!/^.+-?\d+$/.test(pno)) throw new Error('项目编号必须以序号段结尾,如 201-1')
  return xx + pno            // ← 直接拼接,中间不加任何分隔符
}
```

**前置约定(实现时须校验,否则会拼出歧义编号):**

| 约定 | 理由 | 违反后果 |
|---|---|---|
| 客户代号 `XX` **纯字母** | 若含连字符,拼接结果无法反解 | `A-B` + `201-1` ⇒ `A-B201-1`,与 `A` + `B201-1` 混淆 |
| 项目编号 **以 `-<数字>` 结尾** | 末段是设计要的"序号" | `201` ⇒ `FL201`(缺第三段) |
| 同一项目编号**只出一张样品** | 拼接是确定性的,同编号必撞唯一性 | 需两支时,用 `201-1`/`201-2` 两条项目编号(与设计数据一致) |

**唯一性**:实现为**样品内唯一约束**,等价于项目编号唯一 —— 落库前用 `checkSampleNoUnique`(§2.4)拦重复,给清晰提示。

**落点**:
- 字段:`RD_SAMPLE_NO.样品编号` 无需人工填 —— 由 `客户项目代号` + `项目编号` 两格**实时派生**(用户填完后两格自动带出),仍允许手改(编号可能由人工特批)。
- 时机:前端 `watch` 两格变化即重算;**无需后端端点、无需 `docDefaults`**。

### 14.3 客户项目代号 XX 的来源(需维护,但可自动播种)

`XX` 无法从规则推出(实测:`RZ` → `IAPMO认证项目`、`QD` → `青岛信民炭棒认证项目`、`BS` → `浙江保时康` —— 缩写规则不统一,有的是拼音首字、有的是英文、有的看不出)。

**映射键 = 项目名称,不是客户名**(实测证据:飞利浦 7 个不同项目名 → 全是 `FL`;安吉尔 4 个 → 全是 `AJ`;碧纯 2 个 → 全是 `BC`。即**一个客户名可对应多个项目名**,用客户名做键会漏)。

**处置:建客户代号映射,放 `yj_std_lib`**:

```sql
-- lib_code='rd.customer_code',item_code=项目名称,content=代号XX
-- 实测:设计 38 样例覆盖 34 个唯一项目名称,无一对多代号 ⇒ 可直接播种
INSERT INTO yj_std_lib (lib_code, item_code, content, seq, enabled, asp_user1, asp_time1) VALUES
 ('rd.customer_code', N'飞利浦RO-PFAS项目', 'FL', 1, 1, 'system', SYSDATETIME()),
 ('rd.customer_code', N'飞利浦抽水壶芯',    'FL', 2, 1, 'system', SYSDATETIME()),
 ('rd.customer_code', N'安吉尔阻垢炭棒',    'AJ', 3, 1, 'system', SYSDATETIME()),
 ('rd.customer_code', N'GE正牌冰箱滤芯',    'GE', 4, 1, 'system', SYSDATETIME()),

-- … 共 34 条,由 tools/gen-customer-code.cjs 从设计 sheet 反推生成
-- 幂等去重键:lib_code + item_code(项目名称)
```

**字段配成标准库类型即可自动获得维护能力**(增/改/停用/恢复/彻底删除,零新增代码):

```sql
-- RD_SAMPLE_NO 新增「客户项目代号」:存起来才能驱动派生(设计纸面没有此列 ⇒ 列表隐藏、表单可见)

--                                                             seq=5 让它在 样品编号(10) 之前  ^^^ ^^^
```

> ⚠ 三点:
> 1. `标准库` 类型的 `dict_sql` 存**库编码**(`rd.customer_code`),不是 SQL(§1.2 陷阱)。
> 2. `hidden=1, visible=1`(§1.3 第 3 类语义)—— 设计纸面没有这一列,**列表不显示、表单要能填/选**。
> 3. `required=1` —— 不填代号派不出样品编号。它是**新面板**,无历史单据,不受"幽灵必填"约束(§2.3)。

**选择的交互**:字段是标准库下拉,选出的是**代号**(`FL`);若操作人只知道项目名称,可直接从库里挑对应条目 —— 库条目 `item_code` 是项目名称、`content` 是代号,与 `StdLibManager` 的勾选→编辑形态天然吻合。

### 17.1 口径 (a) 带来的一个前置约定(请注意)

`样品编号 = 客户代号 + 项目编号` 是**直接拼接**,所以下列三条成为**硬前置约定**(违反会拼出歧义编号,§14.2 已在生成函数里加校验):

1. **客户代号必须是纯字母**(`FL` / `FLN` / `GE` …)。含连字符会与项目编号的连字符混淆。
2. **项目编号必须以 `-<数字>` 结尾**(`201-1`)。否则拼出的编号缺第三段。
3. **同一项目编号只出一张样品**(`01` 就是项目编号的末段,不是样品计数器)。要两支时用 `201-1` / `201-2` 两条项目编号 —— 与设计数据形态一致。

> 这三条不是我加的限制,是**从 38 个样例反推出来的既成事实**;只是现在写清楚了,以便录入时就拦住不规范的值。
