# 任务单：库存报表面板数据库性能修复（v_stock_balance 单次 65 秒 → 前端 15 秒超时）

> 本任务单可整份转交其他 agent 执行。**结论先行**：后端进程没掉，是 `v_stock_balance` 等库存视图慢到几十秒，
> 把 SQL Server 占住，其它请求（含无关面板）排队，前端 axios 15 秒超时后报 `timeout of 15000ms exceeded`。

---

## 一、现象

- 前端任意面板偶发报 `timeout of 15000ms exceeded`（axios 客户端超时；请求发得出去，服务端回不来）。
- 实测（2026-09-22，本机 HSDZ_MES，库空闲时逐项计时）：

| 对象 / 接口 | 行数 | 耗时 |
|---|---|---|
| **`v_stock_balance`**（库存状况表用） | 84 | **65,290 ms**（最坏一次实测 190 s） |
| `v_stock_movement` | 235 | 1,623 ms |
| `bs_inv` | 3838 | 3,946 ms |
| `inv_cost_ledger` / `v_stock_ledger` | 235 / 235 | 108 ms / 78 ms |
| `qc_insp` / `qc_catalog_detail` / `yj_panel` | 140 / 10 / 162 | 50 ms / 11 ms / 1 ms |
| 接口 `getPanelConfig?panelCode=QC_CATALOG` | — | 32 ms（不排队时） |
| 接口 `queryFormDataList STOCK_BALANCE` | 20 行 | **190,325 ms** |
| 接口 `queryFormDataList QC_RECV`（检验链，无关面板） | 20 张 | 75,172 ms（纯排队） |

**因果链**：库存报表面板（或成本重算）一发查询 → `v_stock_balance` 跑 1~3 分钟 → 库被占住 → 其它请求排队 → 15 秒超时。

## 二、涉及对象与现状

| 对象 | 现状 | 说明 |
|---|---|---|
| `v_stock_balance` | 定义 771 字符：`v_stock_movement` LEFT JOIN `inv_cost_ledger`(按 `src`+`rid`) 后按 仓库键/仓库编码/仓库/存货编码/存货/规格型号/主计量 分组求和 | 库存状况表 `STOCK_BALANCE` 的 `line_table` |
| `v_stock_movement` | 定义 **6415 字符**（8 路 UNION 收敛） | 台账/结存/成本的公共底座 |
| `v_stock_ledger` | 1167 字符 | 库存台账 `STOCK_LEDGER` 用 |
| `v_stock_summary` | — | 收发存汇总表 `STOCK_SUMMARY` 用 |
| `kucun`（库存台账表） | **堆表，无任何索引**（`sys.indexes` 仅 HEAP）；31 行 / 33 列 | 库存状况 `STOCK_STATUS` 的 `line_table` |
| `inv_cost_ledger` | 有 `PK_…`(聚集) + `IX_inv_cost_ledger_part` | 物化成本表（另一任务新建） |
| 库 | **兼容级别 100**（SQL 2008 一代基数估算） | 不能用 `STRING_AGG`/`LAG`；视图不能带 `OPTION (MAXRECURSION)` |

相关面板：`STOCK_BALANCE` 库存状况表 / `STOCK_LEDGER` 库存台账 / `STOCK_SUMMARY` 收发存汇总表 / `STOCK_STATUS` 库存状况。

## 四、目标与验收口径（可量化）

1. **单查询**：`SELECT COUNT(*) FROM v_stock_balance` **< 1000 ms**（现 65 s）；`v_stock_movement` 同样进入百毫秒级。
2. **接口**：`queryFormDataList` 打 `STOCK_BALANCE` / `STOCK_LEDGER` / `STOCK_SUMMARY` / `STOCK_STATUS` **均 < 2 s**（取 20 行；现 STOCK_BALANCE 190 s）。
3. **互不拖垮**：库存面板查询进行中，`getPanelConfig` 与检验链面板（`QC_CATALOG`/`QC_INSP_REC`/`QC_RECV`）接口仍 **< 500 ms**，不再出现 15 s 超时。
4. **语义不变**（不得为了让查询变快而改口径）：
   - 结存金额 = Σ收入金额 − Σ**移动加权发出成本**（成本取自 `inv_cost_ledger`）；
   - 成本/结存分区键 = **(仓库键, 存货编码)**，**不含批号**（批号进分区会导致大量"只出无进"分区，出库成本恒 0）；
   - 仓库键三级兜底（自身编码 → `bs_wh` 按名称 → `'#'+名称`）保持；
   - 需自证勾稽：给出改前/改后同一批数据的结存金额对比（对方任务记录里的口径值是 **3,099,936.64**，如与该值不一致必须说明原因）。
5. **并发不劣化**：3 个面板并发各打一次，总耗时与串行相当，且无超时。

## 五、建议排查/修复方向（按性价比排序，任选并验证）

1. **给 `kucun` 建索引**（`STOCK_STATUS` 的直接数据源；堆表 31 行但参与 UNION）：按实际过滤/连接列建 1~2 个非聚集索引，观察 `v_stock_movement` 是否随之提速。
2. **消解 `v_stock_movement` 的 8 路 UNION**：它能收敛成一处（另一任务已做了一半）——进一步可落**物化表**（沿 `inv_cost_ledger` 的现成思路），视图改读物化表；物化表的刷新挂到既有重算入口。
3. **给 `v_stock_balance` 的 LEFT JOIN 补支撑索引**：`inv_cost_ledger(src, rid)` 的覆盖索引（当前只有 `PK` + `IX_…_part`，确认 JOIN 键是否命中）。
4. **执行计划取证**：`SET STATISTICS IO, TIME ON` 看逻辑读与耗时分布；`SET SHOWPLAN_XML ON` 取计划（注意兼容级别 100 的估算退化，必要时 `OPTION (RECOMPILE)` 只作诊断、不要留在正式视图里）。
5. **兜底**：把三个报表视图的取数改成"查询时读物化表 + 后台增量刷新"，彻底摆脱大 UNION。

> ⚠ 不要为了提速而：删/改业务列、改金额口径、把 `asp_cancel`/软删语义改掉、或让报表读到未审核单据。
