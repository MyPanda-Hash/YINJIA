# 订单结转 → 转工单:一次转单一张新工单(2026-10-31)

> 用户报障(2026-10-30 截图):同一个销售订单行在「订单结转」里分两次转单,生产的却是
> **同一张工单号的两行**(`GD-2026-10-0241 #1` / `#2`),两行「需求数量」都是整条订单行的
> 200 —— 物料一样、单却不是自己的一张,行号也被改了。

## 一、旧口径与病根

`QuickScheduleService.createFromOrderLine`(2026-09-27 定稿的「同一销售订单共用一张工单」):

| 位置 | 旧行为 | 后果 |
|---|---|---|
| 工单号 | `SELECT TOP 1 pl_no FROM plang WHERE od_no=?` 复用该订单**首次转单号** | 同一订单行第二次转单 = 同一张工单里再加一行 |
| 工单行号 `pl_xc` | 复用单号时取 `MAX(pl_xc)+1`(2026-10-19 为修「同号同行号重复」而加) | 第二次转单行号变成 2,**与订单行号(1)脱钩**;追溯/排产/打印都按 `工单号#行号` 走,现场看不出它来自哪条订单行 |
| 需求数量 `xq_sl` | 写**整条订单行数量**(`bl_so_order.数量`) | 200 里先转 100 再转 100 ⇒ 两张工单行各显示需求 200,订单需求被重复计;`订单结转` 页的剩余量又与工单页对不上 |
| 余量 `yl` | `demand − qty` | 同上,同一订单行的剩余被每张工单重复表达一次 |

## 二、新口径(用户拍板)

**一次转单 = 一张新工单号**;工单自带订单号 + 订单行号,订单追溯不靠工单行号凑。

| 列 | 新值 | 说明 |
|---|---|---|
| `pl_no` | 每次 `formNo.next("GD", user)` 取新号 | 同一订单行转几次就是几张工单,可各自排产/报工/打印/结案 |
| `pl_xc`(工单行号) | **订单行号**(`bl_so_order.行号`) | 每张新工单只有这一行 ⇒ 转多少次行号都不漂移(= 用户要的「行号一致」) |
| `od_no` | 销售订单号 | 追溯入口(工单列表/追溯页显示「订单号」) |
| `od_xc` | **销售订单行 id**(沿用历史口径,`bl_so_order.id`) | 工单列表/追溯按它 `JOIN bl_so_order` 反查「订单行号」显示;精确到行,不受 `行号` 历史重复值影响 |
| `xq_sl`(需求数量) | **本次转单数量** | 本工单自己的需求;不再是整条订单行数量 |
| `pl_sl`(转单数量) | 本次转单数量 | 不变 |
| `yl`(余量) | 0 | 需求 = 转单,未排产量由 `pl_sl` 派生 |
| 占用链 | 不变:`form_flow_link`(SO 订单行 → 本工单行,数量 = 本次转单)| `订单结转` 页「已排产 / 剩余数量」口径不变(仍是行级占用汇总) |

代码位置:`backend/src/main/java/com/yinjia/mes/service/QuickScheduleService.java`
(`createFromOrderLine` / `generateFromOrder` 的 javadoc 已同步)。

## 三、存量数据

- 脚本:`tools/migrate-plang-order-demand-20261031.sql`(已登记 `tools/db-migrations.txt`,两账套已执行)
  - 判据:本工单行有 ACTIVE 的 `SO_ORDER→PLANG` 占用链、且 `xq_sl > 占用合计 + 0.0001`;
    完整转出行/切单父子行(需求与占用同步核减)都相等 ⇒ 不动;手机端/参考库直写(无 SO 占用)的行不动。
  - 修法:`xq_sl = 占用合计`、`yl = max(0, 占用 − pl_sl)`;末尾自检「越界行数」必须 `[PASS]`。
- **不改历史 `pl_xc`**:旧「同一工单号多行」的行号已参与占用链键(`pl_no#pl_xc`),改号会拆断
  `form_flow_link`;已经生成的历史多行工单保持原样(修完需求后各行数量自洽),新转单走新口径。

## 四、展示(生产工单列表 / 工单详情·追溯)

- `POST /api/px/workOrderList` 每行新增 `订单号`、`订单行号`;**关键字搜索也支持订单号**(2026-10-31 补);
- `POST /api/px/scheduleBoard/trace` 的 `头` 新增 `订单行号`,并且**按行追溯时用当前行的值**
  (老「一单多行」工单的头默认取首行,按行看必须换成本行的 —— QA 复核发现的 P2 已修);
- 订单行号解析口径收口到 `PlangOrderLine`(生产工单列表 / 追溯头共用一份 SQL):
  ① `plang.od_xc`(销售订单行 id)精确 join `bl_so_order` 取 `行号`;
  ② id 已过期(ERP 订单行重导后 id 会变)时,同订单号下**同物料且只有 1 行**的,取它的行号;
  ③ 仍解析不出 ⇒ 空(宁可空、不给错)。实测正式库有效工单行 395 条:①128 + ②267 = **100% 可解析**,
  且 ①② 重合部分 0 冲突(双账套核对);
- 前端:生产工单列表在「客户」后新增「订单号 / 订单行号」两列(CSV 导出列同步),
  `WorkOrderTraceDialog.vue` 头部显示「订单行号」;译名 `en.js`: `'订单号': 'Order No.'`、
  `'订单行号': 'Order Line No.'`。

## 五、验证要点(改这块必须复验)

1. 测试账套(或副本库)里同一销售订单行 `数量=100`:
   - 第 1 次转 40 → **新工单号 A**,`工单行号=订单行号`、需求 40 / 转单 40 / 余量 0、订单号+订单行号可见;
   - 第 2 次转 60 → **另一张新工单号 B**,同样 `工单行号=订单行号`、需求 60 / 转单 60;
   - `订单结转` 列表该行「已排产=100 / 剩余=0」并自动消失。
2. 工单列表「需求数量」不得再出现「两张单都是整单需求」的重复计。
3. 切单/排产/报工/转领料/打印仍按 `工单号#行号` 正常工作(新单只有一行,链路更简单)。
