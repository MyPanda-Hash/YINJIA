# 角色面板权限词表(组织架构 ·「角色与面板权限」)

> 2026-10-16 立。**一句话口径:组织架构矩阵里能勾的词,必须就是引擎真读的词;一个概念只有一个词。**

## 0. 为什么有这份文档

用户原话:「现在组织架构里面的研发管理模块角色可配置的权限与现在的面板功能是对不上的,现在审视一遍,把这个权限配置完善」。

2026-10-16 审视结果:不是「研发管理一个模块配错了」,而是**矩阵下发的词表与引擎读的词表是两套**,
全库几十张面板都受影响(证据与探针见 `tools/archive/_rd-perm-audit-20261016/`)。三处硬伤:

| # | 症状 | 后果 |
|---|---|---|
| ① | 通用动作集给 `edit 修改 / delete 删除 / price 价格金额 / review 复核反审核 / adjust 调价`,**引擎一个都不认**(引擎只认 `modify/modlog/del`) | 非文书类面板**永远授不出**「申请修改/删除申请」⇒ 用户点「修改/删除」必 403「当前角色无该面板…权限」 |
| ② | 反向:库里几十张面板已授 `modify/modlog/del`,而通用矩阵**没有这三列** | 授权**看得见才怪**:界面上是空白格,管理员既看不到已授的权也点不掉它 |
| ③ | `can_approve` 与 `perms` 的 `audit` 词**两个真源**(前端 approvePanels 读前者,后端前门读后者) | 研发审核在 8 张 RD 面板上 `can_approve='Y'` 但 perms 无 `audit` ⇒ **前端显示审批按钮,一点就 403** |

`price/review/adjust` 全库**零消费者**(任何代码都不读这三个词),纯摆设。

## 1. 词表(唯一真源)

词表真源 = `PanelPermissionService.PERM_LABEL`(中文标签)与 `BUTTON_PERMS`(按钮→词映射);
组织架构矩阵真源 = `SysAdminController.PERMISSION_ACTIONS`。两者**必须逐字一致**,
由 `frontend/src/core/auth/permWordDrift.test.js` 钉住(改一处不改另一处 = 单测红)。

| 词 | 矩阵标签 | 谁在读 | 说明 |
|---|---|---|---|
| `view` | 可见 | `requirePanelView` / 菜单过滤 / 读放行集合 | 恒可勾(其余词以它为前提) |
| `query` | 查询单据 | 矩阵语义位(无独立闸门) | 与 `view` 同批出现 |
| `add` | 新增保存 | `BUTTON_PERMS` 编辑类 | 新增/保存/提交/复制… |
| `modify` | 申请修改 | `BUTTON_PERMS`(`申请修改`)/ 删除类之一 | **旧名 `edit`,2026-10-16 归位** |
| `modlog` | 修改记录 | `BUTTON_PERMS["修改记录"]` | 文书式面板的修改留痕 |
| `del` | 删除申请 | `BUTTON_PERMS` 删除/撤回类 | **旧名 `delete`,2026-10-16 归位** |
| `export` | 导出打印 | 导出/打印入口 | |
| `print` | 打印预览 | 页面级面板(`WORK_ORDER_*`) | 文书式面板无此动作 |
| `audit` | 审批 | `BUTTON_PERMS` 审批族 + `requireApprover` 身份门 | **`can_approve` 恒等于本词**(单一真源) |
| `field` | 自定义字段 | `requireFieldConfig` | 逐面板授予的动态字段配置权 |
| `warn` | 预警配置 | `requireWarnConfig`(仅库存明细) | |
| `date` `convert` `assign` `unassign` `transfer` `revoke` `unclose` `close` `split` `picking` | (页面级面板专属列) | `PagePanelRegistry` 各页面的动作集 | 无 `yj_panel` 行的 4 张页面面板用 |

**已撤销的词(不得再用)**:`edit` `delete` `price` `review` `adjust`。

## 2. 面板动作集(三套,后两套都必须是第一套的子集)

| 动作集 | 用在哪 | 内容 |
|---|---|---|
| `PERMISSION_ACTIONS`(11) | 通用单据/档案面板 | §1 的前 11 个词 |
| `FILE_PANEL_ACTIONS`(9) | 文书归档面板(`ButtonService.DOC_ARCHIVE_PANELS`,21 张 RD_\*) | 通用 11 − `print` − `warn` |
| 页面级动作集 | 订单结转 / 快速排产 / 工单排产 / 生产工单列表(`PagePanelRegistry`) | 各页面按特性裁剪(见该文件) |

矩阵**按模块分组渲染**,组内列 = 该组所有面板动作集的**并集**,不适用处显示 `—`。
所以「研发管理」组 = 通用 11 ∪ 文件 9 = 11 列(归位前是 13 ∪ 9 = 18 列的乱局)。

`can_approve='Y'` 共 21 行 = 上表里 `audit` 出现的全部位置(`RD_*` 9 行 + `DISPATCH/MANU_ORDER/OUTSOURCE_ORDER/ROUTE` 各 3 角色 12 行),**与 perms 的 `audit` 词一一对应,错位 0 处**。

### 仍然"角色之间没有区分度"这件事(已知,未擅自改)

普通用户 vs 研发审核:全库 83 行授权**逐格只差 1 处**(`RD_APPROVAL` 的 `audit`);vs 文件负责人差 6 处(且那 6 处是 `OTHER_*` 出入库统计,与研发无关)。
即「研发审核」「文件负责人」这两个角色**几乎等于普通用户**。这是**业务口径问题**(要给这两个角色收窄到哪些面板),不是技术缺陷 ——
本文档只记录现状,收窄需用户确认目标后另行处理。请勿在未确认前按"看起来更合理"批量改授权。

## 5. 维护规矩(改权限词表前先读)

1. **加词三处同批**:①`PanelPermissionService`(`PERM_LABEL` 标签 + `BUTTON_PERMS` 谁读它)
   ②`SysAdminController.PERMISSION_ACTIONS`(或对应面板动作集)
   ③迁移脚本把库里旧词回正 + 登记 `tools/db-migrations.txt`。少任一处 = 又造一次"勾了不生效"。
2. **删词先查消费者**:`git grep '"词"'` 全仓确认没人读,再撤列(2026-10-16 的 `price/review/adjust` 就是这么确认的)。
3. **`can_approve` 永远不许手写**:它是 `perms` 含 `audit` 的派生值(`SysAdminService.saveRolePanels` 与
   `tools/migrate-role-perm-words-20261016.sql` 均按此写)。前端 approvePanels 与后端 `requireApprover` 都读它,
   脱离 `perms` 就会出现"按钮点得动、一点就 403"。
4. **矩阵是数据驱动的**(`OrgAdmin.vue` 按接口下发的 `actions` 渲染列),所以改词表**不用改前端源码**;
   但改完必须跑 §4 的 ④ 看实际列,别只跑接口。
