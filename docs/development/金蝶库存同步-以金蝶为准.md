# 库存数量以金蝶真实账套为准(每 5 分钟同步)

> **口径来源**:用户 2026-11-10 ——「同步脚本能不能实时同步金蝶真实账套的库存数量,我们想要以金蝶的库存数量为准」。
> **落地选择**:B 方案 —— 直接覆盖 `kucun.yl`(金蝶即唯一库存),5 分钟一轮。
> **关联**:[上线前必验-库存批次追溯](上线前必验-库存批次追溯.md)(批次口径)、[库存状况异常-当前取证与提交影响-20261021](库存状况异常-当前取证与提交影响-20261021.md)(为什么原来的数不对)、`migrate-erp-stock-sync-20261110.sql`。

---

## 零、一句话

`deploy/sync-stock.mjs` 每 5 分钟拉一次金蝶真实账套的**现存量**(`/jdy/v2/inv/inv_inventory_ims`,维度 商品+仓库+批号),
写一张逐键快照 `erp_stock_snapshot`,然后**单事务覆盖 `kucun.yl`**:金蝶有的键照抄,金蝶没有的键置 0(留痕不删行)。
库存状况页看到的就是金蝶的数量;`kucun.差异数量`(计算列 = 金蝶数量 − 现存量)会如实显示"自上次同步以来 MES 本地记了多少账"。

## 一、为什么原来是错的(2026-11-10 实测)

| 项 | 数 |
|---|---|
| 金蝶现存量 | **1,396 行 / 合计 4,314,349.61** |
| MES `kucun`(同步前) | 2,152 行 / 合计 5,846,961.41 |
| 逐键对比 | 交集 1,263 键里**只有 742 键一致**;仅金蝶有 133 键、仅 MES 有 889 键 |
| 根因 | 2026-10-20「把服务器库导进本地」整库覆盖后**9/1 真期初丢失**,此后 MES 只能靠单据流水推结存 |

所以这不是"同步脚本缺个类型"的问题,而是**MES 一直缺一个库存真源**。现在真源 = 金蝶。

## 二、一次运行做了什么(顺序固定,单事务)

1. 拉现存量(1396 行 / 3 页 / `page_size=500`)——**任何一页失败整轮放弃**,绝不拿半份数据覆盖;
2. 三键归一:商品编码 + 仓库编码 + 批号(空批号→NULL;**PC0000 等占位批号按字面保留**,理由见 §五.1);
3. 与 `kucun` 对账分类:一致 / 覆盖 / 新增 / 清零,打印差异 TOP 10(`--dry-run` 到此为止);
4. 前像备份 → `deploy/backup/stock-<批次>.jsonl`(逐行:键 / 金蝶数量 / 原 MES 行 id / 原现存量);
5. 事务内:`erp_stock_snapshot` 整表替换 → 回填覆盖前数量/差异/处理方式 → 补「清零」行 →
   新增缺行 → 覆盖 `yl`/`金蝶数量`/`金蝶同步时间` → 写 `erp_stock_sync_log`;
6. 日志(控制台 + `deploy/logs/stock-sync-YYYY-MM-DD.log`)。

**绝不碰**:`kucun.price`、`inh`/`outh` 流水、`inv_cost_ledger`、月结。单价来自入库单价的移动加权,与数量来源无关。

## 三、三道闸门(任一命中 → 整轮放弃、一个字节不改)

| 闸门 | 值 | 越权办法 |
|---|---|---|
| 金蝶返回 0 行 | 直接失败 | 无(先把接口/授权查清) |
| 本次行数 < 上轮成功行数 × 50% | 拒绝覆盖 | `--force`(金蝶侧真被删了很多行时才用) |
| 上一轮还在跑(锁文件 PID 存活) | 本轮跳过 | 等下一轮 |
| `kucun` 同一三键出现多行 | 拒绝覆盖(会让库存翻倍) | 先合并重复行 |

## 四、怎么用 / 怎么验

```bash
cd deploy
node sync-stock.mjs                 # 正式同步(计划任务 JdyStockSync 每 5 分钟自动跑)
node sync-stock.mjs --dry-run       # 只看差异,不写库
node sync-stock.mjs --probe         # 只验金蝶接口(不连库)
node sync-stock.mjs --db=HSDZ_MES_TEST   # 对测试账套跑一轮
```

验收 SQL(两账套都跑,数值必须成立):

```sql
-- ① 结存合计 == 金蝶现存量合计
SELECT CAST(SUM(ISNULL(yl,0)) AS decimal(18,2)) AS 合计,
       SUM(CASE WHEN ISNULL(yl,0) < 0 THEN 1 ELSE 0 END) AS 负行
  FROM dbo.kucun WHERE ISNULL(asp_cancel,'N') <> 'Y';
-- ② 差异列全 0(刚同步完)
SELECT COUNT(*) AS 有差异行 FROM dbo.kucun
 WHERE ISNULL(asp_cancel,'N') <> 'Y' AND ABS(ISNULL(差异数量,0)) > 0.0001;
-- ③ 最近几轮同步
SELECT TOP 5 批次号,金蝶行数,覆盖行数,新增行数,清零行数,一致行数,差异合计,状态,错误信息
  FROM dbo.erp_stock_sync_log ORDER BY id DESC;
```

2026-11-10 首轮实测(正式库):一致 742 / 覆盖 521 / 新增 133 / 清零 845、差异合计 **−1,532,611.80**;
同步后 `kucun` 合计 **4,314,349.61**(= 金蝶)、负行 **69 → 3**(就是金蝶侧本来那 3 行)、差异列全 0。
测试库连跑第 2 轮:一致 1396、其余全 0(幂等)。

## 五、三处必须知道的口径与坑

1. **批号** —— 真实账套现存量 `batch_no` 当前**全为空**(1396 行 0 行有批号)⇒ 金蝶数量一律落在
   `lot_no` 为 NULL/'' 的那一行;MES 里有真实批次(含 `PC0000`)的行会被**清零**,数量并入无批号行。
   (物料, 仓库) 合计 = 金蝶合计,这正是"验收期不按批次追溯"的口径。
   ⚠ 2026-11-10 试跑踩过的坑:同步器曾把 `PC0000` 也归成"无批号",而 SQL 侧是**字面比较** ——
   两侧口径不一致导致 PC0000 行既没被覆盖也没被清零、每轮重报一次。现在统一按字面匹配。
   正式上线要按批次核销时,见 [上线前必验-库存批次追溯](上线前必验-库存批次追溯.md)。
2. **单价与成本** —— 现存量接口不给单价,同步器**只写数量**。`kucun.price`/`inv_cost_ledger`/月结不受影响。
3. **MES 本地刚审核、还没转ERP 的单据** —— 下一轮同步会把它抹平(金蝶为准)。这不是 bug,是口径:
   ERP 里没发生的事就不算发生。`kucun.差异数量` 在抹平前会亮出来,可当"漏转ERP"的信号看。

## 六、两套口径并存(待用户决定)

| 面板 | 数据源 | 数量 = ? | 合计(2026-11-10) |
|---|---|---|---|
| 库存状况 `STOCK_STATUS` / 库存明细 `STOCK_DETAIL` / 库存选货 `STOCK_PICK` | `kucun`(已被金蝶覆盖) | **金蝶** | 4,314,349.61 ✅ |
| 库存状况表 `STOCK_BALANCE` / 首页「现存量 TOP」/ 流程看板负库存 | `v_stock_balance`(流水聚合) | 流水推算 | 5,844,480.41 ❌ |

`v_stock_balance` 是**成本/流水口径**的报表(结存金额来自移动加权成本物化表),本次**没有动它**:
改成"金蝶数量 × 成本单价"是一次独立的报表口径改造,牵动首页、流程看板、成本报表,需单独评审。
在它改之前,同一个库会看到两个数 —— 以 **kucun(库存状况)** 为准。

## 七、回滚

```bash
# 单轮回滚:用前像把受影响行写回
#   deploy/backup/stock-<批次>.jsonl 每行 = {键, 金蝶数量, 原MES行id, 原现存量}
# 整库回滚(2026-11-10 首轮之前的完整快照):
#   deploy/backup/kucun-before-stock-sync-20261110.jsonl(2152 行)
```

停同步:删除计划任务 `Unregister-ScheduledTask -TaskName JdyStockSync -Confirm:$false`。
停同步后 `kucun.金蝶数量/差异数量/金蝶同步时间` 保持最后一轮的值(不再更新),
后端自检会自动落回"结存 == Σ流水"口径(判据是 `erp_stock_snapshot` 有没有行,见
`InvCostService.erpStockAuthoritative()`)。

## 八、为什么不是"推送式实时"

金蝶星辰开放平台的库存侧只有**查询**接口,没有库存变更的推送/订阅;我们实测与现有代码里也没有订阅能力。
所以"实时"只能是准实时轮询:账套限流 500 次/分钟,一轮只 3~4 次调用 ⇒ 5 分钟一轮开销可忽略;
再快(1 分钟)技术上可行但没意义 —— 单据审核 → 转ERP 本身是分钟级链路。
