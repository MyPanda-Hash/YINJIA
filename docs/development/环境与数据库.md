# 环境与数据库（一系统两账套：登录工厂即切换）

> ADR-0003：单一系统、单实例（8090），登录页「登录工厂」选择即切换账套。
> YJ = 正式库 HSDZ_MES；YJ_TEST = 测试库 HSDZ_MES_TEST。令牌(JWT)携带工厂声明，
> 后端按声明把请求线程路由到对应库（每账套独立 Hikari 连接池，各 10 连接）。
>
> **全库表清单（437 表 + 101 视图逐张登记：表名/中文名/列数/关联面板/归属模块）见 [数据库表清单](数据库表清单.md)**；
> 新增表必须带 `MS_Description` 中文注明并刷新该清单（AGENTS.md「数据库注明」规范）。

## 使用

| 登录工厂选择 | 数据库 | 顶栏/登录页显示 |
|------|--------|------|
| YINJIA-MES | `HSDZ_MES`（正式） | YINJIA-MES |
| YINJIA-MES·测试库 | `HSDZ_MES_TEST`（测试） | YINJIA-MES·测试库 |

- 切换账套 = 退出后重新登录选另一个工厂（令牌在签发时绑定工厂，改选必须重登）。
- 两个工厂的令牌可以并存（不同浏览器/标签页各登各的），互不影响。
- 无工厂声明的旧令牌/API 直连默认落**正式库**（安全默认）。

## 测试库(HSDZ_MES_TEST):定位、陈旧判定与重建

### 定位

**测试库 = 正式库的一份快照副本**（由 `make-test-db.ps1` 的备份还原而来），用途是
「演示 / 试用 / 批量造数」；**正式库只录真实业务**。它对正式库没有任何权威性，
可以随便折腾、随时重建。

### ⚠️ 两种「陈旧」，处置完全不同（别混）

| 类型 | 症状 | 处置 |
|---|---|---|
| **数据陈旧**（正常） | 行数据是快照时点的，与正式库不同步（jdy-sync 只写正式库） | 不用管；要新数据就重建 |
| **结构陈旧 / 不同源**（危险） | **同一面板：正式库 200，测试库报 `列名 'x' 无效`** | **不要逐张表补迁移**，直接重建（见下） |

**结构陈旧为什么「补」不好**（2026-09-22 实测）：测试库的快照年代较早，里面可能有
**同名但结构完全不同**的对象 —— 例如它的 `bl_dispatch` 是 27 列**英文旧表**
（`dispatch_no / dispatch_date / biz_type / plan_qty / …`），而正式库是中文列
（`单据编号 / 工序编码 / 计划数量 / …`）。迁移脚本里遍地是
`IF OBJECT_ID('bl_dispatch') IS NULL CREATE TABLE …` —— 表「已存在」⇒ 建表被跳过，
随后所有中文列的 INSERT / SELECT 一律报「列名无效」。**一条条补下去是打地鼠**：
2026-09-22 实测给测试库补迁移，修掉两处脚本后第 21 条又撞上这个结构差异，链条反复中止。

> **判定口诀：正式库正常、测试库报「列名/对象无效」⇒ 别修，重建。**

### 重建（唯一推荐的修法）

```powershell
# 需 SQL sysadmin（本机 Windows 账号 DESKTOP-JHUNFT6\Lenovo 即是，集成认证即可，无需额外提权；
# 旧文档里写的 PANDA\x1787 是机器/账号改名前，2026-10-22 已核实更正 —— 见文末「sa 密码」一节）
powershell -ExecutionPolicy Bypass -File tools/scripts/make-test-db.ps1
```

- 做法：`BACKUP DATABASE HSDZ_MES` → `RESTORE ... WITH MOVE, REPLACE` 为 `HSDZ_MES_TEST`
  （存在则覆盖）→ 把 `yinjia` 授为测试库 `db_owner` → 打印表数。
- **会覆盖测试库全部数据**（含探针账号与造数）。要留底就先自己 `BACKUP DATABASE HSDZ_MES_TEST`。
- ⚠ **副作用**：重建时 `ALTER DATABASE … SINGLE_USER WITH ROLLBACK IMMEDIATE` 会
  **踢掉 8090 应用连测试库的连接池**。正式库连接池不受影响、**应用不会停**，
  Hikari 下次取连接时自愈；重建瞬间若有请求落在测试账套会短暂报错。
- **重建后核对**（两库应逐项相等）：

  ```sql
  -- 逐库执行；⚠ 必须用 sysadmin(sqlcmd -E)，见下方「已知坑 2」
  SELECT (SELECT COUNT(*) FROM sys.tables) tbls, (SELECT COUNT(*) FROM sys.columns) cols,
         (SELECT COUNT(*) FROM yj_panel) panels, (SELECT COUNT(*) FROM yj_field) fields,
         (SELECT COUNT(*) FROM yj_schema_log) logrows;
  ```
  2026-09-22 实测重建后两库均 **442 表 / 13984 列 / 163 面板 / 3904 字段 / 187 登记**。

### 字段/元数据漂移:用对齐脚本(比重建轻,不丢测试数据)

重建最稳,但**会覆盖测试库全部数据**。若漂移只在「字段/元数据」层面(缺几列、缺视图、
yj_field 的显示名/顺序/参照源被改过、多出若干行),用对齐脚本更合适 —— 2026-10-08 走的就是这条路径
(依据 `docs/development/采购链四单字段与显示字段.md` 这份四单基线)。

**三步取证(全只读,在 `tools` 目录跑,需 `YINJIA_SQL_PASS`)**:

| 工具 | 比什么 |
|---|---|
| `java -cp lib\mssql-jdbc.jar DbSchemaDiff.java <正式JDBC> <测试JDBC> yinjia env` | 表 / 列 / 视图 / 面板 / **字段集合** |
| `java -cp lib\mssql-jdbc.jar archive\_YjFieldAlign.java <正式JDBC> <测试JDBC> yinjia env ALL [--sql]` | yj_field **属性值**(显示名/顺序/place/参照源/可见性…);行身份 = **面板+字段+place**,按**多重集**比;`--sql` 直接给出对齐 SQL |
| `node tools\archive\_q-ledger-field-compare.mjs` | **运行时**(后端实际下发的字段与顺序):分别用登录工厂 `YJ` / `YJ_TEST` 取四单配置逐段比 |

> ⚠️ **只跑前两个会漏**。同一个 `(面板, 字段)` 在 `yj_field` 里可以有多行(既在查询区/表头又在明细页签,
> `place` 不同;甚至完全重复)。2026-10-08 实测就漏掉 4 处(两处 `seq`、一处 `hidden/visible`、一处重复行):
> **库侧报 IDENTICAL,界面顺序仍不一致** ⇒ 三个都要跑,不一致时以「运行时」为准。

**已落地的对齐脚本(两账套都跑;正式库上全部带守卫 = no-op)**:

- `tools/migrate-align-ledger-fields-20261008.sql` —— 第一轮:`bs_line_capacity` 补 `备用1-20`、
  `bl_sale_out.仓库` 宽度对齐 `nvarchar(1000)`、建视图 `v_manu_schedule`、删测试库多出的 10 行 yj_field、
  按正式库取值改 234 行。
- `tools/migrate-align-ledger-fields2-20261008.sql` —— 第二轮:补上面那 4 处盲区(带 `place` + 旧值守卫,
  不用 id 定位 —— 两账套 id 是各自历史,同一个 id 在两边可能是不同字段行)。

**收尾口径(2026-10-08 实测)**:`DbSchemaDiff` / `_YjFieldAlign(ALL)` / `_q-ledger-field-compare`
**三项全 `IDENTICAL`**;`DbNormAudit` 两账套均 **FAIL-7**(与正式库既有基线一致,无新增);
四单基线文档重生成 **12/12 一致、`git diff` 仅「登记日期」一行**(⇒ 正式库未被改动)。

### 与测试库有关的已知坑

1. **元数据与译名缓存已按账套隔离**（2026-09-22 修复，技术债 #11 已结清）。
   修复前 `PanelRegistry` 只有一个 `cache` 字段 + 30s TTL、`TranslationService` 的译名缓存只按**语言**做键
   ⇒ 两账套在 TTL 窗口内**共用同一份**，「谁先刷新谁说了算」——症状是
   **在测试账套新增/改了面板、字段或译名，接口看不见**（实测：向测试库插入 `RD_SHARE_FILE` 面板行后
   连续 8 轮请求仍报不存在；测试库改的面板名译名被正式库的缓存盖住）。
   现在两者都按 `DataSourceRouter.current()` 各存一份快照（面板按账套、译名按「账套+语言」）。
   **回归探针**：`node tools/verify/ledger-cache-isolation-test.cjs` ——
   自己造出"测试库独有"的面板与译名（用完即删/还原），断言正式库看不见、测试库看得见 ×3 轮，
   并以两账套都有的 `PARTNER` 作负向对照。
   写这一类"两账套差异"的探针时注意：**两账套交替问同一接口、答案相同 ≠ 数据相同**（踩坑台账 D17）。
2. **权限过滤会让统计数字不可比**：`yinjia` 在测试库是 `db_owner`（看得全），
   在正式库**不是**（`sys.columns` 受元数据可见性过滤 ⇒ 列数偏小）。
   核对两库规模**必须用 sysadmin（`sqlcmd -E`）**，否则会得出「结构不一致」的假结论
   （2026-09-22 实测：同一正式库，`yinjia` 数出 13911 列、sysadmin 数出 13984 列）。

## ⚠️ 「迁移登记 ≠ 已生效」:本地库漏列的排查与修复(2026-10-15)

`yj_schema_log` 只证明「这条脚本被**登记**过」,**不证明它的效果在库里**。DbSync 按内容哈希判断要不要重跑
⇒ 一条脚本只要被 `baseline`(只登记不执行)登记过、或事后本地库被更旧的快照覆盖过,它就**永远不会再跑**,
库于是静默缺列/缺字段,**而且 `DbSync` 报的仍是「执行 0、失败 0」——体检全绿**。

实测两例,形态完全一样(**代码要用、本地没有、服务器有**):

| 缺什么 | 谁在用 | 症状 | 修法 |
|---|---|---|---|
| `qc_insp_detail.单位` | `ButtonService.inspAutoReturn` 的 SELECT | **来料检验单审核直接 500**(`Invalid column name '单位'`) | `DbSync run migrate-sl-chain-fixes.sql` —— 该脚本 `:42` 本来就补这列,只是登记了没真跑 |
| `bs_inv.来料检验` | `QcRecvGenerateHandler:177` 逐行分流 | **送料暂收单「生成检验或入库单」500** | `tools/migrate-bs-inv-inspection-align-20261015.sql`(对齐服务器:建真实列 + 回填 + INV 面板字段改名) |

排查口径(任一):

1. **逐条核对脚本声明的对象是否真在库里**:`node tools/archive/_verify-migration-claims.mjs`(用法见文件头);
2. **拿「服务器备份还原出来的对照库」直接 diff 列**(最直接):
   ```sql
   SELECT s.name FROM <服务器对照库>.sys.columns s
   WHERE s.object_id = OBJECT_ID('<服务器对照库>.dbo.<表>')
     AND NOT EXISTS (SELECT 1 FROM HSDZ_MES.sys.columns l
                     WHERE l.object_id = OBJECT_ID('HSDZ_MES.dbo.<表>') AND l.name = s.name);
   ```
3. 结论落库后,**补一个幂等迁移脚本**并登记进 `tools/db-migrations.txt` ——
   **不要**手工 ALTER 了事:手工改不进哈希链,下次整库恢复/重建测试库又会丢。

> **教训**:别把 `baseline` 当「补登记」随手用 —— 它会把没执行过的脚本写成「已执行」,
> 效果永久缺席,而且症状会伪装成"代码 bug"(列名无效 / 按钮 500)。用之前先跑上面第 1 条取证。

## 日常约定

1. **演示/试用/批量造数 → 登录工厂选「测试库」**；正式库只录真实业务。
2. **迁移脚本**（tools/migrate-*.sql）两个账套都要执行：先正式、后测试（脚本均幂等）。
   - 执行方式二选一：`tools/SqlRunner.java <jdbcUrl> yinjia env <脚本.sql>`，或在 tools 目录下
     `YINJIA_SQL_DB=HSDZ_MES_TEST java -cp lib/mssql-jdbc.jar DbSync.java`。
   - 🔴 **脚本里写无条件 `USE HSDZ_MES;` 会把会话切回正式库**（2026-09-21 实测：连测试库执行后
     `DB_NAME()` 变成 `HSDZ_MES`）——"给测试账套补迁移"实际改的是生产库、测试库一条没补，且**不报错**。
     一律用守卫形式 `IF DB_NAME() = N'master' USE HSDZ_MES;`（只在未选定库时才切）；**不要直接删该行**，
     `yinjia` 登录的默认库是 `master`，删了会在 master 里建表。DbSync 已加拦截（exit 3）防复发。
3. **jdy-sync 定时任务只写正式库**（每 5 分钟同步星辰销售订单）；测试库销售订单需自造。
4. 启停：`tools/scripts/start-prod.ps1`（`-Stop` 停止）。OCR 密钥走环境变量，脚本不落密钥。
5. 🔴 **别用 `backend/start-backend.bat` 起后端**（2026-10-08 实测踩坑，代价是两次 `mvn package` 失败 + 一个不可运行的瘦 jar）。
   它是**保活循环**（`start-backend.bat:22-27`：`java -jar` 退出后 `timeout 5` 再 `goto loop`），带来两个后果：

   | 后果 | 现象 | 原因 |
   |---|---|---|
   | **抢 jar，打包必失败** | `mvn package` 报 `spring-boot:repackage ... Unable to rename '...jar' to '...jar.original'`，且**磁盘上留下一个瘦 jar**（无 `BOOT-INF`，`java -jar` 起不来） | 你停掉 java → 它 5 秒后重拉 → 新 JVM 立刻占住 jar；repackage 要先把原 jar 改名，改名被拒 |
   | **不注入 `backend\.env`**（潜在） | 若 `backend\.env` 存在，用它起的实例会缺 OCR 密钥 / 空机翻词典（**静默降级**，不报错） | 该 bat 没有注入逻辑；`start-prod.ps1:15-28` 才有 |

   > ⚠ 本机实测（2026-10-08）：`backend\.env` **当前并不存在**，所以这条差异是**潜在的、尚未生效**——
   > 两条路径当下都跑在无密钥的降级态（`/api/locale/dict` 返回 500）。等 `.env` 补上后，用 bat 起就会中招。

   **正确做法**：一律 `tools/scripts/start-prod.ps1`（自带 `.env` 注入 + 启动前 `sync-db` + 幂等）。
   **要重打 jar 时**：先停掉保活窗口（那个 `cmd.exe`，命令行含 `start-backend.bat`）→ 再停 8090
   （`start-prod.ps1 -Stop`）→ 确认 `Get-NetTCPConnection -LocalPort 8090` 无监听 →
   **删掉 `backend\target\yinjia-mes-backend-0.1.0.jar`**（有存量时 repackage 的 rename 仍可能失败）→
   `mvn -DskipTests package` → 校验 `jar tf … | grep BOOT-INF/` 非空 → `start-prod.ps1` 重启。
   ⚠ 只跑构建不看这条：`mvn` 会「BUILD SUCCESS」一半又失败，且失败产物会被后续误当成品启动。

## 开发机环境:必须 JDK 25(2026-09-22 已统一到系统级)

后端硬要求 JDK 25:`backend/pom.xml` 里 `<java.version>25</java.version>`,
打出来的 class 是 **major 69**(= Java 25)。用 21/24 编译会直接报
`错误: 不支持发行版本 25`;用低版本 JDK 跑 jar 会报 `UnsupportedClassVersionError`。

**当前状态(2026-09-22 设置并实测)**:

| 项 | 值 |
|---|---|
| 系统默认 `java` / `javac` | **`C:\Program Files\Java\jdk-25\bin\…` → 25.0.2**(Microsoft build) |
| Machine `JAVA_HOME` | `C:\Program Files\Java\jdk-25` |
| Machine `PATH[0]` | `C:\Program Files\Java\jdk-25\bin`(前置,压过下面的 javapath) |
| 旧 Oracle JDK 24 | 仍在(`C:\Program Files\Java\jdk-24` + `Common Files\Oracle\Java\javapath` 的 PATH 条目都保留),但**已被遮蔽**,`java` 不再解析到它 |
| 用户级 `JAVA_HOME` | **已清空** —— 单一真源是 Machine 级(用户级会覆盖 Machine 级,留着会分叉) |

设置方式与回滚(脚本在仓库里,可重跑/可复现):

```powershell
# 提权执行(UAC);幂等:已存在则跳过复制,只重设环境变量
Start-Process powershell -Verb RunAs -ArgumentList '-NoProfile','-ExecutionPolicy','Bypass',
  '-File','C:\INCER\YINJIA-MES\tools\archive\_set-jdk25-default.ps1'
# 回滚:按 %TEMP%\set-jdk25-default-rollback.txt 里的两行还原 Machine PATH/JAVA_HOME
```

脚本做的事:① 把已装的 JDK 25 复制到 `C:\Program Files\Java\jdk-25`(机器级稳定路径,
不依赖 IDE 的用户目录 `%USERPROFILE%\.jdk`,那个目录会被 IDE 清理);
② 设 Machine `JAVA_HOME`;③ 把它的 `bin` **前置**到 Machine `PATH`;④ 广播 `WM_SETTINGCHANGE`
(否则 Explorer 启动的程序仍拿旧环境);⑤ 写回滚文件。

⚠ **两个实测坑**:
- **Windows 的 PATH 是「系统在前、用户在后」** ⇒ 往**用户 PATH** 加 JDK 25 覆盖不了
  Machine 级 javapath 里的 java(24),必须改 Machine 级、且**前置**(不是追加)。
- 校验用 `java -version` / `javac -version` 各跑一次(实测均 25.0.2),并 `where java` 看**第一项**
  是不是 JDK 25 —— 光看"命令能跑"不够:javapath 还排在后面,顺序错了照样解析到 24。
- 已经打开的终端/cmd 窗口**要重开**才拿到新环境(环境变量只对新进程生效)。

**新写脚本请沿用统一探测,不要把 JDK 路径写死**:`JAVA_HOME` →
`C:\Program Files\Java\jdk-25` → `D:\Program Files\Java\jdk-25` → `%USERPROFILE%\.jdk\jdk-25\jdk-25.0.2`,
都找不到才报错(2026-09-22 刚从两处硬编码 `jdk-24` 改成探测式:硬编码在换版本/换机器后必挂)。
`mvn` 直接跑即可(会取 Machine `JAVA_HOME`);验证:
`& C:\INCER\YINJIA-MES\tools\apache-maven-3.9.9\bin\mvn.cmd -version` → 应显示 `Java version: 25.0.2`。

服务器侧要求与安装步骤见 `deploy/部署说明.md` §4 与 `docs/deploy/服务器部署.md`(均为 JDK 25)。

## SQL Server 的 sa 密码：谁能改、怎么重置（2026-10-22 实测）

本机实例 = **`MSSQLSERVER`（默认实例）**，SQL Server 2019 Enterprise `15.0.2000`，
混合认证**已开**（`IsIntegratedSecurityOnly = 0`），服务账户是 `NT Service\MSSQLSERVER`。

| 登录 | 角色 | 用途 |
|---|---|---|
| `sa` | **唯一 sysadmin** | 只有它能改别人的密码/做实例级操作 |
| `yinjia` | 各库 `db_owner`，**不是** sysadmin、**没有** `ALTER ANY LOGIN` | MES 应用、`DbSync`/`SqlRunner` 等仓库脚本全都用它 |
| `mes_app` | 非 sysadmin | 历史遗留登录（ERP/老工具） |

**实例里没有任何 Windows 登录**（连 `NT AUTHORITY\SYSTEM`、`BUILTIN\Administrators` 都没加）。
所以「用 Windows 账号登进去提权」这条路，只有在**集成认证能通过**时才成立 —— 实测可以通过，
但有个必须知道的细节：

```powershell
# ✅ 能用：走本机共享内存/本地实例名，返回 DESKTOP-JHUNFT6\Lenovo + sysadmin=1
sqlcmd -S . -E -C -Q "SELECT SUSER_SNAME(), IS_SRVROLEMEMBER('sysadmin')"
sqlcmd -S localhost -E -C -Q "..."

# ❌ 不能用：同一个账号走 TCP 回环会报「登录失败…该登录名来自不受信任的域」(18452)
sqlcmd -S 127.0.0.1,1433 -E -C -Q "..."
```

> 原因是本机在 **WORKGROUP**、账号是本地账号，SQL Server 对"TCP 进来的集成认证"判不出信任域；
> 换成 `-S .`（共享内存）就正常。**排查/重置一律用 `-S .`**，别在 `-S 127.0.0.1,1433 -E` 上死磕。

### 重置 sa 密码（在线，不需要重启实例）

```powershell
# 1) 改密码（sa 的 CHECK_POLICY=1：新密码要过本机密码策略；报 15118 就换更复杂的，
#    或临时 ALTER LOGIN sa WITH CHECK_POLICY = OFF 后再改，改完建议再 ON 回来）
sqlcmd -S . -E -C -b -Q "ALTER LOGIN sa WITH PASSWORD = N'<新密码>';"

# 2) 确认启用（sa 默认是禁用的；本机当前为启用）
sqlcmd -S . -E -C -b -Q "ALTER LOGIN sa ENABLE;"

# 3) 验证：分别验「集成认证侧」与「TCP/SQL 认证侧」
sqlcmd -S . -E -C -Q "SELECT name, is_disabled, is_policy_checked FROM sys.sql_logins WHERE name = 'sa';"
java -cp tools\lib\mssql-jdbc.jar tools\SqlRunner.java `
  "jdbc:sqlserver://127.0.0.1:1433;databaseName=HSDZ_MES;encrypt=false" sa "<新密码>" tools\archive\_sa-reset-20261022\_q-verify.sql
```

要点：

- **改 sa 不影响 MES 运行**：应用/脚本连的是 `yinjia`，8090 不用重启、连接池不动；
- **不需要 `SINGLE_USER` 重启**：本机有可用的 sysadmin 入口（`-S . -E`）；
  只有把这条入口也弄丢了（例如删掉/改名本地管理员、实例不开集成认证），才需要
  「停服务 → `net start MSSQLSERVER /m"SQLCMD"` 单用户模式 → 改完再正常启动」这条兜底路，
  那条路会**断开所有连接**（8090 会短暂报错，Hikari 自愈）。
- **口令不进仓库**：`sa` 的新密码只由管理员当面设定/保管，不要写进脚本、文档、`.env` 或提交记录；
  仓库脚本一律用 `yinjia`（默认口令在 `tools/DbSync.java` 里，属历史遗留）。
- 安全建议：日常用不到 `sa` 就 `ALTER LOGIN sa DISABLE;`，需要时再 ENABLE。
