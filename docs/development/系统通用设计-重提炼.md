## 0. 结论先行

**可提炼的是「注册表 + 横切基座」这套骨架,不是「面板引擎」这个成品。**

| 判定 | 内容 | 抄写成本 |
|---|---|---|
| **真通用** | `config/` 包 8 个横切文件、`panel/` 包约 2KB 动作注册表三件套、`DataSourceRouter` 多账套切库、`ApiResult` 统一响应体 | 约 2 天 |
| **半通用** | `PushGenerateHandler` 生单引擎、`PanelConfigService` 元数据装配器、`PanelPermissionService` 权限闸门、自写口令哈希 | 3–5 天,需剥离静态映射表 |
| **私有(换项目即废)** | `ButtonService.java`(5312 行 God Object)、5 张静态业务映射表、6 个具体 handler 的业务逻辑、239 处中文表名字段名 SQL | 不可复用,只能重写 |

一句话证据:字段确实是 DB 元数据(`yj_panel`/`yj_field`)驱动的,但**业务动作全部塌缩进 `ButtonService.java` 这一个文件**;注册表框架只接管了 6 个动作,其余全靠 `service/PxRuntimeService.java:80` 那行 `return buttonService.callButton(...)` 兜底。所以对外只能说「注册表这套骨架可抄」,不能说「面板引擎可抄」。

**第二个结论:本项目最独特的资产不是代码,是约束。** [开发与质量.md](开发与质量.md) §5.5 的踩坑台账(:162 起)是真实事故换来的、带症状与规避做法的硬约束(详见第 6 节)。任何重写不做这几十条约束,就会把同样的坑重踩一遍。

## 1. 契约层:面板引擎对外承诺什么

这一层是**真的成立**的设计。它把"改面板"从"改代码"里摘了出来——但只摘了一半(字段摘了,流程和按钮没摘,见第 5 节)。

### 1.1 元数据模型

面板与字段全部由数据库行描述,不在代码里:

- `yj_panel` —— 面板定义(面板码、名称、表名、模式、分组)
- `yj_field` —— 字段定义(所属面板、位置、标签、类型、参照、字典、序号、别名、可见性)

**数据键是中文,且永不随界面语言改变。** 这是整个系统的地基(见 [ADR-0001](adr/0001-dictionary-only-translation.md)):

| 概念 | 规则 |
|---|---|
| `dataName` / `buttonName` / 单据状态存储值 | 永远中文,跨语言不变 |
| 业务事实数据(客户名、物料的名称) | 不翻译 |
| 机翻 | **只兜底显示层**,结果缓存进 `yj_translation(source='mt')` |
| 新增面板/字段 | 必须同时交付多语言,否则**功能未完成** |

这条约束的代价必须诚实写明:**中文数据键让跨库移植变得不可能**。239 处 SQL 全是中文表名/字段名,换一个项目、换一套库,这些 SQL 一行都用不了。中文键换来了"MES 领域里业务人员能直接读懂数据结构和界面配置"以及"界面语言切换不影响数据契约",代价是牺牲了跨项目可移植性——这是**有意的取舍,不是疏忽**。

### 1.2 运行时契约(26 个必需方法,但只有一半左右真通用)

前端 `frontend/src/core/panel-runtime.js:1-28` 定义 `REQUIRED_METHODS`,共 **26 个**——这是"通用视图 ↔ 私有适配器"之间唯一的接缝,也是整个 core 里最值得通用化的一处。但它当前**把通用契约与业务打印能力混在同一张清单里**:

| 组 | 方法 | 判定 |
|---|---|---|
| **通用契约(13)** | `getPanelConfig`、`getPermMatrix`、`getNewFormPermMatrix`、`getFormDescriptor`、`queryFormDataList`、`callButton`(**唯一动作入口**)、`deleteForms`、`recognizeFormImage`、`queryRefRows`、`refPanelName`、`refColumns`、`refLabelOf`、`fieldOptions` | **换项目原样保留** |
| **通用工具(6)** | `fillCurrentStock`、`roundDecimal`、`errMsg`、`extFieldOverview`、`extFieldAdd`、`extFieldRetire` | 保留,`roundDecimal` 必须与后端逐位一致 |
| **业务打印(7,应降为可选钩子)** | `printPuOrder`、`printPuOrderNoAmount`、`printQcReturn`、`printProductCards`、`printLocationCards`、`printProductionTask`、`woQrText` | **私有**:采购单打印、品检退货打印、工单二维码文本;换项目必然要改契约本身 |

**建议的拆法**:契约只强制「通用契约 + 通用工具」两组,业务打印改为 `optionalHooks`。否则 `frontend/src/core/README.md:28` 那句"PLM 可以提供自己的适配器、不需要复制通用视图"在实现上不成立——适配器必须实现 7 个炭棒/品质业务打印方法才能通过 `installPanelRuntime` 的校验。

校验行为:`installPanelRuntime` 缺失方法时抛 `` `Panel runtime is missing: ${missing.join(', ')}` ``;`usePanelRuntime` 未安装时抛 `Panel runtime has not been installed`;`installAppContext` 用 `Object.freeze({...context})`。

⚠ 安全欠账(已修):`getPanelConfig`/`getPermMatrix`/`getNewFormPermMatrix`/`saveColumnPrefs`/`saveHeaderPrefs` 这 5 个 GET 接口**在 2026-09-22 之前完全无闸门**——任何登录用户拿 token 就能取任意面板的字段结构与字典绑定。修法见 `service/PanelPermissionService.java:159-170`。**这说明"契约"设计得再好,授权也必须逐个接口过一遍,不能靠入口统一。**

### 1.3 面板模式

**`yj_panel.mode` 是 3 个值的枚举,不是自由文本**,截至本次审计共 **79 张在册面板**:`doc` 33 张 / `flat` 23 张 / `archive` 23 张。模式决定了 save 走哪条路径、是否参与审批状态机、是否生成单号。

| mode | 中文名 | 张数 | 语义 | 关键实现点 |
|---|---|---|---|---|
| `doc` | 文档式 | 33 | 头(`bd_`)+ 行(`bl_`)成对,参与审批状态机,有单号前缀 | `PanelRegistry.java:50 public boolean isDoc() { return "doc".equals(mode); }`;新建时 `PanelFacade.java:40-46` 写入 `单据状态=草稿`、`单据日期=当天`,并按 `prefix` 预生成单号 |
| `archive` | 档案式 | 23 | 单表基础档案,状态字段叫 `状态` 而非 `单据状态` | `PanelFacade.java:47-48 } else if ("archive".equals(def.mode())) { data.put("状态", "启用");`(注释自证 `panelState.dataName=状态`);走 `PanelConfigService.java:66 buildArchiveConfig(def)` |
| `flat` | 平铺式 | 23 | 视图平铺,无头无明细,不参与状态机 | `PanelConfigService.java:234 boolean flat = "flat".equals(def.mode());`;查询走 `QueryService.java:58 if ("flat".equals(def.mode())) return queryFlat(def, ...)` |

**判定方式**:后端统一走 `PanelDef` 的 `isDoc()` + 两处 `"archive".equals(def.mode())` 字面量(`PanelFacade.java:47`、`PanelConfigService.java:66/:1447/:1758`)+ 一处 `"flat".equals`(`QueryService.java:58`、`PanelConfigService.java:234`)。**没有枚举类,没有 `isArchive()`/`isFlat()` 方法**——`doc` 有方法,另两种靠散落字面量比较,这是本设计的一处不一致。

**前端不认 `mode`,认面板码白名单**:`frontend/src/core/views/PanelxList.vue:1905 const isApprovalDoc = computed(() => ['RD_APPROVAL', 'RD_PLAN', 'RD_PROGRESS', 'RD_PROD_DOCLIST', 'RD_FILTER_EFF', 'QC_CATALOG', 'QC_INSP_REC', ...RECORD_SHEET_PANELS, ...Object.keys(qcSheetCfgs)].includes(String(panelCode.value)))` —— 在 `doc`(33) 之外又用 7 个硬编码面板码 + 两张配置文件的 key 集合重新划分了一遍范围。`archive` 同样:`:1904 const RECORD_SHEET_PANELS = Object.keys(recordSheetConfigs)`(`frontend/src/core/views/recordSheetConfigs.js`,1655 行),`:1906 const isRecordSheetPanel = computed(() => RECORD_SHEET_PANELS.includes(String(panelCode.value)))`。

**这是全系统最贵的一处口径分裂**:同一件事(这张面板是不是档案式)后端答"`mode` 字段",前端答"面板码在不在这个数组里",而两个答案的交集从没被断言过。`frontend/src/core/views/recordSheetConfigs.js` 的 key 是否与 `yj_panel` 中 `mode='archive'` 的 23 个 `panel_code` 一致,**本次审计未验证**——这正是一个应当自动化断言的点(参 `recordSheetConfigs.keys.test.js` 的同类做法)。

### 1.4 动作注册表(约 2KB,本次审计最干净的机制)

三个文件,总共约 2KB,零业务耦合:

| 文件 | 角色 |
|---|---|
| `backend/src/main/java/com/yinjia/mes/panel/PanelActionHandler.java:9-13` | 处理器接口:`boolean supports(String panelCode, String action)` + `Map<String,Object> handle(PanelActionContext)` |
| `backend/src/main/java/com/yinjia/mes/panel/PanelActionContext.java:6` | 上下文:`record PanelActionContext(String panelCode, String action, Map formData, Map parameters, String userName)` |
| `backend/src/main/java/com/yinjia/mes/panel/PanelActionRegistry.java:11` | 注册表:构造注入 `List<PanelActionHandler>`,`:20` `Optional dispatch(...)`,`:26` 匹配 >1 时抛 `IllegalStateException("面板动作存在多个处理器："+panelCode+"/"+action)` |

**这是本文最推荐照抄的一块。** 它诚实、小、可测。核心是**三态分派契约**(`PanelActionRegistry.java:19-27`):

- **零匹配 → `Optional.empty()`** ⇒ 交回通用生命周期。**"没写专属实现"是合法的,不是错误。**
- **多匹配 → 抛 `IllegalStateException("面板动作存在多个处理器："+panelCode+"/"+action)`** ⇒ **配置错误必须当场炸。**
- 唯一匹配 → `handle(ctx)`。

这三态的语义(`零匹配合法、多匹配即配置错误`)是最值得单独抄的部分:它把"扩展点未命中"从异常变成了正常回落。**多数自研扩展点机制做反了**——未命中抛异常,于是每加一个按钮都得先注册一个空实现。

配套两条:`PanelActionRegistry.java:14-17` 靠 Spring 集合注入自动收集全部处理器再加 `List.copyOf` 冻结,**加一个专属按钮 = 新增一个类,不改注册表**;`PanelActionContext.java:6-11` 的签名里**没有任何业务类型**。

⚠ 但必须同时说明它的**实际覆盖面只有 6 个动作**。分发次序在 `service/PxRuntimeService.java:74-81`:

```java
var dispatched = actionRegistry.dispatch(new PanelActionContext(panelCode, buttonName, formData, buttonParam, currentUserName()));
if (dispatched.isPresent()) return dispatched.get();
return buttonService.callButton(panelCode, buttonName, formData, buttonParam);   // :80 兜底
```

这是一层**迁移兼容层,不是解耦完成**。对外讲这套设计时,不能把 `PxRuntimeService.java:74-81` 说成"注册表分发",它实际是"注册表优先、God Object 兜底"的双轨制。**「扩展点优先、未命中回落通用生命周期」本身是可复用的装配定式**,它让控制器只认一个契约、新老实现共存、老实现不必改一行。

另一条:`PxRuntimeService.java:88-91` 的 `currentUserName()` 从 `SecurityContextHolder` 取不到就返回 `"system"`,**不抛异常**——对定时任务与内部调用友好。这是"认证缺失"与"认证失败"该分开处理的证据。

### 2.1 最值得抄:多账套运行时切库

**同一个应用、同一份代码,在一次请求内决定读哪个库**——这是本案最值得带走的设计。

机制:`JwtAuthFilter` 从令牌里解出 `factory`(`prod`/`test`),写进 `DataSourceRouter` 的 ThreadLocal;`AbstractRoutingDataSource` 在每次取连接时读 ThreadLocal 选池。所以**切换工厂不需要重启、不需要两套部署**。

两条必须一起带的约束:

1. 每个账套**独立 Hikari 池**(上限 10),不是共用一个池换库名——否则连接串缓存会串账套。
2. 令牌里没声明 `factory` 时**回退 prod**(`JwtUtil.java:57`)。这是安全默认值:漏配等于收紧,不是放开。

### 2.2 异常处理的"两套约定"

`GlobalExceptionHandler.java:15-19` 的类注释说明了一个**值得单独写下来的设计决策**:

- 通用业务异常 → 保持 HTTP 状态码(400/409)
- OCR / 上传 / 权限 → 走 **body-code**,HTTP 状态码刻意不用 403

理由是:前端拦截器对 HTTP 403 的既定行为是**登出**。如果权限不足也回 403,用户会莫名其妙被踢出登录。所以权限拒绝回 `200 + body code`,由前端按业务错误提示。

**这是一个用事故换来的设计**:通用规则(HTTP 语义正确)与产品行为(403 触发登出)冲突时,选了后者,并把理由留在了注释里。抄这套设计时这条注释必须一起抄,否则下一个人会"顺手修正"回 403。

| **明细键口径分叉(core/ 包内部)** | 明细键本应由 `yj_panel.detail_key` 在运行时解析,`backend/src/main/java/com/yinjia/mes/service/PanelRegistry.java:56-59` 的 `tabKey()` 就是这么写的(`return detailKey == null \|\| detailKey.isBlank() ? ### 6.4 若干条带来的通用原则(比单条约束更值钱)

把上面几十条压成可复用的原则,这是真正该带走的:

1. **静默失败比报错危险。** D11(REPLACE 静默空操作)、D13(每结果集截断 50 行)、D18(null 让条件恒不成立)、C9(假阴性进了报告)、D12(打穿隔离且不报错)、G9(Maven 静默建目录)——**本项目最贵的 bug 全是"什么也没发生"**。任何新工具/新脚本都要问一句:失败时会响吗?
2. **可见性判断必须用几何(rect),不能用 DOM 关系(offsetParent)。** E7/E8/E10 是同一类错误的三个变体。自动化验收里"假绿"比"假红"贵得多。
3. **中文数据键的代价是双向的。** 换来的是业务人员可读、界面语言与数据契约解耦;付出的是跨库不可移植、工具链全程要防编码事故(C 组)、SQL 里 `NCHAR(65533)` 这类坑。**这个取舍必须在立项时说清楚**,不能等到要换库才发现。
4. **校验必须在服务端。** `ButtonService.java:415/:522` 的注释自曝"此前必填只在前端校验,直连 `/px/callButton` 就能把缺必填的单提交/归档"。前端校验是体验,后端校验才是约束。
5. **构建坏了等于修复没交付。** G11 的收尾口径:2026-10-08 改好的前端进不了 jar,线上 8090 一直跑旧前端。任何"改完了"的结论必须包含"构建产物已验证"。

## 7. 迁移清单:照做几步

按"先骨架后业务"排。**每步都给出验证方式**——没有验证方式的步骤不算步骤。

| # | 步骤 | 内容 | 工期 | 验证 |
|---|---|---|---|---|
| 1 | 横切基座 | 抄 `config/` 8 文件:`ApiResult` + `GlobalExceptionHandler`(12 handler + 双约定) + JWT 三件套 + `DataSourceRouter`/`DataSourceConfig` | 1 天 | 起服务,登录取 token,切账套后 `DB_NAME()` 随之变化;故意触发权限不足,确认 HTTP 200 + body-code 而非 403 |
| 2 | 动作注册表 | 抄 `PanelActionRegistry` + `PanelActionHandler` + `PanelActionContext`(约 2KB) | 0.5 天 | 注册两个 `supports` 命中的 handler,确认抛 `IllegalStateException("面板动作存在多个处理器：…")` |
| 3 | 元数据表 | 建 `yj_panel`/`yj_field` + **把 5 张静态映射表搬进 DB**(一步到位,不要先静态后搬) | 1–2 天 | 改一行元数据新增一个按钮,不改代码重启后按钮出现 |
| 4 | 元数据装配器 | 抄 `PanelConfigService` 的结构(装配器集中,业务特判点状显眼,3 处特判换配置项) | 1–2 天 | 新面板只插 `yj_panel`/`yj_field` 两行即可在列表页出现 |
| 5 | 单一动作入口 | 只保留 `callButton` 一个动作入口,**权限闸门默认拒绝** + 显式登记 | 1 天 | 未登记按钮 → 拒绝且报"当前角色无该面板「x」权限";直连 `callButton` 提交缺必填单据 → 服务端拒绝 |
| 6 | 生单引擎 | 抄 `PushGenerateHandler` 的形状:**排除法声明 + `isBatchTarget` 式的结构判定** | 1 天 | 新增一个带"批次号"字段的面板,不登记任何名单即可被识别为批次目标 |
| 7 | 前端面板视图 | **先补行为测试**,再做"布局类型元数据化"(障碍 1) | 3–5 天 | 四个互斥顶层 `v-if` 消失,由元数据选择布局 |
| 8 | 约束固化 | 把第 6 节的约束写成工程纪律 + 自动化预检 | 1 天 | 预检脚本能在 CI 里拦住 D12 式无条件 `USE`、G1 式瘦 jar |

**总计约 10–14 天**(骨架),不含业务面板本身。

**三条不要做的事**:

1. **不要抄 `ButtonService.java`。** 实测 5312 行(`Get-Content | Measure-Object -Line` 口径)/ 390211 字节 / 17 个构造器依赖 / 356 个中文字面量——它是历史塌缩的产物,不是设计。
2. **不要"先静态表跑起来再搬到 DB"。** `PUSH_TARGETS`/`SELECT_FLOWS` 如果先落成 Java 静态字段,它会永远留在那里(本项目就是证明)。
3. **不要在无测试覆盖时拆 `PanelxList.vue`。** 9204 行、304 函数、零行为测试——改完无法验证,只能靠人肉回归。

**一条最该做的**:第 4.4 节的 `isBatchTarget` 手法——**能力声明放在数据上,判定逻辑读数据不读名单**。这一个模式能替掉第 5 节清单里的绝大多数硬编码。

**一条最该防的**:第 5.5 节障碍 4——**同一条规则存在两份实现**。它比硬编码更难发现,因为两处代码单看都"对"。迁移时任何"优先级链/口径表/白名单"只允许有一个定义点,其余全部引用它。
