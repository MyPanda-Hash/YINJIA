# 工艺清单归档 → 基础数据清单(组装/混料)2026-11-18

> 用户口径(原话):
> 1. 「帮我将这个组装物料清单的基础数据表能被组装工艺清单中的bom表填入进去。只要已归档状态的内容即可。参照产品信息表和物料清单的实现模式。」
> 2. 「烧结工艺也要实现一个混料物料清单能被这里两种烧结工艺清单中的bom表填入进去。」
> 3. 追问澄清:方向是**工艺清单 → 基础数据**(「就是实现我填写组装工艺清单的bom表就能在当前的组装物料清单中看到」);
>    定位键「产品编号应该是唯一的，按照产品编号填入就行」;新单默认不抢「默认BOM」。

本文是这条链的唯一契约:改字段映射、改覆盖语义、排查"为什么没同步"都看这里。

---

## 一、链路(两张源单 → 两张基础数据清单)

```
组装工艺清单 RD_ASM_PROC ──归档──▶ 组装物料清单 ASM_BOM(bs_asm_bom)
烧结工艺清单 RD_MOLD_PROC ─┐
X烧结工艺清单 RD_X_SINTER ─┴─归档──▶ 混料物料清单 MIX_BOM(bs_mix_bom,烧结类型区分来源)
```

- **触发点 = 唯一归档入口** `ButtonService.markArchived()`(保存即归档 / 审批通过 / 二级审批通过 /
  再归档 四条路最后都汇到它)→ `ProcBomArchiveSyncService`。
  这与「产品信息表(RD_PROD_INFO)归档 ⇒ BOM 明细同步进物料清单 WLBOM/mate」是**同一套模式**;
  用户说的「参照产品信息表和物料清单的实现模式」就是它。
- **只同步已归档**:保存(草稿)/审批中的单据不写 —— `markArchived` 本身只在归档那一刻被调用,
  所以「只要已归档状态的内容即可」天然成立。
- 同步失败**只记 warning、不抛**:归档是业务主流程,不能因为基础数据没写进去把单据卡住;
  同步可随时靠重新归档(或下面的回填端点)重算,幂等。

## 二、字段映射

### 2.1 组装工艺清单 → 组装物料清单

| 组装工艺清单(rd_asm_proc_detail,表区='物料清单') | 组装物料清单(bs_asm_bom) |
|---|---|
| 物料编号 | 子件编码 |
| 物料名 | 子件名称(空则回落 `bs_inv.存货名称`) |
| 物料规格 | 子件规格(空则回落 `bs_inv.规格型号`;超 200 字截断) |
| 用量(文本) | 标准用量(解析成小数;`1/124` 按除法;解析不出按 0) |
| — | 计量单位 ← `bs_inv.计量单位` |
| — | 工序 = 组装、状态 = 启用、来源 = `组装工艺清单 <AP号>`、版本号/产品名称 ← 表头 |

表头 `产品编号` 是定位键(为空 => 跳过并记 warning,不建"无产品"的 BOM)。

### 2.2 两张烧结工艺清单 → 混料物料清单

| 烧结工艺清单(rd_mold_proc_detail,表区='配方表') | X烧结工艺清单(rd_x_sinter_detail,表区='配方表') | 混料物料清单(bs_mix_bom) |
|---|---|---|
| 物料种类 | 物料种类 | 物料种类 |
| 物料编号 | 物料编号 | 物料编号 |
| 物料名称 | 物料名称 | 物料名称 |
| 实际添加比例 | 添加比例 | 添加比例 |
| 单支物料含量 | 单支含量g | 单支含量g |
| 设计添加量 | 设计添加量 | 设计添加量 |
| — | — | **烧结类型** = 烧结工艺清单 / X烧结工艺清单 |
| 表头 产品编号(**去掉末尾 -tb**)/ 产品名称 / 版本号 | 同左 | 产品编号 / 产品名称 / 版本号 |
| 单据编号 | 单据编号 | 来源单号 |

整行空(物料编号与物料名称都空)的占位行不写(配方表默认铺 10 行空行,不能把空行带进基础数据)。

## 三、覆盖语义(用户拍板:按产品编号)

- **组装**:定位键 = `产品编码`。优先找「来源 = 组装工艺清单 …」(本服务上次写的那张);
  没有才退回该产品当前会被取料端选中的那张(默认BOM=是 → 版本号倒序 → 单据编号倒序);
  一张都没有才新建(号池前缀 `BOM`)。新建时**只有该产品原本没有任何 BOM** 才置「默认BOM=是」,
  避免悄悄改变生产领料/报工(`WorkOrderBomService.standardOf`)的取数。
- **混料**:定位键 = `产品编号 + 烧结类型` —— 同一产品的两种烧结各一张,互不覆盖;号池前缀 `MIX`。
- 重复归档 = **覆盖同一张**(先删旧行再写新行),不会越归档单据越多。
- ⚠ 刻意**不删**别的来源(金蝶导入)的 BOM 单据 —— 那 3640 行是领料/报工在用的标准 BOM。
  如果某个产品只有金蝶那张单,而它又有一张已归档的组装工艺清单,按上面的规则会**复用并覆盖**
  那张单(产品编号唯一的前提);覆盖前的行可用
  `tools/archive/_mixbom-20261118/rollback-c23-11-before-backfill.sql` 的同类导出脚本回滚,
  或用 `tools/migrate-asm-bom-data-full-20261105.sql` 重灌金蝶来源。

## 四、存量回填(功能上线前已归档的老单)

同步只在归档那一刻发生,所以**上线前已经归档**的单据不会自动补。回填端点:

```
POST /api/px/procBom/resync      (需管理员;幂等)
→ { 组装: [每单结果], 烧结: [每单结果] }
```

每单结果含 `结果`(成功/跳过/失败)、`目标清单号`、`写入行数`、`产品编号`、`烧结类型`。
用途:新环境初始化、怀疑数据不一致时重跑。**不会**把"草稿/审批中"的单据带进来(只遍历
`yj_doc_status.archived='Y'`)。

## 八、「删除单据」:整张物料清单的删除入口(2026-11-18)

用户口径:「怎么样能让这个单能真正被删除,在删除中增加删除单据的按钮可以实现吗」。

- 机制:工具栏删除组由 `PanelConfigService.DELETE_DOC_PANELS` 白名单下发 —— 在名单里 ⇒
  `["删除", "删除单据"]`,不在 ⇒ 只有 `["删除"]`(删除=进入明细行勾选删除模式,只删行)。本次把
  **ASM_BOM / MIX_BOM** 加进白名单。
- 语义(与 ROUTE/三张检验单同口径):「删除单据」= 整单**作废**(`yj_doc_status.canceled='Y'`),
  列表立即不显示;行数据留档、不物理删除。只允许**草稿**删(这两张没有审批流,恒为草稿),
  删不掉的已审单会提示先弃审。前端有二次确认弹窗「确认删除整张单据?该操作不可恢复」。
- 连带口径(本次同改):
  · 领料/报工取 BOM(`WorkOrderBomService.standardOf`)排除已作废清单 —— 否则废单还会被取走;
  · 归档同步定位目标、`hasAnyBom` 判断都**忽略已作废清单** —— 删掉同步出来的那张后,下次归档会
    另建一张新号单(不会往废单里写,也不会因为"已有 BOM"而把新单置成默认BOM=否)。
- 与「真正物理删除」的区别:本系统全局口径是软删/作废,物理删除只在迁移脚本里做。确需从库里抹掉,
  需另走管理员专用脚本(不建议:基础数据留档是追溯依据)。
- 验证(测试账套,旧 jar 的行为面):新建 ASM_BOM 草稿 → 调 `删除单据` → 返回「已作废」→ 列表 total 1→0,
  行仍在表里;测试数据已清理。

**2026-11-18 16:2x 实测(8090,新 jar)**:
- `getPanelConfig(ASM_BOM / MIX_BOM)` 删除组 = `["删除", "删除单据"]`;界面上「删除 ▼」的下拉出现「删除单据」
  (截图 `tools/archive/_mixbom-20261118/12-delete-doc-menu.png`)。
- 测试账套:对 `C-23-11_V0001` 点「删除单据」→ 返回「已作废」、列表 1→0;随后 `resync` 按已归档的
  AP-2026-10-0006 另建 `BOM-2026-11-0004`(6 行),**没有**往废单里写;验完已清理
  (废单痕迹 + 新单 + 状态行),测试库 C-23-11 恢复为原始 8 行/1 张。
- 生产账套:空明细「提交」仍被护栏拒绝(400),`C-23-11_V0001` 6 行不受影响。

## 九、混料物料清单「产品编号」去掉 -tb(2026-11-18)

用户口径:「混料产品编码需要把末尾的-tb过滤了」(截图 MIX-2026-11-0002 显示 B-92-25-tb)。

- 为什么会有 -tb:烧结/成型工艺清单的「产品编号」按前端口径是 `<原始产品编码>-tb`
  (`core/panel/productCodeSuffix.js`,2026-10-27 口径),那是**单据上的产品键写法**;
  混料物料清单是基础数据,必须存原始产品编码,否则与产品信息表/组装物料清单/商品档案对不上。
- 代码:归档同步 `ProcBomArchiveSyncService.syncSinterProc` 写库前用 `DevTaskService.baseProductCode`
  归一化(与前端同一套规则:只剥结尾一层、大小写不敏感、去空格,不另写正则)。
  RD_MOLD_PROC / RD_X_SINTER 两个来源都走这一处。
- 存量:`tools/migrate-mix-bom-strip-tb-20261118.sql`(幂等,只剥结尾 -tb;两账套已执行)
  —— 正式库 MIX-2026-11-0001 `A-48-41-tb→A-48-41`、MIX-2026-11-0002 `B-92-25-tb→B-92-25`。
- 验证:重跑 `resync` 后仍写回**同一张**清单(定位键已归一,不再增生单据),
  产品编号 A-48-41 / B-92-25;界面截图 `tools/archive/_mixbom-20261118/13-strip-tb.png`。
