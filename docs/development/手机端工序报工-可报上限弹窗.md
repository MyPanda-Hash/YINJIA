# 工序报工（手机端）「可报上限」弹窗口径（2026-11-13）

> 页面：**工序报工**（`frontend/src/views/mobile/MobileReport.vue`，路由 `#/panelx/list/MOBILE_REPORT`，
> 页面面板 `MOBILE_REPORT`）。后端：`WorkReportController`（`/api/px/workReport/*`）+ `WoReportService.validateRow`。
> 改这个页面的「报工」卡片 / 超量提示 / 提交失败提示之前，先读这里。

## 1. 用户口径（原文，2026-11-13）

> 「当前这个报工提示不明确，实现一个弹窗提示吧，这个是手机端场景要求适配手机比例，
> 然后报工提示的文案要进行调整要求简洁明了。指出当前工序的可报工数量依赖于上一个工序不能超出当前的值」

背景（改前）：超量提交失败后，页面把后端一长串原文直接挂在顶部横幅（红框处）：

```
报工没有提交成功:审核失败(报工数量超出允许上限(本行工序[装箱]上限 1200(本道可加工量 1200,
来自上一道已审完工折成品 1200),允许至 1212;已报 1100,本次 200))。请稍后重试,或直接到
「工序报工单」手工提单。
```

手机上：字多、嵌套括号、重点（"最多能报多少"）埋在中间，现场看不懂。

## 2. 新交互（弹窗，手机适配）

### 2.1 触发时机
1. **前端预检**（主路径）：点「提交报工」时若 `完工数量 > 本次最多可报`，**不发请求**，直接弹窗；
2. **后端兜底**（并发/别人先报了）：提交返回 409 且文案命中「超出允许/可报上限」⇒ 同样弹窗；
3. 其它提交失败 ⇒ 另一个**简洁**弹窗（一句人话 + 一句建议），不再出现长横幅。

另：完工数量填超时，按钮下方**实时**出现一行 `本次最多可报 100`（以前只在按钮禁用时才提示）。

### 2.2 弹窗内容（三段，只讲三件事）

| 位置 | 内容 | 说明 |
|---|---|---|
| 主数字 | `本次最多可报 100 支`（34px 大号） | 一眼看到能报多少 |
| 第二行 | `你填了 200（超出 100）` | 差多少 |
| 算式块 | `可报 = 上一道「成型」已审完工 1200 − 本道已报 1100 = 100` | **指出依赖上一道工序**；首道换成 `可报 = 本道排产 2500 − 本道已报 600 = 1900` |
| 提示句 | `本道只能报上一道工序真正流下来的量,不能超过它。` | 首道：`首道工序按排产数量封顶。` |

按钮：`知道了` / `改为 100`（改为=只把数量改成可报上限，**不自动提交**，让人再确认一次）。

### 2.3 手机适配
- 弹窗宽度 `92%`，`max-width: 420px`（手机 390 宽实测 359px ≈ 92%；桌面 956 宽实测 420px 封顶）；
- 大字号（主数字 34px、正文 14~16px）、大按钮（`size=large`、两个按钮各占一半）；
- 极窄屏（≤360px，如 iPhone SE 320）按钮**竖排**、主数字缩到 30px；
- 弹窗 `append-to-body`，样式写在 MobileReport.vue 末尾**非 scoped** 的 `.mp-cap-dlg` 段（scoped 够不到 body 下的 el-dialog）。

## 3. 数量口径（唯一真源：按量流转）

```
可加工量   = 上一道已审报工折成品 × 本道换算率（首道 = 排产数量折算）     ← 后端 ProcessFlow
本次最多可报 = 可加工量 − 本道已报                                    ← 与后端「剩余可报」/ 页面 leftOf 同口径
```
- **后道不能超过上一道实际产出**：成型只报 600/2500 时，装箱的可加工量就只按 600 折算（本次现场：上一道已审完工 1200），
  所以装箱可报 = 1200 − 1100 = 100；
- 后端闸门仍在（`WoReportService.validateRow`，`可加工量 × 1.01` 容差），前端预检只是把话说在人话上，**不替代**后端校验；
- 纯逻辑抽在 `frontend/src/business/reportCap.js`（`reportCapInfo / isOverCapMessage / conciseReportError`），
  单测 `reportCap.test.js` 7 条（含现场数 834/500+833/100 与首道/后道/无来料/老接口降级）。

## 4. 后端文案同步简化

- `WoReportService.validateRow` 超量消息：
  旧 `报工数量超出允许上限(本行工序[装箱]上限 1200(本道可加工量 1200,来自上一道已审完工折成品 1200),允许至 1212;已报 1100,本次 200)`
  → 新 `报工数量超出可报上限:本道最多可报 100(上限 1200 − 已报 1100),可加工量 1200 来自上一道已审完工 1200,本次 200`
- `WorkReportController.submit` 包装：去掉「请稍后重试,或直接到…手工建单」长尾巴，只留 `报工提交失败:<原因>`；
  建议语统一由前端弹窗给（`请稍后重试;仍不行就到「工序报工单」手工开单。`）。
- ⚠ 前端**同时认新老文案**（`/超出(允许|可报)上限/`），所以后端未重部署时弹窗也照常工作。

## 5. 验证（2026-11-13，5173 源码 + 8090 后端，正式库 HSDZ_MES）

- 手机视口 390×844（DPR2）：弹窗宽 359px，主数字 100 支，算式与提示句齐全，按钮 `知道了 / 改为 100`；
- 填 200 时按钮下方实时提示 `本次最多可报 100`；点「改为 100」⇒ 数量变 100、弹窗关闭、**未提交**；
- 桌面视口：弹窗宽 420px（max-width 生效），内容同手机；

- 控制台零报错；**没有触发任何真实报工**（`今日报工` 仍为空、装箱已报仍 1100）。

## 6. 事故与清理（误提交的那一笔报工，2026-11-13）

E2E 第一轮脚本在验证「改为 100」后又点了一次「提交报工」，数量正好等于上限 ⇒ **真的建单并审核**
（`BG-2026-11-0017`，GD-2026-11-0012 行3 装箱 100 支）。已按正常业务口回退，再硬删残留：

1. `callButton(WO_REPORT, 弃审)`：单据回草稿，工序台账 装箱 已报 1200 → 1100，待审核 100；
2. `callButton(WO_REPORT, 删除)`：单据 已作废（`yj_doc_status.canceled='Y'`）；
3. `tools/archive/_mob-report-cap-20261113/cleanup-accidental-report-20261113.sql`（**只允许 HSDZ_MES**，
   精确 id/单号守卫 + 末行自检 3 项残留=0）：删 `scjl` 行 + `yj_doc_status` + `yj_form_approval` 留痕；
4. 复核 `context` 接口：装箱 `已报工=1100、待审核=0、剩余可报=100`，`今日报工=[]` —— 与测试前一致。

**教训**：手机端报工页的「提交报工」是**真实写库**动作；UI 验收时脚本只能点到弹窗为止，
**绝不能在后端可接受的数值上点提交**（要测兜底路径就直连 API 打一个"必定被拒"的数量）。
