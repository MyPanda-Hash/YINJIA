## 二、接口(全部复用既有链路,**本轮没有新增/改动后端端点**)

| 用途 | 接口 | 说明 |
|---|---|---|
| 可退单据列表 | `GET /px/mobilePick/returnables?keyword=` | 只列**已完成**且**材料出库单已被仓管审核**的领料单,带 已领/已退/可退/可退项数 |
| 扫码定位 | `GET /px/mobilePick/locate?woNo=&line=&kind=` | 扫领料单纸面码(第 4 段 `@A`/`@M`)直接定位那张;扫工单码回两张 ⇒ 弹窗选 |
| 明细页取数 | `GET /px/mobilePick/doc?id=` | 抬头 + `领料明细`(每行带 `已退数量`) + 出库已审批/退料单号 |
| 反查 id | `GET /px/mobilePick/locate?woNo=LL-…` | 从「生产领料」已完成单点「去生产退料」时只有单号 ⇒ 明细页自己反查 |
| 扫物料码解锁 | `POST /px/mobilePick/returnScan` | 校验物料在这张领料单里、回 已领/已退/**可退**;**不落库** |
| 提交 | `POST /px/mobilePick/submitReturn` | 本次所有项 → 一张**生产退料单**(`bd_material_ret`/`bl_material_ret`)+ 台账 `wo_pick_return`,审核入账、库存加回 |

**数量口径唯一真源** = `wo_pick_return`(作废不计):`可退 = 已领 − 已退`,可分多次退;
提交后页面**重拉 `/doc`** 刷新已退/可退(纸面与台账都由服务端现算)。

## 三、为什么"确认"不逐笔落库(与领料不一样,这不是漏做)

领料有 `wo_pick_line` 可以逐行写入(`setQty`),退料**没有"退料草稿行"这张表** ——
退料的落库单位是一整张生产退料单。所以:

- 逐项「确认」= 记在页面行上(`本次退`),可随时改/清空(`清空本次`);
- 「提交退料」= 把本次所有项一次性交给 `submitReturn` → 生成一张单 + 台账逐行落库。

纯逻辑(行模型/确认覆盖/提交闸门)在 `business/mobileReturn.js`,单测 `business/mobileReturn.test.js`(13 条)。

## 六、已知边界

1. **部分退**:提交闸门只要求"合计 > 0",不要求每行都填 —— 这是退料与领料的业务差别,不是漏做;
2. 确认只在页面累加(**不落库**),中途关页面/换单会丢本次录入 —— 退料没有草稿表,提交才落库;
3. 能不能退由后端硬闸门判(已完成 + 材料出库单已审批),页面只是提前说清原因;
4. 提交后自动补打印**生产退料单**(`slipPrintFlow` 的 `MAT_RET`),打印失败不影响入账;
5. 退料单号是逗号分隔的一串(多次退),「补打印」取最后一个(与生产领料的补打印同一口径);
6. **待清理的技术债**:`MobilePickDoc.vue` 里还留着第一代"退料模式"(`returnMode` / `startReturn` /
   `submitReturn` 等,入口已全部删掉、`returnMode` 恒为 false,模板里那些分支永不渲染)。
   本轮**没有**动它 —— 那一页是领料主流程,清模板分支收益小于改坏的风险;下次专门清一次,连同
   `docs/development/扫码混料-20261118.md` 里提到的同类遗留一起处理(见代码规范 §E)。
