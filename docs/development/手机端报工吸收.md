> 2026-10-16 用户报障：「手机端报工不生成工序报工单，直接产生了数据；完工量超过当前工序计划量后
> **不进入下一个生产线**，是否因为手机端报工数据内无生产线记录？」
> 本文是诊断、修法与验收证据。
>
> 🔴 **2026-10-17 追加（本文最重要的一条）**：用户口径「不能做到当前数据满足就进入下一个工序吗?
> 完成对这个钩子的判定修改,让**当前数据满足就进入**,而不是完成审核才进入」
> ⇒ 转序的**触发条件已从"报工单审核"改成"数据达标"**，见 **§0**。§1 起是原始诊断与吸收实现。

## 0. 转序钩子：判据改成「数据达标即进入」（2026-10-17）

### 0.1 改了什么

`ProcessTaskService.applyNextProcess()` 的**判据没变**（逐道比 `已审核报工量 ≥ 该道计划数量`），
变的是**什么时候被调用**，以及**一次调用推几道**：

| | 改前 | 改后 |
|---|---|---|
| 调用点 | **只有**报工单审核/审批钩子（`ButtonService.runWoAuditHooks`） | ① 报工审核钩子（保留）② **看板明细加载**（`ScheduleBoardController.scheduled` → `advanceSatisfied`）③ 手机端报工吸收 + 它的定时任务 |
| 一次推进 | 只推一道，且要求"本道报工量 = 0" | 逐道走：**已达标的前道全部置「已落实」**；第一道未达标的 = 当前道 ⇒ 落实 + 按计划线切线 |
| 计划线 == 当前线 | 只提示"沿用当前线"，**台账不落实** ⇒ 看板当前工序停在上一道 | **照样置「已落实」**（修掉"工单没有进入下一个预排产处"这一条） |
| 状态列 | 只有转序写台账 | 看板入口顺带 `syncWorkOrderState` ⇒ `plang.当前工序/完工状态` 同步刷新 |

效果：**报工数据一满足（不管这份报工是从哪来的），只要有人看一眼看板明细，工单就进入下一个预排产处**；
没人看板也有后台任务兜（§2.2，可关）。

### 0.2 实测（测试库 `HSDZ_MES_TEST`，用户场景原样复刻）

造数：工单 `GD-TEST-ABSORB-01` 排产 20（路线 `GY-CB-STD` 成型率 3 ⇒ 成型计划 **60**），
手机端样式报工行：成型 **100**（超产）、`报工单号` 空、无产线；台账 成型=已落实(1号机)、切炭=计划(2号机)。

**只调了一个接口**：`POST /px/scheduleBoard/scheduled {生产线:1号机}`（= 打开看板看一眼，**不审核、不做别的**）：

| 观察点 | 调用前 | 调用后 |
|---|---|---|
| `plang.scx`（工单当前线） | 1号机 | **2号机**（进入下一个预排产处） |
| `plang.当前工序 / 完工状态` | `(空) / (空)` | **切炭 / 在制** |
| `plang_pc.scx` | 1号机 | 2号机 |
| 台账 | 切炭 = 计划 | **切炭 = 已落实、实际线 2号机** |
| 轨迹 `wo_transfer_log` | 无 | `1号机 → 2号机｜转序自动派线` |
| 再看「2号机」的明细 | — | 当前工序=**切炭**、计划量 20、完工量 0、**上道工序=成型、上道完工量=100** |

证据：`tools/archive/_hook-state-before.out.txt`、`_hook-state-after.out.txt`、`_hook-state-final.out.txt`；
种子/探针：`_seed-absorb-probe.sql`、`_probe-absorb-state.sql`。

### 0.3 副作用与注意

- 看板明细接口现在会**按需写库**（只对"当前工序已达标"的行动手），推进过会**重新取一次明细**，
  所以界面直接是推进后的结果；工单从原线明细里消失、出现在下一道线的明细下（这就是"进了下一个工序环节"）。
- 切线仍是"只切被判定达标的那一行"（唯一键 = 工单号 + 工单行号），同工单其它行不动。
- **计划线为空**（手机端排产、MES 侧没预排全程线）时：只提示"请人工派线"，**绝不瞎切**（§3）。
- 已完工/已结案的行不再推进。

## 1. 结论（先回答那个问题）

**不是「没有生产线记录」导致的。** 真正的原因是一条钩子链从来没被触发：

参考库（旧系统）的 PDA/手机扫码报工是**绕过 MES、直接往 `scjl` 写行**的 ——
`scjl` 正是 MES「工序报工单 / 报工记录」面板的数据源，所以**数据看得到、看板算得出完工量**
（看板是纯查询），但 MES 后端在那一刻**根本没被调用**，于是这一串「审核后副作用」全是 0 次执行
（`ButtonService.runWoAuditHooks`）：

| 钩子 | 作用 | 手机端报工时的后果 |
|---|---|---|
| `WoReportService.post` → `complete()` | 补排产镜像（`gd_id`/产线/班组/批次/客户/产品…）、写 `wgzt/wgsj/jc_no` | 报工行的 `scx`（生产线）、`wzdm`、`mc` 等**留在空值** |
| `ProcessTaskService.onReport` → `syncWorkOrderState` | 推进 `plang.当前工序 / 当前工序完工量 / 完工状态` | 工单行状态**永远不推进** |
| `ProcessTaskService.applyNextProcess` | **转序派线**：前道完工 → 把工单切到下一道的预排线 | **不切线**，工单卡在当前生产线 |

关于「生产线」这一列要说清：**转序根本不读 `scjl.scx`**。
`applyNextProcess` 读的是 `plang.scx`（当前线）与预排台账 `wo_process_line.计划生产线`（下一道用哪条线），
所以 `scjl.scx` 为空**不会**阻止转序；它只会让报工记录少一列、`jc_no`/入库判仓取错值。
把「无线体」当成转序不动的根因，方向是错的。

另外两个实测事实必须记住（否则会误判）：

1. **超过计划量不会阻止转序** —— 转序判据是 `前道已审完工量 ≥ 该道计划量`（`>=`），
   报 340 / 计划 160 一样满足。用户看到的「340 > 计划 160 却不走」同样只能由「钩子没跑」解释；
2. 但**报工审核路径**会拦超产（`≤ 计划 × 1.01`）—— 手机端直写绕过了这个校验，
   所以吸收**不能**沿用封顶校验，否则超产的历史数据永远吸不进来。

## 2. 修法：新增「手机端报工吸收」

`ExternalReportAbsorbService`（+ 定时任务 `ExternalReportAbsorbScheduler` + 手工端点），
做的事就是**把上面那串钩子补跑一遍**，但**不需要审核动作**（用户口径「输入数据即可，不需要审核」）：

```
扫 scjl（外部直写的已完工行）
   └─ 定位工单行（① gd_id→plang_pc.plang_id ② 工单号+工单行号 ③ 工单号+批次号；取不到不猜）
        └─ 补镜像（**只补空值**：scx/scxmc/jbbh/wzdm/mc/gg/jldw/khdm/lot_no/pl_sl/od_*/zl/llxz/djlx/批次号/工单行号）
             ├─ 顺带把 plang.scx 由空补成 plang_pc.scx（手机端排产只写了排产行，工单行产线是空的）
             ├─ syncWorkOrderState：推进 当前工序 / 当前工序完工量 / 完工状态 / 完工时间
             └─ applyNextProcess：台账「计划」道 → 切到该道的计划生产线（与报工审核同一条路）
```

### 2.1 为什么必须有「扫描」这一步（不能"数据一到就触发"）

手机端是**另一个程序直连数据库**写 `scjl` 的：MES 侧没有 HTTP 进来、`scjl` 上也没有触发器。
所以「MES 发现这些新行」这一步在架构上绕不过去，现实做法只有三种：

| 做法 | 评价 |
|---|---|
| **MES 定时扫描 + 吸收（本次采用）** | 不改外部系统、不改遗留表结构，现场零操作 |
| 手机端改调 MES 接口 | 最干净，但要改**参考库那套程序**（不在本仓库内） |
| 在 `scjl` 上建触发器/CDC | 动遗留表、跨系统耦合、性能与锁风险，不建议 |

### 2.2 触发方式（两条入口，同一段逻辑）

| 入口 | 说明 |
|---|---|
| **定时任务**（默认开） | `@Scheduled` 每分钟第 0 秒；配置：`yinjia.report.absorb-enabled=false` 关掉、`yinjia.report.absorb-cron` 改频率、`yinjia.report.absorb-days` 改回看天数（默认 **3 天**） |
| **手工端点** | `POST /api/px/scheduleBoard/absorbMobile`，body 可带 `{"days":3}`；权限 = 快速排产/生产工单/工单排产看板任一可见；**总是重算**（不受进程内记忆限制），返回逐行明细 |

### 2.3 候选行判据（怎么认出"手机端写的"）

```
scjl: 未作废 且 未删 且 wgzt='Y' 且 gldh 非空
      且 sc_date 在最近 N 天内（默认 3 天，不回放历史账）
      且 ( 报工单号 为空  OR  该报工单号在 yj_doc_status 里查不到 shr )
```

判据后半天经：MES 自己产生的报工单**审核后**会写 `yj_doc_status.shr` —— 那张单的钩子本来就跑过了，
不该再吸一次。反过来说，`报工单号 为空` 是手机端报工的常态（它不生成报工单）。

### 2.4 幂等与安全（为什么可以每分钟跑）

- **补镜像只补空值** ⇒ 重复跑不会覆盖任何已有数据；
- **状态推进是重算**（`syncWorkOrderState`）⇒ 同样输入得同样结果；
- **转序按台账状态机推进**（`计划` → `已落实`）⇒ 同一道不会重复切线；
- **进程内记忆**（`absorbedIds`，上限 2 万条）：成功吸收过的 `scjl.id` 不再重算
  —— 候选行按天窗口筛，一天几百行每分钟全量重算纯属浪费；**跳过/失败的不记**，等下个周期重试；
- **两道守卫**：工单行已结案（`ja in T/Y`）跳过；定位不到唯一行 / 没有排产行 ⇒ **跳过并给原因，绝不猜**；
- **不写** `jc_no`（参考库的 `jc_no` = 进厂编号，如 `Admin-261016`，与 MES 审核生成的
  「产线--yyMMdd-8位」产成品流水**不是同一个东西**），也不改 `wgzt/wgsj`（手机端已是完工态）。

## 3. 前置条件：预排台账（唯一需要现场配合的点）

转序要知道「**下一道用哪条线**」，这个信息**只存在于 `wo_process_line`（快速排产里逐道选的计划线）**，
不在 `scjl`/`plang` 里。所以：

- 工单在 MES 快速排产里**预排过全程线** → 吸收后**自动切线**（本次实测就是这样）；
- 工单只有手机端排产、MES 侧没有台账 → 状态照推，转序返回「该工单行没有预排线（请在快速排产里排线）」，
  **不会瞎切** —— 需人工在快速排产里补一次全程线。

## 4. 实测验收（测试库 `HSDZ_MES_TEST`，两组入口各一轮）

种子（`tools/archive/_seed-absorb-probe.sql`，库名守卫 + 幂等）：

台账 成型=已落实(1号机) / 切炭=计划(2号机) / 组装=计划(3号机)；
报工行**照手机端的样子**写：`报工单号` 空、`scx/scxmc/mc/gg/jldw` 全空、`工单行号` NULL、**报 100（超产）**。

| 断言 | 吸收前 | 吸收后（定时 / 手工两条路都验过） |
|---|---|---|
| `scjl` 镜像 | `scx=(空) wzdm=(空) mc=(空) 工单行号=0 pl_sl=0` | `scx=1号机 scxmc=1号机 wzdm=CP-TEST mc=吸收探针产品 jldw=件 工单行号=1 pl_sl=20` |
| `plang` 状态推进 | `当前工序=(空) 完工状态=(空)` | `当前工序=切炭 当前工序完工量=0 完工状态=在制` |
| `plang` 产线补齐 | `scx=(空)`（只有 plang_pc 有 1号机） | `scx=2号机`（补 1号机 → 转序切 2号机） |
| `plang_pc` | `scx=1号机` | `scx=2号机` |
| 台账 | 切炭 `状态=计划` | 切炭 `状态=已落实 实际线=2号机` |
| 转序轨迹 | 无 | `1号机 → 2号机｜原因=转序自动派线｜plang_id=65` |

- 手工端点：`POST /api/px/scheduleBoard/absorbMobile` → `{"候选行":1,"已吸收":1,...,"补齐工单行产线":"1号机"}`，
  再点一次（`force`）→ 转序 no-op（幂等）；
- 定时任务：日志 `[手机端报工吸收] scjl.id=257 工单=… → 已推进{工序=切炭, 从生产线=1号机, 到生产线=2号机}`，
  下一个 tick **不再重算也不再刷日志**。
