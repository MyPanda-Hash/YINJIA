## 二、为什么"补源单行号"修不好这个报错(证据)

| 事实 | 证据 |
|---|---|
| 行号机制本身是通的:行上有「采购订单行号」时,`src_seq`/`src_entry_id` 真的落到金蝶行上 | 沙箱 `CGRK-20260922-00038`(源自 PI-2026-09-0128)行1/行2 = `src_seq=2/3` + `src_entry_id`(`_q-erp-inbound-lines.mjs`) |
| 报错那三张的目标分录在金蝶**已经没有可再关联的量** | 上表:2000/2000、2000/2000、600/600,`un_out_qty=0`、`entry_realio_status=C` |
| 同一句话 2026-11-24 已定位过:该分录已收 1125/1000(未执行 −125),整单被拒 | `tools/archive/_erp-link-full-20261124/README.md` |
| 金蝶对同一件事有三种说法(都是"这一行满了") | `商品分录已关闭,不允许下推` / `单据已关闭,不允许下推` / `部分数据已经构建了关联关系`(2026-11-07、11-11、11-24 各一次) |

⇒ **补行号不会让这三张单转成功**:那一行本来就没有量可挂,补上行号只会"更精确地挂到满行上"。

**但补行号/带行号仍有独立价值**(所以本轮仍然做):正式库 979 条采购入库明细里只有 **23 行**有
「采购订单行号」、**0 行**有「源单编号」;行上没有行号时,推送只带 `src_bill_no`(订单号)不带 `src_seq`,
**由金蝶按物料在订单里自己匹配行** —— 同一订单里同物料多行时就会挂到不该挂的行,而且现场从日志/界面都看不出来。

## 三、本轮改动(3 项,均已实测)

### ① 转ERP 预检 + 金蝶原文翻译(`KingdeePushService`)

- `PoRefs` 扩成带行级完成度(`PoLineInfo`:`qty/in_qty/un_out_qty/close_state/entry_realio_status`)
  —— 解析采购订单时(`resolvePoRefs`)本来就拉了 `pur_order_detail`,顺带把这几列读进来,**不增加任何接口调用**。
- 新增 `warnPoLineQuota()`:推送前按本次实收数量与该行金蝶未入库量比对,结论拼进返回消息 ——
  「已收满 / 已超收 / 超出未入库量」三种都给出**哪一行、金蝶那边多少、该怎么办**。
- 新增 `erpHumanHint()`:金蝶报错时把三种原文翻译成"含义 + 本次各行完成度 + 三条处置建议"。
- **只预警、不拦截**(刻意):金蝶允许超送(实测同账套里 2000 的订单行被收到 2265),
  到底哪一档会被拒由金蝶判定;MES 若按"未入库 ≤ 0 就拒绝"会把金蝶本来肯收的单据自己焊死
  (同一个坑 2026-11-26 在库存冲回守卫上踩过)。

实测(测试账套 → 沙箱):

```
PI-TEST-1129(挂 CGDD-20260920-00001 第1行,该行 10/10 已收满)
→ 金蝶原文:不符合条件：单据已关闭，不允许下推。
→ 返回给现场:
   金蝶接口失败: …不符合条件：单据已关闭，不允许下推。
   含义:该采购订单(或其中的分录)在金蝶已关闭(通常是已入库满),不能再下推/挂单。
   本次各行在金蝶的完成度:
   · 第1行 YJ-SX-031 → 采购订单[CGDD-20260920-00001]第1行:订单量 10 / 已入库 10 / 未入库 0 / 行关闭 0 / 入库状态 C
   预检提示:第1行 … 已入库 10/订单量 10(未入库 0) —— **该行已收满** …
   怎么办:在金蝶反关闭该分录、或给订单加量/加行之后,再回 MES 重转。
```

### ② 采购入库单批号:改为推 MES「批次号」(`KingdeePushService`)

- 入库行有两个批号列:**「批号」**(金蝶同步来的值,非批次商品恒 `PC0000` 占位)与
  **「批次号」**(MES 生单即定号的业务批次,与台账 `kucun.批号` 同源,如 `20260922`)。
  此前只推「批号」⇒ 金蝶单据行 `batch_no` 恒空/`PC0000`,**MES 的批次一个都没落到金蝶**。
- 现改为**批次号优先、批号兜底**(仅 `PURCHASE_IN`),并打一行日志留痕。

实测:`PI-TEST-1128` 推送日志 ——
`采购入库单[PI-TEST-1128]第1行推金蝶批号改用 MES 批次号[20261128](行「批号」列是[PC0000])`。

⚠ **两条现实约束(必须知道)**:

1. **金蝶只对启用批号管理的商品吃 `batch_no`**:真实账套 3991 个商品里 2463 个启用(61.7%);
   测试沙箱 298 个商品里 **0 个**启用 ⇒ 沙箱里验不出"批号落库",只会看到 `batch_no` 空
   (沙箱验收单 `CGRK-20261128-00050` 就是这种情况,不是代码没推)。
2. **金蝶「现存量」接口 `batch_no` 恒空**:真实账套 1432 行**全部**无批号
   (`_q-batch-reality.mjs`)⇒ 即便单据上带了批号,MES 每 5 分钟的库存同步也拿不回批号维度,
   库存表仍按无批号汇总。批号维度要在两边真正对齐,还得另解(接口参数 / 账套设置 / 只认单据可追溯)。

### ③ 采购订单行号补全(`ButtonService.assignPoLineNo` + 同义词)

- **新建采购订单**时,新增行若「行号」为空 ⇒ 自动按该单现有最大号 +1 补号(既有行一律不动、不阻断保存)。
  根因:金蝶同步进来的订单行天然带 `seq`,但 **MES 手工新建的订单行「行号」是空的**
  (测试账套 `PO-2026-11-0013`;正式库 4804 行里有 88 行空)⇒ 下游
  `行号 → 采购订单行号 → 源单行号` 整条链一路空到入库行。
- `PanelConfigService.FLOW_DETAIL_SYNONYMS` 增补 `{采购订单行号 → 采购订单行号}`:
  同名映射只取前 14 条(seq 靠后的会被挤掉),显式登记保证入库行「源单行号」一定带得下来。
- 推送侧再加一道**兜底**:行上没有可用行号时,按物料在金蝶订单行里**唯一匹配**推导 `src_seq`
  (同物料多行则不猜,照旧不带);解析到行号还会**校验该分录物料与本行物料是否一致**,
  不一致说明 MES 行号与金蝶 seq 不同源 ⇒ 退化为按物料匹配,绝不硬挂错行。

实测:

| 场景 | 结果 |
|---|---|
| 新建采购订单 2 行(不填行号) | `PO-2026-11-0020` 行号自动落 **1 / 2** |
| 入库行**没有**行号,按物料唯一定位 | `PI-TEST-1128` 第1行 → 自动定位 `YJ-20260909-01` 第2行,金蝶行 `src_seq=2` ✅ |
| 入库行**有**行号 | `PI-TEST-1128` 第2行(源单行号=3)→ 金蝶行 `src_seq=3` ✅ |
| 目标行已收满 | 预检 + 翻译都出现(见上 §三①) |

## 四、没做 / 待业务拍板

1. **不挂源单兜底推送**(金蝶报"关联关系"时自动改成无来源单普通入库单):能让单子转成功,
   但代价是这笔**不计入订单执行量**、金蝶该订单行仍未闭环 —— 属业务口径,未擅自加。
2. **超送口径统一**:MES「收料超送比例(20%)」与金蝶超收控制必须一致,
   否则"MES 放行 ⇒ 金蝶拒"会一直复现(`tools/archive/_erp-link-full-20261124` §六.2)。
   ⚠ 2026-11-28 晚的实测补充:**真实账套是「允许超额入库」的**(见 §五),所以这条主要影响
   **测试沙箱**(它没开)与以后换账套时的行为,不是当前生产的主要卡点。
3. **反向同步(治本)**:定时拉**金蝶采购入库单**回写订单行已入库量,
   生单阶段就按金蝶未入库量约束 —— 否则"一边 MES 生单、一边金蝶手工收货"仍会重复。
4. **调拨/盘点**至今不在转ERP 白名单,对库存完全无效(既有结论,本轮未动)。

## 五、2026-11-28 晚 更正:真实账套「允许超额入库」,真正的卡点是分录已满/已关闭

客户口径:「**金蝶那边是设置允许超额入库的**」。实测两个账套**参数并不一致**,这直接改变了
"哪几行会被拒"的判断:

| 账套 | 允许超额入库 | 证据 |
|---|---|---|
| **真实账套**(359797,生产在推的那个) | **是** | `YJ-20260924-04` 第6行(订单 1000)被 **4 张带 `src_seq=6` 的入库单**合计收到 **1125/1000**:`CGRK-20261104-03609`(225)、`CGRK-20261110-03662`(300)、`CGRK-20261113-03703`(300)、`CGRK-20261118-03788`(300);同账套另有 2265/2000、41488/40000、5160/5000 等大量超收行 |
| **测试沙箱**(359220,本机转ERP 的目标) | **否** | `PI-TEST-1130`(实收 5000,目标行未入库 4500)⇒ 金蝶拒:`[采购入库单(CGRK-20261128-00051)…]反写[采购订单(YJ-20260909-01),商品分录第2行]:不允许超额入库`;被拒后沙箱**查无该单**(整单未落库) |

**由此确定的机制(比 §二 更准确)**:

> 卡死转ERP 的**不是"实收 > 未入库"**,而是**目标分录已经"已入库满/已关闭"** —— 那一刻
> 关联关系已经构建完,再建必然被拒,与本次收多少无关。金蝶对同一件事有三种措辞:
> `部分数据已经构建了关联关系` / `单据已关闭,不允许下推` / (`不允许超额入库` 只在**没开**该参数的账套出现)。

**⇒ 对服务器那 6 张的处置要按这个修正**(超送行能过,只有满行要处理):
