# 金蝶订单同步 · 明细行 id 必须稳定(与下游占用的契约)

> 2026-11-16 故障复盘与修复记录。**改动订单同步、订单明细行、行级占用、材料码打印之前,先读这一份。**
> 相关实现:`deploy/sync-core.mjs`(`upsertLines` / `upsertDoc`)、`tools/migrate-erp-linekey-repair-20261116.sql`
> 回归脚本:`deploy/_test-lineupsert-20261116.mjs`

## 一、不变量(违反即等于把下游单据和数据一起弄坏)

**金蝶同步写订单明细行时,同一业务行的 `identity id` 必须保持不变。**

MES 的**行级引用**全部是「`{单据编号}#{行id}`」这一种形状,没有任何兜底:

| 用途 | 位置 | 悬空后的表现 |
|---|---|---|
| 采购链已送量(暂收/检验/退回/入库的按量占用) | `form_flow_link.source_line_key` | 已送量归零、可送上限虚高 ⇒ **重复送料**;分批送料弹窗报「送料行不存在或已失效」 |
| 材料码打印记录(= 弹窗下层「已打印隔离行」) | `bl_pu_label.采购订单行id` | 已打印量切不回去、隔离行整片消失 |
| 销售链已转工单量 | `form_flow_link.source_line_key`(SO_ORDER) | 已转量归零 ⇒ 结转列表可重复转工单 |

## 二、2026-11-16 故障

- 现象:采购订单 `YJ-20261111-06` 分批送料弹窗点「确定生单」报
  `送料行不存在或已失效:YJ-20261111-06#11039`。
- 事实(正式库实测):
  - 该单明细行 id 在 **17:47:07** 被整体换掉:`11035…11043` → `11103…11111`(`asp_user1='jdy-sync'`);
  - 17:41:26 刚生成过暂收单 `SL-2026-11-0064`(占用 `#11040`,40000),弹窗里第 6 行还显示着「已送 40000」;
  - 17:47 同步一跑,弹窗手里的 `#11039` 就作废了 ⇒ 后端重算候选行(全成了新 id)查不到 → 报错。
- 存量损伤(当天):采购链占用 422 条、销售链占用 505 条、材料码记录 24 条指向已删行。

## 三、根因

`deploy/sync-core.mjs` 的 `upsertDoc()` 旧实现:|头表 upsert **+ 明细行 `DELETE FROM … WHERE 单据编号=?` + 逐行 INSERT**。
每写一次,该单明细行就拿一批新的 identity id。

而**"写一次"非常频繁**:同步每 5 分钟一轮,列表级指纹(`fingerprintOf`,采购订单为
`bill_status|bill_close_state|bill_date|supplier_name|supplier_number|emp_name|io_status|real_io_status|remark`)
只要变一个字段(审核、到货/入库进度、关闭、改备注…)就重写整单明细 ⇒ 一天之内反复换 id。

## 四、修复(代码)

`deploy/sync-core.mjs` 新增并导出 `upsertLines(doc, tx, mssql, docNo, lines, log)`,`upsertDoc` 改调它:

1. **行键 = 金蝶分录 seq(本表 `行号` 列)**。seq 在 ERP 里就是分录身份(转 ERP 的 `src_seq` 也用它),
   改数量/交期/审核/入库进度都不变;同键 **UPDATE 保 id**(不动 `asp_time1`,只盖 `asp_user1/asp_user2/asp_time2`)。
2. **没有行号的老行**(2026-09-27 之前的销售订单行、本地研发库存量)兜底行键 =
   `物料编码 + 该物料在本单的第几次出现`(`DOCS` 里按表配置 `lineCodeCol`:采购订单 `物料编码`、销售订单 `存货编码`)。
3. ERP 新增行 → INSERT;ERP 已删除的行 → 硬删(与旧行为一致);**若被删行上还挂着 ACTIVE 占用,打 ⚠ 日志留痕**。
4. 两个键都算不出来(无行号且无物料)或库内同键重复 → 退回旧的「整单删插」并**告警**(宁可换 id 也不错配)。
5. 行号比较按**数值**归一:正式库 `bl_pu_order.行号` 是 `nvarchar('6.0000')`、`bl_so_order.行号` 是 `int('6')`,
   接口给的是数字 `6` —— 不归一会每行都被当成新行(退化回整单删插)。

回归:`node deploy/_test-lineupsert-20261116.mjs`(事务 + 回滚,不留痕),覆盖
①原样重写行 id 一个不差 ②改数量不变 id ③幂等 ④ERP 删行 ⑤ERP 加行 ⑥行键算不出来时退回 replace。
两个账套 × 两种单据(采购/销售)各跑一遍全 `[PASS]`。

## 六、运维口径(以后别再踩)

1. **任何"重写/重导入订单明细行"的代码路径**(同步、导入、数据修复脚本、换库恢复)都必须保证
   **同一业务行的 id 不变**;做不到就在同一次操作里把 `form_flow_link.source_line_key` 与
   `bl_pu_label.采购订单行id` 一起迁移。整单 `DELETE + INSERT` 是最容易踩的写法。
2. 想验证某次同步有没有动到行 id:同步前后各跑
   `SELECT 单据编号, MIN(id), MAX(id), COUNT(*) FROM bl_pu_order GROUP BY 单据编号` 对比;
   或直接跑 `deploy/_test-lineupsert-20261116.mjs`。
3. **金蝶真的删掉一行**时,那行上的下游占用必然失去来源(ERP 侧已不存在),同步会打
   `⚠ 【采购订单】<单号> 金蝶删除了 N 行明细,其上有 M 条下游占用随之失效(需人工核对)` —— 看到这条要人工处理。
4. 分批送料/生单弹窗是**打开那一刻的快照**;若期间来源单被改,后端会拒绝并提示「关闭本窗口重新打开」。
   这是刻意保留的失败(而不是拿旧键硬生成),避免把甲行的量记到乙行。
5. 残留能力边界:同步指纹只看**列表级字段**,如果金蝶只改了**明细行**(数量/交期)而头字段都没变,
   本轮不会重取详情(下一轮头字段一有变化才会带上)。真需要强制重取:`node sync.mjs --refresh=PU_ORDER`。
