## 1. 报障原文与场景

**用户原文(2026-11-04)**:

> 「这个组装物料清单中的表头无法填写啊,那后面这个物料清单不是没法维护吗?」

**场景**:数据建模 → 生产 → 组装物料清单(面板 `ASM_BOM`),打开单号 `T387_V0001`,
红框内**表头字段全部只读**(输入框置灰、下拉/日期/参照都点不动),用户因此无法维护该 BOM 的表头信息。

**实测现场(2026-11-04,两账套只读审计,输出见
`tools/archive/_asm-bom-maintainable-verify-20261104/CHECK-before-output.txt`)**:

- 面板 `ASM_BOM`:1 行,`mode=doc`、`line_table=bs_asm_bom`、`head_table=NULL`、`group_col/code_col=单据编号`、`prefix=BOM`、`module_group=数据建模`。
- `yj_field` 共 **19 行**;其中 `place` 含 `header` 的 **11 个字段 `editable` 全部 = 0**:
  单据编号(seq 10)、产品编码(20)、产品名称(30)、规格型号(40)、工序(50)、版本号(60)、默认BOM(70)、
  工艺路线名称(80)、来源(85)、状态(90)、备注(100)。
- `yj_panel.config = NULL`(没有 `headDefaults`,新建单据的「状态」也没有默认值)。
- `data_type='参照'` 的字段 **0 个**(产品编码/子件编码 都是纯文本,不能从存货档案选料)。
- `bs_asm_bom` **47 列**(与 2026-10-30 建表/验收一致,本次不打算也不允许改 DDL)。
- 单据 `T387_V0001`:两账套都各有 **2 行**(产品编码 `T387`、产品名称 `X烧结炭棒(82#)`、规格型号 `30*12*128`、工序 `组装`、版本号 `V0001`、来源=金蝶BOM引出列表;`yj_doc_status` 无该单记录 ⇒ 是**草稿**)。
  即:用户看到的就是一张已导入、未审核的历史 BOM 单,表头整排锁死。

## 2. 根因链(4 条,逐条带代码/脚本位置)

> 行号基于 2026-11-04 取证时的 HEAD 版本;同批 Java 修复提交后行号可能整体位移,
> 引用时以「文件名 + 锚点代码」为准。

### 2.1 建面板时 11 个表头字段整批登记成 `editable=0` → 后端下发 readonly → 前端置灰

1. `tools/migrate-asm-bom-20261030.sql` **L165-197**:11 个表头字段的 `INSERT INTO yj_field`
   第 12 个值(列 `editable`)全部写 `0`;明细字段(子件编码/名称/规格/单位/用量/损耗/行备注)
   才是 `1`。建面板时按「导入为主、表头只读」的口径整批锁死,是本次报障的**直接原因**。
2. `backend/.../service/PanelConfigService.java` **L749**:
   `if (!f.editable()) m.put("readonly", true);` —— 元数据 `editable=0` 会被下发成前端字段的 `readonly`。
3. `frontend/src/core/views/PanelxList.vue` **L8356-8364** `headerFieldLocked(field)`:
   `return !!field.computed || !!field.autoCode || !!field.readonly || [...]` —— `readonly=true` 即判定为锁。
4. 表头渲染(`PanelxList.vue` **L946-1045**)所有控件都绑 `:disabled="headerFieldLocked(field)"`
   (参照下拉 L956、参照弹窗 L977/L984、字典弹窗 L992/L999、下拉框 L1006、日期 L1017、
   数字 L1025、布尔 L1032、文本框 L1038)⇒ **整排表头置灰**。
5. 另:后端 `buildRefMap` 的「同名带回」循环会**跳过 `editable=0` 的兄弟字段**
   (`PanelConfigService.java` **L833** `if (!sibling.editable()) continue;`)—— 表头字段不解锁,
   连参照带回都不会写进来。

### 2.2 单表 doc 保存时「行内旧值覆盖表头新值」——只放开 editable 仍会「改了存不回来」

- `backend/.../service/ButtonService.java` **L33-39**:`SINGLE_HEAD_WINS_PANELS = Set.of("ROUTE")`
  只放行工艺路线;`ASM_BOM` 不在白名单。
- 同文件 **L674-691**(`saveDoc` 的单表式分支):非白名单面板走
  `Map merged = new LinkedHashMap<>(head); merged.putAll(item);` ⇒ **行内旧值最后覆盖表头值**。
  单表 doc 的明细行本身就携带表头同名物理列(如 产品名称/规格型号/工序),所以表头改了、保存时又被
  行内旧值盖回去,现象与 2026-10-05 ROUTE 那次完全同源。
- 附带风险:表头字段改成「参照 INV」后,前端 refMap 会把参照带回的**异名/多余键**写进表头对象 `cur`
  (`frontend/src/core/ref/refCarry.js` L6-12 `applyRefCarry`),若「表头值优先」合并时
  **全量并入**每一行,会把每行的子件单位/名称/规格冲成父件产品的值 ⇒ 合并必须只并**真正的表头字段标签**。

### 2.3 新增明细行 `行序=0`,连加两行撞唯一索引 `uq_bs_asm_bom_doc_line`

- `tools/migrate-asm-bom-20261030.sql` **L70-71**:
  `CREATE UNIQUE INDEX uq_bs_asm_bom_doc_line ON dbo.bs_asm_bom (单据编号, 行序) WHERE asp_cancel <> 'Y'`。
- 前端「新增数据」`PanelxList.vue` **L8492-8500** `newDetailRow(tabKey)`:
  `if (field.dataType === '小数' || field.dataType === '整数') row[field.dataName] = field.defaultValue ?? 0`
  ⇒ 「行序」是整数型,新行默认 **0**;连加两行就是两个 0,保存即撞唯一索引(用户侧表现为保存报错/失败)。

### 2.4 「新增」空白草稿能建单,但表头没默认值;而且**不需要改 DDL**

- `ButtonService.java` **L520-581**(`saveDoc` 的 `items.isEmpty()` 分支):空表单 = 建一张空白草稿单,
  单表式写一行占位行(`L565 insertRow(...)`);行序列有 DEFAULT(0),所以占位行先落 0。
- `ButtonService.java` **L1945-1969** `insertRow` → **L1990-2013** `fillRequiredDefaults`:
  对「NOT NULL 且无默认值」的列自动补 `''`/`0` ⇒ **空白草稿本来就能建单**。
- 🔴 **明确结论:不需要、也不要 `ALTER TABLE` 放宽 `bs_asm_bom` 的 NOT NULL**。
  本次问题全部是「元数据 + 前端/后端逻辑」问题,表结构(47 列、各列可空性)是对的;
  改 DDL 既不解决问题,又会把两账套表结构推到不同版本、增加部署风险。**后人不要再动表结构。**
- 新建默认值机制是现成的:`PanelRegistry.java` **L141-164** `headDefaults()`
  (读 `yj_panel.config` 的 `"headDefaults"`)+ `ButtonService.java` **L828-844** `putHeadDefaults`
  (建单/保存时只补空列)。缺的只是 ASM_BOM 的 `config` 里没这条配置 ⇒ 由本迁移 §5 补。

### 4.2 下游只读查询(不受「表头可编辑」影响,但受「默认BOM/状态/版本号」取值影响)

1. `backend/.../controller/WorkReportController.java` **L150-180** `asmBomOf(productCode)`(调用点 L132-135):
   移动端**工序报工**选「组装」时展示该产品 BOM —— `WHERE 产品编码=? AND 工序=N'组装' AND asp_cancel<>'Y'
   AND ISNULL(状态,N'启用')<>N'停用'`,`ORDER BY 默认BOM='是' 优先, 版本号 DESC`;
   再按 `单据编号` 取行(`ORDER BY 行序, id`)。
2. `backend/.../controller/MobilePickController.java` **L1385-1431** `latestAsmBom` + `bomDetail`
   (调用点 L324-332):**扫码领料**按 `产品编码 + 工序='组装' + 状态<>'作废'` 取一张 BOM,
   `ORDER BY 默认BOM='是' 优先, **版本号 DESC**, 单据编号 DESC`(**同批已与报工端对齐**,改前是「单号 DESC」);
   明细按 `行序, id`,计量单位空时回退 `bs_inv.计量单位`。
3. 两者都是**只读 SELECT**,不依赖表头是否可编辑;表头可编辑只是「人能维护了」。
   **真正的取值口径风险在「默认BOM」**:
   - 同产品多版本时,**必须把要生效的那版 `默认BOM` 设为「是」**;否则按单号/版本号最大取,
     可能取到并不想用的历史版(影响领料展开与报工展示的 BOM)。
   - 新版本上线建议:旧版 `默认BOM` 选「否」、新版设「是」,再核对移动端两个入口。⚠ 不能靠「清空旧版默认BOM」:headWins 只并非空表头值,清空保存会回弹(见 §6-4)。
   - 另:同批把**扫码领料端**的排序改成与报工端一致(默认BOM → 版本号 DESC → 单据编号 DESC),
     因为 MES 新单号 `BOM-2026-…` 的字符串序**小于**金蝶历史号 `T387_V0001`,旧「单号 DESC」会把新版本判成旧单,
     导致两个移动端入口取到不同版本、可能领错料 —— 走查时务必核对两端取到的是同一张 BOM。
4. 新建单据编码口径(现成机制,不是本次新增):
   - **单据编号** = `BOM-yyyy-MM-NNNN`(`FormNoService` 前缀-年月-四位序号,如 `BOM-2026-11-0001`);
   - **版本号** = `Vyyyy-MM-dd-NN`(`ButtonService.nextVersionNo`,当日流水两位,如 `V2026-11-04-01`,可手改)。
   - ⚠ 实测注意:`nextVersionNo` 的「当日流水」依赖表里有「单据日期」列,而 `bs_asm_bom` **没有**该列
     ⇒ 同一天新建多张 BOM 的版本号会**都是 `-01`**。同产品多版本请**手工改版本号**或在建单后立即维护,
     不要依赖自动流水。
5. 参照/带回(迁移后行为):
   - 产品编码 选存货 → 产品名称(同义词)、规格型号(同名)自动带回;计量单位等同名 INV 字段也会进 refMap,
     但同批代码在表头合并时只并真表头字段,**不会**冲掉明细行的子件单位/名称/规格;
   - 子件编码 选存货 → 子件名称、子件规格(新同义词)、计量单位(同名)带回;
   - 历史值不在存货档案时,参照控件未命中回退显示原值,不会显示成空。
