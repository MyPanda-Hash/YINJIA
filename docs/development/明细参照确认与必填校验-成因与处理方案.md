# 明细参照确认引发的必填报错 —— 成因与处理方案

> 2026-10-14 应报障撰写。**方案 A 已经用户拍板并于同日实施**(改动与验证见 §10;
> §1–§9 保留报障当时的诊断原文,便于回溯口径)。
> 报障原文(材料出库单):
> ①「明细第 1 行批号不能为空,当我点击后会出现这个问题,选择商品造成的什么原因呢?」
> ②「当前这种表都会出现就是当前的校验问题,我填写明细表会提示表头未填写」

---

## 0. 一句话根因

**明细里「选商品/选材料」不是只把值带进表格,而是顺手把整张单保存了一次**;而后端「保存/提交」路径会做
**表头必填 + 明细必填的全量校验**。用户还在录明细(表头没填完、新行还没填批号)时,这次隐式保存必然缺项
⇒ 必然弹报错,而且**带入的值只活在"待保存快照"里,保存被拦下 ⇒ 界面上那一行什么都没进来**。

两条报错是同一个根因的两个面:①是明细必填被拦,②是表头必填被同一次保存连带校验。

---

## 1. 现象与用户可见表现

| 触发动作 | 用户看到 | 实际发生 |
|---|---|---|
| 明细行点「材料编码」格 → 参照弹窗选一条 → 确定导入 | 顶部红字「明细第 1 行批号不能为空」,**表格里那一行仍是空的** | 前端顺带发了一次整单「保存」→ 后端 400;带入值写的是快照,快照整份丢弃 |
| 同上前提下表头「业务类型」还没选 | 红字「业务类型不能为空」 | 同一次保存的表头必填校验 |
| 新推的空行 | 被摘掉(回到点击前的行数) | 失败分支 `discardCreatedDetailRefRow` |

判定命中范围的规则(实测 `yj_panel`/`yj_field`):**面板有「明细参照字段」(`place` 含 `detail` 且
`data_type='参照'`)时,用户在明细里点这个格子选一次,就会触发一次整单保存 + 全量必填校验。**

## 2. 根因链路(逐环,含代码位置)

### 2.1 前端:参照确认 = 整单保存(除工艺路线外全走这条)

`frontend/src/core/views/PanelxList.vue` → `onDetailRefConfirm()`(:5331 起):

1. :5356-5359 把 `cur.value.detail` **深拷贝**成快照 `detail`;
2. :5360-5388 把参照带入值写进 **快照行**(不是表格渲染用的活行)——例外只有 `ROUTE`(:5368 `writeLiveRows`);
3. :5390 `await engine.fillCurrentStock(changedRows)`(现存量刷新,网络请求);
4. :5410-5415 `engine.callButton({ buttonName: '保存', formData: currentFormData(detail) })` ← **就是这次隐式保存**;
5. :5418-5421 成功后 `load()` 重取(所以只有成功时才看得到那行);
6. :5423-5424 失败后 `discardCreatedDetailRefRow(pick)` + 红字弹**后端原话**。

`frontend/src/business/engine.js`:397-401 把「保存」映射成后端 API 的 **`提交`**(`buttonName: '保存'|'保存新增' → '提交'`)。

### 2.2 后端:「保存/提交」路径做全量必填校验

`backend/src/main/java/com/yinjia/mes/service/ButtonService.java`:

1. :111 `case "保存", "提交", "保存新增" -> save(def, formData, true, buttonParam)`(`markSaved = true`);
2. :408-413 `if (markSaved) { ensureRequiredFilled(...); ensureDetailRequiredFilled(...); }`
   - :511-539 表头:只看 `place` 含 `header` 的必填字段,跳过系统字段(`REQUIRED_SYS_FIELDS` :552-553:
     单据编号/单据日期/创建时间/更新时间/编辑人/编辑日期/规格书种类/编号),隐藏字段不校验;
   - :570-587 明细:逐行、只取第一条违规;文案 :584 `"明细第 " + (i+1) + " 行" + displayName() + "不能为空"`;
   - 表头文案 :537 `String.join("、", missing) + "不能为空"`。

### 2.3 两层校验的分工(容易混)

| 层 | 入口 | 文案 | 触发时机 |
|---|---|---|---|
| 前端 `validateInlineDraft()` `PanelxList.vue:5220-5264`(:5257 文案) | 工具栏「保存/提交/审核」→ `saveInlineDraft()` | 与后端**逐字相同**(`明细第 N 行X不能为空`) | 用户点保存类按钮 |
| 后端 `ensureRequiredFilled/ensureDetailRequiredFilled` | `POST /px/callButton` 的 保存/提交 | 同上 | 任何一次「保存」调用,**包括明细参照确认顺带发的那次** |

所以用户在明细里选商品时看到的红字,**是后端**说的(前端那次校验根本没跑),但文案与前端一字不差,
从界面无法区分 —— 这也是"为什么我明明在填明细却骂我"的观感来源。

### 2.4 为什么材料出库单**必然**报「批号」

`yj_field`(HSDZ_MES)实测:

- 明细必填(5 个):材料编码、**批号**、材料名称、计量单位、数量;
- 选「材料编码」那一刻的带入映射(`getPanelConfig` 的 `refMap` 实测):
  存货名称→材料名称、计量单位→计量单位、参考成本→单价、规格型号→规格型号 …
  ⇒ 名称/单位/单价都被带进来了;数量由 `newDetailRow()` 物化成默认 `0`(后端判空用 `isBlank()`,`"0"` 不算空)
  ⇒ **唯一还空着的必填就是「批号」**,所以文案永远指向批号。
- 表头必填(3 个):单据日期、单据编号、业务类型。前两个是系统字段前后端都跳过;
  **「业务类型」没有默认值**(下拉:销售出库/材料出库/其他出库),没选就报「业务类型不能为空」
  —— 这正是报障②。

### 4.3 两个额外的"表头/明细错位"坑(同一族,建议一并记入技术债)

1. **必填字段同时挂在表头与明细**:只有一个面板 —— `SALE_OUT` 的「仓库」

## 5. 处理方案

### 方案 A(推荐):把工艺路线的口径推广到所有面板 —— 参照确认只写本地草稿

**沿用 2026-10-06 已按你口径落地的 ROUTE 做法**(commit `2d13eb06`:「参照选择不再连带保存,
可先选工序;必填只在保存/审核时校验」)。

改法(单函数 + 一处竞态 + 词条):

1. `onDetailRefConfirm()` 去掉 `panelCode === 'ROUTE'` 特判,统一:
   - 带入值写**活行** `cur.value.detail[pick.tabKey]`(`writeLiveRows = true`);
   - `detailRefSaving.value = true` 提到**第一个 await 之前**(否则 `watch(detailRefVisible)`
     :7029-7034 会把刚推的行当"取消"摘掉 —— 这正是 2026-10-06 修过的竞态);
   - 保留 `await fillCurrentStock(...)`(现存量仍是本地刷新);
   - **不再**调 `callButton('保存')`、**不再** `load()`(load 会把未保存的草稿刷掉);
   - 成功提示改为「已带入 N 行,请点『保存』提交」(复用 ROUTE 现文案:`已带入 {n} 条工序,请点「保存」提交`);
   - `markInlineDirty()` 置脏(档案面板会自动 `normalizeArchRaw()` bump 版本、驱动重渲染);
   - 失败分支只保留"带入过程本身出错"的兜底(撤掉本次新建行 + 红字)。
2. 显式「保存/保存新增/提交审批/审核」路径**完全不动**(前端 `validateInlineDraft` + 后端两层校验照旧)。
3. 档案面板不受损:显式保存走 `changedArchiveRows()`(`:2353-2361`,无 id 的新行必被提交)。

- **收益**:两条报错都不再出现;选商品不再丢行、不再"看不到带进来的商品";每次选商品少一次整单保存 + 重载;
  顺带消除"隐式保存触发文书面板保存即归档/送审"的隐患(`ButtonService:456-469`)。
- **代价/需要用户接受的口径**:选商品**不再立即落库** —— 必须点「保存」才写库。未保存离开时由既有守卫
  (`当前单据有未保存的修改,是否保存?`)兜住。
- **风险**:依赖"选完即落库"的个别流程要回归(存货批量导入、参照带出后立刻生单的场景)。
  逐面板回归清单见 §6.2。
- **i18n**:新增/复用词条「已带入 {n} 行,请点『保存』提交」,按 AGENTS.md 补 `en.js`(至少)与
  `yj_translation`(scope='ui')。

### 方案 B(保守):保留"选中即落库",但这次隐式保存跳过必填校验

改法:后端加一条"暂存"通道(如 `buttonParam: { 跳过必填: true }`,在 `ButtonService:408` 那一档
按参数放行 `ensureRequiredFilled/ensureDetailRequiredFilled`),前端 :5410 的那次调用带上它。

- **收益**:落库时机不变,用户点「保存」时才第一次看到必填提示。
- **代价/风险**:
  - 半截数据(批号空、数量 0)会**静默落库**,用户不知道已经存过一版;
  - 文书类面板 `DOC_ARCHIVE_PANELS` 的"保存即归档/自动送审"仍会被这种隐式保存触发
    (`ButtonService:456`);
  - 每次选商品仍是一次整单保存 + `load()`(性能、修改记录噪声照旧);
  - 带入值仍只写快照,"保存被拦下就看不到那行"的问题**依旧存在**(只是不再拦了)。

### 方案 C(最小):只改材料出库单

只给 `MATERIAL_OUT` 开方案 A 的分支(照抄 ROUTE 那段 `if (panelCode.value === 'ROUTE' || panelCode.value === 'MATERIAL_OUT')`)。
其余面板照旧弹同样的报错 —— 成本最低,但"这种表都会出现"的问题只解决一张。

### 对比

| | A 推广口径 | B 暂存通道 | C 只改材料出库单 |
|---|---|---|---|
| 报障①(明细必填拦带入) | ✅ 消失 | ✅ 消失 | ✅ 仅材料出库单 |
| 报障②(填明细弹表头必填) | ✅ 消失 | ✅ 消失 | ✅ 仅材料出库单 |
| 带入值是否可见 | ✅ 立即可见 | ⚠️ 落库后才可见 | ✅ 仅材料出库单 |
| 半截数据静默落库 | ❌ 不会 | ⚠️ 会 | ❌ 不会 |
| 影响面 | 30 个面板公共路径 | 同左 + 后端新参数 | 1 个面板 |
| 与既有口径一致性 | ✅ 与 ROUTE 一致 | ⚠️ 新增第三种"保存"语义 | ✅ 与 ROUTE 一致 |

## 7. 环境备注(本次取证踩到的)

- **Edge 154 + `ws` 包的两个坑**(2026-10-14 实测,已写进探针注释):

     ⇒ 改用 `/json/list` 里既有的 page target;
