## 二、三个关键技术点(踩坑记录)

### ① `point_date` 默认**不返回批号**

`/jdy/v2/scm/inventory` 不传 `include_batch_kf_period` 时,返回的 `batch_no` **恒为空**。
用它导入,期初 1,345 行会全部落在"无批号行",而 MES 9/1 后的领料扣的是 `PC0000` ⇒
**批号永远对不上,负结存从 431 行涨到 785 行**(反而更糟)。

**必须传 `include_batch_kf_period=true`**:此时返回 1,347 行,其中 `PC0000` **981 行**、
无批号 365 行,与 MES 口径一致,**负结存降到 534 行**。

### ② 期初已包含过去单据的影响,9/1 前流水必须清掉

`kucun = 期初(8/31) + Σ(9/1 之后的业务流水)`。**9/1 之前**的业务流水若还在,就是双计。

正式库原有 172 行(入 86 / 出 86),全部是 `TCGRK-*` / `TXSCK-*` 前缀的**测试造数**
(其 `asp_user1` 被补流水脚本改成了 `migration-backfill`,只按 user 判会漏网)。
导入脚本按「`asp_user1='test-seed'` **或** 单号前缀 `TCGRK-`/`TXSCK-`」识别并**软删除**
(`asp_cancel='Y'`),备份 CSV 落盘可还原;若清理后仍有残余,脚本**直接中止**不写库。

### ③ `kucun` 必须按流水重算,不能只写期初

只写"期初 = kucun"仅在库里没有业务流水时成立。正式库有 9/1 后流水,故脚本按
`StockMonthCloseService.reconcileKucun` 同口径重算(`yl = 期初 + Σ(入−出)`,**排除月结结转行**),
否则启动自检「结存 == Σ流水」必然报警。

## 三、PC0000 归一为「无批号」(2026-10-19)

用户口径:「**pc0000全部改为无批号**,出库也可以对有批次号的出库,验收阶段先不管批次号」。
落地脚本 `tools/migrate-pc0000-to-null-20261019.sql`(两账套均已执行)。

**归一前后(正式库实测)**:

| 指标 | 归一前 | 归一后 |
|---|---:|---:|
| `kucun` 行数 | 2,453 | **2,283** |
| 无批号行 | — | **1,417** |
| 批次负结存 | 534 行 | **357 行** |
| PC0000 残留 | 1,222(kucun) | **0** |

归一规则:`PC0000` ≡ 无批号 ≡ `lot_no IS NULL`(金蝶语义本就如此)。
同 (物料,仓库) 若同时有 PC0000 行与无批号行,先合并再置 NULL,保证 kucun 三键唯一、
**余量合计逐分不变**。

> 🔴 **方向注意**:本脚本与 2026-10-15 的 `migrate-lot-normalize-blank-to-pc0000.sql`
> (空批号 → PC0000)**方向相反**,是有意的口径反转 —— 别重跑旧脚本,会把成果抵消。

## 三之二、已知遗留:结存与流水按批次存在分叉(262 键)

用户 2026-10-19 选定 **方案A:就此打住**,验收期不追求批次级对齐。

| 指标 | 值 |
|---|---:|
| `kucun` 与 `Σinh−Σouth` 按批次不一致 | **262 键** |
| 按 (物料,仓库) 汇总为负的真缺货 | 109 组 |

**性质**:历史数据分叉,**不是本次导入/归一引入的**。典型 `YJ-JPL-066 | CK00006 | JPL-20260915`:
`kucun` 结存 25,500 来自金蝶期初,但 `inh` 里该批次**没有任何入库流水**,只有一条 −5,700 的出库
—— 期初按批次给的量,在 MES 9/1 后的流水里没有对应入库行。

根因是「金蝶的批次维度」与「MES 的流水维度」对不齐,与 §四 的追溯问题同源。
**上线当天按批次重建期初时自然消失**,届时须跑通
[上线前必验-库存批次追溯.md](../上线前必验-库存批次追溯.md) §五 的验收标准。
