# 研发「项目流程管控」

> 面向:**填了立项申请、想知道单子走到哪一步的人**(申请人 / 对接人 / 项目责任人 / 审批人)。
> 入口:研发管理 → 项目管理 → **项目流程管控**(`/#/rd/projectFlow`,面板码 `PROJECT_FLOW`)。
> 建立日期:2026-10-20(用户口径见下)。

## 一、为什么有这一页

用户原话:

> 我填写立项申请之后提交审批,但是我不知道我这个文件到底到哪个流程了,现在是只有到项目实施计划填写
> 审批归档之后才会在项目进度查询里面看到,但是中间可能会卡住却不知道 ……
> 看这个编号对应的流程走到哪里了,哪个环节还没有审批,哪个单据审批了下一张单内容还没有开始填写。

**改前**:链路中间的环节(定级分发 / 确认责任人 / 责任人确认收到 / 实施计划建了但没填)在界面上
没有统一出口 —— 只有等实施计划归档进了「项目进度查询」才看得见,卡在中间只能靠逐个面板翻。

**改后**:一个只读页,输入立项单号(支持片段)→ 10 个环节逐条给结论:
已完成 / 进行中(带时间与操作人)/ 未开始,并算出**当前卡在哪一步、该谁动手、停留几天**。

## 二、10 个环节与判定口径(唯一真源 = `frontend/src/core/rd/flowStages.js`)

| # | 环节 | 判据(全部取现役真实字段) |
|---|---|---|
| 1 | 立项申请填写 | `rd_approval` 有该单据行 |
| 2 | 立项申请提交审批 | `yj_form_approval` 有 `RD_APPROVAL/SUBMIT` 留痕,或 `yj_doc_status.pending='Y'`,或已审批通过 |
| 3 | 立项申请审批通过 | `yj_doc_status.shr` 非空 / `archived='Y'`,或 `RD_APPROVAL/APPROVE` 留痕 |
| 4 | 定级分发(等级 + 对接人) | `rd_approval.项目等级` 与 `备用1`(对接人)**都非空**(2026-10-19 起两事一个按钮) |
| 5 | 确认项目责任人 | `rd_approval.备用2` 非空(由对接人签核选人) |
| 6 | 责任人确认收到 | `rd_approval.备用3/备用4` 非空,**或** `RD_APPROVAL/OWNER_ACK` 留痕 |
| 7 | 填写项目实施计划 | `rd_plan.文档编号 = 立项单号` 且**至少一个阶段有计划内容**;只建单不填仍算"没开始填" |
| 8 | 实施计划提交审批 | `RD_PLAN/SUBMIT` 留痕,或 `pending='Y'`,或已审批/归档 |
| 9 | 实施计划审批通过并归档 | `yj_doc_status.shr` 非空 / `archived='Y'`(该类面板审批通过即归档) |
| 10 | 进入项目进度查询 | `rd_progress_detail.[说明] = 计划文档编号`(= 立项单号)且有未作废的进度单 |

**待办人**(该谁动手):

- 2 → 申请立项人;3 / 9 → 「审批人」(具体人要按角色审批权判,不写死)
- 4 → 本单审批人(`shr`)· 5 → 对接人(`备用1`)· 6 / 7 / 8 → 项目责任人(`备用2`)
- 10 → 管理员(超时没自动同步时点「同步进度」)

**停留天数** = 现在 − **最后一次动作时间**(取已完成的各环节时间最大值);
完成的项目不显示停留天数;≥7 天在页面上标红,并计入「超 7 天没动」KPI。

## 三、三种非正常情形(实测会遇到,已按数据真实呈现)

1. **状态没落库、后序已完成**
   例:`HSDZ_MES` 的 `LXA-2026-10-0011` —— 实施计划已归档、进度查询已有行,但立项上
   `责任人确认收到` 的备用3 是空的(老代码路径只写了留痕)。此时该环节显示「进行中」+ 红色
   **状态待核** 标签,detail 末尾注明「后序环节已完成，此处状态未落库」,避免用户以为流程没走到这。
2. **弃审回退**
   弃审会清 `项目等级 / 备用1~4`,但审批留痕与进度行可能还在 ⇒ 页面如实显示"卡在定级分发"且
   5~7 步未开始,由用户按弃审后的真实状态重走流程。
3. **已定级、未分发对接人**(2026-10-21 修的是**入口失效**,不是显示问题)
   2026-10-08 口径「冯总审核及定级」让 `审批通过` 这一步就把 `项目等级` 写进 `rd_approval`;
   2026-10-19 又把「项目定级」与「分发对接人」两个按钮并成一个「定级分发」,而它的门禁写成了
   `等级必须为空` ⇒ **两个口径叠成死结**:审批通过(等级已写) 之后「定级分发」永久置灰,
   而唯一能写 `备用1` 的旧按钮「分发对接人」已下架 ⇒ 对接人再也发不出去。
   **现在的口径**:`canGradeDispatch = 已审核/已归档 ∧ 对接人为空 ∧ 当前人是审批人`(不再要求等级为空);
   `gradeAndDispatch` 在等级已存在时**沿用库内等级**(不接受改级,改级仍只能弃审),只补写对接人,
   留痕写「分发对接人(等级沿用 X)」。界面弹窗此时把等级单选置灰并提示
   「项目等级已由审批定级，不能在此修改；此处只需选择对接人」。
   取证:`tools/archive/_probe-rd-approval-dispatch-20261021/{_q-dispatch.mjs,_q-ui.cjs}`。
4. **作废/删除的单据仍挂在流程管控与进度查询里,而且"删不掉"**(2026-10-30 用户报障)
   用户原话:「我服务器上已经把这个213项目的立项申请和项目实施计划删掉了,但是现在还出现在
   项目进度查询,以及项目流程管控那些已经弃审废弃删除的单据流程就不需要再追踪了,现在还能看到,
   而且删除不了」。
   **根因两层**:
   ① 作废/删除走 `ButtonService.voidDoc`,只写 `yj_doc_status.canceled='Y'`,**不动业务表 `asp_cancel`**;
      而本页与 `pruneProgressRows` 判"还在不在"时只查 `asp_cancel` ⇒ **作废的单据一律算还活着**;
   ② 作废后**没有触发**进度清理,要等下一次「同步进度」;而项目进度查询是**只读面板**
      (`PanelPermissionService.READONLY_PANELS`),用户没有任何人工删除入口 ⇒ 表现为"删除不了"。
   **现在的口径**(代码 + 迁移双向修):
   - 立项/实施计划的取数一律补 `NOT EXISTS(yj_doc_status … canceled='Y')`;
   - `pruneProgressRows` 的两条 live 子查询同样补状态表过滤;判据带 `[说明] = [项目编号]` 守卫
     —— 四级行(测试申请单来源)的 `[说明]` 存的是测试背景文本、`[项目编号]` 才是单号,
     不加守卫会把四级行当孤儿一起清掉(另有单独分支按 `rd_dom_test_head` 判活);
   - `voidDoc` 在 `RD_APPROVAL` / `RD_PLAN` 作废后**立刻**跑一次同步,当次就清掉对应进度行;
   - 存量数据由 `tools/migrate-prune-voided-progress-20261030.sql` 一次性软删(两账套已执行,
     判据与代码完全一致,可幂等复跑)。
   回归守卫:`frontend/src/core/rd/rdVoidPrune.test.js`(6 条)。

## 四、部署到**已有立项单据**的服务器会不会"查不到" / 报错

结论:**不会报错,旧单据全都查得到**——本页不依赖任何新表、新字段、新状态列,数据全部来自既有表:

```
rd_approval(立项)  rd_plan(实施计划)  rd_progress_detail(进度行)  yj_doc_status(审批/归档)  yj_form_approval(留痕)
```

页面列出**全部在册立项**(默认 200 条上限,超出提示用单号缩小范围),
单号搜索同时匹配 `单据编号 / 文档编号 / 机型 / 客户名`。

**「在册」= 两侧都活着**(2026-10-30 修,`asp_cancel <> 'Y'` **且** 没有 `yj_doc_status.canceled='Y'`):
作废/删除单据只写 `yj_doc_status.canceled='Y'`、**不动业务表 `asp_cancel`**,只查前者的话
已作废的单据会一直挂在清单里(见 §三.4)。

旧单据只会有三类「看起来不对、其实是真的」的情形,页面都写清了原因,不是报错:

| 情形 | 页面表现 | 说明 |
|---|---|---|
| 老单没有 定级分发 / 对接人 / 项目责任人 / 确认收到(`备用1~4` 为空) | 显示卡在「定级分发」 | 这些字段是本轮流程才有的,老单确实没做过,按真实状态显示 |
| 没有 `yj_doc_status` 行(功能上线前的老单) | 用 `shr/archived` 或 `APPROVE/SUBMIT` 留痕兜底判"已通过" | 单测 ⑪ 钉住 |
| 实施计划的『文档编号』手填了别的/留空 ⇒ 按单号关联不上 | 第 7 步显示「未按『文档编号』关联到立项单号;**疑似计划 LXB-…**(文档编号空)——请到实施计划把『文档编号』填成 LXA-…」 | 2026-10-20 实测算例:正式账套 `LXA-2026-10-0012` ↔ `LXB-2026-10-0004`(文档编号空) |

另外,字段全空的最老单据(只有单号)也不会抛异常:按 `1/10` 正常渲染、停留天数显示 0(单测 ⑯)。

> 关联键口径(实测两账套都认):
> ① 新口径 `rd_plan.文档编号 = rd_approval.单据编号`(责任人确认收到即自动建单);
> ② 老口径 `rd_plan.文档编号 = rd_approval.文档编号`(如正式账套 `LXA-2026-10-0011` 文档编号=`111`,
>    计划 `LXB-2026-10-0002` 文档编号也是 `111`,照样能串起来 —— 实测它显示 10/10 已完成)。

> 权限:管理员恒可见;迁移脚本给**当时存在的全部角色**授权。若服务器上线后又新建了角色,
> 需在「组织架构 → 角色与面板权限」里勾上「项目流程管控」,或重跑
> `migrate-rd-project-flow-20261020.sql`(幂等)。

## 五、代码位置与边界

| 层 | 位置 | 说明 |
|---|---|---|
| 取数 | `backend/.../service/RdProjectFlowService.java` | **只取事实**(立项/计划/两处 doc_status/进度行/留痕/账号姓名),不判环节 |

| 接口封装 | `frontend/src/business/rdApi` → `rdFlowApi.js` | `apiQueryRdFlow(keyword)` |
| 权限 | `PagePanelRegistry.PROJECT_FLOW`(模块=研发管理,动作 view/query) | 页面级虚拟面板:**不往 `yj_panel` 插行** |
| 授权/译名 | `tools/migrate-rd-project-flow-20261020.sql` | 现有全部角色 `view,query` + 面板名 en 译名 |

**本页不写任何单据** —— 要补审批 / 定级分发 / 确认收到 / 填计划,都回原面板操作。
