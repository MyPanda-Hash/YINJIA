# 金蝶「采购入库单」驱动采购订单行执行量刷新（方案二，2026-11-26）

> 客户报障：「ERP 显示未入库 865，MES 显示未入库 5000，一边又显示完成」。
> 定位结论：同一张采购订单行（`YJ-20260921-10` 行3 `YJ-SX-046`，订单量 5000），
> 金蝶真值 = 已入库 4135 / 未入库 865，MES = 0 / 5000，**冻结在首次同步那一刻**。

## 一、根因（四层，前两层是主因)

| # | 层 | 表现 |
|---|---|---|
| ① | **31 天增量窗**（`sync.windowDays`，`sync-core.mjs` 的 `modify_start_time`） | 单头不再改动的老订单**永远不进列表** ⇒ 明细永不重取。实测：出窗 2312 张，占采购订单 94% |
| ② | **表头指纹** | 即便进了列表，`in_qty / un_out_qty` 不在指纹里 ⇒ 整单判「无变化跳过」。11-23 之前窗内单也靠「明细每日复核日戳」每天重取一次（最坏落后 1 天） |
| ③ | **MES 不拉采购入库单** | 别人在金蝶手工录的收货（批次 `PC0000`/空批次，不是 MES 转ERP 推的）MES 完全看不见 |
| ④ | **「剩余」口径 ≠ 入库** | MES 头部「送料 · 剩余 0」是 `form_flow_link` 已生单占用，现场误读成「已入库完成」 |

2026-11-26 上半场（`beb969629`）修的是「MES 里已审核、还没转ERP 的单据所引用的订单」——
覆盖面只有「MES 自己推过去的单」，手工收货的老订单仍会冻结，于是有了本文的方案二。

## 二、方案二：谁收了货，就把那张订单重拉一遍

**不做「用入库单求和算已入库量」**，只把采购入库单当**触发器**：

```
金蝶采购入库单(按 modify_time 增量,含暂存→审核/弃审/红冲)
   ↓ 逐单取详情,读每行 src_bill_no
被收货涉及的采购订单号
   ↓ 并入 sync-core 的 autoRefreshPos(与「待转ERP 补拉」同一条通道)
这些订单本轮强制重取详情(不受 31 天窗口 + 表头指纹限制)
   ↓ upsertDoc 照常写
bl_pu_order.行已执行数量 / 行未执行数量 = 金蝶订单行 in_qty / un_out_qty(唯一真值)
```

**为什么让它当触发器而不是自己算量**：金蝶订单行的 `un_out_qty` 已经把**超收（负数）、退货、
换算率、单据状态**四处口径算好了。自己拿入库单明细求和，这四处会各错一次
（2026-11-23 实测过 `-1800 / -1000` 的超收死行）。
所以数量永远是金蝶给的，本模块只负责「把这张订单再拉一遍」。

## 三、水位线：为什么每轮只扫 20 分钟

- `state.json` 记 `inboundWatchUntil`；每轮扫 `[上轮成功时间 − 20 分钟, now]`。
- **只有扫描成功、无明细失败、未命中订单上限时才推进水位线** ⇒ 同步停过几天会自动补扫
  （水位线停在停机那一刻），不会因为「怕重复扫」而漏掉收货。
- 首次运行（没有水位线）回看 `firstRunDays`（默认 7 天）。
- 手工补扫：`--inbound-window-days=31`（忽略水位线回看 31 天，上线首跑/停机很久后使用）。

实测成本：31 天窗口 475 张入库单 ≈ 15 张/天；稳态一轮（20 分钟窗口）只有 0~3 张单据、
3 次 API 调用以内。首次 7 天窗口 = 135 张单据 / 约 60 s（受 120 ms/单 节流限制）。

## 四、配置与命令行

`deploy/config.example.json` 的 `sync.inboundWatch`（服务器 `config.json` 不填即用默认值）：

| 键 | 默认 | 说明 |
|---|---|---|
| `enabled` | `true` | 整轮开关；也可用 `--no-inbound` 临时关掉 |
| `firstRunDays` | `7` | 首次运行回看天数 |
| `overlapMinutes` | `20` | 每轮重叠回看 |
| `maxPages` | `10` | 单轮最多翻 1000 张入库单（防端点异常死循环） |
| `maxPoNos` | `200` | 单轮最多触发 200 张订单（与 `pendingPoNos` 同口径） |
| `detailGapMs` | `120` | 逐单取详情节流 |

命令行（入口仍是 `deploy/sync.mjs`，计划任务 `JdySalOrderSync` **不需要改参数**）：

```powershell
node sync.mjs                                  # 正式:库存 → 档案/订单(含入库单触发) → 在册核对
node sync.mjs --no-inbound                     # 跳过入库单触发(排查用)
node sync.mjs --inbound-window-days=31 --yes   # 一次性补扫:把近 31 天收货涉及的订单全刷一遍
```

补拉总量上限 400 张/轮（`sync-core.mjs` 的 `REFRESH_POS_CAP`），超出的顺延下一轮。

## 六、已知边界

1. **只认采购入库单**：本账套 `/jdy/v2/scm/pur_inbound_rt` 等退货端点实测返回 519（不可用），
   若金蝶里用其它单据回冲，这里看不见；但订单行数量会在该单下一次任何入库动作时被纠正。
2. **单据被物理删除**时列表不再返回它 ⇒ 不会触发补拉；窗口内的单靠「明细每日复核日戳」兜住。
3. 采购入库单列表只回表头 19 个键，`src_bill_no` 必须逐单取详情（1 次/单，已节流）。
4. 出窗且**再没有任何收货动作**的老订单（存量 2125 张行级数为空）仍需一次
   `--inbound-window-days=<更大>` 或 `--refresh=PU_ORDER` 回填；本方案只保证「有收货就会被看见」。
