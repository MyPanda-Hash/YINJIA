# 扫码报工后「卡住」+「其它工单全部变已结案」——根因与处置(2026-10-18)

> 现场口径(用户原话):
> ① 「手机端报工后，前端无法操作，只能重新进入系统查看」;
> ② 「我在服务器上扫码的工单是 GD-2026-10-0220，并且每次扫码后，当前的生产工单除去当前扫码的这个工单,
>    其余的全部都会变成结案状态」。
>
> 结论先说:**这是两件事**,而且**都不是「MES 算错了」**:
> - **卡住 = 数据库锁等待没有上限**。手机端小程序是**直连同一个 SQL Server** 写 `plang/scjl` 的,
>   那边只要有事务没提交,MES 的查询扫到被锁的行就会**一直等**(驱动默认 `lockTimeout=-1`)。
> - **全部变已结案 = `plang.ja` 被 MES 以外的程序批量写了**。MES 自己结案一定留痕(`yj_usage_log`),
>   而事发当天**一条「结案」留痕都没有**,只有用户自己 424 条「取消结案」。

---

## 0. 一句话给现场

| 现象 | 真正原因 | 已做的处置 |
|---|---|---|
| 报工后前端转圈、只能重进 | 外部程序(小程序/参考库)**直连库未提交事务** + MES **锁等待无上限** | 连接串加 `lockTimeout=8000`;锁超时翻成 503 + 人话;慢请求/锁等待落盘日志 |
| 其它工单全变「已结案」 | `plang.ja` 是**外部程序也能直接写**的列;MES 只看它,不辨来源 | 列表加「结案异常」标记(按 MES 结案口径反查)+ `/closeAudit` 体检端点 + 回正脚本 |
| 报工后工单不推进/产线是 `0` | 手机端直写行的 `scx='0'`,吸收只补空值 | 吸收新增**产线值体检**:不是有效产线就按排产线纠正 |

## 0.5 只改 MES 能不能解决？(结论)

先纠正一个容易误会的点:**这次的处置全部落在 MES 自己这边**,不需要小程序改代码、也不需要它配合上线。
分三块说清"能"与"不能":

| 要解决什么 | 只改 MES 能不能做到 | 怎么做 / 代价 |
|---|---|---|
| 卡住时**不再永久转圈** | ✅ 能(已做) | 连接串 `lockTimeout=8000` + 503 人话 + 落盘日志。最坏等 8 秒给提示 |
| 卡住**根本不再等** | ✅ 能(已做,不需要动库) | 生产工单列表这条**只读查询**改走 `READ_UNCOMMITTED`(Spring 只对这一次事务生效、结束即还原)⇒ 外部程序锁着行也秒开(实测锁住 1 行时列表 **70ms**) |
| 扫码后**其它工单全变已结案** | ✅ 能(已做,只读判定) | 新增 `PlangClose`:「已结案 = ja=Y **且** 入库≥排产(或参考库号段)」。列表/待排产池/排产/撤销/报工/检验单选单/吸收 全部改用它 ⇒ 外部乱写 ja 再也带不偏 MES,而**一个字节都不写它的数据** |
| 小程序**自己**写库很慢/持锁不放 | ❌ 这部分 MES 管不了 | MES 只能保证"不被它拖死";要它自己变快,只能改它(可选,不是必须) |

> 换句话说:**"只改 MES 就能正常使用"已经做到了** —— 没改表结构、没加触发器、没动库隔离级别、
> 也没写小程序的数据。RCSI(`READ_COMMITTED_SNAPSHOT`)从"必需"降为"可选优化"(见 §3.1)。

## 1. 卡住:根因与实锤

### 1.1 实锤实验(可复现)

用一条占据 `plang` **单行**行锁、40~45 秒不提交的事务(模拟手机端/参考库写库后事务没结束),
同时请求 MES 的生产工单列表:

| 环境 | 请求 | 结果 |
|---|---|---|
| 现在的正式代码(8090) | `POST /api/px/workOrderList` | **HTTP 200,耗时 42,751 ms** —— 整段等于"锁被释放"的那一刻 |
| 本次修改后(8091,`lockTimeout=8000`) | 同上 | **HTTP 503,耗时 8,079 ms**,返回「数据正被其它程序占用…请等几秒再点一次」 |

> 实验脚本:`tools/archive/_diag-scan-report/_LockHold.java`(开事务锁一行,到期**回滚**,不改数据)。
> 复现命令:
> ```bash
> cd tools
> java -cp "lib/mssql-jdbc.jar;archive/_diag-scan-report" _LockHold 40 GD-2026-10-0220 1 &
> node tools/archive/_diag-scan-report/_probe-server-latency.mjs http://127.0.0.1:8091 1   # 或直接 curl 列表接口
> ```

### 1.2 为什么会这样

1. **手机端是"另一个程序直连数据库"**,不在 MES 进程里(见 `docs/development/手机端报工吸收.md`)。
   它写 `scjl`(报工行)时,若把插入/更新包在一个事务里、而事务提交得慢或没提交,
   就会在 `scjl`/`plang` 上留下**未释放的行锁**。
2. MES 的「生产工单列表」是**全表扫 + 每行相关子查询**(424 行,CROSS APPLY + 多个 `scjl` 子查询)。
   SQL Server 的读默认是 `READ COMMITTED` ⇒ **扫到被锁的那一行就整条查询停住**,
   哪怕锁的只是"别的工单"的一行。
3. mssql-jdbc 的 `lockTimeout` 默认 **-1(无限等)**,Spring/Hikari 也没有替我们设上限 ⇒
   前端看到的就是**永远转圈**;用户"重新进入系统"能恢复,是因为那时对方事务已经结束、锁释放了。

### 1.3 本次改了什么(已落地,本地已验证)

| 改动 | 文件 | 作用 |
|---|---|---|
| 连接串加 `lockTimeout=8000`(正式 + 测试账套) | `backend/src/main/resources/application.yml` | 锁等待**最多 8 秒**,不再无限挂 |
| 1222/1205(锁超时/死锁)翻成 **503 + 人话** | `config/GlobalExceptionHandler.java` | 现场看到"外部程序占着数据",而不是"服务异常:PreparedStatementCallback…" |
| 生产工单列表改走 **READ_UNCOMMITTED**(只读事务,结束即还原) | `WorkOrderListController.list` | 外部程序锁着行也**不再等**(实测锁 1 行时 70ms 返回);代价=可能读到别人未提交的中间值(列表页可接受) |
| 慢请求(≥2s)+ 503 落盘日志 | `config/SlowRequestLogger.java`、`config/WebMvcConfig.java` | 下次再卡,**日志里能指到是哪一秒、哪个接口、多少毫秒** |
| **后端落盘日志**(控制台 + `logs/backend.log` 按天滚动) | `backend/src/main/resources/logback-spring.xml` | 补上最大的短板:服务器上 MES 原本**没有一直在写的日志文件** |
| 手机端吸收**逐行独立事务** + 等锁跳过 + 单次上限 + 产线体检 | `service/ExternalReportAbsorbService.java` | 吸收不再"一行卡住拖死整批";`scx='0'` 这类脏值按排产线纠正 |

> 为什么要给吸收也动手术:吸收原来**整个任务一个事务**(候选行全部包住)。外部程序一旦锁住其中一行,
> 吸收会**无限等锁并一直持锁**,反过来把 MES 的列表查询也拖死 —— 这是"扫码后卡住"的第二条链路。

## 2. 全部变「已结案」:根因与实锤

### 2.1 现场证据(只读接口 + 使用留痕)

| 证据 | 值 |
|---|---|
| 服务器 `yj_usage_log`(2026-10-18,动作含「结案」) | **424 条,全部是「取消结案」,时间 02:31:15 UTC(北京 10:31:15);「结案」= 0 条** |
| 服务器 `POST /api/px/workOrderList` | 424 行,**`结案` 全为 N**(用户取消后) |
| 手机端直写的报工行(`scjl` 1085/1086/1087/1089/1090) | `报工单号` 为空、`报工` 人 = Admin、**`生产线='0'`**(不是有效产线) |
| MES 后端日志 | 服务器上**没有运行日志文件**(用户导出的包里 MES 只有 10-06/10-07 的旧文件);`gc.log` 最大停顿 **114ms**(排除 GC 卡顿);金蝶同步日志 10-18 每 5 分钟一次、`失败 0`(排除同步任务) |

### 2.2 推理链

1. 生产工单页的「结案」列 = `plang.ja ∈ ('T','Y')`(`WorkOrderListController.list`)。
2. MES 自己把 `ja` 置 Y 只有两条路:① 页面「结案」按钮(必须入库 ≥ 排产,并写 `yj_usage_log`);
   ② `ProcessTaskService.syncCloseState`(组装成品检验已审核 + 入库 ≥ 排产)。
   两条路都**不成立**:当天没有「结案」留痕;这些行的入库数量 = 0。
3. ⇒ 那批 `ja='Y'` **只能来自直连库的那一侧**(手机端小程序 / 参考库),或历史上被人手工改过。
   「除当前扫码这张单以外**全部**变结案」正是**批量 UPDATE 漏了工单号条件**的典型指纹 ——
   那条 SQL 不在本仓库(小程序不在 MES 代码库里)。
4. MES 没有任何防线:读到 `ja='Y'` 就直接显示「已结案」,现场自然把账算到 MES 头上。

### 2.3 本次改了什么

| 改动 | 位置 | 说明 |
|---|---|---|
| **结案判据收口到 `PlangClose`**(只读) | `service/PlangClose.java` + 列表/待排产池/产线负荷/排产/撤销/报工/检验单选单/吸收 | 「已结案 = ja∈(T,Y) **且** 入库≥排产(>0),或参考库号段 GD2608*」。外部程序把 ja 写成 Y 也不会再让工单从池子/排产/检验单选单里消失 |

## 3. 可选优化(都不做也已经能正常用)

### 3.1 (可选)让「读」在整库层面都不被外部写挡住

生产工单列表已经用 `READ_UNCOMMITTED` 解决了"点不开";其它读接口(看板/统计)仍然是默认隔离级别,
被锁时最多等 8 秒(有 503 提示)。如果希望**整库**都免疫,再开数据库的
`READ_COMMITTED_SNAPSHOT`(RCSI):

```sql
ALTER DATABASE HSDZ_MES SET READ_COMMITTED_SNAPSHOT ON WITH ROLLBACK IMMEDIATE;
ALTER DATABASE HSDZ_MES_TEST SET READ_COMMITTED_SNAPSHOT ON WITH ROLLBACK IMMEDIATE;
```

现状实测:正式库 `is_read_committed_snapshot_on = 0`。
⚠ 这是**库级**动作:`WITH ROLLBACK IMMEDIATE` 会踢掉当前连接(含小程序的连接,它那边会重连/报一次错),
所以要么在无人时段做,要么就不做 —— 不影响本次的可用性修复。
脚本:`tools/migrate-enable-rcsi-20261018.sql`(`@apply=1` 才执行,自带现状查询与自检)。

### 3.2 小程序那边"最好改"的三件事(可选,不是前提)

MES 侧已经能兜住(卡死有上限、误结案会回正),所以下面三条**不阻塞上线**,但改掉能少一半麻烦:

1. **事务要短**:写完 `scjl` 立刻 `COMMIT`,别"先插后查再等用户输入"占着事务;
2. **UPDATE 必须带工单号条件**:`UPDATE plang SET ja='Y' …` 要 `WHERE pl_no=@工单号 AND pl_xc=@行号`;
3. **别写非产线值**:报工行的 `scx` 要写真实产线(现在写成 `0`,MES 侧会自动纠正)。

## 6. 第二轮(2026-10-18 下午):「小程序报工后刷新页面一直转圈」

### 6.1 现场描述

「小程序直接报工提交后,刷新当前页面就一直转圈加载;但只有**第一次**报工会这样,
关掉页面重新打开后再次报工就正常。」

### 6.2 日志与库取证(用户导出 `all-logs-20261018`)

| 证据 | 结果 | 说明 |
|---|---|---|
| 服务器 `logs/backend.log`(11:42:10 起,新加埋点已生效) | `[慢请求]` **0 条**、`[锁等待]` **0 条** | 这期间**没有任何一次接口超过 2 秒** —— 卡的不是后端接口 |
| `db-evidence/04-最近写入的表.txt` | 最后一次写库 `12:37:45`,之后无任何写入 | 卡顿发生时库是**静止**的,排除"写锁/大事务" |
| `db-evidence/05-数据库文件与增长.txt` | 87.5MB,10% 自增 | 排除自动增长卡顿 |
| 复测(13:5x) | index.html + 51 个产物 + 15 个接口:**26~216ms** 全绿 | 服务端当前是快的 |
| 旧 build 产物 | 部署前的 `index-ClhSZrh5.js` 等 → **404** | 部署后浏览器若还持有旧 index.html,会去取 404 的 chunk |
| 13:07:01 唯一异常 | `Invalid character found in method name [0x160x030x01…]` | `0x16 0x03 0x01` = **TLS 握手的 ClientHello**:有客户端拿 **https://** 打 HTTP 端口 8090,连接会被直接断开 |

### 6.3 根因(与"后端一条日志都没有"完全吻合)

1. `index.html` 的 `<div id="app"></div>` 是**空的**,页面内容要等 **entry chunk**(以及非中文时的
   **语言包 chunk**,它是 `await import(...)`,而 `app.mount()` 排在它后面)下载完才出现;
2. 这些 **module 请求不走 axios**,**没有超时**。页面空闲一段时间(你正在手机上报工)后,
   浏览器可能复用一个已被 NAT/防火墙**静默丢弃**的长连接 —— 那条请求就**永远挂着**;
3. 结果:`#app` 永远空着 ⇒ **白屏 + 一直转圈**,而**服务器压根没收到请求** ⇒ 后端日志 0 条;
4. 「关掉页面重新打开就好」= 新建连接;「只有第一次」≈ 第一次是**空闲之后**的刷新,
   后面是页面活着时连着点,连接是热的。

### 6.4 已做的修复(都在前端,不动后端/库)

| 改动 | 文件 | 作用 |
|---|---|---|

### 6.4.1 现场那一屏(14:04 用户截图)说明什么

截图是 `http://36.140.66.163:8090/#/prod/plan/workOrderBoard`,**整页纯白**(连左侧菜单都没有)。
这排除了"某个接口慢":接口慢至少能看到侧边栏/框架;纯白 ⇒ **文档或入口脚本根本没到**,与"服务器日志 0 条"完全一致。

同一个时刻的日志(用户贴的 14:04/14:05 三行)是**正常的**:结案巡检报 423 行、吸收用 20ms 处理完 2089 ——
这正好反证:卷宗里的"卡住"不是后端干的。

### 6.5 下次再遇到,三秒定位

1. 看地址栏:`http://` 还是 `https://` —— 若 https,改成 `http://36.140.66.163:8090`(服务器没有 TLS);
2. 浏览器 DevTools → Network:刷新后看**哪一条一直 pending**(`index-*.js` / `xx-*.js` / `api/...`);
   pending 且**服务器日志没有对应请求** ⇒ 连接层问题(本次这类),点「重新加载」即可;
3. `logs/backend.log` 若出现 `[慢请求]`/`[锁等待]` ⇒ 那才是后端/锁的问题(见 §1)。
