# 扫码出库 · 批次勾选 + PC0000 优先(2026-11-28)

> **用户口径(原话)**
> 「扫码出库是需要连带出批次号。可勾选,按勾选的批次号再进行自动填入和排序,
>  自动填入数量,按顺序扣批次号。并且把 PC0000 放在最上面」
>
> 落地范围:**生产领料(单据明细页扫码)** 与 **其他领料(生成其他出库单)** 两个扫码出库入口都要。

## 1. 落成的四条规则

| # | 规则 | 现场看到的效果 |
|---|---|---|
| ① | **PC0000 永远排第一批** | 批次表最上面一行就是 `PC0000`(带「默认批」小标签),其余按批号日期先进先出 |
| ② | **批次可勾选,只有勾上的批次参与本次出库** | 每行一个勾选框;表头有「全选」(全勾 / 全不勾 / 半勾三态) |
| ③ | **按勾选的批次顺序自动填入数量** | 现场只填「本次数量」,系统从 PC0000 往下逐批填满,一批不够自动落到下一批 |
| ④ | **勾选不够时提示,不硬拦** | 「勾选批次的可用量不够,还差 X — 可再勾选别的批次」;MES 不做库存数量校验(真实库存以金蝶为准) |

补充口径:

- **扫到的码里带批号 ⇒ 那一批优先扣**(用户扫的就是这一批),其余仍按 PC0000 → 日期在前;
- **默认勾选**只在扫到物料那一刻做一次(勾够本次数量为止),之后改数量/取消勾选都不会被"自动勾回来";
- **取消勾选 PC0000 也不会报「不是先进先出」** —— `isNonFifo` 跳过默认批,否则含 PC0000 的单几乎每张都会冒出那句提示;
- **其他退料不变**:退的是手上这批货,仍是一行一个候选卡点选,不做多批勾选。

## 2. 为什么 PC0000 要单独处理

金蝶对**不分批商品**统一填默认批号 `PC0000`,现场真正的货就压在这一批上。
按批号日期排(FIFO)时 `PC0000` 取不到日期(`batchDate('PC0000') = ''`),会被当成"没有日期"排到最后 ——
现场要点到批次表最下面才勾得到它,这正是用户要「把 PC0000 放在最上面」的原因。

## 4. 实测(ego,测试账套 `YJ_TEST`)

造数(测试账套 `HSDZ_MES_TEST`,验证后已清理):`YJ-XH-001` 在 `恒亿仓` 造 4 个批号 ——
`PC0000=10`、`XH-20260904=20`、`XH-20260914=30`、`XH-20261014=40`,另有原本的「无批次」2025。

| 场景 | 结果 |
|---|---|
| 其他领料:扫 `YJ-XH-001` | 批次表 **PC0000(默认批)在最上**,默认勾选并填入 10;其余行未勾 |
| 其他领料:勾 0904 / 0914,数量改 55 | PC0000 10 + 0904 20 + 0914 **25** = 55(按顺序扣) |
| 其他领料:取消 PC0000 | 0904 20 + 0914 30 = 50,提示「勾选批次的可用量不够,还差 5 kg — 可再勾选别的批次」 |
| 其他领料:加入清单 | 按批次拆成 2 行(0904 20 / 0914 30)进「其他领料清单」 |
| 生产领料 LL-2026-11-0054(需求 76):扫 `YJ-XH-001` | 自动按顺序勾满 76 = PC0000 10 + 0904 20 + 0914 30 + 1014 16 |
| 生产领料:取消 PC0000 | 重算成 0904 20 + 0914 30 + 1014 26 = 76(不再勾回 PC0000) |
| 生产领料:表头全选 | 5 行全勾,数量仍按顺序 10 / 20 / 30 / 16 |

证据:截图与可复跑脚本在 [tools/archive/_scan-out-batch-20261128/](tools/archive/_scan-out-batch-20261128/README.md)。

## 5. 注意

- PC0000 是**批号字面值匹配**(大小写/空格不敏感),不要扩成"所有默认批都要最前";
- 批次勾选只影响**本次出库分摊**,不改库存口径;过账仍按 `(物料,仓库,批号)` 逐批核销;
- 用户手动跳批仍会写进明细备注(「当前不是先进先出」那段),默认批不算跳批。
