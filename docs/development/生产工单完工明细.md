# 完工明细（生产执行独立列表）

用户纠正位置：生产工单追溯原来已有「完工数据」，不应再在工单内增加入口。

## 当前实现

- 菜单：生产制造 → 生产执行 → 完工明细。
- 通用元数据列表：`/panelx/list/WO_COMPLETION_LIST`，无需勾选工单即可查看全部当前完工记录。
- 呈现方式与现役报工记录一致：`mode=flat` + `category=报表`，所有记录同表展开、按页查询；不显示逐张单据导航。菜单仍属于生产执行。
- 数据来源：原 `scjl`，通过 `v_wo_completion_detail` 只读视图筛选 `wgzt='Y'` 且未作废。视图不复制事实、不新建物理存储表。
- 字段：报工单号、工单号、工单行号、批次号、工序、完成数量、单位、产品编码/名称/规格、生产线、报工人、完工时间、产成品流水号、入库单号；均支持通用查询。
- 权限：按原报工记录查看权限等价补授，新面板只读；不开放新增/保存/删除/审核。
- 中文、英文、日文面板与字段译名同迁移交付。
- 保留原生产工单追溯；撤销上一轮新增的工单完工明细按钮、弹窗、专用controller/service。原追溯不改动。

## 完工时间口径(2026-10-16)

- **「完工时间」= 该笔报工**完成那一刻**的时间**(审核 / 提交审批→审批通过 两条路都算完成,
  两条路都经 `ButtonService.runWoAuditHooks` → `WoReportService.post/complete()`)。
- 写入源**必须是应用本地墙钟** `LocalDateTime.now()`,**不能用 SQL Server 的 `GETDATE()`**。
  根因:开发机 SQL Server 跑在 Docker 容器(`mssql2019`)里,容器 TZ=UTC
  (`SYSDATETIMEOFFSET` = `+00:00`),`GETDATE()` 比北京时间**慢 8 小时** ⇒ 完工明细上出现
  「现场 17:5x 完成、明细显示 09:5x」。同一行 `scjl.asp_time1`(应用写入,17:56:23)与
  `scjl.wgsj`(库写入,09:56:39)只差 16 秒却相差 8 小时,就是这么来的。
- 同一把钟也用在两处:报工行 `scjl.wgsj`(`WoReportService.complete()`)与
  工单行 `plang.完工时间`(`ProcessTaskService.syncOneRowState()`,只在该行**首次**进入
  「生产完工」时写、退回在制即清空 —— 首件检验单的「生产日期」正是取这一列,用 UTC 会把
  凌晨完工算成**前一天**)。
- 应用侧留痕(`asp_time1/asp_time2`)一向就是 `LocalDateTime.now()`(ButtonService),本次把
  完工时刻与它对齐;服务器为原生 SQL Server(库时钟=本地)时两种写法结果相同,故可安全通用。
- 回归探针:`tools/archive/_wo-completion-wgsj/_q-completion-done-time.mjs`
  (测试账套上弃审+重审一张完工报工单,断言完工时间 ≈ 本机当前时间且不是 −8 小时);
  时钟取证 `_ProbeClock.java`、机制取证 `_ProbeWgsjWrite.java`(绑定 LocalDateTime → datetime 列)。

## 落库与验证

初版曾错误使用 `category=生产执行`，flat仅控制后端取数而非前端呈现，导致仍按单据逐张浏览。新增幂等修复 `tools/migrate-wo-completion-flat-report.sql` 对齐报工记录的报表呈现契约；两账套已执行。浏览器回归必须同时断言三笔完工记录可见，不能只检查第一笔。

幂等迁移 `tools/migrate-wo-completion-list.sql` 两账套执行。视图DISTINCT包含唯一id，一行一事实且不能通过该视图写入。
`tools/archive/_verify-completion-list.mjs` 验证两账套通用配置、查询。正式库查询返回3笔完工记录（成型161、切炭161、组装160），不跨工序合计成品量。菜单测试12项通过，前端构建通过。

旧 `937c76bd` 的工单弹窗方向已被本次替代，不再作为当前功能说明；旧探针保留历史证据但不应再运行旧接口测试。
