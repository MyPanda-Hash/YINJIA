### 2.2 行序逻辑边界 —— PASS(+ 2 CONCERN)

实现:调用点 `ButtonService.java` L689;方法 L1650-1679(`intValueOf` L1682-1692);空白草稿首行=1 在 L568-577。

逐场景结论:

- **连加 2 行**:两条都无 id ⇒ max(库内同单存活行)=既有最大,依次 +1 ⇒ 不撞索引。✅
- **删行后再加**:max 取「尚有存活行」的 MAX,且 upsert 先于 softDeleteMissing ⇒ 新号落在所有存活旧号之后;空号不参与索引判定(filtered index 只要求存活行不重复)⇒ 不撞。✅
- **空白草稿首行=1 + 再加行**:占位行(库内 id,行序=1)在提交 items 中(QueryService.loadDocs 不过滤空行)→ 既有行只抬升基线 max=1 → 新行=2。✅ 空草稿 `BOM-2026-10-0001` 是改前数据(行序=0),不影响。
- **既有行行序被前端改大**:`行序` 在 ASM_BOM 仍 editable=0,UI 改不了;若 API 直改,`Math.max(max, intValueOf(该行))` 会把新行推到其上方 ⇒ 不撞。✅
- **upsert 先于 softDelete 的顺序影响**:max 把「本次将软删的行」也算作占用 ⇒ 新号跳过这些号,产生空号但不会冲突(保守安全)。✅
- **「整单重排为何不行」论证成立**:把 1,2 压成 1..N 时,若把 3→2 而 2 尚未软删,UPDATE 当场撞唯一索引;softDeleteMissing 在 upsert 之后执行,无法先释放。只往上补号永远落在已占用区间之外。✅

### 5.0 下游两端不是严格「同口径」(P1)

### 5.1 assignNewLineSeq 实际也作用于 WLBOM(与注释不符)

- 证据:代码注释 `ButtonService.java` L1630-1648 称「全库目前只有 ASM_BOM 满足,其它面板进来直接 return,零影响」。实测 `yj_field` 里 **WLBOM** 也有 `行序`(col=`xc`,整数,place=detail),`yj_panel` WLBOM=doc/`mate`,而 `mate` 确有 `xc int` 与 `asp_cancel` 列(只读查询实测)⇒ 空草稿首行会写 `xc=1`、保存新行会按 max+1 重写 `xc`。`mate` 当前 0 行、且只有 `PK_mate_1(comm,id)` 无 `(m_no,xc)` 唯一索引 ⇒ 无约束冲突,改了 `xc` 也只是排序值;但「零影响」表述不实,且未回归。
