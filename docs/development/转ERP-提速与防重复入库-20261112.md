# 转ERP：提速与「重复入库」防重（2026-11-12）

> 客户口径（原话）：
> 「这个转ERP时反应好慢，要等很久，有时点了两下就会生成两个入库单，这样就有重复入库的风险」
>
> 交付范围：① 在**确保安全**的前提下给转ERP 提速；② **一定要解决多次点击的重复入库问题**。
> 本文是这两件事的取证、改法、验证与残留风险。代码：`KingdeePushService` / `ErpPushGuard` /
> `ButtonService` / `PanelxList.vue` / `PanelxForm.vue` / `core/views/erpOutcome.js`。

---

## §0 一句话结论

| 问题 | 根因 | 处置 | 证据 |
|---|---|---|---|
| 点两下 → 金蝶两张入库单 | 唯一的防重是**事后判据**（读 `是否已转ERP`），而回写 `是` 发生在金蝶落单**之后**，慢的时候十几秒；这十几秒里两个请求都读到"未转"⇒ 各自 POST 一次 | 后端 `ErpPushGuard` **单号级互斥**（第二次立即拒，不排队、不发第二次 POST）＋ 前端列表/表单在推送期间**置灰并解释**＋ 批量弹窗防重复开始 | 并发双请求实测：1 个进推送、1 个 270ms 被拒；金蝶侧该单**只有 1 张** |
| 转ERP 要等很久 | **冷启动**：商品档案 3981 条 ⇒ 20 页 × 每次 0.2~0.8s，加上取 token，第一次点击要 10~20s（越慢越容易被连点） | 档案缓存**并行加载**＋启动后**后台预热**＋每 3 小时刷新＋token 保鲜 | 预热 5 张档案并行 **866ms** 完成；预热后一次推送 **总 1151ms**（准备 102ms ＋ 金蝶保存 1035ms） |

**没有做的事**（以及为什么）：不改金蝶单号规则（把 MES 单号当 `bill_no` 推上去能天然幂等，但那是业务编号规则，
必须客户拍板）；不新增锁表；不为了快而跳过任何校验。

**"改错后重推"是正常流程，不是禁止项**（2026-11-12 用户口径：「弃审后重新审核要确保是可以重新转 erp 的，
这样可以做到 mes 改错、erp 重新同步，原先修改前的单据就可以他们在 erp 上删除就行」）：
`弃审 → 改 → 审核 → 转ERP` 全链已实测可走通并拿到**新的**金蝶单号（见 §5.1），
唯一的前置是**旧那张先在金蝶删掉** —— 这句话现在出现在「弃审确认」框里（`ERP_UNAUDIT_WARN`），
因为在事后提醒就没人看了。

## §1 证据一：金蝶侧**无法**按 MES 单号反查（所以只能在 MES 侧互斥）

原本最理想的闸是"推之前先问金蝶：这张单是不是已经在了"。只读探针实测（`tools/archive/_erp-speed-20261112/probe*.mjs`，
全部 GET，不写金蝶）：

| 试过的过滤 | 结果 |
|---|---|
| `pur_inbound?outside_pk_id=<值>` | **无效**：返回未过滤的整页；且 `outside_pk_id` **不在**列表返回字段里 |
| `?remark=[MES:CGRK-…]` | **无效**：返回整页 |
| `?search=<MES 单号>` | 0 行 —— `search` **只匹配单据编号**，不搜备注（`search=单据编号后 6 位` 才命中 1 行） |
| `?bill_no=<金蝶单号>` | 生效（精确）——但这是**推成功后才知道的号**，挡不住第一次重复 |

⇒ 结论：金蝶星辰这几个接口没有"按外部单号去重"的能力，**防重必须在 MES 这一侧做**。

同样记录一下**不能**靠它兜底的路径：`采购订单`（`PU_ORDER`）推之前本来就有"目标账套已有同号订单则拒绝"
（`resolvePoRefs` 命中即拒），所以订单不在此次问题范围内。

## §2 改法一：后端单号级互斥（`ErpPushGuard`）

```java
// KingdeePushService.pushDocument —— 入口即占位,拿不到就**立刻拒**
Long runningMs = pushGuard.acquire(panelCode + "|" + docNo);
if (runningMs != null) throw new IllegalStateException("该单据正在转ERP推送中(已 X 秒),请勿重复点击…");
try { return doPushDocument(...); } finally { pushGuard.release(key); }   // 成败都放开
```

三条设计取舍（都有自检钉住，见 `tools/archive/_erp-speed-20261112/GuardCheck.java`）：

1. **立即拒、不排队**：排队会让第二个请求干等十几秒，用户以为又卡住了；而且超时后再点会更乱。
2. **键 = 面板 + 单号**：不同单据并行转不受影响（真实业务要一次转多张）；不同面板同号码互不干扰。
3. **`finally` 一定 release**：否则一次异常/超时会让这张单**永久转不了**（比重复入库更难查）。
   自检 ③ 专门测了"release 之后可重入"。

> 前端只是"少发一次请求"，**服务端互斥才是真正的闸**：两个标签页、两台电脑、"第一次超时后再点一次"
> 全都绕过前端。这也是为什么不能只改按钮置灰。

## §3 改法二：前端置灰 + 说清原因

- `core/views/erpOutcome.js` 新增纯函数 `erpClickBlocked(action, pushing)` —— 列表页与表单页**共用同一判据**，
  免得"某天只改了一边"。`erpOutcome.test.js` 直接钉住（含"不能误伤其它按钮"）。
- `PanelxList.vue` / `PanelxForm.vue`：`erpPushing` 在请求发出前置真、`finally` 置假；期间
  - 按钮置灰（`isDisabled`）；
  - 点击给出解释（`disabledReason` → `ERP_BUSY_KEY`：「该单据正在转ERP（正在连金蝶推送，通常十几秒），
    请勿重复点击；完成后列表会自动显示 ERP 单号」）；
  - `onButton` 里再拦一道（防"置灰样式还没刷新出来就被连点"的竞态）。
- 批量弹窗：`openBatchErp` / `doBatchErp` 各加一道"正在跑就别再来一次"（并行跑两遍 = 同一批单据推两遍）。
- **弃审确认框带上"先去金蝶删旧单"**（`ERP_UNAUDIT_WARN`）：对一张已经转过 ERP 的单据点「弃审」时，
  确认框从通用的「确认弃审该单据？」改成
  「本单已转过ERP（{ERP单号}）：请先在金蝶删除那张单据，再修改 → 审核 → 重新转ERP，否则金蝶侧会有两张」。
  同时"已转再点转ERP"的提示也补上了同一句（`ERP_ALREADY_KEY`，10 个语种同步）。
  ⚠ 这句话必须出现在**弃审那一刻**：用户唯一会读提示的时机就是按下按钮的瞬间，事后提醒等于没说。

## §3.1 顺手拆掉一个会"复发"的结构性隐患

"支持转ERP 的面板清单"原先**写了三份**（`pushToErp` 白名单、`listPushableErp` 白名单＋取数表、
`unaudit` 清标记的面板＋表名）。任一处漏更新，后果都是"这张单的转ERP 坏掉"，其中最隐蔽的一种正是
用户本次要求的场景：**弃审那段漏了新面板 ⇒ 弃审重审后点转ERP 仍被"已转"守卫挡住，单据被永久焊死**。

现改为**唯一真源** `ButtonService.ERP_HEAD_TABLE`（面板→单据头表），三处全部从它取；新增转ERP 面板只改一处。
另外 `KingdeePushService` 里那串 `isPur/isOrder/...` 的兜底分支默认是**销售出库**，
故在 `doPushDocument` 开头加面板白名单硬拦（未知面板直接报错，绝不会被当成销售出库单推出去）。

## §4 改法三：提速（只动缓存加载方式，不动推送内容）

事实（`probe.mjs` 实测，每次金蝶调用 0.2~0.8s）：真实账套 **3981 个商品**（本机 `HSDZ_MES.bs_inv` 实测），
商品档案要分 **20 页**才拉完 ⇒ 冷启动光商品档案就 8~16s，加取 token 与其余 4 张档案 ≈ **10~20s**。
这就是"点了没反应 → 再点一下"的物理原因，也是重复入库的诱因。

| 改动 | 说明 |
|---|---|
| 档案缓存改为**按缓存键加锁** | 原来 3 个方法是 `synchronized`（一张档案在拉时其余全排队）；现在不同档案并行、同一档案只拉一次 |
| 启动后 **20s 预热**，之后每 **3 小时**一轮 | 守护线程；5 张档案并行（商品/仓库/职员/部门/计量单位），单张失败只告警不抛 |
| token **保鲜** | 预热时若剩余寿命 < 6h 就提前换新，避免"正好那天点第一下踩上过期" |
| 耗时**留痕** | 每次成功推送记一行：`转ERP[单号] 完成:总 Xms(准备 Yms,金蝶保存 Zms)` —— 下次再报慢，日志直接分得清"本地缓存冷启动"还是"金蝶侧慢" |

开关：`kingdee.push.warmup=false` 可关掉预热（探针/无凭证环境）。

> 为什么**不**把 `page_size` 调大（比如 500）来减少页数：那是未验证的接口行为，一旦金蝶按上限截断，
> 我们会在**静默少商品**的情况下推单（用错/缺 material_id）—— 提速不值得冒这个风险。

### §5.1 「MES 改错 → ERP 重新同步」闭环（`e2e-reaudit-push.mjs`）

用户口径要的是"弃审后能重推"，所以这一条单独立案、逐步实测（对测试单 `TCGRK-0049`）：

| 步骤 | 实测结果 |
|---|---|
| ① 起始 | 已审核 / 是否已转ERP=是 / ERP单号 `CGRK-20260802-00044` |
| ② 弃审 | 状态回草稿；**是否已转ERP=否、ERP单号/操作人/时间 全部清空**（`ButtonService.unaudit` 的联动，8 个转ERP 面板都覆盖） |
| ③ 重新审核 | 已审核，是否已转ERP 仍是「否」⇒ 转ERP 按钮可用、批量列表也会重新列出它 |
| ④ 再转ERP | **真的再推一次**，拿到**新**金蝶单号 `CGRK-20260802-00045`（不是旧的、也没被"已转"守卫挡住） |
| ⑤ 最终 | 已审核 / 是否已转ERP=是 / ERP单号 = 新号 |

⇒ 结论：**弃审 → 重新审核 → 再转ERP 闭环成立**，互斥 guard 无残留（`release` 在 `finally`），
单据不会被焊死在某一次推送状态上。前提：**旧那张先在金蝶删除**；否则金蝶侧会有两张
（这不是 MES 能拦的 —— 金蝶没有"按外部单号查重"的接口，见 §1）。

界面取证（ego 浏览器，5173；只到确认框就点「取消」，**没有真的弃审**）：
对已转单 `CGRK-20261014-03407` 点「弃审」→ 弹「弃审确认」，正文实测为
「确认弃审该单据？本单已转过ERP（CGRK-20261014-03407）：请先在金蝶删除那张单据，再修改 → 审核 → 重新转ERP，否则金蝶侧会有两张」；
取消后复核库里该单 `是否已转ERP=是 / ERP单号 / shr` 全部保持原样。复跑脚本 `round-10.mjs`。

⚠ 已知的**弃审前置门禁**（既有逻辑，本次未动）：弃审会冲回 MES 库存台账，
若该批库存**已被消耗**，`StockLedgerService.unpostIn` 会以「冲回将使现存量为负…库存已被消耗,不可冲回」拒绝弃审。
也就是说"货已经发出去/领用掉"的单子要先在库存上把账理顺，才能走改错重推。这条与转ERP 无关，属库存口径的既有守卫。

## §6 残留风险与后续可选（写清边界，不做暗改）

1. **进程内互斥**：本项目是单实例 jar 部署，`ErpPushGuard` 覆盖所有并发入口。若将来上多实例/集群，
   需要升级为数据库或 Redis 级互斥（届时建议用独立锁表，`REQUIRES_NEW` 短事务占位/释放，
   **不要**用单据行上的 `UPDATE … 推送中` 做法 —— 那会把行锁挂住十几秒，列表查询会跟着卡）。
2. **崩溃窗口**：金蝶 POST 成功、MES 回写 ERP单号之前进程被杀，会留下"金蝶有单、MES 未转"。
   这种状态用户重推仍会再落一张（金蝶无幂等钩子，见 §1）。彻底消除只有两条路：
   ① 让入库单带 MES 单号作 `bill_no`（业务编号规则变更，需客户确认）；
   ② 加"推送流水表 + 事后对账"（按 `create_time` 窗口 + 金额/数量人工核对）。
3. **"弃审→重推"依赖人去金蝶删旧单**：MES 只能在确认框里提醒，无法代删（金蝶接口没有按外部单号删除/查重）。
   若客户希望"系统自动清理"，那是另一个功能（需要按 ERP 单号精确删除，风险更高，得单独评估）。
4. **预热会周期性访问金蝶只读接口**（每 3 小时约 25 次 GET）。如客户对调用量敏感，可调大间隔或关掉预热
   （关掉只影响"第一次点击的等待时间"，不影响正确性）。
5. **测试残留**：接口验证往**测试沙箱**推了几张测试单（`TCGRK-0049` → `CGRK-20260802-00043/44/45`），
   真实业务单一张未动。`TCGRK-0049` 头上 `是否已转ERP=是` 予以保留 —— 它**确实是**在沙箱里，
   写"未转"反而不实。
