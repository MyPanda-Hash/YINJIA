## 二、对比方法(可复现)

1. 备份文件拷进 SQL Server 容器的绑定目录(`D:\sql\data` = 容器 `/var/opt/mssql/data`);
2. 以 `sa` 还原为**临时库 `HSDZ_MES_YJ2`**(MOVE 到 `HSDZ_MES_YJ2.mdf` / `_log.ldf`),本机现役库一律不动;
3. 用只读对比器逐对象比对(表 / 列 / 视图 / `yj_panel` / `yj_field`),输出 UTF-8 报告。

```powershell
# 1) 备份放进容器可见目录
Copy-Item db\yjmes2.bak D:\sql\data\yjmes2.bak -Force
# 2) 还原为临时库(需 sa 权限)
java -cp tools\lib\mssql-jdbc.jar tools\SqlRunner.java `
  "jdbc:sqlserver://127.0.0.1:1433;databaseName=master;encrypt=false" sa "<sa密码>" `
  tools\archive\_restore-yjmes2.sql
# 3) 全量结构对比(只读,不截断)
java -cp tools\lib\mssql-jdbc.jar tools\archive\_DbStructDiff2.java `
  "jdbc:sqlserver://127.0.0.1:1433;databaseName=HSDZ_MES_YJ2;encrypt=false" `
  "jdbc:sqlserver://127.0.0.1:1433;databaseName=HSDZ_MES;encrypt=false" sa "<sa密码>" `
  tools\archive\_yjmes2-vs-local-full.txt
```

> 既有的 `tools\DbSchemaDiff.java` 也能比,但它「缺 40 / 多 20」就截断,列差异看不出构成,故本次改用新写的

## 六、结论与后续建议

1. **两边不是"同构差一点",而是"备份库旧一档 + 本机多一批新功能"**:
   本机多 = 制程检验单(`qc_proc_insp_head/_detail` + 面板 + 54 字段)等 10-14 之后的迁移;
   备份库多 = 09-29 清理链**没真跑**留下的 6 张老表 + 来源机器 10-13 自建的 2 张 `*_bak_20261013` + `inh/outh` 的旧一档重建版本。
2. **若要把备份库的数据搬到本机**(方向:备份 → 本机):
   - 先解决 4.5 的 62 个「本机 NOT NULL、备份可空」列 —— 备份里若有 NULL,插入会被拒(本次**未测**这些列的实际空值率,建议下一步用 SQL 逐列 `COUNT(*) WHERE col IS NULL` 扫一遍);
   - 8 个 `datetime → nvarchar` 的日期列要做格式转换(文本化改造后的格式),3 个 `float → decimal` 列注意精度;
   - `inh`/`outh` 两边物理列不同(58/59 vs 47/48),流水数据不能整表搬,须按列映射。
3. **若要让备份库的结构追平本机**(方向:本机 → 备份库):
   - **不能只跑 `DbSync`**:它按脚本内容哈希判断「是否执行过」,备份库已登记 482 条,未变更的会被跳过,而 `migrate-drop-unused-tables.sql` 正是"登记了没执行"的虚账;
   - 按仓库既定纪律,应先用 `tools/archive/_verify-migration-claims.mjs` 这类证据核对「能不能 baseline」,再决定 `run <脚本>` 或整链重放;
   - 若目标就是让备份库(=来源机器)整体对齐,仓库既有路线是「**全量备份覆盖**」(见 `AGENTS.md` 部署规范 §二 A),前提是先清干净本地测试数据、部署当时新打备份。
4. **本次只做只读对比,未改动任何现役库**;临时库 `HSDZ_MES_YJ2` 与 `D:\sql\data\yjmes2.bak` 仍保留,便于继续取证。清理方式:

```sql
ALTER DATABASE [HSDZ_MES_YJ2] SET SINGLE_USER WITH ROLLBACK IMMEDIATE;
DROP DATABASE [HSDZ_MES_YJ2];
```
