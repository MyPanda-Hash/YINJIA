# 送料暂收单 / 来料检验单「验收造数」批次清理（2026-11-26）

> 用户口径：「又一批之前 10 月份系统生成的暂收单和检验单等单据（为了过验收的），占用了采购订单的生单，
> 但是实际并没用采购入库，我现在要在服务器上把它们删除掉」；补充：「还有 9 月份的，当时是有 Excel 表的，
> 不用删采购入库单」「要保证这个不会占用到实际的生产需求，如生单等」。

## 一、批次判定（怎么认出来的，可复算）

| # | 判据 | 实测 |
|---|---|---|
| ① | **审核时间恰为 `12:00:00`** —— 脚本批量审核的指纹（人工点审核不会整秒落 12:00:00） | 9 月 245 张、10 月 39 张，共 **284** 张暂收单 |
| ② | **暂收数量 = 采购订单行全量**（一张单吃满一整行） | 284/284 全量 |
| ③ | **下游没有任何采购入库单** | 0 张有 `采购入库单`（`来源单号 = SL-…` 命中 0） |
| ④ | 对照：10 月另有 13 张暂收单是**人工**录的 | 审核时间参差（11:41/14:44/23:02…）、数量多为部分量、其中 2 张已生成采购入库并转 ERP ⇒ **未动** |

单号本身也是连续脚本号：`SL-2026-10-0083`~`0090` 一次生成，而 `SL-2026-10-0129/0130` 序号排在
10-12/10-13 那批之后，单据日期却回填成 10-05 / 10-13（**倒填日期**）。

**同一批的暂收退回单**（`TH-2026-10-0003 / 0005 / 0006`）也是造数：审核时间同样恰为 `12:00:00`、
`转ERP时间` 只有日期没有时分、`ERP单号` 是 `CGTH-YYYYMMDD-0000N` 这种「按日从 1 起」的编号 ——
而金蝶真实采购退货单是 `CGTH-YYYYMMDD-00NNN` 连续号（见第六节取证），**这三张在金蝶查不到**。

## 二、执行通道（为什么只能这么做）

| 通道 | 状态 |
|---|---|
| `8090`（应用 HTTP API） | ✅ 通 |
| `5985/5986`（WinRM，部署脚本用） | ❌ 超时 |
| `1433`（SQL 直连） | ❌ 超时 |
| `3389`（RDP） | ✅ 通（未用） |

⇒ 只能走系统自己的按钮链：**弃审 → 删除**（`POST /api/px/callButton` 弃审、`POST /api/px/deleteForms` 删除）。
这条链正是业务口径：弃审会冲回库存台账/成本、级联处理下游；删除会把 `yj_doc_status.canceled='Y'`
并 `form_flow_link` 置 `RELEASED`（占用才能真正还给采购订单），同时把单据从列表里隐藏。
**这不是物理删表**：行还在库里（`canceled`/`asp_cancel` 标记），要物理清表得在服务器本机跑 SQL。

## 三、执行步骤

1. **先回弹检验目录**：8 张批次检验单挂在「检验数据记录明细表」`qc_catalog_detail` 上且状态是
   `已完成检验`，此时 `QcCatalogService.assertLinkedRowNotCompleted` 会挡住弃审。
   → `node reopen.mjs`（调 `callButton(QC_CATALOG, 修改, {编号:JYML-2026-10-0001, id})`），共回弹 **10 行**。
2. `node exec.mjs run cleanup-list.json`：逐张 `弃审`（已审核的）→ 删关联检验单 → `删除` 暂收单；
   草稿单直接 `删除`（不占库存、无下游）。
3. `node purge-returns.mjs`：最后 3 条带退回单的链（见第六节）：
   `弃审退回单 → 弃审暂收单（级联弃审检验单并把退回单草稿作废）→ 删检验单 → 删暂收单`。
4. 逐张核对：`exec-log.txt` / `exec-result.json`。

> 弃审暂收单会**级联弃审**它生成的来料检验单（`ButtonService.slUnauditCascade`），这是名单里检验单
> 一并变成草稿的原因；随后再调 `deleteForms` 把检验单也作废。

## 六、那 3 张退回单为什么最终可以删（金蝶取证）

初始被弃审守卫挡下（「自动生成的暂收退回单已审核，请先弃审该退回单」），但追到金蝶后发现它们
**从未真正落到金蝶**：

| MES 退回单 | MES 记的 ERP单号 | 金蝶 `pur_ret` 里有没有 | 金蝶同期真实退货单 |
|---|---|---|---|
| `TH-2026-10-0003`（福建鑫恒 XH-002 4000） | `CGTH-20260915-00001` | ❌ 无 | 9-14 `CGTH-20260914-00101`（佛山云创壹芯） |
| `TH-2026-10-0005`（福建鑫恒 XH-002 9000） | `CGTH-20260921-00002` | ❌ 无 | 9-21 `CGTH-20260921-00105`（深圳泰兴盛） |
| `TH-2026-10-0006`（韶关英克瑞斯 YKRS-009 1000） | `CGTH-20260927-00003` | ❌ 无 | 9-28 `CGTH-20260928-00108`（惠州双喜） |

取证方式：`GET /jdy/v2/scm/pur_ret` 逐页扫 117 行（覆盖 2026-06-23 ~ 11-26），三个单号 0 命中；
且金蝶 9 月**没有任何「福建鑫恒」的采购退货单**。⇒ 这三张的 `是否已转ERP=是` 是造数时自编的标记，
弃审清掉它不会造成金蝶侧孤儿单。弃审后它们的草稿被级联作废，随即一并清掉。

## 七、效果：全库采购订单占用审计（"不会占用实际生产需求"的证据）

口径：MES 选单剩余量 = 订单行数量 − Σ`form_flow_link`(ACTIVE).linked_quantity + Σ已审核退回量；
金蝶侧未入库量 = 订单行 `un_out_qty`。**MES 剩余 < 金蝶未入库 ⇒ 说明有 MES 单据把这行的收货额度占着。**

扫描范围：全库 **2444** 张采购订单 → **427** 张仍是「已审核」（可被选单），共 1282 行，
其中金蝶仍有未入库的 **706 行**，逐行比对：

| 判定 | 行数 | 说明 |
|---|---|---|
| 剩余 ≥ 金蝶未入库 | **673** | 正常，能按金蝶欠货量生单 |
| 剩余 < 金蝶未入库（部分被占） | 16 | 占用人**全部是 11 月真实暂收单**（jxg 录、已审核、待转ERP） |
| 剩余 = 0（全被占） | 17 | 同上 |
| 选单查不到该行 | 0 | — |

**33 行被占的全部占用人逐个列出核对：100% 是 11 月真实暂收单，没有一张是 9-10 月造数单。**
清理前那 34 行里有 1 行（`YJ-20260915-02` 行1 `YJ-XH-001` 5000）是被造数单占的，删完那 3 条链后已恢复：

| 采购订单 | 清理前 | 清理后 |
|---|---|---|
| `YJ-20260915-02` 行1 YJ-XH-001（金蝶未入库 5000） | 剩余 0（被 SL-2026-10-0121 占满） | **剩余 5000**，可选单生单 |

另：10 月批次里 6 张「金蝶还有未入库量」的订单（`YJ-20261005-06/-07`、`YJ-20261006-02/-08`、
`YJ-20261010-01`、`YJ-20261012-07`）占用已清零、剩余量全部恢复（明细见 `oct_recover.csv`）；
其余 33 张订单在金蝶已全量入库（关闭状态 `S`/`C`），选单本来就不列，与占用无关。

另做了三项：

1. **提交数据记录（同批造数，审核时间同样是 12:00:00）已一并清理**：`JYSJ-2026-10-0089~0098`
   共 10 张，弃审→删除，`QC_INSP_REC` 25 → 15 张，现在 0 张指向已删检验单。

   `YJ-20261119-04` 仍正常列出 3 个 ACTIVE 批次。

### 唯一残留：10 行待检验目录（界面看不到，且按钮删不掉）

| 事实 | 说明 |
|---|---|
| 这 10 行（`qc_catalog_detail.id` 54~63）仍写着已作废的检验单号 | `JYML-2026-10-0001` 的明细行 |
| 界面上**看不到** | 「检验数据记录明细表」的 statusGate 只放「已完成检验」的行，这 10 行现在都是「正在检验中」（目录 28 行 = 9 行真·已完成 + 19 行正在检验中，其中 10 行是本批残留、9 行是 11 月正常待检） |
| 面板按钮**删不掉** | `QcCatalogService.assertNoLinkedDocs` 用 `SELECT COUNT(*) FROM qc_insp WHERE 单据编号=? AND asp_cancel<>'Y'` 判"挂靠单据还活着"；而作废写的是 `yj_doc_status.canceled`（物理行 `asp_cancel` 仍 NULL）⇒ 守卫恒判活着 |
| 处置 | 附 `_close-orphan-catalog-rows-20261126.sql`：只把这 10 行置 `asp_cancel='Y'`（与按钮同效），带"必须已作废"守卫与行数断言，可重复执行。⚠ 需在**服务器本机**跑（1433/5985 从开发机不可达，本次没法代跑） |

> 根因是守卫口径缺陷（`countAlive` 没认 `yj_doc_status.canceled`），彻底修要改 `QcCatalogService` 并部署；
> 本次部署通道不通，故按数据侧收尾，代码侧留待下次一并修。

## 九、回滚

删除 = 软删（`yj_doc_status.canceled='Y'`），单据行仍在 `sl_recv` / `sl_recv_detail` / `qc_insp` /
`qc_insp_detail` / `qc_return` / `qc_return_detail`。回滚不是「复原」而是「重做」：清掉 `canceled`
再逐张重新审核（库存/占用会按当时数据重算）。弃审同时清了 `shr/shsj`，故不能只清 `canceled` 了事。

被删清单（单号/日期/状态/采购订单/物料/数量/批次/关联检验单）见 `deleted-docs.csv`（284 行，
含最后删除的 3 张及其退回单）；
清理前面板快照见 `QC_RECV.json` / `QC_INSP.json`。
