# 采购订单「未入库」三个数对不上（865 / 5000 / 完成）— 2026-11-26 排查

> 客户原话：**「ERP 显示未入库的数量是 865 个，MES 系统一般显示未入库 5000，一边又显示完成，
> 现在两个系统有 3 个不同的数据」**（附金蝶《采购入库单》`CGRK-20261125-03863` 截图，制单时间 20:51:26）。
>
> 结论：三个数说的是**同一张采购订单的同一行** —— `YJ-20260921-10` 第 3 行（物料 `YJ-SX-046`，订单量 5000）。
> 不是三个系统坏了，是**三个不同口径**，外加 **20:51 那张入库单超收了 135**。

## 一、三个数分别是什么（同一条订单行）

| 显示位置 | 客户看到的 | 数据来源 | 判定 |
|---|---|---|---|
| 金蝶（ERP）采购订单行 | 已入库 **4135** / 未入库 **865** | 金蝶 `in_qty` / `un_out_qty`＝订单量 − 已审核采购入库量 | ✅ **唯一真值** |
| MES 采购订单明细「金蝶未入库数量」 | 已入库 **0** / 未入库 **5000** | 同步写进 `bl_pu_order.行已执行数量/行未执行数量`，**冻结**在该单首次同步那一刻 | ⚠️ **旧数**（不是 5000 未收，是 MES 不知道已经收了 4135） |
| MES 采购订单头部 | 送料「已送 2 批 / **剩余 0** / 可补 0」 | `form_flow_link` 已生单占用量（生单 ≠ 入库） | ⚠️ 这是**送满**，不是**收满** |
| 金蝶（21:05 现在） | 已入库 **5135** / 未入库 **−135**；整单 关闭=S、入库=C | 20:51 那张单收 1000 > 剩余 865 ⇒ **超收 135** | 🔴 新问题，见 §三 |

## 二、为什么 MES 是 5000 而不是 865

1. **MES 从不拉「采购入库单」**（`deploy/sync.mjs` 只拉 采购订单＋档案＋库存）。金蝶里手工补录的收货，
   MES 永远不知道 —— 这张单的收货全是手工单：批次 `PC0000` / 空批次（MES 转ERP 一定带自己的批次号）。
2. **行级数量不参与同步判据**：采购订单指纹只有表头字段（状态/关闭/日期/供应商/io_status…），
   `in_qty / un_out_qty` 变了指纹不变 ⇒ 整单被判「无变化」跳过。
3. **31 天修改窗**：`YJ-20260921-10` 单据日期 2026-09-21，早已出窗 ⇒ **永远不会再重取明细**。
   生产库实测：该单行1 `YJ-SX-004-1` MES 显示 8000/27000，金蝶实际 35000/0 —— 冻结已一两个月。
4. **服务器还没吃到 2026-11-26 的修复**（`beb969629`，`pendingPoNos()` 强制补拉）：
   `deploy/部署台账.md` 最后一次部署 = **2026-11-25 19:25**，这次修复没上去；
   而且该修复只覆盖「已审核未转ERP 的单据所引用的订单」，这张单不在其中 ⇒ **即使部署也不会自动纠正**。

旁证：本地账套 `HSDZ_MES`（11-26 同步过）同一行是 **4135 / 865**，与金蝶一致 —— 说明数据源没问题，
是生产 MES 那份冻结了。

## 三、20:51 那张单把 865 收成了 1000（超收 135）

金蝶真实账套实查（`CGRK-20261125-03863`，状态 `C` 已审核，创建 `2026-11-26 20:51:27`）：

| 行 | 物料 | 数量 | 源单 | 源单行 | 批次 | 仓库 |
|---|---|---|---|---|---|---|
| 1 | YJ-SX-034 端盖 | **6000** | YJ-20261111-06 | 6 | PC0000 | 华北工控仓 |
| 2 | YJ-SX-046 端盖 | **1000** | YJ-20260921-10 | 3 | （无） | 华北工控仓 |

第 2 行当时源单只剩 **865**，实收 1000 ⇒ 金蝶该行 `in_qty=5135 / un_out_qty=−135`，
整单从「部分入库」变 **关闭=S / 入库=C（全部入库）**。
⇒ 客户说的「一边又显示完成」现在两边都成立了：MES 是「送料剩余 0」，金蝶是「超收后整单完成」。
⇒ 这一行按 2026-11-23 文档的口径属于「超收死行」：既不会按正常完成，负未入库也关不掉。

## 四、现场该怎么说、怎么做

1. **口径**：只有「金蝶未入库量」是真值；MES 那两列在服务器上既是旧数、又只覆盖窗口内订单。
2. **先处理 135**：核对实物到底到 865 还是 1000；多收就在金蝶做采购入库退回（红字）135，
   不要把 `−135` 留着（否则该行永久闭不了环）。
3. **单张补数**（部署后在服务器跑，≈立刻让 MES 与金蝶对齐）：
   `node deploy/sync.mjs --refresh-bill=YJ-20260921-10 --yes`
   老订单超出 31 天窗，自动同步不会覆盖它，需要**一次性回填**（窗口外「还有未入库」的订单批量 refresh）。
4. **部署 11-26 修复**（`beb969629`）：按 `AGENTS.md §2.6`，`git push` 后 `deploy_src.py --ref <SHA>`，
   并在 `deploy/部署台账.md` 记账。
5. **建议补的两刀**（未实施，需用户拍板）：
   - 同步侧：把「金蝶未关闭 / 行未入库>0」的采购订单也纳入每轮强制补拉（与 `pendingPoNos` 同处），
     否则所有老单永远停在旧数；
   - 界面侧：「剩余」改名为「已生单(未入库)」，并在生单框里与「金蝶未入库」并排显示
     （2026-11-23 文档 §五-2 已提，一直没做）。
   - 治本：定时拉金蝶采购入库单回写「订单行 × 已入库量」，谁在金蝶做的单 MES 都能看见。

## 五、影响面量化（本地同步快照，`_q-po3-07-window-impact.mjs`）

`deploy/config.json` 里 `sync.windowDays = 31`，增量模式只把**近 31 天被修改过**的采购订单拉进列表
（`sync-core.mjs:961` `modify_start_time`）。所以快照里：

| 项 | 数量 |
|---|---|
| 窗口内（单据日期 ≥ 2026-10-26）采购订单 | **134** 张 —— 只有这些的「金蝶已入库/未入库」每天会被日戳复核一次 |
| 出窗（< 2026-10-26）采购订单 | **2312** 张 —— 明细**永不再重取** |
| 其中「行未入库 > 0」（冻结值仍显示还欠货） | **41 张 / 79 行**，如 `YJ-20261023-05` 欠 14600、`YJ-20261021-06` 欠 55555、`YJ-20261022-09` 欠 6600 |
| 出窗且行级数**从未同步过**（`行未执行数量 IS NULL`） | **2125 张** —— 这两列对它们完全空白 |

⇒ 现场看到的「MES 未入库」只要落在出窗那 2312 张里，一律不可信。本单 `YJ-20260921-10`（9-21）
就是典型案例：老值停在「0 / 5000」。
