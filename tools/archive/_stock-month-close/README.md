# 库存月结(2026-10-15)

> 用户口径:「每月 1 号自动月结上个月的」+「上月月结 / 取消上月月结 / 重新月结」三按钮 +
> 按 (物料编码, 仓库编码, 批号) 汇总上月入库(含上月结转来的量)+ 用上月入库数据循环运算逐笔统计出库汇总 +
> 写进 `inh` 生成结转单据 + 出入库三步(统计本月合计 → kucun 有则改无则增 → 改余量)+
> 报表左侧做成「采购入库单选单同款、按仓库选择」。

## 1. 两个定了才敢动数据的口径(用户 2026-10-15 拍板)

| # | 口径 | 取值 | 为什么 |
|---|---|---|---|
| A | 结转行写进 `inh` 后,**累计口径**怎么不翻倍 | 结转行 `src=0` + `单据类型='月结结转'` + `单号 JZ-YYYYMM` + `日期=次月1号`;**`v_stock_movement` 按 `单据类型<>'月结结转'` 排除它** | 三张报表与成本引擎都是「全部历史求和」;若把结转行算进去,8月末结存 X 会被 9 月再记一遍 ⇒ **库存逐月翻倍** |
| B | kucun 的「有则改无则增」 | **幂等重算**:`rkl/ckl` = 截至期末累计、`yl` = 累计入 − 累计出 | kucun 已由审核/弃审钩子**实时维护**;若按「本月入−本月出」累加就是**双计**。重算还有个附带好处:542 行负现存量那类偏差会按流水回正 |

**结转行为什么落次月 1 号**(而不是被结月份的月末):用户口径是「汇总上月的入库数量(**包含上月结转过来的数据**)」——
落在次月 1 号,次月的「本期入库」就天然含上月结转来的量;落在被结月月末则次月求和会漏掉它。

### 计算顺序(有依赖,别调换)

```
① 汇总 期初/本期入/本期出   ② FIFO 分摊(顺带回写缺批号出库行的批号)
③ 用分摊结果覆盖每键出库量   ④ 写结转行(inh)  ⑤ kucun 幂等重算  ⑥ 月结头/行表
```
②必须在⑤之前:回写批号改变了流水侧的键归集,⑤要按回写后的结果重算,才能与⑥的行快照对得上。

### FIFO 循环运算(用户口径③的实现)

- 队列 = **期间开始前的结存**(按期初日合成一行,保证排在期间入库之前)+ 本期间入库行,按 (单据日期, id) 升序;
- 出库行按 (单据日期, id) 升序逐笔取用:带批号的只吃自己那一批(取空记「超发」,不阻断);
  **不带批号的在整组内先进先出,整笔恰好落在单一批次时回写 `outh.批号`**(跨批的行不回写,单行拆不成两条批号);
- 产出每批的**分摊出库量**与**最晚出库日期**;分摊不掉的余量留在原键上(不隐藏、不吞掉)。

   正好差一份结转行。若不做这个排除,累计口径就会凭空多出一整份库存(逐月翻倍)。

(设计如此:回滚反而会把它改错);要退回月结前的数值,得用月结前备份(`bd_stock_close` 里记了合计)。

### 5.3 单价列也摘掉 / 「同仓同存货为什么多行」(2026-10-15 用户追问)

**单价**:用户「把单价也给我删除了」⇒ 展开明细列最终为
`月份 · 单据日期 · 单据类型 · 单据编号 · 数量 · 往来单位 · 经手人`
(入库单价与出库成本单价本来就是两把尺子,混在一列反而误导;引擎写入月结行表时仍记单价,只是不展示。)

**「同仓库 + 同存货编码为什么被拆成多行」= 粒度是<u>三键</u>`(物料编码, 仓库编码, 批号)`**,不是两键。
取证见 `q-04-kucun-grain.sql`(正式库实测):

| 口径 | 组数/行数 |
|---|---|
| `kucun` 行数 = 三键组合数 | **2507** |
| (物料, 仓库) 两键组合数 | **1611** ⇒ **896 组**被批号拆成了多行 |
| 拆分分布 | 1 行 **973** 组 · 2 行 **438** · 3 行 **173** · 4 行 15 · 5 行 4 · 6 行 3 · 7 行 3 · 9 行 1 · 11 行 1 |
| 样本 | `CL002 / CK01` **9 行**(TL00070、TL00140、TL00142、TL00262、TL00301、TL00340、TL00360、TL00370、TL00371),`CL002 / CK02` **7 行** —— 差异**只在批号** |

批号从哪来(决定了同一物料在同一仓会被分成哪几行):

1. **采购链批次号**:如 `SX-20261014` / `GL-20261014`(按「供应商编码+日期」生成),`inh` 里 357 行;
2. **出库行携带的批号**:`PC0000` 这类(旧账/导入的默认批号),1 398 行;
3. **金蝶同步下来的批号**:`TL00070` 这类,只出现在 `YJ-*` 物料上;
4. **无批号**(`lot_no` 为 NULL):`inh` 3 032 行 —— 2026-10-14 的**期初导入那 2004 行**就是无批号的,
   与后来带批号的业务行在「同仓同存货」下并存 ⇒ 这才是"同一物料同一仓库冒出来两行"的主因;
5. 于是**出库打在某个批号、而该批号的期初/入库不足**时,那一行就成了负余量(542 行负值同源,月结重算后 381)。

> 也就是说:拆行**不是 bug,是批号台账的本意**(与金蝶/T+ 同款);真正需要处理的是第 4/5 条那种
> **批号口径错位**(期初挂无批号、出库打 PC0000)。要不要合账/回填批号属数据决策,未擅自动。

### 5.4 第四轮:报表改按 (仓库编码, 存货编码) 归类 + 补名称字段(2026-10-15)

用户口径:「那就先只按仓库编码和存货编码分类,还有仓库名称,存货名称字段不能少」。

**做法**:面板 flat 取数是 `SELECT t.<col> FROM <line_table> t`(**不能带 GROUP BY**),所以按兄弟报表同款
加一层聚合视图 `dbo.v_stock_kucun`(数据源仍是 `kucun`,含 `id` = ROW_NUMBER、`asp_cancel` = 常量 `'N'`),
面板 `line_table` 指向它。**批号不再拆行**,名称从 `bs_wh` / `bs_inv` 取(一律 `OUTER APPLY TOP 1`,避免 bs_wh 同名多行翻倍)。

| 面板字段(9 列,正式库实测) | 说明 |
|---|---|
| 仓库编码 · **仓库名称** | 仓库编码声明为**参照**(WH)⇒ 查询区按名称挑、按编码精确过滤;左栏多选走 `_whCodes` |
| 存货编码 · **存货名称** · 规格型号 | 存货编码同样声明为参照(INV) |
| 累计入库量 · 累计出库量 · 现存量 · 更新时间 | 跨批号 **SUM**;更新时间取 `MAX(update_date)` |

**实测**:
- 视图行数 **1611** = (物料,仓库) 两键组合数(聚合生效;批号级原本 2507 行);Σ现存量与 `kucun` **逐位相等**(自检项);

### 5.8 顺带修:重键残留(重算只 upsert 不清旧键)导致库存虚高

#### 5.3.1 追查「是不是不同日期造成的」——(2026-10-15 用户追问后实测,`q-05`/`q-06`)

**批次号规则(代码为准)**:`BatchService` 第 18/197 行 ——
**批次号 = 供应商编码去掉 `YJ-` 前缀 + `-` + 生单当天 `yyyyMMdd`**(可人工改;打印时登记为权威值)。
⇒ **规则上确实是"不同日期 = 不同批号"**(用户理解正确)。

**但现有库里 638 个「多行」组,没有一组是"跨日期"造成的**:

| 归因(同一 (物料,仓库) 的多行组 = 638 组) | 组数 |
|---|---|
| 含**多个日期**的供应商-日期型批号 | **0** |
| 含**多个供应商** | **0** |
| **无批号 与 有批号 混存** | **546**(86%) |
| 含 `PC0000`(旧账/导入默认批号) | **503** |
| 含金蝶 `TL*` 批号 | 51 |

原因:这些单据/期初是 **2026-10-14 同一天**生成导入的,日期型批号全是 `...-20261014`
(只有个别纯数字批号如 `20260924`/`20260922` 例外)。所以真正把同一物料同一仓拆成多行的是
**四套批号体系并存**:

| 形态(kucun) | 库存行数 | 物料数 | Σ现存量 |
|---|---|---|---|
| ① 无批号(NULL,期初导入) | **1432** | 1285 | +4,324,097.47 |
| ② `PC0000`(旧账/导入默认批号) | **573** | 528 | **−1,153,445.10** |
| ③ 金蝶 `TL*` | 209 | 14 | +17,063.00 |
| ④ 供应商-日期型(本系统生成) | 277 | 251 | +1,557,934.40 |
| ⑤ 其它(纯数字批号等) | 16 | 15 | +5,484.00 |

典型实例 `YJ-AJ-030 / CK00006`(3 行,同一批货被三套口径各记一次):

```
(无批号)        2172/… → +10212   期初导入
AJ-20261014   +10212                stock:admin(业务入库)
PC0000        −10212                期初导入(出库扣在这个假批号上)
```
净值是对的(+10212),但行拆成 3 行且带负数 —— 那批负余量(月结重算后 381 行)主要就出在 ② 这一形态上。


## 6. 踩坑留档(本任务实测,别重犯)

| # | 坑 | 现象与根因 |
|---|---|---|
| 1 | `单据日期` 是 **datetime** 不是 date | `String.valueOf(Timestamp)` → `"2026-09-30 10:20:30.0"`,直接喂 `java.sql.Date.valueOf` 抛 `IllegalArgumentException: null`(**消息为空** ⇒ 全局异常处理器只回一个 `code:400/500`,没有线索)。两处都得上 `toDate()` 截前 10 位 |
| 2 | NULL 被拼成字面量 `"null"` | `String.valueOf(null)` = `"null"`,同样会喂给 `Date.valueOf` 炸掉;判空必须在取值处 |
| 3 | 全局异常处理器吞堆栈 | `GlobalExceptionHandler` 把异常归一成 code+message,**不打日志**。为此给月结加了运维直调入口 `POST /api/stock/monthClose/run`(返回异常类名 + 消息 + 前 8 帧),后续排查先打它 |
| 4 | `rebuild-prod.ps1` 的 fat jar 自检 | 脚本用 `jar tf`,而 `jar` 不在 PATH(`$JAVA_HOME\bin` 没进 PATH)⇒ 打包成功后卡在自检、**没重启服务**。自检要显式用 `"$env:JAVA_HOME\bin\jar.exe"` |
| 5 | 停服才能 repackage | 后端跑着 `target\*.jar` 时 `mvn package` 报 `Unable to rename ... .jar.original`;必须 `start-prod.ps1 -Stop` 后再打包 |
| 6 | **改了后端必须重打 jar 才生效** | 8090 跑的是 jar 里的 class:我先改了 `QueryService._whCodes` 却在旧 jar 上验前端 ⇒ 勾选仓库**看着像前端没生效**(条数纹丝不动),其实是后端不认这个条件键。判据:同一个接口用 curl 直接带 `_whCodes` 试一次,能区分「前端没送」还是「后端没认」 |
| 7 | 改带中文的 `.ps1` 会丢 BOM | 编辑工具写回的是无 BOM UTF-8,PowerShell 5.1 按 GBK 解码 ⇒ 语法报错。改完 `.ps1` 要**补回 BOM**(本仓库既有脚本都是带 BOM 的) |
| 8 | SQL 拼接漏空格 | `" UNION ALL"` 紧跟 `"SELECT …"` 会拼成 `UNION ALLSELECT`,报「ALLSELECT 附近有语法错误」。多行 SQL 拼接处**两端都留空格**最稳 |
| 9 | 展开看哪个月要说清 | 月结行落在**次月 1 号**,展开按月看就永远看不到月结单据;改看**当前月**后,`2026-09月结` 才会出现在 10 月的单据列表里 |
