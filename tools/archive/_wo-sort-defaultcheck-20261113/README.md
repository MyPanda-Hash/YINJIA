# 生产工单：列表排序/转单时间修复(方案 A+B) + 点排产后快速排产默认勾选（2026-11-13 第三轮）

> 用户口径：
> ① 「新工单应该排列在旧工单上方」，并追问「是不是因为当前手工新增的工单号和原来订单结转的工单号排序方式不一样」；
> ② 「按照图片参考当前点击排产后，默认勾选这个快速排产中的列。实现这种形式的操作」。

## 结论

### 需求 1：排序 + 转单时间（A+B 都已落地）

**根因（实测取证，正式库 HSDZ_MES）**

| 工单号 | pl_date | 转单(北京) | 来源 |
|---|---|---|---|
| GD-2026-11-0018 | **2026-11-13 00:00:00** | 15:03 | 手工新增 |
| GD-2026-11-0019 | **2026-11-13 00:00:00** | 15:05 | 手工新增 |
| GD-2026-11-0021 | **2026-11-13 00:00:00** | 15:40 | 手工新增 |
| GD-2026-11-0022 | **2026-11-13 00:00:00** | 15:54 | 手工新增 |
| GD-2026-11-0023 | **2026-11-13 00:00:00** | 15:55 | 手工新增 |
| GD-2026-11-0017 | 2026-11-11 07:29:28 | 15:29 | 订单结转（od_no 非空） |

两条原因叠加（与"编号规则不同"无关：手工新增/草稿提交/订单结转都用同一个 `GD-yyyy-MM-NNNN` 号池）：
1. 列表 SQL 是 `ORDER BY pl_date DESC, pl_no, pl_xc` —— 同一天按**工单号升序**，号越大(越新)反而越靠下；
2. 手工新增把 `pl_date` 写成**当天 00:00:00**（只保留日期），订单结转写 `GETDATE()`（含时分）——
   同一天里手工单的 00:00 比任何带时分的都小 ⇒ 手工单一定沉到当天组底部。
3. 另外 `转单时间` 列原来直接显示 `asp_time1`，而本机 SQL Server 在 Docker 里 **TZ=UTC**
   ⇒ 15:07 显示成 07:07（差 8 小时）。

**改法**

- **A. 排序**（`WorkOrderListController` 列表 SQL）：
  `ORDER BY p.pl_date DESC, p.id DESC, p.pl_xc`
  —— 先按工单日期倒序（业务口径不变），同一天按**自增主键 id DESC = 建单先后倒序** ⇒ 后建的排最上面。
  明确不用 `pl_no` 做时间判据（nvarchar、跨月/跨年前缀会翻车）。
- **B. 手工建单写时刻**（`WorkOrderCreateService.create`）：
  `pl_date = 用户选的工单日期(日) + 当前 UTC 墙钟时刻`。
  - 日期部分保「单据日期」不变；
  - 时刻部分用 **UTC**（与容器 TZ=UTC、订单结转 GETDATE() 同一口径），否则本地时刻/UTC 时刻混排
    会让同一天内先后错乱；
  - 新建单不再全是 00:00 ⇒ 排序自然靠前；同日同秒再由 id DESC 兜底。
- **转单时间显示**（同一列表 SQL）：
  `CONVERT(varchar(16), DATEADD(hour, 8, p.asp_time1), 120)` —— 库内存 UTC，显示按北京时间（中国无夏令时，
  固定 +8 安全）。**只改显示**，不改库值、不影响排序。

**验收**

- 只读模拟新排序（正式库）：`2026-11-13` 这一组从「0018→0019→0021→0022→0023」变成
  「（新）→0023→0022→0021→0019→0018」，转单时间显示 15:03~15:55（原 07:03~07:55）。
- 8091 新 jar（测试账套）接口探针 `tools/archive/_wo-sort-defaultcheck-20261113/probe/verify.mjs` → **6/6 PASS**：
  连续建两张同日工单（GD-2026-11-0030/0031）→ 列表新单 idx=0、旧单 idx=1；
  转单时间与当前本地时间差 < 1 分钟；单据日期=所选日期；需求=排产=生产数量。
- 落库实测：`pl_date = 2026-11-13 08:35:20 / 08:35:21 / …`（UTC 时刻，日期为所选工单日期）。
- 界面（ego，8091）：列表前 5 行 = 0031→0030→0029→0028→旧测试单，转单时间 16:35（北京时间）。
- **8090 正式实例重建重启后（只读核对）**：列表今日顺序 = `GD-2026-11-0023-1(16:13) → 0023(15:55) → 0022(15:54) → 0021(15:40) → 0019(15:05) → 0018(15:03)`；
  转单时间全部为北京时间（与库内 UTC 值 +8 一致），旧规则下的 0018/0019/0021 已被新单压在下面。

### 需求 2：点「排产」后快速排产默认勾选当前工单行

- 现状：生产工单页勾 1 行点「排产」→ 内嵌「快速排产」按 `工单号#行号` 收敛①待排产池，
  但**没有默认勾选**（多行批量模式 2026-10-30 才有默认全选）。
- 改法（`ScheduleBoard.vue`）：`loadPool()` 末尾，单行内嵌模式（未传 `行id列表` 且是 `embedded`）调用
  新增的 `selectEmbeddedRows()`：按「工单号(+工单行号)」匹配①池里的行并 `toggleRowSelection` 勾上
  （带行号精确到行；不带行号勾该工单全部行，与 keyword 收敛口径一致）。
  ⇒ 打开弹窗即已勾选，直接点「排产」/双击行即可，与多行模式体验一致；刷新后也保持默认勾选。
- 验收（ego，8091 新 jar，截图 `ego/r01-schedule-default-checked.png`）：
  点列表第 1 行 → 「排产」→ 弹窗①待排产池 `rowCount=1 / checkedCount=1 / 排产按钮可用`，零 pageerror。

## 注意

- 历史数据的 `pl_date` 仍是 00:00（B 只影响**改后新建**的单）；A 的 `id DESC` 让历史同日单也按创建先后倒序。
- `转单时间 +8` 依赖「SQL Server 容器 TZ=UTC」这一既有环境事实（仓库多处记录）。若将来库时区改成
  东八区，这一处会多 8 小时，需要同步去掉偏移（代码注释已写明）。
