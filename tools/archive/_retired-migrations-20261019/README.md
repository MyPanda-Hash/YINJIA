# 已退役的迁移脚本(2026-10-19)

这里放**曾经在 `tools/db-migrations.txt` 链里、现已退役**的脚本。保留原文只为查证据,
`DbSync` 不会再执行它们(已从清单移除)。

## migrate-plang-row-state-backfill-20261015.sql(退役于 2026-10-19)

**为什么退役**:该脚本除了重算 当前工序/完工状态 三列(这部分是对的),还在第 110 行把结案写成:

```sql
p.ja = CASE WHEN c.排产 > 0 AND (c.全道报工达标 = 1 OR c.入库 >= c.排产 - 0.0001) THEN 'Y' ...
```

也就是「**报工做完了 = 结案**」—— 这个口径在 2026-10-15 就已经被代码删掉了
(`ProcessTaskService.syncOneRowState` 的注释:「这里**不再动 ja**」,结案改为
`syncCloseState` 按「组装成品检验已审核 + 入库 ≥ 排产」重算),但同一口径被留在了这份脚本里。

**留着它的后果**:`DbSync` 按内容哈希判断是否重跑,任何人改动这份 SQL 的字节(哪怕只改注释)、
补登记、或重建账套,它就会**重放**,把"报工做完了但还没入库"的行批量写成 `ja='Y'` ——
这正是 2026-10-18~19 现场「扫码报工后其余工单全变已结案 / 生产工单页一排结案异常」的同一现象。

**取证指纹**:它写过的行会带 `asp_user2 = 'migration'`、`asp_time2 = GETDATE()`。
2026-10-19 用 `/api/px/workOrderList/closeAudit` 查正式库 38 行异常,**没有一行带该指纹**
⇒ 那次的 `ja='Y'` 不是它写的(是外部程序直连库写的),本脚本只是**潜在**隐患。

**要恢复"按报工回填状态"能力时**:另写新脚本,只回填 `当前工序 / 当前工序完工量 / 完工状态`
三列,**不得写 `ja`**;`ja` 只允许由 `ProcessTaskService.syncCloseState`(入库+检验)或
生产工单页「结案」按钮(入库)改动。
