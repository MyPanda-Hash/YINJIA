## 2. 「加工单号」到底是什么

不是金蝶的号，而是 **生产工单号 `plang.pl_no`**（形如 `GD-2026-10-0117`）。三处现役代码同口径：

- `WorkOrderPickingService`：「加工单号 = 工单号」+「工单行号 = plang.pl_xc」；
- `ButtonService` 出单：`head.put("加工单号", wo)`（wo = 工单号）；
- 工单追溯 / 工单结案 / 工单拆分：一律 `WHERE bd_finish_in.加工单号 = ? (+ 工单行号)`。

⇒ 只能填库里**真实存在**的工单号，编一个号会让追溯查到空气。

## 4. 判定规则（strict / lenient）

对每张 `加工单号` 为空的产成品入库单：

1. **候选** = `plang` 里含本单产品的工单号（`bl_finish_in.产品编码 = plang.dm`，去首尾空格）；
2. **时间闸门（用户要的"符合时间"）**：该工单的**最晚一行工单日期 ≤ 入库单日期**（工单不可能晚于入库），
   且距今 ≤ `@MaxDays`（默认 180 天）；
3. **一张单只落一个工单号**：排序取 `覆盖产品数 desc → 时间差 asc（离得最近）→ 数量差 asc → 单号 desc`；
4. **strict（默认）**：只有"该工单含本单**全部**产品"才填 —— 本单与工单对得上，填了才是事实；
   **lenient**：允许"只对上部分产品"也填，并把覆盖率写进留痕供复核；
5. 单产品单顺带填 `工单行号`（`plang.pl_xc` 里对该产品的那一行）；多产品单**不填**工单行号
   （一行对不上多个产品；留空 = 占整单，语义才对）；
6. **只填空值**，已有值（含金蝶导入的真号）一行不碰；每改一张单写一条 `yj_usage_log` 留痕。

## 5. 为什么 strict 补不全（数据事实），以及第二轮怎么放宽补完

| 分类 | 单数 | strict | 第二轮 |
|---|---|---|---|
| ① 全覆盖 | 31 | ✅ 已补（M1） | — |
| ② 部分覆盖（本单 3~7 个产品里只 1~3 个能在某工单找到） | 113 | ❌ 不填 | ✅ 补（M2：产品对得上 + 时间合理） |
| ③ 产品对得上、但工单日期**晚于**入库日 | 33 | ❌ 不填 | ✅ 补（M3：时间越界，先入库后开工） |
| ④ 产品在 `plang` 里**完全没有**（66 个产品没工单，但都在商品档案里） | 54 | ❌ 不填 | ✅ 补（M4：无产品依据，按 |入库日−工单日| 最近的工单） |

**M4 的时间接近度实测：54 张全部 ≤ 7 天**（= 与入库单最近的工单基本就是那几天在产的）。
补完 = 232 张全部有号（0 张空）。

### 5.1 风险（必须知道）

- **M3**：工单在入库日之后（-1 ~ -37 天）——"先入库后开工"业务上说不通，只是产品对得上；
- **M4**：完全没有产品依据，只有"时间最近"这条线索；
- 这两档会把不属于该工单的产品数量算进该工单的"已入库"（工单追溯/结案读数会受影响）。
- 要"经得起推敲"的版本：服务器包里加 `-StrictOnly`（只补 M1 那 31 张）；
  已经全补了想收回来：`rollback.ps1` 一次全撤，或按留痕里的档位人工挑（留痕 action_name 带 `M3`/`M4`）。
