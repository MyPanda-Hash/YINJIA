# 产成品入库单「加工单号」补齐包 —— 给服务器上的 AI / 运维直接执行

> 一句话：**给 `bd_finish_in` 里空着的 `加工单号` 补上生产工单号**（`plang.pl_no`），
> 先跑最稳的一档，再把剩下的全部补上。**只做数据、不动 jar、不重启服务、不改表结构。**
>
> 用户口径：「写个脚本可以补齐成产品入库的加工单号。按照有的补齐。要合理，符合时间。」
> → 第二轮：「放宽要全补上，并且把补充的脚本发给我，方便服务器直接用。」

---

## 0. 先搞清楚这一列是什么

`加工单号` = **生产工单号 `plang.pl_no`**（形如 `GD-2026-10-0117`），不是金蝶的号。
依据现役代码三处同口径：

- `WorkOrderPickingService`：「加工单号 = 工单号」+「工单行号 = plang.pl_xc」；
- `ButtonService` 出单：`head.put("加工单号", wo)`；
- 工单追溯 / 工单结案 / 工单拆分：一律 `WHERE bd_finish_in.加工单号 (+ 工单行号)`。

⇒ 只填库里**真实存在**的工单号；编一个号会让工单追溯查到空气。

## 2. 执行（两条命令）

> 工作目录 = 解压后的包目录；PowerShell 一律 `-ExecutionPolicy Bypass`。

```powershell
# ① 先只看不动（可选，但建议先跑一次把报告留档）
powershell -ExecutionPolicy Bypass -File .\apply.ps1 -ReportOnly

# ② 真跑：第一档 strict + 第二档 full 全补
powershell -ExecutionPolicy Bypass -File .\apply.ps1
```

期望最后一行：`RESULT: FINISH-IN-WO-OK`

只要最稳那一档（不想要 M3/M4 的放宽结果）：

```powershell
powershell -ExecutionPolicy Bypass -File .\apply.ps1 -StrictOnly
```

- **不重启服务、不碰 jar**：面板数据是实时查库，刷页面就能看到；
- `加工单号 / 工单行号` 本来就是「产成品入库单」面板的**查询条字段**，补完可以直接按工单号查入库单；
- 有 `logs\apply-<时间戳>.log` 留档。

## 3. 两档口径（这就是"合理、符合时间"的具体含义）

对每张 `加工单号` 为空的产成品入库单，按下面顺序取**第一条**：

| 档 | 判据 | 说明 |
|---|---|---|
| **M1**（第一档 strict） | 某工单的产品集**恰好覆盖**本单全部产品，且该工单最晚一行日期 **≤ 入库日**、距今 ≤180 天 | 本单与工单一一对得上，填了就是事实 |
| **M2**（full 内） | 本单**部分**产品出现在某工单里，工单日期 ≤ 入库日（180 天内） | 产品对得上，但只覆盖一部分 |
| **M3**（full 内） | 产品对得上，但工单日期**晚于**入库日 | 先入库后开工 —— 时间上说不通，属于"放宽" |
| **M4**（full 内） | 本单产品在 `plang` 里**完全查不到** | 无产品依据，只能按**时间最近**的工单硬落 |

每张单的档位都写进了留痕（见 §5），事后可以按档过滤复核。

判定细节：
- 排序：档位升序 → 覆盖产品数 desc → **|时间差| asc** → 数量差 asc → 工单号 desc；
- `工单行号` 只在「单产品 + M1/M2/M3（有产品依据）」时填（= 该工单里对这个产品的那一行）；
  **M4 与多产品单不填**（留空 = 占整单，语义才对）；
- 只填空值：`ISNULL(加工单号,'') = ''` —— 已有值（金蝶导入的真号、之前补过的）一行都不碰。

## 4. 本地实测（2026-10-22，正式库 HSDZ_MES）

| 项 | 结果 |
|---|---|
| 产成品入库单 | 232 张（808 明细行） |
| 补之前空着 | 231 张（唯一有值的是 MES 自建草稿 `FI-2026-09-0001 → MO-2026-09-0002`） |
| 第一档 strict | 补 **31** 张（M1） |
| 第二档 full | 再补 **200** 张：M2 **113** / M3 **33** / M4 **54** |
| 补之后 | **232 张全部有加工单号**（0 张空） |
| M4 的时间接近度 | 54 张**全部**落在 |入库日 − 工单日| **≤ 7 天**内 |
| 幂等 | 再跑一次 `RESULT: FINISH-IN-WO-FULL-NOOP`（0 张） |
| 回滚实测 | 一次撤掉 231 张（回到 231 空 / 1 有值），留痕标「（已回滚）」 |

> 服务器上的数字会不一样（那边是真实业务数据），以 `apply.ps1` 打出来的报告与汇总为准。

## 5. 留痕与回滚

- 每改一张单写一条 `yj_usage_log`：
  `panel_name=产成品入库单`，`user_name=datafix-finish-in-wo`，
  `action_name=数据修复·补齐加工单号(覆盖m/n/M2)→GD-2026-10-0117`，`doc_no=单据编号`。
  ⇒ 在「系统管理平台 → 使用权限查看」里能看到这批操作。
- 回滚：

```powershell
powershell -ExecutionPolicy Bypass -File .\rollback.ps1
```

  只还原**当前值仍等于留痕值**的单据（有人后来手工改过的，按新事实保留不动）；
  加工单号与工单行号都置空；留痕行标「（已回滚）」，重复执行不会二次回滚，也不会误撤别人的补齐。

## 6. 注意事项（务必看一眼）

1. **M3/M4 是放宽的结果，不是事实**：
   - M3 的工单在入库日之后（先入库后开工，业务上说不通）；
   - M4 完全没有产品依据，只有"时间最近"这一条（实测都 ≤7 天）。
   如果只要"经得起推敲"的那部分，用 `-StrictOnly`，或者跑完后再按留痕里的档位人工复核/回滚。
2. **补完会影响工单追溯的读数**：这些入库单会挂到对应工单下（这正是补齐的目的），
   但 M3/M4 那部分会把不属于该工单的产品数量算进该工单的"已入库"。
3. **不覆盖既有值**：金蝶导入的号、第一档补过的号都不会被改。
4. **两个账套都要跑**：正式库 `HSDZ_MES` 与测试库 `HSDZ_MES_TEST`。
   测试库 `plang` 是 0 行（快照里没有工单）⇒ 跑出来是 NOOP，属正常。
5. **不改表结构、不动 `asp_*` 字段**：只写 `加工单号` / `工单行号` 两个业务列。
6. 想撤干净：`rollback.ps1`；想重来：先回滚再跑 `apply.ps1`。

## 7. 排错

| 输出 | 含义 / 处理 |
|---|---|
| `RESULT: FAIL-NO-TABLE` | `bd_finish_in` / `bl_finish_in` / `plang` 缺失 —— 这台库不是本系统的完整账套，先核对部署方式 |
| `RESULT: PREFLIGHT-NO-PLANG` 且继续跑 | `plang` 0 行：没有工单可匹配，脚本会 NOOP（不是报错） |
| `RESULT: FAIL-DB` | 某个脚本没报告成功，看 `logs\apply-<时间戳>.log` |
| `RESULT: FAIL-NO-JAVA` | 需要 JDK（`java` 在 PATH 或设 `JAVA_HOME`）；本包只跑 SQL，不需要 `jar` |
| 报告里 ② 全覆盖 = 0 | 已经补过了（幂等），或该库确实没有能对上的工单 |
