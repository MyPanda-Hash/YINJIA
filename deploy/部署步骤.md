# 全量部署步骤（2026-09-21 版）

> 路线：**全量恢复** —— 用开发机的干净账整体覆盖服务器库（部署说明 §二 A，第三次走这条：09-10 / 09-14 / 本次）。
> 服务器：`36.140.66.163`（RDP 3389）· 安装目录 **`C:\yinjia\`** · 站点 <http://36.140.66.163:8090>
> 本包：`pkg-20260921.zip`。解压后是扁平的一堆文件，**解压到哪个 ASCII 目录都行**（脚本用自己所在目录当源）。

## ⚠ 四个坑（前两个本次实测踩到，后两个是本地演练揪出来的漏洞，务必先看）

1. **服务器上已经有一个 `C:\yinjia\HSDZ_MES.bak`**（2026-09-14 那次部署留下的旧备份），而还原脚本固定从
   `C:\yinjia\HSDZ_MES.bak` 还原 —— 不先处理就会**静默装回旧库**。
   `deploy-all.bat` 已自动处理：先把旧的移到 `C:\yinjia\backup\HSDZ_MES.bak.old-<时间戳>`，
   再把**包里的**备份复制成 `C:\yinjia\HSDZ_MES.bak`，核对字节数后才还原。
   日志里会看到 `RESULT: OLD-BAK-ARCHIVED …` 与 `RESULT: STAGED-BAK-IN-PLACE …`。
2. **`\\tsclient\C\yj-deploy\…` 这条路在这台服务器上不通**（RDP 驱动器重定向被禁用，服务器里 `dir \\tsclient\C\…`
   报「找不到网络名」）。所以包得**你自己拷过去**（U 盘 / 网盘 / 邮件），不能用重定向盘直接跑。
3. **别把包解压到 `C:\yinjia\` 本身**：脚本第 4b 步会先把 `HSDZ_MES.bak` 挪去 `backup\`，
   而那个文件就是包自己的 —— 然后复制回去必然失败（`FAIL-STAGE-BAK`，看着像丢数据）。
   现在脚本开头就会拦：`RESULT: FAIL-PKG-IN-INSTALL-DIR` 直接停。解压到自己的目录（`C:\yj-deploy\`）即可。
4. **还原的"成功"判定只有一个标记：`RESULT: RESTORE-DONE`**（只可能从真正执行 RESTORE 的那个分支打出来）。
   2026-09-21 本地演练揪出一个 **fail-open**：老写法用 `RESULT: DB-OK` 当闸门，而守卫拦下（备份文件读不到、
   一个字节都没动）时**旧库还在、照样打得出这行** ⇒ 部署会带着新 jar 跑在旧库上，最后还报 `ALL-OK`。
   现在：守卫拦下打 `RESULT: NOT-RESTORED`，没有 `RESTORE-DONE` 一律 `RESULT: FAIL-RESTORE` 硬停；
   `RESULT: DB-PRESENT` 只是"库在"，别拿它当成功判定。
   两个变体都在本地临时库上演练过（`tools/archive/_dryrun-restore.ps1`），闸门本身也单测过
   （`tools/archive/_probe-deploy-gate.ps1`，从 `deploy-all.bat` 里抽取真实代码块跑 3 个用例）。

## 1. 拷过去 + 解压

把 `pkg-20260921.zip` 弄到服务器，解压到一个 ASCII 目录（例：`C:\yj-deploy\`）。

## 2. 先跑 CHECK（只读，不改任何东西）

服务器 cmd（**用管理员身份**开：脚本要 `sqlcmd -E` 与写 `C:\yinjia`）：

```
C:\yj-deploy\deploy-all.bat
```

CHECK 会打印：
- 前置：`SQLCMD-OK` / `JAVA-OK` / `DEST-OK C:\yinjia` / `NEW-JAR …` / `DB-BAK …` / `TASK-OK YINJIA-MES`
- 现状：`SYSADMIN 1`（不是 1 就别往下走）、`DB-EXISTS 1`、`PANELS n`、`DEMO-* 0`（换库前服务器上应**没有** DEMO 数据）
- **环境取证（2b）**：任务计划真正启动的命令行、`C:\yinjia\start-service.bat` 前 25 行、`C:\yinjia` 目录清单、
  已有 `.bak` 清单、`backup\` 最新几个 —— 给"部署后核对"用，也方便出问题时判断任务到底从哪个 jar 起

## 4. 手工兜底（脚本走不通时）

1. `HSDZ_MES.bak` 复制成 `C:\yinjia\HSDZ_MES.bak`（**先把服务器上同名的那份移走/备份**）；
2. SSMS 连 `localhost`（Windows 身份验证）→ 打开 `restore-db.sql` 整段执行（先校验备份在不在，不在就硬停）；
3. 停应用：`schtasks /end /tn YINJIA-MES` + `taskkill /f /im java.exe`；换包：`app.jar` 覆盖 `C:\yinjia\app.jar`；起应用：`schtasks /run /tn YINJIA-MES`；
4. 验收：`powershell -File probe-login.ps1` → 必须 `LOGIN-OK`。

## 5. 回滚

- **只回代码**：`C:\yinjia\backup\app-<时间戳>.jar` 覆盖回 `C:\yinjia\app.jar`，重启任务。
- **连库一起回**：用 `C:\yinjia\backup\pre-deploy-<时间戳>.bak` 走一次 SSMS 还原（同 `restore-db.sql`，只换备份文件路径）。

## 7. 两条必须记住的

1. **健康检查不算验收**：Tomcat 在启动期缓存预热**之前**就开始监听，`curl` 首页拿到 200 是假阳性；只有 `POST /api/auth/login` 拿到 token 才算可用（脚本第 8 步就是这么判的）。
2. **`.bat`/`.ps1` 必须纯 ASCII**：zh-CN 的 cmd 按 GBK 解析批处理，UTF-8 中文的 `.bat` 会把乱码直接当命令执行（本次实测：加了中文注释的那版一跑就报一堆 `'…' is not recognized`）；PS 5.1 也把无 BOM 的 UTF-8 `.ps1` 按 ANSI 读、中文注释会破坏语法。中文一律放 `.sql`（`sqlcmd -f i:65001,o:65001` 读）。
