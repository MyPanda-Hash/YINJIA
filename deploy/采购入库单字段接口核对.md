## 二、关键验证:挂了源单也读不回「订单基本数量」(2026-09-20 实测)

用户口径:**只需把采购订单号推给金蝶,订单信息金蝶自己带**。前半句成立,后半句分两半:

- ✅ **金蝶侧成立**:推出 `src_bill_no` 后,金蝶把入库行挂到采购订单源单上。真实账套实测 123/138 行带源单,关联字段全集为:
  `src_bill_no`(订单号)、`src_bill_type_id` / `src_bill_type_number`(**常量字符串 `pur_bill_order`**)、`src_bill_type_name`=`采购订单`、`src_inter_id`(订单单据id)、`src_seq`(订单行号)、`src_entry_id`(订单分录id)。
- ❌ **接口读回不成立**:逐键比对 138 行(其中 123 行挂了源单)的键集 vs 官方详情接口基线 —— **挂源单行的键集与未挂源单完全相同(83 键,零新增)**。接口里**没有**任何「订单数量 / 源单数量」族键,只有本单的 `qty` / `base_qty` / `inv_qty` / `inv_base_qty` / `aux_qty` / `def_float_qty` / `return_qty`。
  → 金蝶界面会自己显示订单数量,但**不会通过采购入库单接口把「订单基本数量」还给我们**;MES 要用只能自己取(见 §四)。

**推送方向(MES→金蝶,转ERP)的缺口**

- 已推:`src_bill_no` = MES 采购订单号 + `src_bill_type_name`=「采购订单」(`KingdeePushService` 第 182~186 行);实测单据 `TCGRK-PO-001`(订单号 `YJ-20260916-01`)已转ERP成功 → 金蝶单 `CGRK-20260917-00033`。

## 四、「订单基本数量」的取数方案(推荐不新增接口)

1. **本地 join(推荐)**:MES 已同步采购订单头+行(`bl_pu_order` 有 `基本数量`、`行号`),入库行已有 `源单编号` + `源单行号` → 直接
   `bl_purchase_in.源单编号/源单行号 = bl_pu_order.单据编号/行号` 取 `基本数量`,零额外金蝶调用。
   先决条件:入库行必须真带上 `源单编号/源单行号`(见上:同步未接入、推送未带行号)。
2. 金蝶回查:按 `src_bill_no + src_seq` 调 `pur_order_detail` 取 `base_qty`(多一次请求,仅在本地订单缺失时需要)。

## 6.2 顺带修掉的两个断点(不修则链路走不通)

> 说明:链路还要靠「单位」和「单价」才能推送成功(金蝶要 `unit_id`)。补齐 `sl_recv_detail.计量单位` 字段注册后,`单位→计量单位` 同义词生效,单位/单价随链一路带到入库行。

## 6.4 转ERP 推送实测(测试沙箱 359220,`tools/archive/_verify-erp-push.mjs`)

**账套事实(只读判定,`tools/archive/_q-account-id.mjs`)**

| 凭证 | 账套 | 规模 | 说明 |
|---|---|---|---|
| `deploy/config.json`(clientId 359797) | **真实账套** | 采购入库 3213 张、采购订单 2137 张(含 `YJ-20260916-01` id=2569669939711649792、`YJ-20260915-06`) | 订单存在且已审核 → 可挂来源单 |

> 这就是"以前转ERP 推上去的单在真实账套里找不到、且没有来源单"的原因。

**三条实测结论**

1. **旧写法被金蝶静默忽略**:沙箱里 MES 早先推送的单(如 `CGRK-20260917-00033`)行上 `src_bill_no=(空)`、`src_seq=0`。旧代码只发 `src_bill_no`+`src_bill_type_name`,金蝶不认 → **来源单从未真正挂上**。
2. **补齐 `src_bill_type_id`/`number` 后金蝶会真校验来源单**(实测报错即证据):
   - 订单号在目标账套不存在 → `单据"CGRK-20260917-00034"的源单""已被删除`;
   - 订单存在但**未审核** → `关联的源单未审核或已被删除`;
   - 后者只可能在金蝶已把 `src_inter_id`/`src_bill_no` 解析到具体订单并检查其状态时出现 → **id 族字段确实被接受与解释**。
3. **挂来源单的三个前置条件**:①目标账套存在该采购订单;②该订单**已审核**;③带齐 id 族字段(`src_bill_type_id/number` + `src_inter_id` + `src_entry_id` + `src_seq`)。

**据此落地的容错口径(已实现)**

- 解析到订单 → 推全 7 字段(其中 `src_seq`/`src_entry_id` 仅在该行号确实存在于订单分录时才推,防"源单分录不存在"整单被拒);
- 解析不到订单(账套配错/订单不在该账套/号写错)→ **整组不推**,按无来源单的普通入库单推送,并在返回消息里明确提示:
  `…；注意:金蝶账套内未找到采购订单[X],本次未挂来源单(请核对账套/订单号,或先在金蝶补建该订单后重审再转)`
  → 实测推送成功(`CGRK-20260917-00034`),不再因账套缺单而整单失败(旧行为保留,无回归)。

推送服务读行值用的是 `SELECT *`(键=**物理列名**),而我按面板**标签**取「采购订单行号」→ 实际列名是 `源单行号` → `src_seq` 静默丢失(日志出现"该行不带 src_seq")。已改为列名优先、标签兜底(`lineColumn`)。

过程中发现并补齐的两个**挂联硬要求**(只推 `src_bill_no` 时看不到、挂联时才暴露):

   另外数量不得超过源单分录(`不允许超额入库`——属业务校验,正常数据不会触发)。

## 6.5 转ERP 账套守卫(默认只允许测试沙箱,2026-09-20 用户口径)

**要求**:转ERP 按钮**绝不能**把单据写进正式账套。

**实现**(`KingdeePushService.assertPushTargetAllowed()`,在取 token/发任何 HTTP **之前**执行):
- 沿用本项目凭证约定判定:凭证含 `outerInstanceId` ⇒ 动态授权 ⇒ **真实账套**;留空 ⇒ 静态 appKey/appSecret ⇒ **测试沙箱**;
- 命中真实账套且未显式开启 **`kingdee.push.allowProd=true`** → 直接拒绝,文案:
  `已拒绝转ERP:当前金蝶凭证指向**真实账套**(outerInstanceId=xxx…),本功能默认只允许推测试沙箱,以免测试单据写进正式账。确认要推真实账套时,请显式配置 kingdee.push.allowProd=true 后重试`
- 每次转ERP 都记一条目标账套日志(`转ERP 目标账套 = 测试沙箱/真实账套(clientId=…, domain=…)`),账套标识脱敏;
- 写入路径唯一(`ButtonService.pushToErp` → `pushDocument`),守卫覆盖全部转ERP(含批量)。

**实测**(`tools/archive/_verify-prod-guard.mjs`,以带 `outerInstanceId` 的凭证启动实例):转ERP 被拒、文案含"真实账套"与 `allowProd`、
且后端日志**无 app-token 获取**记录 → 守卫在联网前拦下,未向任何账套写入。沙箱凭证下推送照常(见 §6.4)。
