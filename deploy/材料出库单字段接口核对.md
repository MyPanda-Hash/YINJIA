# 材料出库单(MATERIAL_OUT)字段 ↔ 金蝶「生产领料单 inv_pick」接口核对

> 起因(用户口径,2026-10-04):「检查材料出库单里面的字段是按照金蝶的系统来对照的吗?」
> 并顺带**实测转ERP 到测试账套**。本文是该次核对的取证记录与结论。
> 同族先例:`deploy/采购入库单字段接口核对.md`(采购链七单据)。

## 1. 结论(一句话)

**是**,材料出库单的字段是**按金蝶系统对照建的** —— 对口单据是金蝶云·星辰的
**生产领料单 `/jdy/v2/scm/inv_pick`**(星辰**没有**"材料出库单"这个接口;材料出库在星辰就是生产领料单,
真实账套 2026-10-04 实测 **4828 张在用**,见 §2)。

对照方式 = **接口并集**:金蝶该接口的头/行键**逐个**在 MES 里落列(可显示的注册为面板字段、id/留痕/图片/空值族隐藏),
每列的 `MS_Description` 都写明「材料出库单↔金蝶生产领料单(inv_pick)接口键 X」——
即"这一列是哪来的"在库里有据可查,不是凭印象拼的。

但**对照正确 ≠ 推送正确**:本次端到端实测抓出**两个真 bug**(转ERP 一直推不出去,见 §4),
连同凭证失效一起修掉后,材料出库单已成功落入金蝶沙箱(`SCLL-20261004-00001`)。

## 3. 覆盖情况:105 个金蝶键,101 个有承接

| 类别 | 数量 | 说明 |
|---|---|---|
| 有专门列(接口并集) | **86** | 24 头 + 62 行;每列 `MS_Description` 记着对应接口键 |
| 由 MES **原生业务字段**承接 | **15** | 见下表 —— 这些字段本来就存在且语义一致,不重复建列 |
| 金蝶**容器键**(自定义字段) | 2 | `custom_field`(头)/ `custom_entity_field`(行):金蝶侧按 Map 传,不落列 |
| 金蝶**内部主键** | 2 | 头 `id` / 行 `id`:金蝶自己编号,回写用的是 `bill_no`,故不落列 |

**原生字段承接对照(15 个)**

| 金蝶键 | MES 列 / 面板字段 |
|---|---|
| `bill_no` / `bill_date` / `remark` | 单据编号 / 单据日期 / 备注 |
| `dept_name` / `emp_name` | 生产车间(参照 DEPT.部门名称) / 领用人(参照 EMP.员工名称) |
| `seq` | 行号(材料出库单领料行序,从 1 连续) |
| `material_number` / `material_name` / `material_model` | 材料编码(参照 INV.存货编码,显示存货名称) / 材料名称 / 规格型号 |
| `stock_name` / `batch_no` | 仓库(名称) / 批号 |
| `unit_name` | 计量单位(参照 UOM.计量单位名称) |
| `qty` / `price` / `comment` | 数量 / 单价 / 明细备注 |

**有意不建的一族:税金**。金蝶 `inv_pick` 的头/行**根本没有** 税率/税额/含税单价/金额/价税合计
(与采购入库/销售出库**本质不同** —— 那两张单有税金族);价格族只有 `price`/`cost`/`unit_cost` 三键,
且真实账套采样 244 行实测**全为 0**。故 MES 侧不建税金列,推送时也不推(2026-09-28 用户口径)。

反向核对也做了:MES 有列、金蝶当前键集里没有的只有 **1 个** —— `单据标签`(`mul_bill_label`,
金蝶详情接口在值为空时不返回该键,09-28 快照里有、10-04 实测没返回),不是错配。

### 4.1 抓出并修掉的两个真 bug(`KingdeePushService`)

1. **行仓库只推 `stock_number`,金蝶静默忽略 → 整单被拒**
   现象:`转ERP失败: 金蝶接口失败: 请求接口返回失败:请填写"材料分录"第1行："仓库"。`
   (单据明明填了仓库 华北工控仓/CK00006,而该仓在金蝶仓库档案里**确实存在**,已用 `/jdy/v2/bd/store` 核对)。
   原因:金蝶保存接口行字段表收的是 **`stock_id`**,`stock_number` 是**未知键被丢弃**(不报错,只说缺仓库)。
   修复:新增基础资料 `编号→金蝶id` 缓存(`/jdy/v2/bd/store`,22h,与商品/单位同款),行上补 `stock_id`。
   > 采购入库/销售出库走的是同一段代码,原来也只有 `stock_number` —— 本次一并补上 `stock_id`(解析不到时不带,不改变旧行为)。
2. **头经手人只推 `emp_number`,经手人丢失**
   修复:新增 `/jdy/v2/bd/emp` 缓存(编号→id),补 `emp_id`;实测金蝶侧落 `白兴发/ZY00059`。

## 5. 顺带修掉的根因:沙箱凭证写死必然过期

- 现象:转ERP 报 `获取app-token失败: 授权密钥校验失败，请获取最新密钥加密`(errcode **1030002006**)。
- 原因:`deploy/push/config.json` 里是 2026-09-24 写死的**沙箱静态** appKey/appSecret;
  金蝶的 appSecret **含沙箱同样 24h 轮换** ⇒ 隔天必失效(本项目文档只把"24h 轮换"记在真实账套上)。
- 修复:新增 `kingdee.push.sandboxInstanceId`(= 测试账套第三方实例 id,值见 `deploy/push/config.json`),
  **沙箱也走动态授权**(拿 clientId/clientSecret + 实例id 取最新 appKey/appSecret/domain),
  但**不算真实账套**、不触发 `allowProd` 守卫。`deploy/push/config.json` 现为:
  `clientId 359220 + clientSecret + sandboxInstanceId`,`appKey/appSecret` 留空。
- 附带说明:用户给的 40 位十六进制串是**轮换出来的新 appSecret** 本身,不是实例 id
  (按它当 `outerInstanceId` 取授权会回「第三方实例id…不存在」),故它属于"该换成动态授权"的证据而非配置项。
  本仓库不落该串(密钥只进 gitignored 的 `deploy/push/config.json`)。

## 7. 已知缺口(本次未做,需业务定)

| 缺口 | 影响 | 说明 |
|---|---|---|
| **部门(dept)** | 推入金蝶的领料单**没有部门** | 金蝶 v2 没有部门列表接口(`/jdy/v2/bd/dept` → HTTP 519;`/jdy/v2/bd/department` 只回公司节点),拿不到 `dept_id`;现在只推 `dept_number`,被金蝶静默忽略。要补需另找口径(如按金蝶侧返回的部门id 建档)。 |
